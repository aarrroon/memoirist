## 10. Concepts to learn from this task
- **Programs inherit their environment** (§8): environment variables are copied into a process when it starts, from the process that started it. Changing one in System Properties saves it to the registry and tells Explorer, but programs already running keep their copy. The common mistake is "I fixed `JAVA_HOME` but the build still uses the old one" from a terminal or IDE that was open before the change.
- **`JAVA_HOME` and `PATH` are different questions** ([DEVELOPMENT.md:118](../../DEVELOPMENT.md#7-troubleshooting)): `PATH` decides which `java` runs when you type `java`. `JAVA_HOME` is a convention that tools (the Gradle wrapper, Maven, IDEs) read to find a JDK folder. Nothing makes them agree, so checking only `java -version` can miss a broken build.
- **A Gradle build uses up to three JVMs** (from Gradle's docs, via context7). The **client** JVM is whatever launched the wrapper (`JAVA_HOME`, else `PATH`). The **daemon** JVM runs your build scripts, and is the same as the client's unless `org.gradle.java.home` or the Daemon JVM criteria file (`gradle/gradle-daemon-jvm.properties`, made by `./gradlew updateDaemonJvm`) says otherwise. **Toolchain** JVMs compile and run tests, chosen by `java { toolchain { languageVersion = JavaLanguageVersion.of(25) } }`. Gradle's compatibility matrix says Java 25 needs Gradle **9.1.0** or later, both to run Gradle and as a toolchain: that's what [D-02](../../DECISIONS.md#d-02-spring-boot-4x-on-java-25)'s "Gradle must be a version that runs and compiles Java 25" means for task 2.1. `./gradlew -q javaToolchains` lists the JDKs Gradle found.
- **`java -XshowSettings:properties -version`**: prints the JVM's system properties to stderr (hence `2>&1`), including `java.home`, the folder the running JVM came from. It answers "which JDK is this really?" when several are installed.
- **`git check-ignore -v <path>`**: prints the file, line and pattern that ignore a path, and exits 0 when it's ignored. The trap: with `-v` it also prints, and exits 0, when the last matching rule is a `!` negation, which means the path is *not* ignored. So read the printed pattern, and when you test by exit code (`git check-ignore -q f && echo ignored`), leave out `-v`. It skips tracked files by default, so exit 0 also means "not tracked". A secret committed *before* its ignore rule is still tracked, and adding the rule doesn't remove it: you need `git rm --cached`, and the secret must be rotated because it's in history.
- **Exit codes as tests** (§6): `test -f`, `[ -x "$f" ]`, `git check-ignore` and `docker info` all report through their exit code (`$?`: 0 means success). `cmd && echo ok || echo failed` turns one into readable output. CI pipelines work the same way: a non-zero exit fails the step.
- **Docker API versions**: `docker version` reports server API 1.56, minimum 1.40. Every Docker client, including the docker-java library inside Testcontainers, must speak at least the minimum. An old Testcontainers version pinned from a blog post can fail with "client version … is too old". Using the version Spring Boot manages, on a current Boot patch, avoids that.
- **MCP servers in `.mcp.json`** ([.mcp.json](../../../.mcp.json)): `"type": "http"` plus a `url` means Claude Code connects to a remote server, so there's no local process and nothing to install. A `stdio` server instead names a `command` that Claude Code starts on your machine. context7 exposes two tools: `resolve-library-id` turns a name into an ID like `/websites/gradle_current_userguide`, and `query-docs` fetches the docs for one concept.

## 12. At work
- **Several JDKs on one laptop.** Bank services often sit on different Java versions: one on 17, another moving to 21 or 25. Whenever you switch, the stale-environment trap from §8 appears. Toolchains and Daemon JVM criteria make the build pick its own JDK, the same on every laptop and in CI, instead of trusting each developer's `JAVA_HOME`. A reviewer would question a committed `org.gradle.java.home=C:/...`, because it only works on one machine.
- **Secrets hygiene.** `.env` plus `.gitignore` is the local version of what a bank does with a secrets manager such as Vault or a cloud provider's, plus secret scanning in CI. In review, look for: no values in the diff, an `.env.example` with placeholders only, and evidence such as `git check-ignore`. If a secret is ever committed, rotate it; deleting it from history isn't enough.
- **Docker in a corporate network.** Docker Desktop needs a paid licence at large companies, and images usually come from an internal mirror rather than Docker Hub (Testcontainers supports this through *image name substitution*). When Testcontainers fails in CI, `docker info` and `docker version` are the first two commands to run.
- **MCP, as in your agent project.** `.mcp.json` shows the two transport styles you'll meet at work: a remote HTTP server, like this one, or a local `stdio` process. A bank reviewer would ask where the server runs, what data leaves the network, and who approved it. context7 sends your query text to an outside service, and its own tool description says never to include credentials or proprietary code in a query.
- **Reviewing a setup PR.** Ask for evidence, meaning commands and their output, rather than "works on my machine". For a docs change, check that it states the symptom, the cause and the fix, in that order.

8. An `http` server is reached at a URL, so Claude Code only needs the address. A `stdio` server is a local program (a `command`, often `npx ...`) that Claude Code starts. context7 here is `http`, so nothing runs or installs locally.
