    ```yaml
    POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in .env}

  E=http://host.docker.internal:8333

curl -s -H 'Accept: application/json' http://127.0.0.1:8888/buckets/
```

- **To repeat the V1 check:** copy the two fenced `sql` blocks from DATABASE_SCHEMA.md into files, then:

```bash
docker compose exec -T postgres sh -c 'createdb -U "$POSTGRES_USER" v1_check'
docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 --single-transaction -U "$POSTGRES_USER" -d v1_check' < v1.sql

```

  The single quotes matter: `"$POSTGRES_USER"` is expanded by the container's shell, which has the value, not by yours.

## 8. What went wrong
1. **My log scrubber missed a derived value.** SeaweedFS's startup line is `Added admin identity from AWS environment variables: name=admin-<first 8 characters of the access key ID>, accessKey=<access key ID>`. The scrubber replaced exact `.env` values, so it caught the `accessKey=` field but not the 8-character prefix inside the name, and that prefix reached this session's output. It never reached the repo or this entry, and it's part of the access key ID, the public half of the key pair, not the secret. *Fix:* every later read also redacts `name=admin-…`. *Lesson:* scrub derived forms too (prefixes, hashes, base64), not just exact values.
2. **A quick stop was really a kill.** `docker compose stop seaweedfs` returned in 4.7 s, but the exit code was `137` (128 + 9, SIGKILL). `docker events` showed SIGTERM, then SIGKILL 3.07 s later. Docker's documented default grace period is 10 s; on this machine both `docker stop` and `docker compose stop` used about 3 s. I didn't open Docker Desktop's settings to find out why. With `-t 30`, SeaweedFS exited cleanly (`0`) after 26 s: 10 s of volume-server pre-stop, then the filer's "gRPC server graceful stop timed out after 15s, forcing stop". *Fix:* `-volume.preStopSeconds=1` brought a clean stop to about 17 s, and `stop_grace_period: 30s` lets it finish. Measured afterwards: 18.7 s, exit `0`. Postgres needed nothing: its stop signal is SIGINT ("fast shutdown"), and it exited `0` in 0.7 s.
3. **An `E` line at every SeaweedFS start:** `Failed to load IAM configuration: no signing key found for STS service`. From the 4.48 source ([`s3api_server.go` lines 389–403](https://github.com/seaweedfs/seaweedfs/blob/4.48/weed/s3api/s3api_server.go#L389-L403)), it's the optional advanced IAM layer, switched on by the IAM API's default; it logs the error and carries on without that layer, and ordinary key checks don't depend on it. *Fix:* `-s3.iam=false`, since the app needs no IAM API. Afterwards the log had no `E` lines, and every S3 check in §7 ran with the flag in place.
4. **Quoting.** A one-line `psql -c "…'…'…"` inside `sh -c '…'` inside Git Bash failed with `` unexpected EOF while looking for matching `'' ``. *Fix:* send the SQL on stdin with a heredoc (`<<'SQL'`), which needs no escaping.
5. **A misleading timing.** Through the AWS CLI the "first write" took 4.1 s and the second 5.1 s, so the CLI's own start-up (Python) was most of it. *Fix:* signed `curl --aws-sigv4` inside a one-off container, run from the SeaweedFS image (it ships curl 8.22): first `PUT` into a new bucket 0.24 s, second 0.07 s.
6. **`docker image inspect --format` errors:** `map has no entry for key "Entrypoint"`, then `"User"`. Those fields live under `.Config`, and a Go template fails on a key the JSON leaves out. *Fix:* print the JSON and pick fields with a short `node` script.
7. **Docker Hub's tag list was mostly signatures.** The first page was nearly all `sha256-….sig` tags (cosign image signatures). *Fix:* filter them out, and query by name prefix (`?name=4.4`).

Neither was published, but neither is needed. *Fix:* `-s3.port.iceberg=0` and `-s3.port.lance=0`, then a recreate and a re-run of every Done-when check on the final file (§7). *Lesson:* list a container's listeners (`netstat -tln` inside it) instead of trusting what you meant to start.

## 10. Concepts to learn from this task
- **Compose interpolation and `${VAR:?message}`** ([`docker-compose.yml:13-19`](../../../docker-compose.yml)). Compose reads `.env` from the project folder and replaces `${...}` in the YAML before it creates anything. `${VAR:-default}` fills a gap; `${VAR:?msg}` refuses to continue when the value is unset **or empty**; `${VAR?msg}` only when it's unset. The common mistake is `${VAR}` alone, which quietly becomes an empty string: here that would have started SeaweedFS with no identity, open to everyone (D-03). To leave a `$` for the container's shell, write `$$`.
- **Three kinds of "env file".** Compose's `.env` (interpolation only), a service's `env_file:` (every line goes into that container), and `docker run --env-file` (one container). They parse differently: Compose strips quotes, `docker run --env-file` keeps them, so `KEY="abc"` gives `"abc"`, quotes included, to the container. `.env.example` uses no quotes, and the signed checks passing shows that Compose and `docker run` read the same values here.
- **Health checks** (lines 24–31 and 69–75). `test` runs inside the container, exec form (`["CMD", …]`) or through a shell (`["CMD-SHELL", "…"]`). Checks run during `start_period` too: failures there don't count against `retries`, and the first success marks the container healthy at once. (Docker's getting-started page says checks "begin" after the start period, which is looser than what Docker does.) A container is `unhealthy` after `retries` failures in a row. `docker compose up -d --wait` blocks until everything is healthy, and `depends_on: {db: {condition: service_healthy}}` makes one service wait for another. A health check should test what the client needs: the backend reaches Postgres over TCP, so `pg_isready` on the socket asked the wrong question.
- **Publishing ports** (lines 21, 61–62). `"5432:5432"` listens on every interface of the host; `"127.0.0.1:5432:5432"` only on loopback. On a Linux server, Docker's published ports go around firewalls like `ufw`, because Docker writes its own iptables rules, so a database published on `0.0.0.0` can be open to the internet even with the firewall "on".
- **Named volumes** (lines 23, 65, 77–79). Docker manages them, and they outlive containers: `--force-recreate` gave both services new containers, and the data was still there. A *bind mount* maps a host folder instead (slow on Windows, and file ownership differs). An *anonymous* volume is created for an image's `VOLUME` when you don't name one; `docker run --rm` deletes it with the container. Only `docker compose down -v` deletes named volumes.
- **The Postgres image's first run.** `POSTGRES_*` variables apply only when the data directory is empty; on later starts the log says `Skipping initialization`. Changing the password in `.env` afterwards does nothing, which is the most common Postgres-in-Docker surprise. During that first run a temporary server listens on the Unix socket only (`listen_addresses=''`).
- **Signals and exit codes.** `docker stop` sends the image's stop signal (SIGTERM, or SIGINT for Postgres), waits for the grace period, then sends SIGKILL. Exit code `137` is 128 + 9, killed. The signal goes to PID 1, so the real program must be PID 1 and handle it. Here the entrypoint fixes `/data`'s owner as root, re-runs itself as the `seaweed` user through `su-exec`, then `exec`s `weed`; `ps` in the container shows `1 seaweed /usr/bin/weed … server …`. Each `exec` replaces the process instead of starting a child, which is what keeps `weed` at PID 1.
- **S3 request signing (SigV4).** Both sides know the secret key, but it never travels: the client signs each request with it and sends only the access key ID and the signature, and the server recomputes the signature to check it. That's why an access key ID can appear in logs and headers while the secret must not. `--no-sign-request` leaves the signature off; the answers differ: `AccessDenied` (unsigned, or not allowed), `InvalidAccessKeyId` (unknown key, as after the rotation), `SignatureDoesNotMatch` (right key ID, wrong secret). `curl --aws-sigv4 "aws:amz:<region>:s3"` signs too, handy for timing.
- **A side door around authentication.** S3 on 8333 rejects unsigned requests, but the filer on 8888 serves the same files with no login. It read `hello.txt`, deleted `hello2.txt` (`204`) and accepted a new file (`201`), while S3 refused the same read with `403`. Authentication on one entrance says nothing about the others. That's why 8888 is on loopback only, and why production uses R2, not this.
- **Secrets in logs and `docker inspect`.** SeaweedFS logs the access key ID at startup. `docker inspect <container>` prints the container's whole environment, secrets included, so ask for one field with `--format`. Scrubbing must catch derived values (§8, item 1).
- **Choosing a dependency version.** Read the release notes *and* the issues opened since. Here the newest release was the wrong choice for a test-heavy project. Record why, and what would change your mind (D-03, Version).
- **Single-master Raft.** SeaweedFS's master uses Raft, a consensus protocol, to agree on a leader. With one master, `-master.peers=none` lets it lead at once instead of waiting out an election timeout.

## 12. At work
- **The same file, at a bank.** Many teams keep a `docker-compose.yml` for Postgres, Kafka, Redis and so on. Images come from an internal registry (an Artifactory mirror, say) and are scanned, and CI often pins by digest. Expect a reviewer to ask: is every image pinned? Is anything published on `0.0.0.0`? Does `env_file` hand a container more secrets than it needs? Does it start safely when a variable is missing?
- **Fail fast on configuration.** `${VAR:?}` is the Compose form of what Spring does with `@ConfigurationProperties` plus `@Validated` and `@NotBlank`: refuse to start rather than run half-configured. The dangerous defaults are the quiet ones, like SeaweedFS turning "no keys" into "no authentication".
- **Readiness versus liveness.** Kubernetes probes split "alive" from "ready for traffic". SeaweedFS even has `/healthz` and `/readyz`. The `pg_isready` trap is a readiness probe that's true too early; the same mistake in a pod sends traffic to a service that can't serve it yet.
- **Graceful shutdown.** Kubernetes gives a pod `terminationGracePeriodSeconds` (30 s by default) between SIGTERM and SIGKILL, plus `preStop` hooks: the same mechanics as `stop_grace_period`. An exit code of `137` in a pod's status means it was killed, not that it crashed.
- **Key rotation.** The rotation test (old key `InvalidAccessKeyId`, new key `200`, no restart of anything else) is what an auditor asks for: rotating a credential must retire the old one immediately. In production that's a secrets manager such as Vault plus a rolling restart.
- **Side doors.** The filer on 8888 is the local version of an admin console or a management port left reachable next to a well-protected API. In a threat model, list every listener, not just the main one.
- **Reviewing a dependency upgrade.** "Bump to latest" PRs are common. Ask what changed, which issues are open against the new version, and how the team will know it still works (here: re-run the `403` check, D-03).

<details><summary>Answers</summary>

1. `:?` stops Compose with an error when the variable is unset or empty. Plain `${VAR}` substitutes an empty string, SeaweedFS then loads no identity, and it accepts every request unsigned (D-03's watch-out; shown with a throwaway server, where an unsigned `ListBuckets` got `200`).
2. `pg_isready` without `-h` checks the Unix socket. During the first run the image's temporary server listens only there while it creates the database, so the check can pass before `memoirist` exists and before anything listens on TCP (0.4 s early in this run's log). The temporary server then shuts down and the real one starts, so a TCP client arriving in between is refused. With `-h 127.0.0.1` the check also uses TCP, which only the real server opens.
3. Two halves. S3 itself refuses unsigned requests, but the filer on 8888 reads, writes and deletes the same files with no login. What protects the data from other computers is that every port is published on `127.0.0.1` only.
4. The image applies `POSTGRES_*` only when the data volume is first created, so the database still has the old password. Put the old value back, or change it inside the database (`docker compose exec postgres psql`, then `\password <user>`), or delete the data with `docker compose down -v` and start again.
5. Docker sent SIGTERM, waited out its grace period (about 3 s on this machine), then sent SIGKILL: 137 is 128 + 9. SeaweedFS needs about 17 s to stop cleanly, so the task set `-volume.preStopSeconds=1` and `stop_grace_period: 30s`.
6. `env_file` copies every line of `.env` into the container, so Postgres would hold the S3 secret and the Spotify keys. It also can't rename `STORAGE_ACCESS_KEY` to `AWS_ACCESS_KEY_ID`, and it can't refuse to start when a value is empty.
7. 4.50 and 4.51 make the first write on a fresh server wait about 15 s, and every Testcontainers run starts a fresh server (#12145). Move once a release fixes that, then re-run the signed and unsigned checks, because the credential code changes often.
8. In `CMD-SHELL` form, or anywhere a `$` should reach the container's shell instead of being filled in by Compose from `.env`. For example `["CMD-SHELL", "pg_isready -U $${POSTGRES_USER}"]`: Compose turns `$$` into `$`, and the container's shell expands the variable.
