# Task 3.5: Entries: create, read, update, delete, seal, redaction

> **Sprint:** 3 · **Commit:** `Sprint 3.5: Add the Entries endpoints` · **Status:** done (every Done-when item is met; `./gradlew build` passes with 836 tests; the review is §9) · **Time taken:** roughly 71 minutes by the machine clock for the first sitting (05:06 to 06:17 on 2026-10-31), including one real bug found by the tests, a manual run of the app, the full build and this entry, plus about 25 minutes in two later re-check sittings (the run was paused between them; see §8, item 10)
> **Built:** the five `/api/v1/entries` operations that make an entry exist: create (with the week found or made, the client-supplied id, a validated TipTap caption and a memory date in the user's time zone), read, edit (guarded by the version the client read), delete (into Recently deleted, or erased at once when there is nothing in it) and seal (a Loot Drop). Every answer is built by one class, `EntryMapper`, which shows a sealed entry as an allow-list of nine non-private fields. 299 new tests cover it.

## 1. The goal
[Task 3.5](../../SPRINT_PLAN.md#sprint-3-phase-1-api) is the sprint's largest task and the heart of the privacy promise: a Loot Drop that has not opened must leak nothing, anywhere (D-10, non-negotiable 4). Its block says what to build (`WeekCalendar`, `EntryContentValidator`, `ContentTextExtractor`, `EntryMapper`, `EntryService` with the seal rules) and what the tests must prove, as 13 points (the run adds a 14th, that the whole build passes):

- an optional title is saved, and a blank title is `400`;
- the first entry of a week creates the week, the second reuses it; 23:30 on a Sunday in Melbourne is that Melbourne week; a daylight-saving week boundary works;
- backdating works; a future date, or one before 1900-01-01, is `400`;
- changing the date moves the entry to the matching week and clears `dateUnknown`; `dateUnknown: true` on create is saved and shown, sealed or not (D-34);
- disallowed nodes and `javascript:` links are `400`;
- a sealed entry is redacted on `GET`, `PUT` and `seal`; editing a sealed entry is `409`, and so is moving its seal earlier;
- a `PUT` with an older `version` is `409 entry-stale` and changes nothing; a current one saves and returns the next `version` (D-23);
- deleting an entry, sealed or not, moves it to Recently deleted, after which `GET`, `PUT` and `seal` are `404`;
- another user's entry is `404`; replaying an existing id is `200`, another user's id or one in Recently deleted is `409`.

## 3. The plan
The order, and why:

1. **`WeekCalendar` and `WeekService.findOrCreate`** (a small static class and one native `INSERT ... ON CONFLICT`). The service needs them, and `WeekCalendar` is pure, so it gets exact tests first.
2. **`EntrySeal`, `EntryContentValidator`, `ContentTextExtractor`** (pure, static). Both content classes are about untrusted input and the sealed check is used by two later classes, so they are written and unit-tested before anything depends on them.
3. **The DTOs and `EntryMapper`**, with unit tests that fill every field with something private. The redaction is the point of the task, so it is built and attacked before the service exists.
4. **`EntryRepository` additions, `EntryService`, `EntryController`.** The service is the only place the rules combine, so it comes last.
5. **Test infrastructure:** a clock a test can move (`MutableClock`) and one base class for all the HTTP tests.
6. **HTTP tests by area** (create and read, dates, content, update, seal, redaction, delete, API description). Run, read the failures, fix.
7. **Docs** (API_CONTRACT, TECH_STACK, DEVELOPMENT, DATABASE_SCHEMA), a **manual run** of the real app with `curl`, the **full build**, and this entry.

Two practice blocks (§11) are planned in the code that carries a real decision: the link check and the version comparison. Neither is in the mapper: a wrong answer there could leak a sealed entry, and a practice block must not sit where a mistake leaks.

## 4. Decisions and alternatives
| Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|
| Where the caption is validated | A Jakarta constraint on the request record (`@ValidTipTap`); a `@Component` validator; a static class called from the service | A static class, `EntryContentValidator.validate`, called by `EntryService` | Over 200 KB must be `413`, and bean validation can only answer `400`. Static and pure means plain unit tests with no Spring | A bad caption is reported after the bean-validation errors (title, version), not in the same response |
| Content over 200 KB: `413` or `400` | `400` (the "Content rules" list); `413` (the error table, and the Javadoc of `PayloadTooLargeException`) | `413`, for size only; every other rule is `400` | Three places say `413` for content over 200 KB, one list says "anything else is `400`", and "anything else" reads as "anything other than the rules above it" | A client must handle a second status for one field. Written into the contract |
| How 200 KB is counted | Characters; the raw request body; bytes of the compact JSON in UTF-8 | `200 * 1024` bytes of `JsonNode.toString()` in UTF-8, checked before the walk | It is what is stored, it is independent of how the client spaces its JSON, and it can't be beaten by multi-byte text (a test uses about 102,000 accented letters, which is far fewer characters than the limit and still too large) | The text is serialised once more just to measure it |
| TipTap attributes | Allow-list every attribute of every node; strip unknown ones; check only the two that matter | Check `heading.attrs.level` (1 to 3) and `link.attrs.href`; keep other attributes as sent; refuse unknown *node fields* (`html`, `style`) | The contract names only levels and link protocols; the renderer reads the attributes it knows; the 200 KB cap bounds the rest. A stricter list would reject real TipTap output the frontend has not been written to avoid | A future renderer must not trust an attribute it did not validate. Written into TECH_STACK |
| How links are checked | Parse with `java.net.URI` and check the scheme; a regex for `scheme:`; an allow-list of prefixes after stripping, refusing control characters | The prefix allow-list (`http://`, `https://`, `mailto:`) with a control-character ban | `URI` rejects real addresses (`|`, `[`, a space) and accepts `javascript:alert(1)` as a valid URI. A browser deletes tabs and line breaks inside an address before reading the scheme, so `java<TAB>script:` is a script link; banning control characters ends that whole family | A bare `example.com` or `/path` is refused; the client must send a full address |
| How a sealed entry is hidden | Copy everything, then blank the private fields; a Jackson view or filter; a separate projection query; build the sealed response from an allow-list | A `sealed()` method that names the nine visible fields and passes `null` or an empty list for the rest | If a field is added to the record later, both branches fail to compile, so somebody has to decide; "copy and blank" would leak the new field by default. It also never touches `getMedia()` or `getTags()`, so a sealed entry costs no query and no signed URL | The two branches must be kept in step by hand; a reflection test (§6) checks it |
| `EntryMapper` shape | Static like `EraMapper`; an instance `@Component` | A `@Component` with `toResponse(entry, now)` | It has to presign media, which needs `StorageService`. Passing the service into a static method would make every caller carry it, and the rule is `toResponse(entry, now)` | One more bean to inject |
| One definition of "sealed" | A method on `Entry`; a private check in the mapper and another in the service; a small helper | `EntrySeal.isSealed(unlockDate, now)`, package-private | `Entry`'s own Javadoc says it knows nothing about being sealed. Two private copies could drift (at the unlock instant, say) | A third class for a one-line rule |
| Keeping "the mapper is the only path" true | ArchUnit; a private constructor; a package-private record; a test that reads the sources | A test that reads `src/main/java` and fails if any file but `EntryMapper.java` contains `new EntryResponse(` | ArchUnit is a new dependency (not approved); a record's constructor can't be hidden; the DTO has to be public for the controller's signature | It is a text search. It would miss `EntryResponse::new` if that were not also checked, which it is |
| Finding or making the week | Select, insert if missing; `@Lock`; an advisory lock; catch the unique violation and retry; `INSERT ... ON CONFLICT DO NOTHING` then select | The `INSERT ... ON CONFLICT DO NOTHING`, then select (D-08), in `WeekService` | The database settles the race. A test creates entries from eight threads in one new week and gets one week | Two statements for every create, even when the week is there |
| How `PUT` guards against stale edits | Rely on Hibernate alone; copy the client's `version` onto the entity and let Hibernate compare; compare in the service and let Hibernate be the backstop | Compare `request.version()` with the loaded entity's, throw `EntryStaleException`; Hibernate's `WHERE version = ?` catches a race after the comparison | `Entry` has no `setVersion` (D-23). Hibernate alone only protects an entity it loaded in the same request, not the copy in the client's editor | Two checks that say the same thing; both end as `409 entry-stale` |
| A version that is *ahead* of the stored one | `400`; ignore; treat like an old one | `409 entry-stale`, same as an old one | A client that is ahead made its number up or talks to another database. Either way it must not write | The name "stale" is a little off for that case |
| Order of the checks in `PUT` | Stale first; sealed first; validation first | Not found, then sealed, then stale, then the values | A stale client of a sealed entry must hear that it is sealed; reloading and retrying would only find the same wall | A forged request can learn that an entry is sealed without knowing its version, but sealed entries show `isLocked` to their owner anyway |
| A `PUT` that changes nothing | Always bump the version (a forced increment); let Hibernate's dirty check decide | The dirty check decides: nothing is written and the version stays | "Raised on every change" stays literally true; a retry of a successful `PUT` with the new version is harmless | A client can't use a no-op `PUT` as a heartbeat |
| Where the week is looked up in `update` | After setting the new date (natural order); before touching the entity | Before | Hibernate flushes pending changes before a native query, so the setter was written by its own `UPDATE` and `saveAndFlush` wrote a second one: the version went up by two (§8) | The order is a rule to remember. Written into TECH_STACK |
| When the date limits apply on `PUT` | Always; only when the date changes | Only when it changes | A user who moves from Melbourne to Los Angeles has an entry dated "tomorrow". Editing its title must still work | An entry can sit with a date that would now be refused on create |
| What counts as an empty entry for erase-at-once | `contentJson == null`; `content_text` blank; also no soundtrack or tags | No title, `content_text` blank (so an empty paragraph or a divider counts as nothing), no media | D-30 says "no title, caption or media". A caption that holds no words is not a caption anyone needs back | A caption of only a divider is erased without the 30 days |
| Delete: soft or hard | Always soft; always hard; D-30's split | The split: soft for anything with content (`deleted_at` from the injected `Clock`), hard for an empty entry | D-30. The sweep counts its 30 days from this timestamp, so it must come from the `Clock` | A soft delete is a change to the row, so it raises `version` by one |
| Create with an id that might be in Recently deleted | `existsById` (JPQL); a native `EXISTS` | `EntryRepository.idIsTaken`, native | `@SQLRestriction` hides deleted rows from JPQL, so `existsById` would say "free" and the insert would fail on the primary key with a `500` | One more unscoped lookup (it reveals only "taken") |
| Seal edge cases | Equal date as a no-op; a past date as `409`; refuse to re-seal an opened Loot Drop | An equal date on a sealed entry is `409` ("must be later"); a past date is `400` first; an opened Loot Drop can be sealed again to any future date; microsecond truncation | The contract says "must be later", D-10 says "only moves later", and the database keeps microseconds so the answer should show what is stored | A retried `seal` with the same date after a timeout is `409`, not `200` |
| What `tags`, `soundtrack`, `replyToEntryId`, `replyIds` show now | Leave them out of the shape; accept them in the body and store; show them empty and ignore the body fields | Always in the shape, empty, and ignored in the body until 3.8, 3.13 and 3.14 | The shape matches the contract from the first day and the mapper already redacts them; the frontend's types don't change later. As in 3.3 for Era covers | A client that sends `tagIds` gets no error and no tags |
| Telling the tests what time it is | `@MockitoBean Clock`; `Clock.fixed` per class; relative dates on the real clock; a movable clock | A `MutableClock` bean, `@Primary`, imported by `MutableClockConfiguration`, shared by one base class | "23:30 on a Sunday in Melbourne" and the DST seconds need exact instants, and one test must move time (the unlock moment) | Its own Spring context and Postgres container, shared by all the entry test classes |
| Proving the version race | Reason about it; a hook inside the service; real threads | Eight threads send the same `version`; exactly one gets `200` and seven get `409` | It exercises both paths (the comparison and Hibernate's check) without a test-only hook | Which path rejects a given thread is not deterministic; the outcome is |

## 10. Concepts to learn from this task
- **Optimistic locking, compare and not copy** ([`EntryService.java:240`](../../../backend/src/main/java/com/memoirist/entry/EntryService.java#L240), [`Entry.java`](../../../backend/src/main/java/com/memoirist/entry/Entry.java) `@Version`). A version column goes up on every change; an `UPDATE ... WHERE id = ? AND version = ?` that matches no row means someone else got there first. Two layers: the service compares the client's number with the one it loaded (this catches the copy in the user's editor), and Hibernate's `WHERE version = ?` catches a commit that lands between the comparison and the flush. The mistake: copying the client's number onto the entity, which turns a guard into a value the client controls.
- **Hibernate's flush before a native query** ([`EntryService.java:165`](../../../backend/src/main/java/com/memoirist/entry/EntryService.java#L165)). With the default `FlushMode.AUTO`, Hibernate writes pending changes before a query whose result they could change; a *native* query is opaque, so it flushes everything. The mistake: setting fields, then running a native statement, then expecting one `UPDATE` at the end. Read and run native statements first, mutate last.
- **`INSERT ... ON CONFLICT DO NOTHING`** ([`WeeklyLogRepository.java:29-39`](../../../backend/src/main/java/com/memoirist/week/WeeklyLogRepository.java#L29-L39)). An "insert unless it exists" that is atomic: the database, not your code, settles two writers racing for the same unique key. It returns a row count, not the row, so you select afterwards. The mistake: `select`, then `insert if missing`, which has a gap.
- **Redaction by allow-list** ([`EntryMapper.java:83-103`](../../../backend/src/main/java/com/memoirist/entry/EntryMapper.java#L83-L103)). Build the restricted view from the fields that *may* be shown instead of copying everything and blanking some. The default for a field nobody thought about is then "hidden". Records make the compiler enforce it: adding a component breaks every `new EntryResponse(...)`.
- **Allow-list validation of untrusted structured input** ([`EntryContentValidator.java`](../../../backend/src/main/java/com/memoirist/entry/EntryContentValidator.java)). Name what is allowed and refuse the rest, so new things are refused until someone decides. Check size before shape. Say where, never what.
- **URL schemes and the browser's own parsing** ([`EntryContentValidator.java:162-174`](../../../backend/src/main/java/com/memoirist/entry/EntryContentValidator.java#L162-L174)). Browsers trim spaces and delete tabs and line breaks inside an address before they read its scheme, so a check on the raw text is not a check on what the browser will do. Prefix allow-list plus "no control characters". `Character.isISOControl` covers `U+0000`-`U+001F` and `U+007F`-`U+009F`; `String.strip()` removes Unicode whitespace (unlike `trim()`, which removes only characters up to `U+0020`).
- **Jackson 3's `JsonNode`** ([`EntryContentValidator.java`](../../../backend/src/main/java/com/memoirist/entry/EntryContentValidator.java), [`EntryText.java`](../../../backend/src/main/java/com/memoirist/entry/dto/EntryText.java)). Package `tools.jackson.databind`. `isString()`/`stringValue()` replace `isTextual()`/`asText()`; `propertyNames()` replaces `fieldNames()`; a JSON `null` read into a `JsonNode` record component is a `NullNode` while a missing field is Java `null` (checked with a ten-line scratch program), which is why `EntryText.content` maps both to `null`. `StreamReadConstraints` caps nesting at 500 and leaves the document length unlimited.
- **Code points versus chars** ([`ContentTextExtractor.java:146`](../../../backend/src/main/java/com/memoirist/entry/ContentTextExtractor.java#L146)). A Java `char` is a UTF-16 unit; an emoji is two. Cut with `offsetByCodePoints` or a surrogate pair can be split in half. The database counts code points; `@Size` counts chars, which is never more, so a value that passes always fits.
- **Dates versus instants and daylight saving** ([`WeekCalendar.java`](../../../backend/src/main/java/com/memoirist/week/WeekCalendar.java)). Keep the user's calendar day as a `LocalDate` and a week is simple arithmetic. The only place a zone matters is turning an *instant* into a day, and that is where a 23-hour or 25-hour Sunday moves midnight by an hour in UTC.
- **A `@Primary` test bean and `Clock.withZone`** ([`MutableClock.java`](../../../backend/src/test/java/com/memoirist/MutableClock.java)). The service asks the clock for a zone view; the view must share the moment with the clock the test moves, so `withZone` returns a new object around the same `AtomicReference<Instant>`.
- **Test base classes and the Spring context cache** ([`EntryApiTest.java`](../../../backend/src/test/java/com/memoirist/entry/EntryApiTest.java)). `@Import` and `@IntegrationTest` on an abstract superclass apply to every subclass; the context cache key is the configuration, so all the subclasses share one app and one container. A test class that adds a bean (the movable clock) costs one more start, once.
- **Race tests with a `CountDownLatch`** ([`EntryUpdateTest.java`](../../../backend/src/test/java/com/memoirist/entry/EntryUpdateTest.java)). Submit the tasks, have them wait on a latch, release them together, and assert on the *outcome* (one winner), not on which thread won.
- **A source scan as an architecture test** ([`EntryMapperIsTheOnlyPathTest.java`](../../../backend/src/test/java/com/memoirist/entry/EntryMapperIsTheOnlyPathTest.java)). When the language can't enforce a rule (a record's constructor is public) and the usual tool isn't approved, a test that reads the files is crude and unarguable. Add a positive control (the scan found more than 50 files) so a wrong working directory can't make it pass.

## 12. At work
- **Optimistic locking is the standard answer to "two people edited the same record".** In an enterprise Spring Boot service the same `@Version` column guards a customer record, a case or a limit; the REST version is an `ETag`/`If-Match` pair or a version in the body, and the status is `409` or `412`. A reviewer there looks for: the comparison happens in the service (not only in the database), the client's version is never written, a stale write changes nothing (assert the whole row, as `EntryUpdateTest` does), and there is a test with two threads.
- **Idempotent creates** (the client-supplied id, `200` on replay, `409` on someone else's) are the same idea as an idempotency key on a payment or transfer request. The detail a reviewer looks for is the one in `EntryService.create`: the replay check comes first and does not re-validate the body, and the "taken" check must see rows that other queries hide (here Recently deleted; at a bank, a soft-deleted or archived record).
- **One exit for sensitive data.** `EntryMapper` is the single place that decides what a caller may see, with an allow-list and a test that fails if another class builds the DTO. That is how masking of account numbers or PII is kept honest: not "remember to mask in each controller", but one mapper, default hidden, and a test that fills every field with a secret and reads the JSON for it.
- **Allow-list validation of rich input.** Anywhere free text or structured content is stored and later rendered (notes on a case, a message to a customer) the questions are the ones in the validator: what is allowed, what happens to an address with a tab in it, what is the size limit and which status does it return, and do the error messages echo the input.
- **Time zones and business dates.** A cut-off ("before 5pm on a business day", an end-of-day batch, a statement period) is a calendar day in a zone, not a timestamp in UTC. The week tests show how to test it: pick the exact instants either side of the boundary, including the day the clocks change, and make "now" injectable.
- **Concurrency tests that assert the outcome.** The reviewer's question for any "find or create" or "check then write" is "what if two requests do this at once?". A latch and eight threads is cheap and answers it.
- **What a reviewer would also ask here:** why is the `409` for a sealed entry decided before the `409` for a stale one (§4); why is the week looked up before the setters (§8); why the `PUT` of a sealed entry has no redacted answer (§4).

1. The service's comparison passed, so no `EntryStaleException`. Hibernate's `UPDATE ... SET ..., version = 4 WHERE id = ? AND version = 3` matches no row because the other request already made it 4, so the flush throws `ObjectOptimisticLockingFailureException`. `GlobalExceptionHandler` maps it to the same `409 entry-stale` with the fixed `detail`. Nothing of the losing edit is stored (`EntryUpdateTest.whenManyDevicesSaveTheSameVersionAtOnce...` exercises both paths).
2. `findOrCreate` runs a native `INSERT ... ON CONFLICT`. Hibernate flushes pending changes before a native query, so if `setEntryDate` came first it would be written by its own `UPDATE` (version 0 to 1), and the later `saveAndFlush` would write the other fields in a second `UPDATE` (1 to 2). The response would say `"version": 2` after one edit, so a client that expects "one edit, one step" and sends `version: 1` next gets `409 entry-stale` against an entry that nobody else touched (this is exactly how `EntryDatesTest` caught it).
3. Adding the component makes both `new EntryResponse(...)` calls in `EntryMapper` fail to compile, so the author has to pick a value for the sealed branch. `EntryMapperTest`'s reflection loop also fails unless the new component is empty while sealed or is added to the visible list on purpose. With "copy everything, then blank" the new field would have been copied by default and leaked until someone noticed.
4. `" javascript:alert(1)"` (leading space; browsers trim it): `strip()` then the prefix check refuses it because it doesn't start with `http://`, `https://` or `mailto:`. `"java\tscript:alert(1)"` (browsers delete the tab): the control-character ban refuses it. `"JaVaScRiPt:alert(1)"` (case): refused because it matches no allowed prefix, and the prefix match itself is done on `toLowerCase(Locale.ROOT)` so `HTTPS://` is accepted. Also `data:text/html,...` and `//evil.example` fail the prefix test.
5. 03:00 UTC on Monday 2 November is 19:00 on Sunday 1 November in Los Angeles (UTC-8 after the US change), so the entry date is 2026-11-01 and the week is the one that starts on Monday 2026-10-26. Two things make it so: `LocalDate.now(clock.withZone(ZoneId.of(user.getTimezone())))` (the user's zone, not UTC) and `WeekCalendar.firstDayOf(date)` on that date. A Melbourne user at 13:30 UTC on Sunday is already at 00:30 on Monday 2 November (UTC+11), so their entry is in the *next* week.
6. `existsById` is JPQL, and `@SQLRestriction("deleted_at IS NULL")` hides deleted rows from JPQL, so a deleted entry's id would look free and the insert would fail on the primary key with a `500`. `idIsTaken` is a native `SELECT EXISTS (SELECT 1 FROM entries WHERE id = :id)`, which Hibernate doesn't rewrite. Own live entry: `findByIdAndUserId` finds it first, `200` with the stored entry. Someone else's: `409 conflict`. Own deleted: `409 conflict` (restore it instead, D-30).
7. The response says the same version it was sent (for example `0` stays `0`). Hibernate's dirty check finds nothing changed, so it writes no `UPDATE`, `updated_at` doesn't move and the version stays. "Goes up on every change" is literally true because nothing changed; forcing an increment would make a harmless retry produce a new version for no reason.
