# Task 3.2: `/users/me`

> **Sprint:** 3 · **Commit:** `Sprint 3.2: Add GET and PATCH /users/me` · **Status:** done (every Done-when item is met, and `./gradlew build` passes with 359 tests; the spec review is in §9: pass with notes, no blocker or major finding) · **Time taken:** roughly 30 minutes by the machine clock (01:19 to about 01:49 on 2026-10-31), including five break-it runs, a manual run of the app, the full build and this entry
> **Built:** the first real endpoints. `GET /api/v1/users/me` returns the current user, and `PATCH /api/v1/users/me` changes the display name and the time zone. A time zone must be an IANA name (`Australia/Melbourne`, not `+10:00`), and a name must be 1 to 100 characters once its spaces are stripped. A well-formed `X-Dev-User-Id` that names nobody is `404`, and every later create will get the same answer from `UserService.currentUser()`. 96 new tests cover it, and the new endpoint made one task 2.5 test fail, which §8 explains.

## 1. The goal
[Task 3.2](../../SPRINT_PLAN.md#sprint-3-phase-1-api) is the first endpoint in the app. Its block says:
- **Read:** D-07, API_CONTRACT §Users.
- **Also decide:** what a well-formed `X-Dev-User-Id` that names a user who isn't there does when a create inserts a row: a foreign key error or `404`.
- **Done when:** tests prove `GET` and `PATCH` work; an unknown timezone returns `400`; a `displayName` that is blank or over 100 characters returns `400`. (`birthday` is task 3.13.)

It comes now, straight after storage (3.1), for three reasons:

| Why now | What it gives the next tasks |
|---|---|
| It is the smallest real endpoint: one table, no ownership puzzle (there is no id in the path), no sealing | A first controller → service → mapper → DTO chain, with validation and error bodies running end to end. Eras (3.3) and Templates (3.4) copy its shape |
| It is the first thing that calls `CurrentUserProvider` over real HTTP | Task 2.5 tested the header only through a test-only controller. Now a live Tomcat and the real app prove it |
| It owns the question every create will ask: *what if the user isn't there?* | `UserService.currentUser()` is the answer. Without it, 3.3 would invent its own |

The frontend (Sprint 4) will also call `GET /users/me` first, to learn the display name and the time zone it must use for every date it shows.

## 3. The plan
1. **Decide the contract questions before any code** (the unknown user, `birthday`, `null` versus missing, what a zone is) from the docs. The text itself went into `API_CONTRACT.md` and D-11 in the same change, after the endpoint worked, which the API rule allows ("before or with the code").
2. **DTOs and the time zone constraint**, with their unit tests (`UserUpdateRequest`, `@IanaTimeZone`). They have no dependencies, so they can be run in milliseconds.
3. **`UserService` and its unit test** with mocks: the unknown-user rule and the PATCH semantics are decisions, so they get tested without a database.
4. **Controller and mapper**, then the **integration test** over real HTTP and Postgres.
5. **Run `user.*`: expect the 2.5 profile test to break**, because the app now has something that needs a `CurrentUserProvider` (it did; §8).
6. **Break the code on purpose** (five mutations) to see which tests notice.
7. **Run the real app** against Compose and call it with `curl`.
8. **Docs** (D-11, TECH_STACK, DEVELOPMENT, the contract, the schema), then the **full build**, then this entry.

## 4. Decisions and alternatives

| # | Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|---|
| 1 | **The "also decide":** a header naming nobody, on a request that inserts a row | (a) do nothing: the foreign key fails and the client gets `500`; (b) map the foreign-key error (`SQLState 23503`) to `404` in the error handler; (c) every create loads the user first and `UserService.currentUser()` throws `404`; (d) check in the provider or a servlet filter on every request | **(c)** | (a) is a client mistake shown as a server fault, and it logs a stack trace for something that isn't a bug. (b) can't tell *which* foreign key failed without reading the constraint name, so a template deleted a second ago would also become "user not found". (d) adds a query to every request, turns the provider (a seam, 2.5 decision 8) into a service, and Phase 2's JWT replaces it anyway. (c) costs nothing extra in practice: most creates need the user's time zone for "today" and the week | Every create author has to remember to call it. A forgotten call shows up as a `500` in that endpoint's own "user isn't there" test, so the rule is: **each create endpoint gets that test** (recorded in D-11 and TECH_STACK; I did not edit the `new-endpoint` skill, see the hand-off in §5) |
| 2 | Who offers the user | each service calls `UserRepository.findById(provider.currentUserId())` itself; a `UserService.currentUser()`; a `@CurrentUser User` argument resolver | **`UserService.currentUser()`**, public | One place for the lookup and the exception, one place to change when Phase 2's provider arrives. | 3 | Is `birthday` in 3.2? | include it read-only on `GET`; leave it out until 3.13 | **Leave it out** | Task 3.13 lists "birthday on GET and PATCH" as its work and has its own tests (a future birthday is `400`). A `GET` that shows a field `PATCH` can't set would be half a feature. The contract gets one line saying it arrives in 3.13 | The contract's `GET` row lists `birthday` while the code doesn't have it yet (noted in the contract). A `birthday` in the body is ignored |
| 4 | The `/api/v1` prefix | a global prefix (`PathMatchConfigurer.addPathPrefix`); a constant; the literal in each controller | **The literal `@RequestMapping("/api/v1/users")`** | A global prefix by `@RestController` would also move the test-only probe controllers (`/test-support/...`), which are `@RestController`s too. The full path stays greppable and matches the contract word for word | The text `/api/v1` is repeated once per controller |
| 5 | What counts as a time zone | `ZoneId.of(text)` doesn't throw; `ZoneId.getAvailableZoneIds().contains(text)`; a hard-coded list of 400 names | **`getAvailableZoneIds()` minus `SystemV/`** | The contract says *IANA zone*. `ZoneId.of` also accepts `+10:00`, `UTC+10` and `Z`, which the browser's `Intl.DateTimeFormat` rejects, and the frontend renders every time in this zone (D-07). `SystemV/AST4` is in Java's list but isn't IANA. A hard-coded list would go stale when the JDK's tzdb updates | The JDK's list is a few names behind or ahead of a browser's from time to time; a rare new zone could be refused until the JDK is updated |
| 6 | Where the zone rule lives | a check in `UserService` that throws `ValidationFailedException("timezone", …)`; a custom Jakarta constraint on the request record | **A custom constraint, `@IanaTimeZone`** | A bad name *and* a bad zone are then reported together in one `400`; a service check runs after bean validation passes, so the client would fix one, resubmit, and meet the other. It also keeps the rule next to the field it checks | Two more files; a pattern (a custom `ConstraintValidator`) the project hasn't used before. Phase 2 sign-up can reuse it |
| 7 | How the name is checked | `@NotBlank @Size(max = 100)`; strip in the service; strip in the record's compact constructor and then `@Size(min = 1, max = 100)` | **Compact-constructor strip + `@Size(min=1,max=100)`** | `@NotBlank` rejects `null`, and in a `PATCH` `null` means "no change". Stripping in the service would measure the length *before* stripping, so `"  Sam  "` would count as 7 characters. Stripping in the record means validation and storage both see `"Sam"` | A little magic in a record; documented in its Javadoc and tested. The `@Size` message for a blank name says "size must be between 1 and 100", which is correct but not as friendly as "must not be blank" |
| 8 | `null` vs missing, and `{}` | `null` is an error; `null` clears the field; `null` = missing = no change | **`null` = missing = no change; `{}` is a valid no-op** | Both columns are `NOT NULL`, so "clear" can't mean anything. `{}` returning `200` is the usual PATCH reading | Task 3.13's birthday **can** be cleared, and a plain record can't tell `null` from missing. It will need a different shape (hand-off in §5, question 7 in §13) |
| 9 | How `update` writes | `repository.save(user)`; a JPQL `UPDATE users SET …`; set fields on the managed entity and let Hibernate flush | **Set fields on the managed entity** | The service is `@Transactional` and `currentUser()` returns a managed entity, so Hibernate sees the change at commit and writes one `UPDATE` (none if nothing changed). `save()` would be redundant. A JPQL update skips the entity and `@UpdateTimestamp` | Beginners find "no save call" surprising; the test `anEmptyBodyObjectChangesNothingAndRunsNoUpdate` shows it with the SQL log |
| 10 | Keeping the body from changing other columns (mass assignment) | bind the body to the entity; bind to a DTO with only the two fields; `FAIL_ON_UNKNOWN_PROPERTIES` | **A DTO with only the two fields; unknown properties ignored** | The record has no `email`, `id` or `createdAt`, so a body naming them can't reach them. Rejecting unknown properties would make a client that already sends `birthday` fail before 3.13, and Spring Boot ignores them by default | A typo such as `"displayname"` is silently ignored, so the client must read the response |
| 11 | Mapper shape | a `@Component` mapper; MapStruct (not allowed); a package-private class with a static method | **`UserMapper.toResponse(User)`**, static | No dependencies, nothing to mock; `EntryMapper` will need the clock and storage, `UserMapper` doesn't | Not swappable in a test, which nothing needs |
| 12 | The test that broke (§8) | delete `DevProviderAbsentInProdTest`; make `UserService` take an `Optional<CurrentUserProvider>`; keep the test and give it a stand-in provider, and add a fast test for the failure | **Stand-in provider, plus `anAppThatNeedsAProviderDoesNotStartWithoutOne`** | The point of the missing bean is that an app with no way to say who the user is must not start. An `Optional` provider would turn that safety off. Deleting the test would drop the check that the dev provider is absent in `prod` | The `prod` test now needs a fake provider that must be replaced in Phase 2 |
| 13 | Which user the integration tests change | edit the seeded dev user and put it back; make a user per test | **A user per test, deleted afterwards** | The dev user is shared by every test class on this Postgres container; changing it would make other classes depend on test order | Each test pays one `INSERT` and one `DELETE` |

In the order a reviewer should read it.

**Contract and decisions (docs)**
- [`API_CONTRACT.md`](../../API_CONTRACT.md#users-tag-users): the *Who is the current user?* bullet now says what a missing user does (`404` on `/users/me` and on every create, an empty list on a list), and a short list under the Users table states how `/users/me` behaves: `birthday` arrives in 3.13, `null` and missing mean no change, the name is stripped and 1 to 100 characters, the zone is an IANA name (no offsets), both fields are checked before anything is saved, `404`, `415` and `405`.
- [`DECISIONS.md` D-11](../../DECISIONS.md#d-11-ownership-and-the-dev-user): a new bullet (a header naming nobody is `404`; creates start with `UserService.currentUser()`) and a **Why** with the three rejected options. Its Updated date is 2026-10-31.

**The request and the response**
- [`dto/UserResponse.java`](../../../backend/src/main/java/com/memoirist/user/dto/UserResponse.java): a record with four components. Exactly the contract's fields; no `createdAt`.
- [`dto/UserUpdateRequest.java:18-25`](../../../backend/src/main/java/com/memoirist/user/dto/UserUpdateRequest.java#L18-L25): a record with `@Size(min = 1, max = 100) String displayName` and `@IanaTimeZone String timezone`. The compact constructor on line 22-24 strips the name before Jakarta looks at it, so a name of only spaces becomes `""` and fails `min = 1`.
- [`IanaTimeZone.java`](../../../backend/src/main/java/com/memoirist/user/IanaTimeZone.java): the constraint annotation. `@Constraint(validatedBy = …)`, `message()`, `groups()` and `payload()` are the three members Jakarta requires. The message is plain text on purpose (Hibernate Validator would read braces in it).
- [`IanaTimeZoneValidator.java:22-31`](../../../backend/src/main/java/com/memoirist/user/IanaTimeZoneValidator.java#L22-L31) (a practice block): the allow-list is built once into a `static final Set` (`getAvailableZoneIds()` builds a fresh set on every call), and `isValid` is `value == null || ZONES.contains(value)`. `null` is valid because a `PATCH` that leaves the zone alone sends none; Jakarta's rule is that `@NotNull` says whether a field is required.

**The service**
- [`UserService.java:37-40`](../../../backend/src/main/java/com/memoirist/user/UserService.java#L37-L40) `currentUser()`: `users.findById(currentUser.currentUserId()).orElseThrow(() -> new NotFoundException("User"))`. The message `"User not found."` doesn't repeat the id, which came from a header. `@Transactional(readOnly = true)` on the method; when a create calls it inside its own transaction, it joins that one and the entity stays managed.
- [`UserService.java:52-61`](../../../backend/src/main/java/com/memoirist/user/UserService.java#L52-L61) `update(request)`: loads the user, sets each field that is not `null`, returns the mapped response. There is no `save`. The mapping happens inside the transaction (`open-in-view` is off).
- [`UserMapper.java`](../../../backend/src/main/java/com/memoirist/user/UserMapper.java): one static method.

**The controller**
- [`UserController.java:20`](../../../backend/src/main/java/com/memoirist/user/UserController.java#L20): `@RequestMapping("/api/v1/users")`, `@Tag(name = "Users")`. `GET /me` and `PATCH /me` ([line 30](../../../backend/src/main/java/com/memoirist/user/UserController.java#L30), [line 39](../../../backend/src/main/java/com/memoirist/user/UserController.java#L39)). ## 6. How it was tested
- **Strategy:** three layers, because there are three kinds of claim.
  1. **Pure rules, no Spring** (milliseconds): the zone table (`IanaTimeZoneValidatorTest`), the body rules with a real Jakarta `Validator` (`UserUpdateRequestTest`).
  2. **The service's decisions with mocks** (`UserServiceTest`): a missing user is `NotFoundException` with a message that doesn't contain the id; only present fields change; no `save()`.
  3. **The wiring, over real HTTP and real Postgres** (`UserEndpointTest`, `@IntegrationTest`): status codes, JSON field names, `fieldErrors`, database rows, the SQL actually run, the OpenAPI description. This is the only layer that proves Spring MVC, validation, the advice and Hibernate fit together.
- Users are made per test, not edited from the seed (decision 13).

What `UserEndpointTest` covers (the 46 tests are 32 methods; three of them are parameterised and run 5, 4 and 8 times):
- **`GET`:** exactly four keys `id, email, displayName, timezone`; the seeded dev user without a header; two users each see only themselves.
- **Unknown user:** `404 not-found`, `detail` `User not found.`, the id not repeated, on `GET` and on `PATCH`; a `PATCH` creates no row; an invalid body for such a user is `400` (the body is checked first, and the answer doesn't depend on whether the user exists).
- **The header over real HTTP** (2.5 tested these only through MockMvc): not a UUID → `400`; empty → `400`, not the dev user; a value that is not a UUID is refused; whether two header lines were sent is not shown by this test (see the caveat in §8; task 2.5's MockMvc test proves two lines).
- **`PATCH` changes:** name only, zone only, both; five valid zones; the name is stripped; 100 characters is saved; `{}` and explicit `null`s change nothing and run **no** `UPDATE`; a real change runs exactly **one** `UPDATE`; Bob's `PATCH` never touches Alice.
- **`PATCH` refusals:** blank names (4 forms), 101 characters (and the text isn't repeated), 8 unknown zones (with the response holding exactly the two fixed sentences), two wrong fields in one `400`, a good name with a bad zone saves neither, broken JSON, an array, no body, `text/plain` (`415`), `PUT`/`DELETE` (`405` with `Allow`), `/users/{id}` and `/users` (`404`).
- **Mass assignment** (practice block): `email`, `id`, `createdAt` and `birthday` in the body change nothing, even an `email` that belongs to another user.
- **OpenAPI:** both operations under the `Users` tag with the documented response codes, and `minLength 1` / `maxLength 100` in the schema for the frontend.

## 10. Concepts to learn from this task
- **Custom Jakarta constraint** ([`IanaTimeZone.java`](../../../backend/src/main/java/com/memoirist/user/IanaTimeZone.java), [`IanaTimeZoneValidator.java`](../../../backend/src/main/java/com/memoirist/user/IanaTimeZoneValidator.java)): an annotation tagged `@Constraint(validatedBy = X.class)` plus a class implementing `ConstraintValidator<Annotation, Type>`. It plugs into `@Valid` like `@Size`. The mistakes: forgetting `@Retention(RUNTIME)` (the annotation is invisible at run time and nothing validates), returning `false` for `null` (every optional field then fails; `null` means "use `@NotNull`"), and keeping per-request state in the validator (one instance serves all threads).
- **Compact canonical constructor of a record** ([`UserUpdateRequest.java:22`](../../../backend/src/main/java/com/memoirist/user/dto/UserUpdateRequest.java#L22)): `public UserUpdateRequest { displayName = …; }` runs before the fields are assigned and may reassign the parameters. Jackson builds the record through it, so the validator sees the stripped value. The mistake: writing `this.displayName = …`, which doesn't compile in a compact constructor.
- **`@Valid @RequestBody`** ([`UserController.java:48`](../../../backend/src/main/java/com/memoirist/user/UserController.java#L48)): without `@Valid`, the annotations on the record are only decoration. Failure is `MethodArgumentNotValidException`, which the advice from 2.6 turns into the `fieldErrors` body.
- **JPA dirty checking and a managed entity** ([`UserService.java:52-61`](../../../backend/src/main/java/com/memoirist/user/UserService.java#L52-L61)): an entity loaded inside a transaction is tracked; at commit Hibernate compares it with the loaded copy and writes an `UPDATE` for what changed. No `save()` needed, and no `UPDATE` when nothing changed. The mistake: loading the entity *outside* a transaction (it is detached, and changes are lost silently), or calling `save()` on everything out of habit.
- **`@Transactional(readOnly = true)` joining a bigger transaction** ([`UserService.java:37`](../../../backend/src/main/java/com/memoirist/user/UserService.java#L37)): when `currentUser()` is called from a create's transaction, it joins it, and the read-only flag doesn't apply. Called alone, it is its own read-only transaction. Calling a method on `this` (as `update` does with `currentUser()`) skips the proxy, so no new transaction starts; here that is fine because `update` already has one.
- **Mass assignment** ([`UserEndpointTest.java:565`](../../../backend/src/test/java/com/memoirist/user/UserEndpointTest.java#L565)): a client sends fields you didn't mean to expose, and a framework that binds a body straight onto an entity applies them. Binding to a DTO that has only the allowed fields removes the problem. Jackson's default (ignore unknown properties) means the extra fields vanish without an error.
- **`ZoneId.of` vs the IANA list** ([`IanaTimeZoneValidator.java:23-25`](../../../backend/src/main/java/com/memoirist/user/IanaTimeZoneValidator.java#L23-L25)): Java's `ZoneId` is a bigger idea than a time-zone name: it includes fixed offsets and prefixed forms. `ZoneId.getAvailableZoneIds()` is the region list. It builds a new `HashSet` each call, so keep the result in a `static final` field.
- **`@TestConfiguration` stand-in bean** ([`DevProviderAbsentInProdTest.java:47-58`](../../../backend/src/test/java/com/memoirist/user/DevProviderAbsentInProdTest.java#L47-L58)): a nested static class with `@Bean` methods, pulled in with `@Import`, adds or replaces beans for one test class only. It also changes the test's context key, so the class gets its own context (and container).
- **`ApplicationContextRunner` for a failing start** ([`CurrentUserProfileTest.java:62`](../../../backend/src/test/java/com/memoirist/user/CurrentUserProfileTest.java#L62)): `run(context -> assertThat(context).hasFailed())` builds a tiny context and lets you assert that it could *not* start, and why (`getStartupFailure()`).
- **`SqlLog` to assert on the SQL** ([`UserEndpointTest.java:299`](../../../backend/src/test/java/com/memoirist/user/UserEndpointTest.java#L299)): the project's test helper captures what Hibernate ran. "No `UPDATE`" and "exactly one `UPDATE`" are claims about behaviour that a status code can't show.
- **`PATCH` vs `PUT`**: `PUT` replaces the whole resource; `PATCH` changes only what is sent. The rule here ([api.md](../../../.claude/rules/api.md)): `PATCH` exists only for `/users/me`.
- **404 for "not there" versus 500** (§4, decision 1): a request that names something that doesn't exist is the client's problem. A 500 says *we* broke.

## 12. At work
- **Mass assignment** (OWASP API Security's "broken object property level authorization") is a classic code-review finding when a controller takes an `@Entity` or a `Map` as `@RequestBody`. A reviewer there looks for the body type first: a dedicated request DTO with only the fields the caller may set. A test that sends the extra fields and reads the database is the proof.
- **`/me` removes a whole class of bug.** There is no id for a caller to change, so object-level authorization ("can this user read user 42?") has nothing to check. When a bank API has `/accounts/{id}`, the equivalent is the `findByIdAndUserId` finder and a `404` for someone else's id, which is what Eras (3.3) will do.
- **A missing referenced row is a `4xx`.** In enterprise code a foreign-key violation that reaches the client as `500` pages the on-call team for a typo. The review question is "what happens if the id is wrong?", and the answer should come from the service's own check, not from the database's error.
- **Allow-lists beat parsers.** Accepting "whatever `ZoneId.of` doesn't throw on" is the same mistake as accepting "whatever `new BigDecimal` accepts" for an amount, or "whatever `LocalDate.parse` accepts" for a booking date. Say what the downstream system can use, and refuse the rest.
- **Custom Bean Validation constraints** are everywhere in Spring codebases (account numbers, BSB/IBAN formats, currency codes). The things reviewers check: `null` handling, no state in the validator, a message that doesn't echo the input, and a unit test table of good and bad values.
- **Validate together, not one at a time.** Returning every wrong field in one `400` saves a form from the "fix one, resubmit, meet the next" loop, and it's why the zone rule is a constraint and not a service check.
- **"No `save()`"** surprises people who learned JPA through Spring Data's `CrudRepository`. Know the lifecycle (managed, detached) and the flush at commit, because reviewers will ask why a change was or wasn't written.
- **Change one thing in a test run, and watch it fail.** The break-it table (§6) is the habit worth keeping: a green test you have never seen red proves little.
