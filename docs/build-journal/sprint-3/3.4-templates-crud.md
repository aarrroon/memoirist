# Task 3.4: Templates CRUD

> **Sprint:** 3 · **Commit:** `Sprint 3.4: Add the Templates endpoints` · **Status:** done (every Done-when item is met; `./gradlew build` passes with 537 tests after the fix pass; the review is §9) · **Time taken:** roughly 22 minutes by the machine clock (04:35 to 04:57 on 2026-10-31), including a break-it run, a manual run of the app, two full builds and this entry
> **Built:** the five `/api/v1/templates` operations. A template is a name and up to 20 prompts ("subheadings"). The limits are enforced where the request is read, so a bad list is a `400` that names the item (`subheadings[2]`); `GET /templates` sorts by name in Java, ignoring case and accents; and deleting a template leaves every entry that used it, sealed or in Recently deleted, with its content untouched and only `template_id` emptied. 69 new tests cover it.

3. **Entity and repository.** Put the three limits on `Template` as constants; add `saveAndFlush`, `existsById` and a sort for `GET`.

5. **Service, mapper, controller.** Thin copies of the Era ones.
6. **Tests, cheapest first:** the validation rules with a plain `Validator` (no Spring), the sort order (plain Java), then the HTTP tests against Postgres.
7. **Break it on purpose:** swap `Stream.toList()` for `List.copyOf` in the cleaning helper and check that the tests notice.
8. **Run the real app** (`local` profile) and call all five operations with `curl`.
9. **Docs (contract detail, TECH_STACK, DEVELOPMENT, DATABASE_SCHEMA), this journal entry, then the full build** with every test re-run.

## 4. Decisions and alternatives
| Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|
| Is `subheadings` required? | Optional with a default of `[]`; required but may be empty | **Required**, `[]` allowed | The contract's table marks optional fields with `?` (`id?`), and `subheadings` has none. On a `PUT` (a full replace) a body that forgets the list must not silently wipe the prompts | A client must always send the array. The frontend always will |
| Clean the text, and when | Reject `" Where? "` as it is; strip then validate; strip but drop items that end up empty | **Strip, then validate**, in the record's compact constructor. An item that is empty after stripping fails its `1..200` rule | Same as Eras' title (3.3) and the user's display name (3.2). Dropping items silently would turn a client bug into data loss | One more step in two records, shared through `TemplateText` |
| A `null` inside the list | Let it crash; drop it; report it | **Report** it as `subheadings[n]: must not be null` | A `400` that names the item is what the contract promises. The cleaning step must therefore never throw on a `null`, which rules out `List.copyOf` (see §8) | A hand-written null check in the helper |
| How to validate the items | Container-element annotations (`List<@NotNull @Size(...) String>`); a class-level `ConstraintValidator`; a loop in the service | **Container-element annotations** on the record component | Declarative, in the same place as the other limits, reported by Spring as `subheadings[2]` with no code, and visible to springdoc as `maxItems` | A long component declaration (the formatter puts it on three lines) |

| Repeats and shared names | Reject repeated prompts; unique name per user; allow both | **Allow both** | The contract doesn't forbid them and the starter gallery's "one tap adds a copy" would otherwise answer `409` on the second tap. ## 8. What went wrong
1. **A shell command that wrote seven files at once wrote none.** I put seven `cat > file <<'EOF'` blocks in one Bash call; the shell stopped with `unexpected EOF while looking for matching '''` and `ls` showed that not even the first file existed. The whole call is parsed before any of it runs. Fix: the Write tool, one file per call. Lesson: a long multi-heredoc command is one parse; one stray quote anywhere loses all of it.
2. **The first break-it attempt broke the code instead of the behaviour.** I used `sed` to turn the `return subheadings.stream()` line into `return List.copyOf(...) //MUT` plus a commented-out start of the chain, which left the `.map(...).toList()` lines hanging. That wouldn't have compiled, so it proved nothing. I restored the file from a copy kept in the scratch folder and redid it with a multi-line `perl -0pi` substitution. The second attempt compiled and failed exactly two tests (§6).
3. **Two weak tests in my first draft.** One asserted that the three constants equal 100, 20 and 200 (the boundary tests already prove it, so it only repeated the numbers); one claimed to check ordering of names with spaces and digits but only asserted "the same answer twice". I replaced them before the first run: the second became `digitsSortAsTextSoTenComesBeforeTwo`, which states the behaviour, and the first was dropped.
4. **The formatter changed the records.** `spotlessApply` moved each annotated record component onto its own lines, so the diff of `TemplateCreateRequest` differs from what I typed. Not an error, but expect it when you retype a practice block: `./gradlew spotlessApply` before `build`.
5. **My own time labels in the notes were guesses.** I wrote "05:00" and "05:25" in the running notes; the machine clock said 04:50 when the first full build had run for 40 seconds. §Time taken uses `date` output only.
7. **Fix pass after the review (close-out).** Four quick fixes, no code logic changed: the `update` Javadoc now says "one UPDATE, or none if nothing changed" (the entity has no `@DynamicUpdate`, so all columns are written when any is dirty); TECH_STACK says "the stored row"; this entry's §12 no longer claims the 20-item limit bounds the work; the practice-block hint was re-flowed into four comment lines (the formatter had split it). `spotlessApply` then `./gradlew build` passed again (537 tests, 0 failures). Nothing failed in the fix pass.
6. **Nothing failed in the tests themselves.** All 69 new tests passed on their first run. That is why the break-it run in §6 matters: a test that has never failed has not shown it can.

## 10. Concepts to learn from this task
- **Container-element constraints** ([`TemplateCreateRequest.java:28-29`](../../../backend/src/main/java/com/memoirist/template/dto/TemplateCreateRequest.java#L28-L29)): `List<@NotNull @Size(min = 1, max = 200) String>` puts rules on each item, while the annotations before `List` apply to the list. Bean Validation 2.0 added this. Spring then names a failure `subheadings[2]` (it drops the validator's `.<list element>` suffix). The mistake people make: writing `@Size(max = 200)` in front of the list and wondering why the items are unchecked.
- **Records with a compact constructor** (same file, line 31): `public TemplateCreateRequest { name = ...; }` runs before the fields are set, so it can clean the input. Jackson uses the canonical constructor, so the cleaning happens on every request, and validation sees the cleaned values. Anything thrown here is a `500`, not a `400`.
- **`Stream.toList()` versus `List.copyOf` versus `List.of`** ([`TemplateText.java:21-28`](../../../backend/src/main/java/com/memoirist/template/dto/TemplateText.java#L21-L28)): all three give an unmodifiable list; only `Stream.toList()` accepts a `null` element. `List.copyOf(list)` and `List.of(...)` throw `NullPointerException` on one. `Arrays.asList` and `ArrayList` accept `null`s too.
- **Collation and `java.text.Collator`** ([`Template.java:33-37`](../../../backend/src/main/java/com/memoirist/template/Template.java#L33-L37)): comparing strings with `compareTo` compares UTF-16 values, so every capital precedes every small letter and `É` follows `z`. A `Collator` knows letter order for a locale. `PRIMARY` strength ignores case and accents; `TERTIARY` (the default) does not. Use `Locale.ROOT` when the answer must not depend on the machine.
- **Composing comparators** ([`Template.java:45-48`](../../../backend/src/main/java/com/memoirist/template/Template.java#L45-L48)): `Comparator.comparing(key, keyComparator).thenComparing(...)`. Each later comparator is only asked when the earlier ones say "equal". `Comparator.nullsLast(...)` wraps a comparator to tolerate `null` keys.
- **Referential actions** (V1, `entries.template_id ... ON DELETE SET NULL`): the database changes the child rows when the parent goes. It happens in the same statement, for every row, and no JPA filter (`@SQLRestriction`) can hide a row from it. The mistake people make is to model the same thing again in application code and miss a case.
- **Idempotent create** ([`TemplateService.java:48-65`](../../../backend/src/main/java/com/memoirist/template/TemplateService.java#L48-L65)): the client picks the id, so repeating a request is safe: the same user gets the stored resource back (not re-applied), another user gets `409`. The same idea as an idempotency key on a payment request.
- **`saveAndFlush` and `@UpdateTimestamp`** ([`TemplateRepository.java:18`](../../../backend/src/main/java/com/memoirist/template/TemplateRepository.java#L18)): Hibernate fills the timestamps while it writes the row, which normally happens at commit. Building the response before that shows empty `createdAt` or the old `updatedAt`. A `PUT` that changes nothing runs no `UPDATE`, so `updatedAt` stays put.
- **Mass assignment** (`aUserIdOrTimestampsInTheBodyChangeNothing`): the request record has no `userId`, `createdAt` or `updatedAt` component, so Jackson skips them. The safe design is a body type that cannot hold the dangerous field, not a check that clears it.
- **Reading the database from a test** (`entryRow`, `subheadingsJson`): `JdbcClient` with `SELECT *` and `.query().singleRow()` returns a `Map` of the row. Comparing two such maps is the strongest "nothing else changed" check there is, because it covers a column nobody listed.

## 12. At work
- **Strict input at the edge.** A bank API gets lists from other systems: beneficiaries, line items, tags. The questions here are the ones a reviewer asks: is the list bounded (the 20-item limit gives a clean `400` for a huge list, but it does not stop the parsing, because the check runs after the whole body is read; bounding that needs a request-size cap, which is not in scope here), is each item bounded, is a `null` item a `400` rather than a `500`, and are the error messages free of what was sent (a name in an error message ends up in a log). Container-element constraints and a total cleaning step are the Spring way to answer all four in a few lines.
- **Idempotent creates.** Payments, transfers and onboarding requests all carry an idempotency key. `TemplateService.create` is the same idea in miniature: the same key from the same caller returns what was stored and applies nothing; the same key from another caller is a conflict that tells them nothing.
- **Referential actions and soft delete.** In an enterprise database, "what happens to the children when the parent is deleted" is a decision in the schema (`CASCADE`, `SET NULL`, `RESTRICT`), and it interacts with soft-delete filters. A reviewer looks for a delete that quietly misses the rows a filter hides, and for a test that proves the children survive. Comparing whole rows is what they would like to see.
- **Ordering that doesn't depend on the environment.** "Sorted by name" in SQL changes with the database's collation, which is exactly the kind of difference between a developer laptop, a test container and production that causes a "works on my machine". Sorting a small list in Java with an explicit locale removes the variable. For a large list you would set the collation on the column or index instead.
- **Review habit.** When a reviewer sees a new endpoint copy of an old one, they diff it against the original: what is the same (the pattern), and what is different (and why). §4 lists the differences.
