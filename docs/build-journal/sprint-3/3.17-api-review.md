## 8. What went wrong
1. **The first read of the document was the finding.** `jq`-style output of one `POST /tags` showed `"400": {... "schema": {"$ref": "#/components/schemas/TagResponse"}}`. The cause is how springdoc builds a response for an `@ApiResponse` that has no `content`: it copies the method's return type onto it. Every earlier `*ApiDescriptionTest` checked the *codes* only (`containsExactlyInAnyOrder("200", "201", "400", "404", "415")`), so none could see it. Fix: the customizer.
2. **`@Schema(types = {"object", "null"})` on `contentJson` did nothing useful.** The first try, `@Schema(type = "object", nullable = true)`, produced `"type": ["string", "null"]` (the `object` was lost). The second, `types = {...}`, produced `oneOf [$ref JsonNode, null]`: the `$ref` to the Jackson type won over the explicit type. Fix: let the type be `JsonNode`, `nullable = true`, and replace the `JsonNode` component by `TipTapDocument` in the customizer; `wrapNullableReferences` rewrites the `{"type": "null", "$ref"}` springdoc emits for every nullable `$ref`.
3. **The live-walk test found a gap the by-hand comparison missed.** First run: `GET /eras/{id}.weeklyLogs[0].title is null, but the schema does not allow null` (seven times). `EraWeekResponse.title` is the week's title, `null` until the user names it, and I had annotated the same field on `WeeklyLogResponse` but not on this sibling record. One annotation; then PASSED. This is the case for the test: it only appears when the data has an unnamed week in an Era.
4. **A silent no-op in my own script.** Editing the customizer from a Node one-liner, `String.replace` with an anchor that did not match changed nothing and printed nothing; the first restart showed `JsonNode` still there. The anchor had been `"schemas.put(PROBLEM, problemSchema());\n"` against a file with CRLF line endings. Fix: apply the missing edit with the Edit tool, and check the result with `grep` after every scripted edit. (Line endings: the Windows checkout is CRLF; Spotless and git normalise, so only scripted edits notice.)
5. **A mis-ordered import.** The first scripted import insertion on `MusicResult.java`, a file with no other imports, put the `import` above `package`. Spotless failed with `palantir-java-format ... class, interface, annotation type, enum, record, method or field expected`. Fix: move it below the `package` line.
6. **A wrong-language import** in my first draft of `OpenApiConfiguration` (`org.springframework.http.MediaType.Companion`, a Kotlin habit) failed to compile; removed. It was never needed: the swagger `MediaType` is the one used.
7. **One Gradle run reported 20 minutes** (`test --tests '*ApiDocsContractTest' --tests '*ApiDescriptionTest'`) and hit the 10-minute limit of the shell, so it ran in the background. Cause not found: the Postgres container, SeaweedFS and a second cached context all start for the first time in a fresh Gradle run; the tests themselves report seconds. Mentioned so that the next run is not mistaken for a hang.
8. **No failing test was left.** Nothing needed more than one fix attempt.
9. **Close-out:** no code changed after the review (all four findings were minor and the two code-adjacent ones are optional or Phase 2), so no fix pass failed and the build was not re-run. Another session's changes in docs/README.md, docs/WORKFLOW.md and docs/design/ were left out of the commit.

## 10. Concepts to learn from this task
- **`OpenApiCustomizer`** ([`OpenApiConfiguration.java:66`](../../../backend/src/main/java/com/memoirist/common/OpenApiConfiguration.java#L66)): a bean springdoc calls with the finished `OpenAPI` object, for changes that annotations can't express or would have to repeat. The mistake: using it to paper over a wrong annotation instead of fixing the annotation when there are only a few.
- **OpenAPI 3.1 is JSON Schema** (`:119`): "can be null" is `type: ["string", "null"]`, not 3.0's `nullable: true`; a nullable reference is `oneOf: [{$ref}, {type: null}]`. Tools that read 3.0 and 3.1 differ, so check what the generator needs.
- **`required` means "always present", not "never null"**: in JSON Schema they are separate. A field can be required and nullable, which is what the API sends (`"title": null`). The mistake is leaving a field out of `required` because it can be null; `openapi-typescript` then writes `title?: string | null`, and every use needs a check for `undefined` that can never happen.
- **A contract test walks the real thing against the schema** ([`ApiDocsContractTest.java:459`](../../../backend/src/test/java/com/memoirist/common/ApiDocsContractTest.java#L459)): three rules (no unknown property, every required property, null only if allowed) catch nearly all drift between a server and its description. It is a tiny JSON Schema validator, written because pulling a library in for 40 lines was not worth a dependency decision (and none was approved).
- **`@Schema(nullable = true)` on a record component**: annotations on a record component are copied to the field and the accessor; swagger-core reads them. Gotcha: on a component whose type is another record it produces `{"type":"null","$ref":...}` (§8.2).
- **`JsonPath.read(text, "$")`** returns plain `Map`s and `List`s (json-smart), which is what makes the walker 60 lines. Use it for tests that explore JSON without a DTO.
- **Asserting on collections**: `containsExactlyInAnyOrder` / `containsExactlyInAnyOrderElementsOf` for key sets and endpoint lists (order is not the point), `isEqualTo(List.of(...))` only where order is part of the promise (the `required` list, which springdoc sorts alphabetically).
- **Content negotiation vs documentation**: `produces` changes what the server does; the customizer changes only what the document says. Keep them apart.

## 12. At work
- **Contract-first APIs and their drift.** In a bank, the OpenAPI file is often the contract between teams (the payments API consumed by the mobile app). The usual failure is exactly this task's: the file is generated from code, everyone trusts it, and it has been wrong for a year. A test that calls the real service and validates the response against the published schema (Pact, Spring Cloud Contract, or a hand-rolled walker like this one) is how teams stop that.
- **Error shapes are part of the contract.** RFC 9457 `application/problem+json` is what many internal API standards require. Declaring it once (a shared `Problem`) and not per endpoint is what API governance reviews look for; a reviewer will ask where the `4xx` schemas are defined.
- **Generated clients amplify documentation bugs.** If `required` is missing, every consumer writes `?.` and `?? ""` for fields that are never absent, and a real absence later is hidden. A reviewer will ask: "is this nullable, or just not required?"
- **Customizer vs annotation.** Cross-cutting rules ("every response field is required", "every error is a problem") belong in one place; per-field facts (this one can be null) belong on the field. Reviewers dislike 120 copies of one annotation and also dislike a customizer with a list of field names.
- **Don't add a validator library for 40 lines** is a conversation about supply chain in a bank: every dependency is a vendor review. Here none was approved, so the walker is test code.
