# Task 3.9: Entry list for the timeline

> **Sprint:** 3 · **Commit:** `Sprint 3.9: Add the entry list for the timeline` (hash in the OVERNIGHT_REPORT) · **Status:** done (every Done-when item is met; `./gradlew build` passes with 1214 tests; the review is §9) · **Time taken:** roughly 36 minutes by the machine clock (01:29:17 to 02:04:38 on 2026-11-01, unattended). That includes a break-it run, a live run of the app, an `EXPLAIN` on 80,000 synthetic rows, one full build (6 min 57 s) and this entry
> **Built:** `GET /api/v1/entries`, the all-entries timeline: one short `EntrySummary` row per entry, newest memory date first, paged, with an optional `tagId` filter. A sealed Loot Drop is a locked row with nothing private in it, and while filtering it is neither listed nor counted. A page costs 3 SQL statements however many entries, photos and tags it holds. 86 new tests cover it.

## 1. The goal
[Task 3.9](../../SPRINT_PLAN.md#sprint-3-phase-1-api) is the first of four tasks that return `EntrySummary` rows (3.10 Opened, 3.11 Recently deleted, 3.12 On this day). Its block:
- **Do:** `GET /entries` with paging and an optional `tagId`, returning `EntrySummary` rows with `title`, `previewLine`, media counts, `firstMediaKind` and tags.
- **Done when:** tests prove ordering (newest memory date first, then newest created); the tag filter, which never returns sealed entries; `previewLine` is the caption's first non-heading line, capped at 120 characters, falling back to the first heading; `firstMediaKind` names the first media item; a sealed entry's title, preview, counts, media kind and tags are hidden; the query count per page doesn't grow with the number of entries.

Why now:

| Why now | What it gives the next tasks |
|---|---|
| 3.5 already stores `preview_line` on every caption write, and 3.6 and 3.8 made media and tags real | Nothing new is stored: this task only *reads*, and no migration is needed |
| 3.7 worked out how to load a page of entries with their media and tags in a fixed number of queries | The same trick applies here, and the new `EntryListService` is where 3.10 to 3.12 put their lists |
| 3.8 wrote the rule "a sealed entry is left out *inside the query*" for tag counts | The tag filter is the second place that rule has to hold, and it is the one that could leak the most (a filtered list is exactly where "does this Loot Drop carry this tag?" would be answered) |
| The frontend's timeline screen (Sprint 4) is blocked on this shape | The row is the contract the generated types will be made from |

**What the docs didn't settle** (each is a decision in §4):
- The default `size` (the Pagination section says 10; the endpoint's own example says 50).

- How `photoCount`, `voiceNoteCount` and `firstMediaKind` are worked out from `media_type` and `purpose`.

## 3. The plan
In the order it was done, and why:
1. **Read the contract, the decisions and the nearest code** (the feed). A list is "the feed's loading trick, one level up".
2. **Plan the load.** Decide what a row needs (the entry, its media kinds, its tags), how many statements that may cost, and what a sealed entry must cost (none beyond the page).
3. **Two small pure pieces first:** `MediaKind` (what an item is) and `MediaSummary` (counts and first kind). They have no database, so they get plain unit tests.
4. **The row and the mapper:** `EntrySummaryResponse` and `EntryMapper.toSummary`, written as an allow-list like `toResponse`.
5. **The queries:** the two page queries and the two fetch-by-id queries in `EntryRepository`.
6. **The service and the controller:** `EntryListService`, then `GET /entries`.
7. **Tests:** the mapper (plain), then the HTTP behaviour (`EntryListTest`, `EntryListTagFilterTest`), then the statement counts.
8. **Break it on purpose:** remove the sealed rule from the tag filter and the tie-break from the sort, and check the tests fail.
9. **Run the real app** and call it with `curl`; **`EXPLAIN`** the sort on 80,000 rows.
10. **Docs, the full build, this entry.**

## 4. Decisions and alternatives
| Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|
| Where the list code lives | Add `list` to `EntryService`; a new read-only `EntryListService` | **`EntryListService`** (`@Transactional(readOnly = true)`) | `EntryService` is the write path and already 336 lines of rules about changing an entry. The reads that return `EntrySummary` (3.10 to 3.12) are about queries and statement counts, a different reason to change | Two services touch `Entry`; the controller takes both |
| Entities or a projection for the page | Select only the columns a row needs (`select new …`) and map from that; load whole `Entry` rows and use `toSummary(entry, now)` | **Whole entities** | The docs name `toSummary(entry, now)`, 3.10 to 3.12 return entities too (Recently deleted comes from native queries that return `Entry`), and one mapper input keeps the seal rule in one shape | The page query reads each caption (up to 200 KB) although a row doesn't show it. A projection is the first thing to try if long captions make a page slow; §5 and TECH_STACK say so |
| How a page's media and tags are loaded | Leave them lazy (`@BatchSize(50)`); one query per row; two `left join fetch` queries by entry id; two slim projection queries | **Two `left join fetch` queries by id, for the open entries only** | Exactly the same statement count for any page, which is the Done-when item. `@BatchSize` alone costs two more statements for each further 50 entries (and a page may hold 100). The ids are those of open entries by `EntrySeal`, and the query repeats the rule, so a Loot Drop's media and tags are never read | A fetch join sends an entry's row once per photo or tag. Accepted in 3.7, and for the same reason here |
| The sort | `entry_date desc, created_at desc`; add `id desc` as the last key | **`entry_date desc, created_at desc, id desc`** | The photo dump makes entries in the same instant on the same day. With ties the database may order them differently between two page requests, so a client paging through sees one entry twice and misses another. A total order fixes that. `EntryListTest` proves it, and fails without the `id` | One more sort key. `EXPLAIN` shows it costs nothing: the index gives the dates in order and Postgres sorts only the rows of one day |
| One query with an optional `tagId` or two | `where (:tagId is null or …)` with a cast; two methods | **Two methods**, `findTimelinePage` and `findOpenTimelinePageByTag` | They differ in more than one condition (the sealed rule applies to one only), and a nullable parameter in Hibernate needs a `cast(… as UUID)` or Postgres can't type it. Two queries read as two rules | Two near-identical `order by` clauses (a comment above them says why) |
| How to match "has this tag" | `exists (select 1 from e.tags t …)`; `:tagId member of`; `join e.tags t where t.id = :tagId` | **`join e.tags t where t.id = :tagId`** | `entry_tags` has a primary key on `(entry_id, tag_id)`, so one tag matches an entry at most once and the join can't repeat a row. The page and the count agree without `distinct` | If the table ever allowed duplicates this would break; the primary key is the guarantee |
| Where the seal rule goes in the tag filter | Filter in Java after loading; the query | **In the query, in both the page query and the count query** | A Java filter would load the sealed entries (their captions) and leave `totalItems` wrong, so the total would move when the user sealed an entry. Both queries say `unlock_date is null or unlock_date <= :now`, the rule of `EntrySeal` | The rule is written in SQL as well as in `EntrySeal`; the tests pin the boundary (open at the very instant) |
| A `tagId` that is not the user's | `404`; `200` with an empty page | **`404 not-found`**, after one `findByIdAndUserId` | Rule 3: a referenced id the user doesn't own is `404`, as on an entry's `tagIds`. An empty page would look the same as a tag nobody used, and the client couldn't tell a stale tag from a new one | One extra statement when filtering (the tests count it) |
| The default `size` | 10 (the Pagination section); 50 (this endpoint's example row) | **50** | The row `GET /entries?page=0&size=50` is the endpoint's own statement, and the Pagination section says a row can override it | A client that sends nothing gets up to 50 rows |
| A `size` over 100 | Clamp to 100; `400` | **`400 validation-failed`** with `fieldErrors.size` | Same as 3.7's feed: a silent clamp hides the limit from a client that asked for 101 | None |
| An empty `tagId=`, `size=` or `page=` | Hand-parse the strings and answer `400`; leave Spring's rule (empty is "not sent") | **Leave Spring's rule and pin it with tests** | Hand-parsing would throw away the OpenAPI `uuid` and `integer` types for a case that cannot leak anything: an empty `tagId` means the unfiltered list, which only shows a sealed entry as a locked row anyway | A client bug that sends `tagId=` gets the unfiltered list instead of an error |
| Where "what is a photo, a diary page, a voice note" lives | In the mapper; in a SQL aggregate (`count(*) filter (where …)`); in the `media` package | **`MediaKind` and `MediaSummary` in `media`**, plain Java | One definition used by the counts and the first kind, and a unit test away. A SQL aggregate would put the rule in a second language and still need Java for the kind | The rule is evaluated in memory over the page's media rows |
| What "first" means | The head of the list Hibernate filled; the lowest `displayOrder` | **The lowest `displayOrder`** (`Stream.min`) | The list's order comes from an `@OrderBy` that a fetch join applies. "The first item" should not silently depend on that detail staying true (a practice block, §11) | One tiny sort per row |
| Counts of a sealed row | `0`; `null` | **`null`** (`Integer`, not `int`) | The contract says `null`. A `0` would claim "no photos" about an entry that may have 20 | Callers must handle `null` |
| `deletedAt` on a row | Leave it out until 3.11; include it | **Include it, mapped from the entity** | It is part of the documented shape, so the generated types are right from now on. It is always `null` here because deleted entries are hidden by `@SQLRestriction`; 3.11 reuses the mapper. A sealed row keeps it (it is not private, and Recently deleted needs the 30-day clock) | A field that is always `null` until 3.11 |
| Offset paging or keyset paging | `limit/offset`; `where (entry_date, created_at, id) < (…)` | **Offset** (the contract has `page`) | A journal's timeline is small and the contract is `page`/`size`. `EXPLAIN` measured the cost of depth (§6) | A deep page reads all rows before it; keyset is the fix if it ever matters |
| The guard that only the mapper builds a row | Trust review; extend `EntryMapperIsTheOnlyPathTest` | **Extend the test** to `new EntrySummaryResponse(` and `EntrySummaryResponse::new` | The 3.5 test already anticipated it in its Javadoc, and a second place building a row is a second place that can forget to hide a sealed one | None |

## 8. What went wrong
In order.
1. **`python3` isn't on this machine.** The first multi-line edit of `EntryMapper` used a Python script and got "Python was not found; run without arguments to install from the Microsoft Store" (the Windows stub). **Fix:** used the editor tool for multi-line edits, and `node` for scripted ones.
2. **A long `bash` command did not parse and so nothing in it ran.** One command wrote a test file with a heredoc and then ran a big `node -e '…'` edit; Bash reported `unexpected EOF while looking for matching '` and *neither* part ran, including the file write. The next `ls` showed the file missing. **Fix:** write files with the file tool, and put longer scripts in a file instead of a quoted one-liner.
3. **Windows line endings made a scripted edit do nothing.** The working tree is CRLF (`core.autocrlf=true`; the index is LF), so a `node` string replace of text that spans lines found no match and silently changed nothing, while a single-line replace in the same script did apply and left the file with mixed endings. `grep` showed the missing test, which is how it was noticed. **Fix:** redid the edit with the editor tool; `spotlessApply` normalised the endings. ## 10. Concepts to learn from this task
- **`Page` with an explicit `countQuery`** ([`EntryRepository.java:131-144`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L131-L144)): a `@Query` that returns `Page<T>` runs the query with a `limit`/`offset` and, only when the page might not be the last, a second `count`. Spring Data skips the count when the page has fewer rows than `size` (the total is then `offset + rows`), which is why the statement count has a "full page" case. The mistake: assuming the count always runs, or never.
- **A total order for paging** ([`EntryRepository.java:125-129`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L125-L129)): `order by` on columns that can tie is not a stable order; the database may break ties differently each time. Add a unique last key (the id). The classic bug is a list where "page 2 shows something from page 1".
- **`left join fetch` to initialise a lazy collection on entities you already hold** ([`EntryListService.java:86-103`](../../../backend/src/main/java/com/memoirist/entry/EntryListService.java#L86-L103)): inside one transaction the persistence context returns the *same* objects, and the fetch join fills their lazy lists on the way. You ignore the result. Never fetch-join two collections in one query (`MultipleBagFetchException`), so it is two queries.
- **An allow-list mapper** ([`EntryMapper.java:109-126`](../../../backend/src/main/java/com/memoirist/entry/EntryMapper.java#L109-L126)): the sealed branch names what is shown instead of blanking what is hidden, so a new field fails to compile until someone decides. The mistake is "copy everything, then null the secret ones", which leaks every field added later.
- **`switch` over an enum with arrows** ([`MediaSummary.java:33-38`](../../../backend/src/main/java/com/memoirist/media/MediaSummary.java#L33-L38)): `case PHOTO, PAGE_SCAN -> photos++;`. No fall-through and no `break`; several labels share one arm.
- **`Stream.min` with `Comparator.comparingInt`, then `Optional.map` and `orElse(null)`** ([`MediaSummary.java:39-44`](../../../backend/src/main/java/com/memoirist/media/MediaSummary.java#L39-L44)): the lowest by a key without sorting the list. `Optional` is fine inside a method; the record's field stays a plain nullable.
- **Records with static factories and constants** ([`MediaSummary.java:17-20`](../../../backend/src/main/java/com/memoirist/media/MediaSummary.java#L17-L20)): `EMPTY` and `of(...)` give a record a name for its common cases.
- **`@ParameterizedTest` with `@CsvSource`** ([`MediaKindTest.java`](../../../backend/src/test/java/com/memoirist/media/MediaKindTest.java)): one test body, a table of cases, and JUnit converts the text to an enum.
- **Counting statements with Hibernate `Statistics`** ([`EntryListQueryCountTest.java:43-49`](../../../backend/src/test/java/com/memoirist/entry/EntryListQueryCountTest.java#L43-L49)): `clear()`, make a request, read `getPrepareStatementCount()`. Compare two journals of different sizes rather than only hard-coding a number: an extra statement everyone pays is a design change, an extra statement per row is a bug.
- **Spring's handling of an empty query value:** an empty string for an optional or defaulted `@RequestParam` is "not sent" (for a `UUID` the converter returns `null`). It is not an error, which is why the tests pin it.
- **Offset against keyset paging:** `limit/offset` is simple and lets a client jump to page N, but it reads every row before the page; `where (a, b, id) < (?, ?, ?)` reads only the page. The `EXPLAIN` numbers in §6 are the evidence either way.

## 12. At work
- **Every list screen has the same four problems:** which rows, in what order, how many queries, and what the user may see. Here they are one test class each (`EntryListTest`, the tie test, `EntryListQueryCountTest`, the sealed tests). In a bank's Spring Boot service the "may see" part is entitlements or data classification, and the same lesson applies: **filter in the query, including the count**. A total that moves when a hidden row changes is an information leak, however well the rows themselves are hidden.
- **Stable ordering is a review comment you will write.** Any paged `order by` whose columns can tie (a timestamp to the second, a status, a date) needs a unique last key. Ask "what happens to page 2 if two rows tie?".
- **N+1 does not show in functional tests.** The answer is the same, only slower, so a reviewer asks for a statement-count test, or looks for `@OneToMany` read inside a loop. Hibernate's statistics make it a three-line assertion.
- **A mapper that is the only way out** (and a test that fails if a second one appears) is the defence in depth against "someone added a new endpoint and returned the entity". It is cheap and it works.
- **A reviewer would look for:** an `order by` without a tie-break; a count query that differs from the page query; a Java `filter` after a `findAll`; a `0` where the data is hidden (it claims knowledge); and a check that a referenced id (here `tagId`) belongs to the caller.

1. The database may order the tied rows differently for each query (a different plan, or a different `limit`/`offset`), so an entry can appear on two pages and another on none. A test with one big page runs one query and sees one order. The tie test builds seven tied entries, walks three small pages and compares them with the big page; removing `e.id desc` makes it fail.
2. `totalItems` comes from the count query. If it counted sealed entries, the number would change when the user sealed an entry, which says something about a hidden entry even though the rows are hidden. Both queries must use the same rule. A test pins it (`aSealedEntryIsNeverListedAndNeverCounted…`) and another reads the SQL of both.
3. 99 rows on a page of 100: the page has room to spare, so Spring Data skips the count: the page, the media and the tags, 3 statements. With exactly 100 rows the page is full, so it also runs the count: 4. (This is the mistake in the first run of `thePageCostsTheSameJustPastTheBatchSizeOf50…`.)
4. Fetch-joining two `List`/bag collections at once throws `MultipleBagFetchException` and, if it were allowed, would multiply the rows (photos × tags per entry). Two queries keep it to one extra row per photo or per tag and a fixed count.
5. An empty value is treated as "not sent", so it is exactly `GET /entries`, which is allowed to show sealed entries as locked rows with nothing private. If those rows showed tags, the *unfiltered* list would be the leak, and the fix is in the mapper (the sealed branch must show no tags), not in parameter parsing.
6. The order of `entry.getMedia()` comes from an `@OrderBy` on the collection that a fetch join happens to apply. Nothing in `MediaSummary` should depend on that; `min(displayOrder)` states what "first" means and is covered by a test with a shuffled list.
7. `404 not-found`, the same as a tag that doesn't exist, with a `detail` that doesn't repeat the id. An empty page would look like a tag nobody has used, and the client could not tell a stale tag from a new one; `404` also follows the rule that a referenced id the user doesn't own is never confirmed.
