## 10. Concepts to learn from this task
- **`ApplicationRunner`** ([`SampleContentSeeder.java:77`](../../../backend/src/main/java/com/memoirist/dev/SampleContentSeeder.java#L77)): code Spring Boot runs once after the context is ready. Runners of the same order have no promised sequence, which is why `seed()` calls `ensureBucket()` itself. Mistake: assuming "my runner runs after that one".
- **`@Profile` plus `@ConditionalOnProperty` on a bean** (`:75`): both must be true. A profile says where the app runs; a property says whether this developer wants it. Mistake: relying on only one, then enabling a dev job by accident in a shared environment.
- **Name-based UUIDs** (`id(...)`, `:403`): `UUID.nameUUIDFromBytes(bytes)` hashes a name into a version 3 UUID, the same every time. Use it for fixtures and idempotent loads; never for secrets or anything that must be unguessable.
- **`TransactionTemplate.executeWithoutResult`** (`:162`): a transaction you open by hand when a method must not be `@Transactional` as a whole (the file uploads should not hold a connection). The lambda commits on return and rolls back on any exception.
- **`EXISTS` against `COUNT(*)`** (`:175`): `EXISTS` stops at the first row. Asking "is there at least one?" with a count reads every row. Four `EXISTS` joined with `OR` is one round trip.
- **`@SQLRestriction` hides rows from JPA but not from SQL** (D-30): the guard has to see Recently deleted entries, so it asks the table with `JdbcClient`.
- **Idempotent seed versus repeatable migration**: a Flyway `R__` migration reruns when its checksum changes; this seeder reruns never. Pick by who owns the data: schema-owned reference rows (the dev user) belong in Flyway, sample data a person may edit belongs to code that refuses to touch a used journal.
- **`ApplicationContextRunner`** (`SampleContentBeanTest.java:55`): builds a tiny context in milliseconds to test wiring rules. Gotcha from §8.4: a bean registered with `withBean` is judged against the environment at that moment.
- **`java.awt` headless drawing** (`PlaceholderImages.java:90`): `BufferedImage` + `createGraphics()` + `ImageIO.write` work without a display; `dispose()` the graphics in a `finally`; avoid text, which needs installed fonts.
- **Test pollution of shared fixtures**: the dev user is shared by every integration test, so a test that writes for it must empty it before and after (`@BeforeEach`/`@AfterEach`).

## 12. At work
- **Idempotent loads** are everywhere in a bank: reference-data loads, nightly batch imports, migration scripts that get re-run after a half failure. The rule is the same as here: decide what "already done" means, check it in one place, make the second run a no-op, and test the second run, not only the first.
- **Environment gates for dev-only code.** Test data generators and "reset the demo user" endpoints are a classic way for sample logic to reach production. Two independent gates (profile and property), a test that proves the bean is absent in every other profile, and no controller for it are what a reviewer will look for. A seeder that is a bean in `prod` is a finding.
- **Seeding through the domain or around it.** Writing through repositories bypasses validation and audit hooks; in a regulated system you would usually go through the service layer with a system principal. Here the services need an HTTP request, so the code validates what matters itself and a test reads everything back through the API. Know which side of that trade you are on, and say so in the code.
- **Files before rows, rows in one transaction.** A file store and a database cannot commit together. Writing the files first with stable keys means a crash leaves harmless orphans that the next run overwrites. The opposite order leaves rows pointing at nothing, which a customer would see.
- **Shared fixtures in a test database** (a "test customer" every suite uses) are the usual cause of flaky suites; clean up in both `@BeforeEach` and `@AfterEach` so a crashed test cannot poison the next.

1. The services find the caller through `CurrentUserProvider`, which reads the current HTTP request; a startup job has none.
