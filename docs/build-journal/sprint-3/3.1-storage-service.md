# Task 3.1: Storage service

> **Sprint:** 3 · **Commit:** `Sprint 3.1: Add the storage service` · **Status:** done, reviewed: pass with notes (the one Done-when item is met, and `./gradlew build` passes with 263 tests; the one thing no test here can settle, whether Cloudflare R2 likes the SDK's checksum setting, is handed to task 5.6, §8 and §9) · **Time taken:** roughly 41 minutes by the machine clock (00:28 to about 01:10 on 2026-10-31), including two full builds, five mutation runs and two runs of the real app
> **Built:** `storage/StorageService`, the only door to object storage: put, delete, delete-after-commit and presign, on an `S3Client` that calls `storage.endpoint` and an `S3Presigner` that signs for `storage.public-endpoint`, with path-style access. In the `local` profile the app creates the bucket at startup. A real SeaweedFS in Testcontainers proves that a file can be uploaded, fetched through its presigned URL and deleted, and that a rolled-back transaction never loses a file.

## 1. The goal
[Task 3.1](../../SPRINT_PLAN.md#sprint-3-phase-1-api) is the first task of Sprint 3, the Phase 1 API. Its **Do** list:
- `StorageService`: put, delete and presign, with an `S3Client` using `endpoint` and an `S3Presigner` using `public-endpoint`.
- Path-style access.
- A local-profile bucket bootstrap.
- After-commit object deletion.

**Done when:** a Testcontainers test (SeaweedFS) uploads, presigns (URL host = public endpoint; GET returns the bytes) and deletes.

Why it comes first in Sprint 3, before any endpoint:

| Later task | What it needs from 3.1 |
|---|---|
| 3.5 Entries, redaction | `EntryMapper` builds a media item's `fileUrl` with `StorageService.presignGet(objectKey)`, and never for a sealed entry |
| 3.6 Media | Upload is validate, `put`, insert the row, and delete the file again if the insert fails. Deleting a media item or erasing an entry calls `deleteAfterCommit` |
| 3.11 Recently deleted | The 30-day sweep erases entries and must remove their files after its transaction commits |
| 3.16 Local sample content | Puts sample photos in the bucket the bootstrap created |
| Every test that stores a file | `SeaweedFsTestConfiguration`, so each task doesn't invent its own container |

It builds on [2.2](../sprint-2/2.2-configuration-and-profiles.md) (`StorageProperties`, which already validates all eight settings at startup), [2.6](../sprint-2/2.6-global-error-handling.md) (`StorageUnavailableException` already maps to `503`) and [1.3](../sprint-1/1.3-docker-compose.md) (the SeaweedFS service and its pinned tag).

What users get from it (README, Phase 1: "Write, add photos and record voice notes", photo dump, photos of paper diary pages): nothing visible yet. This is the plumbing under all three.

1. **Read the SDK's builder methods in the current docs,** because I wasn't sure the presigner has `forcePathStyle` (it doesn't: §4 decision 8).
2. **Main code, smallest piece first:** `StorageConfiguration` (the two SDK objects), then `StorageService`, then the event, the listener and the bootstrap. The service came before the listener because the listener calls it.

6. **A real run:** the app in the `local` profile against Compose's SeaweedFS, once with storage up and once with it stopped (§7).
7. **Docs, then the full build,** then this entry.

## 4. Decisions and alternatives
| # | Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|---|
| 1 | Shape of `StorageService` | An interface with an S3 implementation; a concrete class | A concrete `@Service` class | D-03 says there is exactly one storage implementation: R2 speaks S3, so the "second implementation" is the same class with other settings. Tests that don't want storage use Mockito, which mocks a class as easily as an interface (the build loads Mockito's agent) | A reader who expects `StorageService` to be an interface is wrong. If Phase 4 ever needs a fake, extracting one is a small change |
| 2 | What `put` takes | `MultipartFile` (what the controller has); `byte[]`; `File`/`Path`; `InputStream` plus a length | `put(key, InputStream, length, contentType)`, plus a `byte[]` overload | The storage package shouldn't know Spring MVC's multipart type, and a 25 MB photo shouldn't have to sit in memory. S3 needs the length up front, so the caller passes it (`MultipartFile.getSize()`). The `byte[]` form is three lines and what sample content and small generated files will use | The SDK retries by rewinding the stream and keeps only the first 128 KiB for that. A file stream can't be rewound, and without help the first retry throws `IllegalStateException` (a `500` for storage merely hiccuping). So `put` wraps such a stream in a `BufferedInputStream` (found late, §8 item 3). After more than 128 KiB is sent a failed attempt can't be retried and the user tries again |
| 3 | How the delete waits for the commit | Delete inside the transaction; `TransactionSynchronizationManager.registerSynchronization`; an event plus `@TransactionalEventListener`; an outbox table | An `ObjectDeletionRequested` event, published by `StorageService.deleteAfterCommit(keys)`, handled by `ObjectDeletionListener` | TECH_STACK names the listener. Deleting inside the transaction loses files when the commit fails afterwards. `registerSynchronization` works but puts transaction plumbing in the service and can't be tested apart from it. An outbox (a table of "files to delete") survives a crash between commit and delete, but it is a migration and a poller, and Phase 1 only needs a best effort (the docs say a sweep can collect stragglers later) | A crash between the commit and the delete leaves a file nobody points at |
| 4 | No transaction running when the event is published | `fallbackExecution = false` (Spring's default: the event is dropped silently); `true` (the listener runs at once) | `true` | With `false`, a caller who forgot `@Transactional` would leak files and nothing would say so. A test (`withNoTransactionTheObjectsAreDeletedAtOnce`) and a mutation check pin it | A forgotten `@Transactional` now deletes before a later rollback could matter. That bug is the caller's, and it is visible |
| 5 | A delete fails inside the listener | Let it throw; retry; log and carry on | Log and carry on, one key at a time | An exception from an after-commit callback is rethrown to whoever called `commit`, so a saved change would answer `500`. The rows are already gone, so a surviving file is only wasted space | A failed delete is only a log line until the sweep exists. The log names the key, so it can be found |
| 6 | The listener class | Public or package-private; one listener per feature or one shared | Package-private `ObjectDeletionListener` in `storage/` | Nothing outside the package calls it: callers publish through `StorageService.deleteAfterCommit`, which keeps the event type an implementation detail | The event record is public (Spring publishes it), but only the service constructs it |
| 7 | What the listener logs for a failure | `ScrubbedException.of(e)` from `common`; `e.getMessage()`; the exception class and HTTP status | The class name and, for a service error, `HTTP <status>` | `.claude/rules/security.md` says never log presigned URLs or secrets, and an SDK message can name the host (and for some calls a signed URL). `ScrubbedException` would be right but is package-private in `common`; making it public to save one line would change a 2.6 class for this task. A stack trace for a failed delete isn't worth it | Less to go on than a trace. The key, the class and the status tell the usual stories (refused, gone, not running) |
| 8 | How the two SDK objects get their settings | The SDK's default credential chain and region lookup; the properties | Static credentials and region from `StorageProperties`, endpoint per object, path-style on both (`forcePathStyle` on the client, `pathStyleAccessEnabled` on the presigner's `S3Configuration`: the presigner has no `forcePathStyle`) | A stray `AWS_ACCESS_KEY_ID` or `AWS_REGION` on a developer's machine can't change which store the app signs for. This is the value of having validated properties | None |
| 9 | The SDK's checksum default | Leave it; `WHEN_REQUIRED` for requests and responses | `WHEN_REQUIRED` | Since SDK 2.30 every upload carries a CRC32, and R2 rejected uploads over it in early 2025. But I could not confirm that R2 needs this today, and **SeaweedFS passes both ways** (I ran the integration test with the lines removed: all 7 passed). So it is a precaution for a store I can't test, and no test can guard it | Uploads lose the SDK's end-to-end CRC32 (TLS still protects them in transit). Task 5.6 tries both against a real R2 bucket and decides |
| 10 | When and how the bucket is created | Compose creates it (an init container); the app creates it on first `put`; the app creates it at startup in `local` | At startup, in `local` only, by an `ApplicationRunner` | Task 1.3 left it to the backend. Creating on first `put` hides a missing store until a user uploads. Production never creates buckets: R2's is made once, by hand, as a private bucket, so a mistyped name stops the app instead of making an empty new one | An `ApplicationRunner` runs after the web server has started, so on a dead store the app listens for about 1.5 seconds before it exits (seen in §7). A `SmartInitializingSingleton` would fail before Tomcat listens. I kept the runner: it is the idiom a reader expects, and the difference is cosmetic on a laptop |
| 11 | Storage down at local startup | Log a warning and carry on; stop the app | Stop, with a message naming the endpoint and bucket, what to check and the docs section; never the secret | The same as Postgres being down. A warning would be scrolled past and the first upload would fail instead | You can't work on screens that don't touch files with Docker's SeaweedFS stopped |
| 12 | Where the profile gate sits | `@Bean @Profile("local")` in the configuration; `@Component @Profile("local")` on the class | On the class, like `DevHeaderCurrentUserProvider` | The same pattern as the dev header, and the test configuration can declare its own `BucketBootstrap` bean without fighting a profile | The test profile doesn't run component scanning's copy, so the test config is how a test gets one |
| 13 | How the test container gets to the app | `@ServiceConnection` (no support for a generic container); `@DynamicPropertySource` in each test class; a `DynamicPropertyRegistrar` bean | A `DynamicPropertyRegistrar` bean in `SeaweedFsTestConfiguration`, taking the container as a parameter | Spring Boot's documented way for a technology without service-connection support; the parameter makes Spring start the container before it reads the port; and it lives in one place that any number of tests can `@Import` | None |
| 14 | A named container type | Inject `GenericContainer<?>`; a subclass | `SeaweedFsContainer extends GenericContainer<SeaweedFsContainer>` | The context also holds the Postgres container, which is a `GenericContainer` too. Injecting by the shared type would be ambiguous. The subclass also holds the two endpoint helpers | A tiny class |
| 15 | The test container's keys | Constants in the Java; read them from the Environment | `environment.getRequiredProperty("storage.access-key")` (and the secret) | `application-test.yml` already has them, so the app's client and the container can't disagree | The container bean needs the Environment |
| 16 | The two endpoints in the test | The same address twice; two different hosts | `endpoint` = `http://localhost:<port>`, `public-endpoint` = `http://127.0.0.1:<port>` | With one address, a presigner built from the wrong setting would still pass. With two, the test asserts the URL's host is the public one and that it differs from the endpoint's. A mutation (§6) failed three tests | The test assumes Docker's host is `localhost`. It asserts the hosts differ, so a machine where that isn't true fails with a clear message |
| 17 | Keeping the test image the same as Compose's | Only a constant; derive it by reading the Compose file; a constant plus a test that compares | A constant (`SEAWEEDFS_IMAGE`, `SEAWEEDFS_COMMAND`) plus `SeaweedFsComposeTest`, which parses `docker-compose.yml` with Spring's `YamlMapFactoryBean` and compares the image, the command and the key names | The brief asks for "the same pinned image, configured like Compose". A comparing test turns "remember to update both" into a red build, and the constant stays easy to find. Deriving it would hide the tag from a reader | One Gradle system property (`memoirist.composeFile`) mirroring the one for the API contract |
| 18 | `StorageUnavailableException` for `presignGet` | Wrap everything; wrap `put` and `delete` only | `put` and `delete` only | Presigning calls nobody: it is arithmetic on the key and the secret. If it throws, our code is wrong, and that should be a `500`, not a "storage is down" `503` | None |
| 19 | The injected `Clock` for presigning | Give the presigner a `Clock`; let the SDK read its own | The SDK reads its own | `S3Presigner` has no clock setting. Only the expiry length matters to the app, and it is configured. The exception to the backend rule is written in TECH_STACK | A test can't fix the signing time. None of mine needed to |
| 20 | What was **not** built | An `ObjectKeys` helper; `get`/`exists`; `deleteObjects` in batches; the sweep for stragglers; excluding the unused `netty-nio-client` (the async HTTP client; `S3Client` and `S3Presigner` use the Apache client) | Nothing of these | 3.6 builds keys from its own ids. Nothing in Phase 1 reads an object through the backend (Phase 4's transcription does). A media item is at most 20 files, so one `deleteObject` each is fine. The sweep belongs with 3.11 | They are small to add when a task needs them |

## 5. How it was built
Read in this order.

**Storage settings → SDK objects** ([`StorageConfiguration.java`](../../../backend/src/main/java/com/memoirist/storage/StorageConfiguration.java))
- `s3Client` ([line 31](../../../backend/src/main/java/com/memoirist/storage/StorageConfiguration.java#L31)): `endpointOverride(properties.endpoint())`, the region, the static keys, `forcePathStyle` ([line 39](../../../backend/src/main/java/com/memoirist/storage/StorageConfiguration.java#L39)), and the two `WHEN_REQUIRED` lines ([45 and 46](../../../backend/src/main/java/com/memoirist/storage/StorageConfiguration.java#L45)) with a comment that says what is and isn't known.
- `s3Presigner` ([line 51](../../../backend/src/main/java/com/memoirist/storage/StorageConfiguration.java#L51)): the same keys and region, but `endpointOverride(properties.publicEndpoint())` ([line 53](../../../backend/src/main/java/com/memoirist/storage/StorageConfiguration.java#L53)) and path-style through `S3Configuration` ([line 58](../../../backend/src/main/java/com/memoirist/storage/StorageConfiguration.java#L58)).
- The class is `@Configuration(proxyBeanMethods = false)` and package-private. Spring calls `close()` on both beans at shutdown, because a `@Bean` method's return value is closed by its public `close()`.

**The service** ([`StorageService.java`](../../../backend/src/main/java/com/memoirist/storage/StorageService.java))
- `put` with a stream ([line 68](../../../backend/src/main/java/com/memoirist/storage/StorageService.java#L68)) checks the key, the type and the length before it builds a `PutObjectRequest`. It wraps a stream that can't be marked in a `BufferedInputStream` so the SDK can retry, then calls `RequestBody.fromInputStream(rewindable, contentLength)`. An `SdkException` becomes `StorageUnavailableException("Storing an object failed", cause)`: the message names no host, because the cause does and the advice never sends it to a client.
- `put` with bytes ([line 89](../../../backend/src/main/java/com/memoirist/storage/StorageService.java#L89)) is the same with `RequestBody.fromBytes`.
- `delete` ([line 112](../../../backend/src/main/java/com/memoirist/storage/StorageService.java#L112)) builds a `DeleteObjectRequest` object, not the SDK's lambda overload. S3 answers `204` for a missing key, so deleting twice is harmless. The explicit request matters for the tests: a Mockito mock of the interface doesn't run the lambda overload (a default method), so the unit test stubs the one abstract method.
- `deleteAfterCommit` ([line 136](../../../backend/src/main/java/com/memoirist/storage/StorageService.java#L136)) validates every key, copies the collection and publishes one `ObjectDeletionRequested`. It deletes nothing itself, and with no keys it publishes nothing.
- `presignGet` ([line 150](../../../backend/src/main/java/com/memoirist/storage/StorageService.java#L150)) signs for `storage.presign-ttl`. It calls no network, so a key that doesn't exist still gets a URL.

**The event and the listener**
- [`ObjectDeletionRequested.java`](../../../backend/src/main/java/com/memoirist/storage/ObjectDeletionRequested.java): a record of keys whose compact constructor does `List.copyOf`, so a caller who reuses its list afterwards changes nothing (and a null key fails at once).
- [`ObjectDeletionListener.java`](../../../backend/src/main/java/com/memoirist/storage/ObjectDeletionListener.java): the practice block (lines 33-51, §11). `@TransactionalEventListener(phase = AFTER_COMMIT, fallbackExecution = true)` ([line 41](../../../backend/src/main/java/com/memoirist/storage/ObjectDeletionListener.java#L41)), a loop with a `try`/`catch` per key, and a `describe` helper ([line 54](../../../backend/src/main/java/com/memoirist/storage/ObjectDeletionListener.java#L54)) that unwraps our exception to the SDK's and adds `HTTP <status>` for a service error.

**The local bucket** ([`BucketBootstrap.java`](../../../backend/src/main/java/com/memoirist/storage/BucketBootstrap.java))
- `@Component @Profile("local")` and an `ApplicationRunner` ([lines 26-28](../../../backend/src/main/java/com/memoirist/storage/BucketBootstrap.java#L26)). `ensureBucket()` ([line 51](../../../backend/src/main/java/com/memoirist/storage/BucketBootstrap.java#L51)) asks `headBucket`; only `NoSuchBucketException` ([line 56](../../../backend/src/main/java/com/memoirist/storage/BucketBootstrap.java#L56)) means "create it". Any other SDK failure becomes an `IllegalStateException` whose message ([line 72](../../../backend/src/main/java/com/memoirist/storage/BucketBootstrap.java#L72)) names the endpoint and bucket, says `docker compose up -d` and `.env`, and points at the docs. It returns whether it created the bucket, which the tests use. A race (`BucketAlreadyOwnedByYouException`) counts as "already there".

**The test side**
- [`SeaweedFsTestConfiguration.java`](../../../backend/src/test/java/com/memoirist/SeaweedFsTestConfiguration.java): the image and command constants ([lines 44 and 47](../../../backend/src/test/java/com/memoirist/SeaweedFsTestConfiguration.java#L44)), the container bean that reads the keys from the Environment ([line 63](../../../backend/src/test/java/com/memoirist/SeaweedFsTestConfiguration.java#L63)), the `DynamicPropertyRegistrar` ([line 68](../../../backend/src/test/java/com/memoirist/SeaweedFsTestConfiguration.java#L68)), the bucket bootstrap bean ([line 78](../../../backend/src/test/java/com/memoirist/SeaweedFsTestConfiguration.java#L78)) and the container subclass with Compose's own health check as its wait strategy ([line 93](../../../backend/src/test/java/com/memoirist/SeaweedFsTestConfiguration.java#L93)).
- [`build.gradle.kts`](../../../backend/build.gradle.kts#L68): `composeFile`, passed to the tests and listed as an input, the same way as the API contract a few lines above it.
- The test classes are in §6.

**Docs changed in the same commit:** [TECH_STACK §2 Storage](../../TECH_STACK.md#storage) (the clients, the checksum note, path-style, a table of the service's methods, how deletion works, the local bucket, storage in tests) and its Profiles row; [DEVELOPMENT.md](../../DEVELOPMENT.md) (the test paragraph and a troubleshooting row for the new startup message); [D-03](../../DECISIONS.md#d-03-object-storage-seaweedfs-locally-cloudflare-r2-in-production) (the Version bullet now says where the tag is written and which test guards it, and its Updated date moved to 2026-10-31). ## 6. How it was tested
- **Strategy:**
  - Anything that needs a store or a transaction runs against a real SeaweedFS and a real Postgres. Spring caches the application context, so the three classes that import `SeaweedFsTestConfiguration` (`StorageServiceIntegrationTest`, `AfterCommitDeletionTest`, `BucketBootstrapTest`) share one app, one Postgres and one SeaweedFS.
  - Everything else needs no Docker. Signing is arithmetic, so URL shape, expiry and path-style are plain unit tests; storage failing is a mocked `S3Client`; profile gating is an `ApplicationContextRunner`.
  - The places a wrong line would do real harm (the transaction phase, the no-transaction fallback, the presigner's endpoint, the stream wrapper) were mutation-checked.

## 10. Concepts to learn from this task
- **Presigned URL** ([`StorageService.java:150`](../../../backend/src/main/java/com/memoirist/storage/StorageService.java#L150)): a normal URL plus a query string (`X-Amz-Credential`, `X-Amz-Expires`, `X-Amz-Signature`, and so on) that proves the holder may do one thing, GET this key, until it expires. The signature is made offline from the secret key over the method, host, path and expiry, which is why `presignGet` never contacts storage, why a URL for one key is refused on another (`aSignedUrlOpensOneFileOnly`), and why the host in the URL has to be the one the browser will use (`X-Amz-SignedHeaders=host`). Anyone who holds it can use it until it expires, so it is treated like a short-lived password: not logged, not stored.
- **Path-style and virtual-hosted-style addressing** ([`StorageConfiguration.java:39`](../../../backend/src/main/java/com/memoirist/storage/StorageConfiguration.java#L39)): `http://host/bucket/key` against `http://bucket.host/key`. Path-style works against an address like `127.0.0.1:8333`; the other form needs a DNS name per bucket. The two SDK builders spell the setting differently (`forcePathStyle` on the client, `S3Configuration.pathStyleAccessEnabled` on the presigner), and forgetting the second gives you working uploads and broken photo links.
- **`@TransactionalEventListener`** ([`ObjectDeletionListener.java:41`](../../../backend/src/main/java/com/memoirist/storage/ObjectDeletionListener.java#L41)): an event listener that Spring holds back until the publishing transaction ends, then runs only for the chosen phase (`AFTER_COMMIT`, `AFTER_ROLLBACK`, `AFTER_COMPLETION`, or `BEFORE_COMMIT`). Two traps: with no transaction the event is dropped unless `fallbackExecution = true`, and an exception in an after-commit callback is rethrown to the caller of `commit`. The mistake to avoid is database work inside it without `REQUIRES_NEW`: the transaction is finished but its resources are still bound.
- **Side effects that can't be rolled back, and the order they happen in** (`StorageService.deleteAfterCommit`): a file deletion is not part of the database transaction. Do the reversible thing first (the rows), the irreversible thing after it succeeds, and accept the failure mode that costs least (an orphaned file, not a row that points at nothing). A stronger version is the transactional outbox (§4, decision 3).
- **`ApplicationRunner`** ([`BucketBootstrap.java:41`](../../../backend/src/main/java/com/memoirist/storage/BucketBootstrap.java#L41)): a bean whose `run` method Spring Boot calls once the context is up. An exception from it stops the application with "Application run failed". `CommandLineRunner` is the same with raw arguments.
- **`@Profile` on a component** ([`BucketBootstrap.java:27`](../../../backend/src/main/java/com/memoirist/storage/BucketBootstrap.java#L27)): the bean exists only when the profile is active. A different profile doesn't get an "empty" version; the bean is absent, and anything that needs it fails at startup (the dev-header provider relies on that).
- **`DynamicPropertyRegistrar`** ([`SeaweedFsTestConfiguration.java:68`](../../../backend/src/test/java/com/memoirist/SeaweedFsTestConfiguration.java#L68)): a bean that adds properties to the test's environment when they are first read. Taking the container as a parameter is what makes Spring start it first. This is how you pass a random port from Docker into `storage.endpoint`.
- **`ApplicationContextRunner`** ([`BucketBootstrapProfileTest.java:19`](../../../backend/src/test/java/com/memoirist/storage/BucketBootstrapProfileTest.java#L19)): builds a tiny Spring context in milliseconds. You choose the beans, properties and profiles, then assert on what exists. `withBean(Type.class, supplier)` adds a bean without a configuration class.
- **A record's compact constructor** ([`ObjectDeletionRequested.java:15`](../../../backend/src/main/java/com/memoirist/storage/ObjectDeletionRequested.java#L15)): `public R { field = transform(field); }` runs before the fields are set, so you can validate or copy. `List.copyOf` makes an unmodifiable copy, rejects nulls, and returns the same list if it is already unmodifiable.
- **A stream and its length** (`StorageService.put`): `RequestBody.fromInputStream(in, length)` needs the exact length because S3 wants `Content-Length` before the body. The SDK retries by rewinding the stream (`mark`/`reset`, with a read limit of 128 KiB). A stream that can't be marked, such as `Files.newInputStream`, makes the first retry throw `IllegalStateException`, so `put` wraps it in a `BufferedInputStream` (`StorageServiceUnreachableTest`). Check how a library recovers from failure before you trust that a failure is reported as a failure.
- **AssertJ for exceptions**: `assertThatExceptionOfType(X.class).isThrownBy(...).withCause(c).withMessage("...")`, and `withMessageNotContaining`, which is how a test says "the message must not leak this".
- **`SdkAutoCloseable` beans:** the S3 client and presigner hold connection pools. Spring closes a `@Bean` result that has a public `close()`; a test that builds one by hand closes it itself (try-with-resources).

## 12. At work
- **Side effects after the commit.** In a bank's Spring services the same bug shows up as "the email, message or API call went out, then the transaction rolled back". Reviewers look for any call to another system inside a `@Transactional` method. The usual fixes are an after-commit listener (this task), or an outbox table that a poller drains, which also survives a crash between commit and send. Knowing why `fallbackExecution` and swallowing exceptions are decisions, not defaults, is what separates the two in a review.
- **Presigned URLs are bearer tokens.** Documents in a bank (statements, ID scans) are often served this way. The questions a reviewer asks are the ones this task answered: how long it lives (60 minutes at most, validated at startup in 2.2), who is allowed to be given one (the caller checks, not the storage service), that it never reaches a log, that it is bound to one object, and that the bucket itself refuses unsigned requests.
- **Error messages and logs that name infrastructure.** SDK exceptions carry hostnames and request ids. Clients get a fixed sentence, the log gets the class and status, and the cause stays attached for the people who need it. Security reviews at a bank do check this.
- **Testing against the real thing.** A test against a mocked S3 would not have shown that a 5 MB stream works, that a presigned URL is bound to one key, or what the second endpoint does. A containerised real service in the build is normal in a mature pipeline, and "the container uses the same image and flags as the dev environment, and a test fails if they drift" is a good habit when environments are defined in several files.
- **A setting you can't test.** The checksum setting is a real situation: a compatibility switch for a system the pipeline can't reach. The honest outputs are a comment that says so, a note on the task that will test it, and not claiming a vendor said something it didn't.
- **Environment parity.** The app uses the same two classes for SeaweedFS and R2 and changes only settings, as most enterprise services do between a test stack and production. What differs (the bucket is created by hand in production) is written down in one place.

<details><summary>Answers</summary>

1. If the delete ran inside the transaction and the commit then failed (or the transaction rolled back for another reason), the database would still point at files that were already deleted. Publishing an event that the listener acts on only after the commit means the rows go first. If the process dies between the commit and the delete, the database no longer mentions the files but they still exist: wasted space, no broken row. The other order leaves rows pointing at nothing, which shows the user broken photos. An outbox table would survive the crash; Phase 1 accepts the orphan.
2. Spring drops the event without a trace, because there is no transaction to wait for. The files are never deleted. You would notice only by looking in the bucket. `fallbackExecution = true` runs the listener at once instead, and `withNoTransactionTheObjectsAreDeletedAtOnce` pins it.
3. An exception from an after-commit callback is rethrown to the code that called `commit`, so a change that was saved would answer `500` and the client might retry it. And one bad key would stop the others from being deleted. The rows are already gone, so a surviving file is only wasted space and a log line is the right response.
4. The `S3Client` (uploads, deletes) uses `storage.endpoint`, `localhost` in the test; the `S3Presigner` uses `storage.public-endpoint`, `127.0.0.1`. Making them differ means a presigner built from the wrong setting fails the host assertion; with identical addresses it would pass either way. The mutation that swapped them failed three tests.
5. SeaweedFS answers `403` (the test checks it). The signature was computed over the path, including the key, so it doesn't match the changed path. A URL opens one object and nothing else.
6. S3 wants `Content-Length` before the body, so the SDK can't discover it by reading to the end (and a 25 MB photo shouldn't be read into memory first). A stream can be read once. To retry, the SDK must rewind (`mark` and `reset`), and it keeps only the first 128 KiB for that. A stream that can't be marked (a file stream) makes the retry throw `IllegalStateException`, which would have been a `500` for a storage hiccup, so `put` wraps it in a `BufferedInputStream`. Past 128 KiB sent, a failed attempt can't be retried and ends as `503`.
7. In production the bucket is created once, by hand, as a private bucket, so a mistyped bucket name stops the app instead of quietly creating a new empty one, and the app's key doesn't need permission to create buckets. Locally Compose starts SeaweedFS empty, so the app has to make the bucket. For production you want the bucket to exist, to be private, and to refuse unsigned requests (task 5.6 checks it).
8. SeaweedFS is not the production store. R2 had trouble with the SDK's default CRC32 in early 2025, so "when required" is the cautious setting, but nothing local proves it is needed today and it gives up an end-to-end integrity check. Task 5.6 will try uploads against a real R2 bucket, with and without it. That task should also try `chunkedEncodingEnabled(false)`, which Cloudflare's own Java page asks for and which this task did not add.
