# Task 3.6: Media

> **Sprint:** 3 · **Commit:** `Sprint 3.6: Add the Media endpoints` · **Status:** done (after the review: one doc-only fix pass) · **Time taken:** roughly 45 minutes (13:35 to about 14:20 on 2026-10-31, unattended, with one full build and a dozen partial test runs)
> **Built:** a user can add a photo, a diary page or a voice note to an entry, reorder them and delete them, and the files in storage always follow the rows in the database, including when an entry is erased for good.

## 1. The goal
Task 3.5 made entries that can hold a caption. A journal entry is mostly its photos, so 3.6 adds the three media calls of [API_CONTRACT §Media](../../API_CONTRACT.md): upload (`POST /entries/{entryId}/media`), reorder (`PUT /entries/{entryId}/media/order`) and delete (`DELETE /media/{mediaId}`). The block in [SPRINT_PLAN.md](../../SPRINT_PLAN.md) adds one more thing that is easy to miss: "stored-file cleanup when an entry is erased (D-30)".

Why now: the storage service (3.1) and the entry endpoints (3.5) exist, the feed (3.7) and the entry list (3.9) need real media to show, and the front end (Sprint 4) uploads photos straight after it creates an entry (D-23).

The hard part is not receiving a file. It is that a file in object storage and a row in Postgres cannot be committed together, so for every path (success, failure, a second request at the same moment, a rollback) the task has to say which one is allowed to be wrong.

- how the type is judged (declared `Content-Type` or the file's bytes), and what to do with `audio/webm;codecs=opus`;
- what `displayOrder` means when it is given (insert and shift, or replace) and what a value past the end does;
- the order of the checks (`404`, `409`, `400`, `415`, `413`);
- whether a missing `file` part is `malformed-request` (Spring's default) or `validation-failed`;
- who erases an entry in 3.6, since the `erase` endpoint is 3.11;
- how two requests at once are kept from picking the same position.

## 3. The plan
1. **Rules first** (`UploadRules`): the allow-list, the limits and the purposes as pure functions with a unit test, because every other layer depends on those answers.
2. **The shared pieces**: `MediaMapper` (the one place that signs a URL), a locking lookup on `EntryRepository`, and `EntryErasure` (the one place that erases an entry).
3. **`MediaService`** (upload, reorder, delete), then **`MediaController`**.
4. **Tests from the inside out**: the rules, then the endpoints one by one, then the cases where the file and the row drift apart, then the concurrency cases.
5. **Docs** (API_CONTRACT, DATABASE_SCHEMA, TECH_STACK), then the full build.

Order: rules before service because a service test that fails on "is this a valid type" is a slow way to find a one-line bug. The service before the controller because the controller is thin. The drift and concurrency tests last because they need everything else working to be meaningful.

## 4. Decisions and alternatives
| Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|
| Transaction shape of an upload | One `@Transactional` method around everything; store the file first with no recheck; a short read-only check, store with no transaction, then a short write transaction that rechecks | The third, with two `TransactionTemplate`s | A transaction around a 25 MB transfer holds a database connection (Hikari's pool is 10) and the entry's lock for seconds. Storing with no recheck lets a seal or an erase slip in during the transfer | More code than an annotation, and the entry is checked twice |
| Keeping two uploads from taking the same position | Retry on the unique violation; `SERIALIZABLE` isolation; an advisory lock; a row lock on the entry (`SELECT ... FOR NO KEY UPDATE`) | The row lock (`@Lock(PESSIMISTIC_WRITE)` on `findForUpdateByIdAndUserId`) | The deferred unique constraint only fails at commit, which is too late to retry cleanly; the entry row already exists to lock and the lock says what it protects | Calls on one entry take turns; fine for a personal journal |
| Do media changes raise `Entry.version`? | Yes (any change to the entry); no | No | A photo added while the user types a caption would make the caption's `PUT` stale (D-23) | A client can't use `version` to see that media changed; it re-reads the entry |
| How to judge the type | Declared `Content-Type`; sniff the bytes (Tika or the JDK); both | The declared type, parameters dropped, against the D-17 list | `api.md` already says "check the declared type"; Tika is not an approved dependency; the file is served back as the allow-listed type, never as HTML | A mislabelled file is stored under its label. | Stripping parameters | `MediaType.parseMediaType`; `split(";", 2)[0]` | `split(";", 2)[0].strip().toLowerCase(Locale.ROOT)` | The parser also validates the parameters, and `image/jpeg; charset=binary` made it throw. The allow-list is the validator | None |
| What is stored as `media_type` | The header as sent; the plain type | The plain type (`audio/webm`) | "One of the D-17 MIME types" (schema); Chrome's recorder sends `audio/webm;codecs=opus` | The codec isn't recorded |
| File name | Keep it for the extension; ignore it | Ignored; the extension comes from a table | A name like `../../x` can't reach the key, and nothing needs it | No original name to show |
| `displayOrder` given | Replace that position; clamp a too-big value to the end; insert and shift, `400` past the end | Insert and shift; `400` past the end | The positions are always `0..n-1`, so "put it here" has one meaning; a number past the end means the client's view is stale, and telling it is better than guessing | A client that sends positions out of order gets `400` (it should send none and let the server append) |
| Missing or empty `file` | Spring's `400 malformed-request`; `400 validation-failed` with `fieldErrors.file` | `validation-failed` | The same shape as every other field problem; the client reads `fieldErrors` | Needs `required = false` on the parameter and a check |
| Order of checks | Body first, entry first | Entry (`404`), seal (`409`), then the form, then room | Nothing about the request is said before the caller is known to own an unsealed entry; a sealed entry answers `409` even for a bad file | A file over 25 MB is `413` before any of it (the multipart limit runs earlier), which reveals nothing |
| Reorder with an id that isn't the entry's | `404` for a foreign id; `400` for any wrong set | `400`, one sentence for "not this entry's" | The contract says missing, extra or duplicate ids are `400`; a `404` for another user's id would confirm it exists | Three messages, none repeats an id |
| Renumbering | A bulk `UPDATE ... SET display_order = display_order - 1`; set each entity's position | Set each entity's position (`renumber`) | At most 20 rows; the deferred constraint allows the temporary repeats; unchanged rows write nothing | One `UPDATE` per moved row |
| Who erases an entry in 3.6 | Build `POST .../erase` early; put `CascadeType.REMOVE` on `Entry.media`; a component called by the service | `EntryErasure`, called by the empty-entry `DELETE` now and by 3.11's erase and sweep later | The endpoint is 3.11's; cascading in Hibernate would load and delete every media row but still not delete files | The Done-when "after erasing an entry" is proved through the component, not an endpoint |
| `EntryErasure` transaction rule | Plain method; `@Transactional`; `MANDATORY` | `@Transactional(propagation = MANDATORY)` | With no transaction, `deleteAfterCommit` runs at once, so the files would go before the row. `MANDATORY` makes that mistake fail loudly | A caller must already be in a transaction |
| How `EntryErasure` finds the keys | `entry.getMedia()`; a JPQL projection; a native query | A native query (`findObjectKeysByEntryId`) | See section 8: the first two fail on an entry in Recently deleted (one with an exception, one silently) | A native query is not checked against the entity |
| Cleanup after a failed upload | `deleteAfterCommit`; delete directly in a `catch` | A direct `storage.delete` in the `catch`, errors logged | A rollback drops after-commit events, and here a rollback is exactly the case that needs the delete | The delete can fail too; then the file is left as wasted space and the first error is the one reported |

## 5. How it was built

**The rules: [`UploadRules.java`](../../../backend/src/main/java/com/memoirist/media/UploadRules.java).** Pure functions, no Spring beans: the six types with their extensions (`EXTENSIONS`, line 28), `MAX_FILE_BYTES` and `MAX_ITEMS_PER_ENTRY` (lines 19 and 22), `allowedType` (line 49, the first practice block), `purpose` (line 80, a `switch` over the two constants, anything else `400`), and `requireImageForPageScan` (line 91). Every refusal is a fixed sentence that lists what is allowed and never repeats what was sent.

**The signer: [`MediaMapper.java`](../../../backend/src/main/java/com/memoirist/media/MediaMapper.java).** `toResponse(entryId, media)` (line 27) turns a row into a `MediaResponse` with a presigned URL. It is given the entry id so mapping a row costs no query. [`EntryMapper`](../../../backend/src/main/java/com/memoirist/entry/EntryMapper.java) now calls it instead of signing itself.

**The lock: [`EntryRepository.findForUpdateByIdAndUserId`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java).** The ordinary user-scoped lookup plus `@Lock(PESSIMISTIC_WRITE)`; Hibernate 7 on PostgreSQL writes `for no key update`, which blocks other lockers but not the foreign-key checks of inserts. The test `theLockingLookupTakesARowLockAndMakesASecondRequestForItWait` captures the SQL and checks the keyword.

**The eraser: [`EntryErasure.java`](../../../backend/src/main/java/com/memoirist/entry/EntryErasure.java).** `erase(entry)` (line 46): read the keys with the native query, delete the `entries` row (the database removes the `media` rows), then `storage.deleteAfterCommit(keys)`. [`EntryService.delete`](../../../backend/src/main/java/com/memoirist/entry/EntryService.java) (line 198) now locks the entry first and calls it for the empty-entry case.

**The service: [`MediaService.java`](../../../backend/src/main/java/com/memoirist/media/MediaService.java).**
- `upload` (line 116) is deliberately not `@Transactional`. Step one (line 119) is a read-only `TransactionTemplate`: the entry is the user's (`findEntry`), not sealed (`refuseIfSealed`), the form is valid (`check`, line 207) and there is room (`checkRoom`, line 229). Step two stores the file with no transaction. Step three (line 145) is a write `TransactionTemplate` running `insert` (line 240): lock the entry (`lockEntry`, line 318), check the seal and the room again, shift later items down one, `saveAndFlush` the new row, map it. The `catch` at line 147 is the second practice block: delete the object, and rethrow the first failure.
- `reorder` (line 160) locks the entry, checks the seal, and `inRequestedOrder` (line 285) validates the set in three steps (a repeat, a stranger, a missing id) before `renumber` (line 305) writes the new positions.
- `delete` (line 176) finds the item through the user-scoped finder, locks its entry, rereads the list under the lock, removes the item, renumbers the rest and asks for the file to go after the commit.

**The controller: [`MediaController.java`](../../../backend/src/main/java/com/memoirist/media/MediaController.java).** Thin. The class maps `/api/v1`, because the three paths sit under two prefixes (`/entries/{id}/media` and `/media/{id}`). `file`, `displayOrder` and `purpose` are plain `@RequestParam`s with `required = false`, so the service gives the missing-file answer in the API's own shape; they are `@Parameter(hidden = true)` and the body is described by [`MediaUploadForm`](../../../backend/src/main/java/com/memoirist/media/dto/MediaUploadForm.java), a documentation-only record.

**Smaller pieces.** `MediaOrderRequest` (`@NotNull @Size(max = 20) List<@NotNull UUID>`), `MediaRepository` (`saveAndFlush`, `countByEntryId` and the native key query), and `EntrySeal` made public so `MediaService` uses the same definition of "sealed" as the mapper.

**Docs.** API_CONTRACT gained a "How `/media` behaves" block (the order of the checks, the type rules, the size, the positions, files and rows); DATABASE_SCHEMA and TECH_STACK say where the new rules live.

## 8. What went wrong
1. **A parser that was too strict.** `allowedType` first used `MediaType.parseMediaType` and then `getType() + "/" + getSubtype()`. `UploadRulesTest` failed on `image/jpeg; charset=binary`: Spring checks that a `charset` parameter names a real charset and throws. Fix: cut at the first `;`, strip and lower-case, and let the allow-list validate. The practice block's hint records the dead end.
2. **Tests that asserted the wrong thing about errors.** Three tests said the response body must not contain the entry id, the media id or `not-a-uuid`. `instance` is the request path, and the contract says so, so the id is in the body by design. The promise is about `detail` and `fieldErrors`. The tests now read `$.detail`.
3. **A compile error from AssertJ.** `assertThat(List<?>).extracting(...).containsExactly("a", "b")` doesn't compile (the element type is a wildcard capture). `isEqualTo(List.of(...))` does, and is what the upload test already used.
4. **The erase failed with `TransientPropertyValueException`.** `EntryErasure` first read the keys with `entry.getMedia()`. Erasing an entry in Recently deleted then failed at flush with "Media references an unsaved transient instance of Entry". My reading, from Hibernate's behaviour and not proved against its source: at flush, Hibernate checks that the entry a `Media` points at is saved; it sees the entry as being deleted, so it asks the database for a snapshot of the row; that query goes through `@SQLRestriction("deleted_at IS NULL")`, finds nothing for a Recently-deleted entry, and calls it transient. A live entry passes, which is why the empty-entry erase never showed it.
5. **The fix hid a worse bug.** Switching to a JPQL projection (`select m.objectKey from Media m where m.entry.id = :id`) made the exception go away and the test still failed, with no error at all: every file was still in storage. With `SqlLog` the SQL was `select m1_0.object_key from media m1_0 join entries e1_0 on e1_0.id=m1_0.entry_id and (e1_0.deleted_at is null) where e1_0.id=? ...`. Hibernate 7 joins `entries` even for `m.entry.id` and adds the restriction, so the query found **zero keys** for a deleted entry, and the erase deleted the rows and leaked the files silently. Fix: a native query, which Hibernate never rewrites. A test that only checked the rows would have passed; the one that checks storage caught it. The same trap applies to anything that wants an entry's media through the entry, which is why DATABASE_SCHEMA now says so.
6. **springdoc described the form wrongly.** The first `MediaApiDescriptionTest` showed `displayOrder` and `purpose` as query parameters and only `file` in the multipart body. Fix: `@Parameter(hidden = true)` on the three parameters and `@RequestBody(content = @Content(mediaType = multipart, schema = @Schema(implementation = MediaUploadForm.class)))`, plus a test that the operation's only parameter is `entryId`.
7. **Tooling slips.** Bash heredocs containing apostrophes failed with "unexpected EOF"; I wrote the test files with the file tool instead. A `perl -0pi` edit with `\x27` escapes silently did nothing and I used the edit tool. One scratch file was written under `/tmp` by mistake and deleted at once. My running notes carried guessed clock labels; the times in this entry are from `date`.

9. **Fix pass (close-out).** `sed -i` on `MediaUploadForm.java` turned its CRLF line endings into LF and `spotlessCheck` failed; `spotlessApply` restored them. No other attempt failed. The `@Schema` maximum, the contract sentence, the SPRINT_PLAN 3.11 line and two journal corrections were the only changes.

Nothing was left failing.

## 10. Concepts to learn from this task
- **`TransactionTemplate`** (`MediaService.java:119`, `:145`): a transaction you open in code instead of with `@Transactional`. Use it when one method needs several short transactions with something slow between them. The mistake: annotating the whole method and holding a connection through a network call.
- **Compensating action** (`MediaService.java:147`): when two systems can't commit together, do the one you can undo less easily first or last on purpose, and write the undo for the other. Here the file is stored first and deleted again if the row fails. Whatever the undo throws must not replace the first error.
- **Pessimistic row lock** (`EntryRepository.java:50`): `@Lock(PESSIMISTIC_WRITE)` becomes `SELECT ... FOR NO KEY UPDATE`. Others who ask for the lock wait until your transaction ends. Optimistic locking (`@Version`) detects a conflict after the fact; this prevents it. The lock must be taken before you read what you are about to change.
- **Deferrable unique constraint** (V1, `uq_media_entry_order`): the uniqueness check happens at commit, so a swap or a shift can pass through a moment of repeated values. It is also why a missing lock shows up as an error at commit, not at the insert.
- **`Propagation.MANDATORY`** (`EntryErasure.java:45`): "I must be called inside a transaction", enforced at runtime. A method whose correctness depends on running inside the caller's transaction should say so.
- **`@SQLRestriction` leaks into queries you didn't expect** (`MediaRepository.java:44`): it applies to JPQL, derived queries and joins, and apparently to Hibernate's own internal checks. Rows it hides can't be found by those; a native query can.
- **Allow-list at a trust boundary** (`UploadRules.java:49`): decide what you accept and refuse everything else, after normalising (parameters, case). A deny-list of "bad" types is always incomplete.
- **`@MockitoSpyBean` with `doAnswer(...).callRealMethod()`** (`MediaCleanupTest.java:182`): a spy keeps the real behaviour, and a stubbed answer can run the real call and then do something else, which is how a test makes the world change in the middle of a request.
- **Mutation checking**: break the code on purpose and check that the test goes red. A concurrency test that passes without the lock tests nothing.
- **Java syntax seen here:** `switch` with constants and `->` (`UploadRules.java:80`), `split(";", 2)`, `Locale.ROOT` (so `"IMAGE".toLowerCase()` can't turn into a dotless i on a Turkish machine), `Collectors.toMap`, `try`-with-resources nested in a `try`/`catch`.

## 12. At work
A bank has the same shape wherever a document meets a case: a dispute with attached statements, a KYC pack with scanned ID, a complaint with photos. The attachments live in an object store, the metadata in a relational table, and the two can't be committed together. A reviewer there would look for:
- **Which store is allowed to be wrong.** Here a stray file is acceptable (wasted space) and a row pointing at a missing file is not, so the row is written last and deleted first. Ask the same question of every integration.
- **No slow I/O inside a transaction.** Holding a database connection during a file transfer or an HTTP call is how a pool of 10 runs dry under a small load.
- **Locking the right thing.** Two clerks adding a document to one case at the same moment must not get the same sequence number. The case row is the natural lock; a unique constraint is the safety net, not the plan.
- **Ownership returning `404`, never `403`** (the same IDOR rule as in a customer-data API), and an error that never repeats what the caller sent.
- **The file type is a security control**, not a UI nicety. A real system would also scan the bytes (magic-number checks, antivirus) before accepting; this task documents that it doesn't.
- **A reconciliation job** for the files nothing points at, because best-effort deletes will eventually miss one.
- **Soft delete and its hidden filter.** `@SQLRestriction` is the Hibernate version of a `WHERE deleted = false` view. Any "find the children of a soft-deleted parent" query must be checked against it, which is exactly what section 8 hit.

<details><summary>Answers</summary>

1. Storing a 25 MB file takes seconds, and an annotated method would hold a database connection and the entry's lock for all of it. It uses two short `TransactionTemplate`s: a read-only one to check early and a write one to lock, recheck and insert after the file is stored.
2. A row lock on the entry (`SELECT ... FOR NO KEY UPDATE`) taken in the write transaction makes the second request wait; it then reads the new count. Without it both read "3 items" and insert at 3, and the deferred unique constraint fails one of them at commit as a `500`. The mutation check showed exactly that.
3. After-commit events are dropped on a rollback, and a failed insert is a rollback, so the file would never be deleted. The cleanup has to run in the failure path, directly.
4. Hibernate 7 joins `entries` and adds the `@SQLRestriction` condition (`deleted_at IS NULL`) even for `m.entry.id`, so a Recently-deleted entry's media isn't found. With no keys, the erase deleted the rows and silently left every file in storage. An exception is loud; a leak shows up months later as a storage bill.
5. `audio/webm`. A plain `equals` (or `contains`) against `audio/webm` would have refused every voice recording from Chrome with `415`.
6. The entry's state is checked first, so the answer says nothing about the request's own mistakes. The 30 MB file never reaches the service: Spring's multipart limit stops it while the body is read, before the entry is looked up, and that reveals nothing about the entry.
7. At most 20 rows, set one at a time through the entities, with the `(entry_id, display_order)` unique constraint `DEFERRABLE INITIALLY DEFERRED`, so the temporary repeats inside the transaction are only checked at commit, when the values are `0..n-1` again.
8. A photo added while the user types a caption would make the caption's `PUT` carry an old `version` and fail with `409 entry-stale` (D-23). Media have their own endpoints and their own lock; the version guards the caption.
