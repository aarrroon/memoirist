# Task 3.8: Tags

> **Sprint:** 3 · **Commit:** `Sprint 3.8: Add the Tags endpoints` (hash in the OVERNIGHT_REPORT) · **Status:** done (every Done-when item is met; `./gradlew build` passes with 1128 tests; the review fixes were re-checked; the review is §9) · **Time taken:** roughly 33 minutes by the machine clock (00:46 to about 01:19 on 2026-11-01, unattended), after an earlier sitting of about 5 minutes (15:17 to 15:22 on 2026-10-31) that was interrupted once it had read the docs, written the plan and the contract text, and started `NameCollation`. > **Built:** the four `/api/v1/tags` operations and `tagIds` on `POST` and `PUT /entries`. A user's tag names are unique ignoring case (a duplicate `POST` returns the stored tag with `200`, and two requests at the same moment still give one tag), `entryCount` leaves out sealed Loot Drops and Recently deleted entries, a sealed entry shows no tags and refuses to change them, and a tag deleted while an entry is being saved with it is a `404`, not a `500`. 70 new tests cover it.

## 1. The goal
[Task 3.8](../../SPRINT_PLAN.md#sprint-3-phase-1-api) is the fourth endpoint family, and the first one that is **not** a self-contained resource: a tag is only useful when it is attached to an entry, so this task touches the Entries code from 3.5 as well as adding its own. Its block:
- **Do:** tag CRUD; `tagIds` on `POST` and `PUT /entries`; `tags` on `Entry` through `EntryMapper`.
- **Done when:** tags are scoped to the user; names are unique ignoring case (creating a duplicate returns the existing tag); renaming to an existing name is `409`; deleting a tag untags its entries; more than 20 tags is `400`; another user's tag ID is `404`; a sealed entry's tags are hidden and can't be changed (`409`); and `entryCount` doesn't count sealed entries.

Why now:

| Why now | What it gives the next tasks |
|---|---|
| 3.5 left a hook for it: the `tags` and `entry_tags` tables are in V1, `Entry.tags` and `replaceTags` exist, `EntryMapper` already maps tags (always empty so far) | Nothing new in the schema is needed, so this task is pure service and API work |
| 3.7's feed already fetches the tags of open entries in one query (`fetchTagsOfOpenEntries`) | The feed starts showing real tags the moment this task lands, with no change to it |
| 3.9 (the entry list) filters by `tagId`, and must never return sealed entries | It will reuse the rule written here: a sealed entry is left out *inside the query* (D-10) |
| 3.11 (Recently deleted) says tag counts must leave out deleted entries and count them again on restore | This task's count query is where that rule first has to be true, and it is tested now |

**What the docs didn't settle** (each is a decision in §4):
- Whether the 20-tag limit is counted on the list as sent or after repeats are removed, and whether a user has a cap on their total number of tags (D-26 only limits one entry).
- What a duplicate `POST` should return: the stored spelling or the one just sent.
- Whether `tagIds` may be left out of a `PUT`.
- How two requests creating (or renaming to) the same name at the same moment should end.

## 4. Decisions and alternatives
| Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|
| How `POST /tags` handles an existing name | Select, then insert if missing; insert and catch the unique-index error; `INSERT … ON CONFLICT DO NOTHING` and check how many rows it wrote; a `REQUIRES_NEW` retry | **`ON CONFLICT (user_id, lower(name)) DO NOTHING`**, returning 1 or 0; on 0, read the winner's tag | Same two steps as a week (D-08). "Select, then insert" has a gap two requests can both fall into, and the loser dies on the index with a `500`. Catching that error does not help: in Postgres a failed statement aborts the whole transaction, so the service could not select afterwards. One statement settles it, and the common (new name) path is a single `INSERT` | A native query; the conflict target repeats the index's expression |
| How to compare names | A derived `findBy…NameIgnoreCase`; compare in Java; JPQL `lower(t.name) = lower(:name)` | **JPQL `lower(...) = lower(...)`** | The unique index is on `lower(name)`. A derived `IgnoreCase` finder emits `upper(...)`, which the index cannot serve and which can disagree with `lower` for a few letters. The lookup and the guard now mean the same thing | The repository method keeps its old name though it is now a `@Query` |
| What a duplicate `POST` returns | The tag as sent (`work`); the stored tag (`Work`) | **The stored tag, `200`** | The contract says "returns the existing tag". Returning the sent spelling would show a name that is not stored, and a later `GET` would disagree | A user typing `work` sees `Work` come back; that is the point of unique-ignoring-case |
| Two renames to the same free name at once | Ignore it (`500`); lock all of a user's tags; check first, then treat the index's error as `409` | **Check first, and turn the index's violation into `409`** (`isNameClash` looks for `uq_tags_user_name` in the cause chain) | Cheap: no lock on the common path. The outcome is the same whichever request wins: one `200`, one `409`. Matching the constraint name means any *other* integrity error is still a `500` | A string match on an exception message |
| `entryCount` | One count query per tag (N+1); a counter column on `tags`; one grouped query | **One grouped query** (`countOpenEntriesByTag`), merged with the tag list in Java | A counter column would need to be kept right when entries are sealed, unsealed, deleted and restored, with a time-based rule (a Loot Drop starts counting *when it opens*, with no write at that moment). A grouped query is always right. A test asserts `GET /tags` is 2 statements for 1 tag and for 8 tags with 96 links | A tag with no entries is absent from the query, so the service defaults it to 0 |
| A tag that only sealed entries carry | Hide it from the list; list it with `0` | **List it, `entryCount: 0`** | Tags are the user's own vocabulary; hiding one would itself hint that something sealed carries it. The count must not say. The answers of a rename and a duplicate create apply the same rule | A user can see a tag with count 0 and not know why |
| Where the 20 limit is checked, and how it counts | After removing repeats; on the resolved tags; on the list as sent, in the request record | **As sent, in the request record** (`@Size(max = 20)`) | Validation runs before any database work, gives the standard `fieldErrors.tagIds`, reaches OpenAPI as `maxItems: 20`, and caps the work an attacker can ask for. 21 copies of one id is a `400` | A client that repeats an id 21 times is refused although it names one tag |
| Is `tagIds` required on `PUT`? | Optional, and a missing list clears the tags (what 3.5's note assumed); optional, and a missing list keeps them; required (`400`) | **Required**; `[]` clears | The contract lists `"tagIds": [uuid]` without "or null" (its neighbours say "or null"). A full replace that forgot the field must not quietly strip every tag; the same reasoning and the same answer as `subheadings` on a template (3.4). Keeping the tags would break "full replace" | Departs from the 3.5 note; a client must always send the array. Flagged in §9 |
| Is a tag change an entry change? | Exclude the tag collection from the version (`@OptimisticLock(excluded = true)`); leave Hibernate's default | **Default: a changed set raises `version` by one and moves `updatedAt`**; the same set writes nothing | The entry owns the collection, so Hibernate treats it as part of the entry. Two devices editing the same entry then conflict on tags as they do on text (`entry-stale`) rather than overwriting each other. A test shows it is exactly one step even when the date, caption and tags change together | An edit made only to tags makes another device's open editor stale |
| A tag deleted while an entry is saved with it | Do nothing (`500` from the foreign key); catch the violation and map it; lock the tags while the entry transaction runs | **`SELECT … FOR SHARE` on the tags** (`findAndLockByIdInAndUserId`) | A delete takes an exclusive row lock, so it waits for the entry's transaction; or, if it committed first, the lookup finds nothing and the answer is `404`. Share locks do not block each other, so two entry edits using the same tag never wait. Same family of fix as the entry row lock in 3.6 | One more locking query; the lock applies to a read, which looks odd until you know why |
| Deleting a tag | Load the entries and remove the tag from each; a bulk `DELETE FROM entry_tags`; delete the tag and let the database cascade | **Delete the tag; the foreign key's `ON DELETE CASCADE` removes the links** | `Tag` has no list of entries, so Hibernate issues one `DELETE FROM tags`. No entry is read or written, so no `version` or `updatedAt` moves, and sealed and Recently deleted entries are covered without any special case | The behaviour lives in the schema, so a test (not the Java) is what proves it |
| One request record or two | `TagCreateRequest` and `TagUpdateRequest`; one shared `TagRequest` | **One `TagRequest`** | Templates needed two because `POST` has an `id`. A tag has no client id and a `PUT` changes the only field it has, so the bodies are identical | If a tag ever gains a second editable field, the two bodies may need to differ |
| The sort | Copy the `Collator` into `Tag`; share it | **`common/NameCollation.BASE_LETTERS_ORDER`**, used by `Template.BY_NAME` and `Tag.BY_NAME` | Two copies of a subtle `Collator` set-up (locale, strength) would drift. `EntryMapper` now sorts an entry's tags with `Tag.BY_NAME` too, so the list and the entry agree | Touches 3.4's `Template` (a refactor with its existing tests as the safety net) |
| Fixing the tests that sent `PUT` without `tagIds` | Edit the ~40 call sites; give the shared `put` helper a default | **The helper adds `"tagIds": []` when the body has none**, and `putAsSent` sends a body untouched | The entries these tests make have no tags, so `[]` changes nothing they check. The tests *about* `tagIds` use `putAsSent` | A default hidden in a helper; its Javadoc says so |
| The two "client can't set these" tests that sent random `tagIds` | Keep them; remove `tagIds` from them | **Removed it** | `tagIds` is now something the client *may* set, and a random id is a `404`. Its own tests live in `EntryTagsTest` | None |

## 10. Concepts to learn from this task
- **`INSERT … ON CONFLICT DO NOTHING` as a race-free "create if missing"** ([`TagRepository.java:73-79`](../../../backend/src/main/java/com/memoirist/tag/TagRepository.java#L73-L79)): the database decides who wins, and the statement reports whether it wrote a row. The mistake is "select, then insert" (a gap), and its common repair, "catch the duplicate-key error and select", which fails in Postgres because a failed statement aborts the transaction.
- **An index on an expression** (`uq_tags_user_name` on `lower(name)`): a query uses it only when it contains the same expression. That is why the finder is written `lower(t.name) = lower(:name)` ([`TagRepository.java:61`](../../../backend/src/main/java/com/memoirist/tag/TagRepository.java#L61)).
- **Pessimistic locks on a read** (`@Lock(PESSIMISTIC_READ)`, SQL `FOR SHARE`, [`TagRepository.java:51-53`](../../../backend/src/main/java/com/memoirist/tag/TagRepository.java#L51-L53)): a shared lock lets other readers in and keeps a writer (here, a delete) waiting. It protects a row you are about to point a foreign key at.
- **Who owns a `@ManyToMany`** ([`Entry.java:295`](../../../backend/src/main/java/com/memoirist/entry/Entry.java#L295)): the side with `@JoinTable` writes the join rows and counts as part of the entity, so changing it bumps `@Version`. The other side (`Tag`) knows nothing about entries, which is why deleting a tag is one statement.
- **`ON DELETE CASCADE` as behaviour you test**: the Java is one line; the schema does the rest, so a test must compare the entry rows before and after.
- **Container-element constraints** (`List<@NotNull UUID>`, [`EntryUpdateRequest.java:45`](../../../backend/src/main/java/com/memoirist/entry/dto/EntryUpdateRequest.java#L45)): the annotation before `List` limits the list; the one inside the brackets applies to each item and gives the path `tagIds[1]`.
- **Constructor expressions in JPQL** (`select new com.memoirist.entry.EntryCountByTag(t.id, count(e)) … group by t.id`, [`EntryRepository.java:156-164`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L156-L164)): the query returns your record directly. A group with no rows is absent, so the caller supplies the default.
- **`CountDownLatch` and a thread pool to force a race** ([`TagRaceTest.java:40-65`](../../../backend/src/test/java/com/memoirist/tag/TagRaceTest.java#L40-L65)): every thread waits on one latch, then all are released together. Design the assertion so it holds whichever thread wins, or the test is flaky.
- **Holding a transaction open on purpose** ([`TagRaceTest.java:128-170`](../../../backend/src/test/java/com/memoirist/tag/TagRaceTest.java#L128-L170)): to test a lock, run a delete inside a `TransactionTemplate`, signal, and wait; start the competing request; assert it is *still running* after half a second; then release. The assertion "not done" is the proof that the lock exists.
- **Matching an exception by constraint name** ([`TagService.java:149-156`](../../../backend/src/main/java/com/memoirist/tag/TagService.java#L149-L156)): walk the cause chain, because Spring wraps Hibernate's exception, which wraps the driver's.

## 12. At work
- **References inside a payload are the usual hole.** A bank API takes `accountIds`, `beneficiaryIds` or `documentIds` in a request body. The check that the *path* resource belongs to the caller is easy to remember; the check on every id *inside* the body is the one that gets forgotten, and it is how one customer ends up attached to another's data. A reviewer looks for the scoped finder, the size comparison, a `404` that does not say which id was wrong, and a test that mixes a good id with someone else's.
- **Unique-ignoring-case and idempotent create.** Usernames, merchant names, reference codes: "must be unique ignoring case" is a database index plus a lookup that uses the same expression. The part reviewers probe is the race: what happens when two requests arrive together? An `ON CONFLICT` (or a unique key and a clean retry) is the answer; a `SELECT` followed by an `INSERT` is not.
- **Locking the thing you are about to reference.** A payment that references a beneficiary being deleted at the same moment is the same bug as an entry that references a deleted tag. Either you lock the referenced row, or you accept a foreign-key error and translate it. The choice is made on purpose and tested with a held transaction.
- **Counts that must not leak.** An "N items" figure next to a hidden item is a side channel. In a bank this is the balance or count of something the viewer may not see. The rule written here (filter in the query, list the container, show zero) is the same one a privacy review asks for.
- **Optimistic versioning and child collections.** Whether a change to a child list bumps the parent's version is a design decision with user-visible effects (stale editors). Make it explicit and test it, as `aPutReplacesTheWholeSetAndEachChangeRaisesTheVersionByOne` does.
- **Review habit.** When a reviewer sees a new create endpoint they ask three questions of it: what does a retry do, what does a simultaneous duplicate do, and what does a request from the wrong tenant do. The tests here answer each by name.

1. The statement decides the winner in the database and reports whether it wrote a row (1 or 0), so there is no gap between "is it free?" and "take it". With a lookup first, two requests can both find nothing and both insert; the loser fails on the unique index (`500`). Catching that error does not help because Postgres aborts the whole transaction after a failed statement, so the same transaction cannot run the follow-up `SELECT`. With `ON CONFLICT` the loser waits for the winner to commit, inserts nothing, reads the winner's tag and answers `200`.
2. `400 validation-failed` with `fieldErrors.tagIds` = `size must be between 0 and 20`. The limit is checked on the list *as sent*, before anything else, so 21 copies are refused even though they name one tag. Twenty copies pass the limit, are counted as one tag (`LinkedHashSet`), and give an entry with one tag.
3. `409 entry-sealed`. The seal check comes before the tag lookup, and the answer carries nothing from the entry. A `404` would have said "that id is not one of yours", so a sealed entry would have become a way to test whether another user's tag id exists. `EntryTagsTest > aSealedEntryCannotHaveItsTagsChangedWhateverTheListHolds` checks that a good, an empty, someone else's and an unknown list all get the same answer.
4. *Work* shows `entryCount: 1` (only the open entry counts, because the query leaves out entries whose unlock date is still ahead). The tag only the sealed entry carries is still listed, with `0`. Hiding it would itself hint that a sealed entry has something; tags are the user's own vocabulary, and only the count must not say. A Loot Drop counts from the unlock instant; sealed again, it stops counting until it opens again.
5. `Tag` has no collection of entries, so Hibernate issues only `DELETE FROM tags`; the foreign key's `ON DELETE CASCADE` removes the `entry_tags` rows. That covers every entry (open, sealed and Recently deleted) with no special case. `version` and `updated_at` of each entry are unchanged, which `deletingATagUntagsItsEntriesAndChangesNothingElseAboutThem` proves by comparing whole rows before and after.
6. A share lock is enough to stop a delete (which needs an exclusive lock) and does not stop other readers, so two entry edits that use the same tag never wait for each other. `FOR UPDATE` would serialise them for no benefit. Without a lock, the check can pass, the delete can commit, and the insert into `entry_tags` then breaks the foreign key: a `500`. With the lock, the delete waits, or has already committed and the lookup finds nothing, which is `404`.
7. The update can only be blocked if the lock exists: the test holds a delete open (its tag row is locked), starts the update, and the update must not finish until the delete is released. If it were done, the lookup did not wait, so it saw the tag that was about to be deleted, which is exactly the race. The final `404` shows the update then found the tag gone.
8. Yes, by exactly one. The entry owns the `@ManyToMany`, so Hibernate treats a changed set as a change to the entry and raises the `@Version`; it also moves `updatedAt`.
