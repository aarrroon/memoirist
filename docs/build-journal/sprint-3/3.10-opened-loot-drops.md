## 4. Decisions and alternatives
| Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|
| How `mark-seen` writes the time | (a) load the entry, `setUnlockSeenAt(now)`, save; (b) the same with `@OptimisticLock(excluded = true)` on the field; (c) a JPQL bulk `UPDATE`; (d) native SQL | **(c) a JPQL bulk `UPDATE` with every rule in its `WHERE`** | A bulk update goes straight to SQL: it skips `@Version` and `@UpdateTimestamp`, so a look is not an edit and `updatedAt` stays honest. With (a), opening a Loot Drop would make a caption `PUT` based on the version just read `409 entry-stale` (the user would lose nothing, but be told their copy was stale for no reason). The conditions make it idempotent and race-free without a read-then-write: a repeat matches no row, and a seal that lands in between moves `unlock_date` into the future so the `UPDATE` matches nothing. (b) fixes only the version, still reads then writes, and I did not try whether it keeps `updatedAt` still. (d) works, but Hibernate adds `@SQLRestriction` to JPQL and not to native SQL, so it would need `deleted_at IS NULL` written by hand, and JPQL is checked when the app starts | `Entry`'s `@Version` and its change tracking are bypassed for this one column, which D-23's wording ("every change") did not foresee; API_CONTRACT and DATABASE_SCHEMA now say so |
| Look the entry up first, or only run the `UPDATE` | Only the `UPDATE` and read the row count; **a lookup, then the `UPDATE`** | **Lookup, then `UPDATE`** | A row count of `0` can mean "not yours", "doesn't exist", "deleted", "sealed", "never sealed" or "already seen", and the contract wants three different answers (`404`, `409`, `204`). The lookup (`findByIdAndUserId`) is the ownership check and the `404`; the seal check gives the `409`; the `UPDATE`'s own conditions still protect the write if the state changes in between | Two statements, not one (`EntryOpenedQueryCountTest` pins the count at 2) |
| An entry that was never sealed | `204` and write nothing; `404`; `409 entry-sealed`; `400` | **`204`, nothing written** | The contract says "safe to repeat" and only lists `409` for "still sealed". `409 entry-sealed` would be false (it is not sealed), `404` would say an entry the user can `GET` doesn't exist, and `400` would punish a client for a state it can't see. The `UPDATE` has `unlock_date IS NOT NULL`, so no mark is written to a plain entry | A client bug (marking something that isn't a Loot Drop) goes unnoticed |
| `@DynamicUpdate` on `Entry` | Add it so a `PUT` can't write the old mark back; leave `Entry` saved with full-row `UPDATE`s | **Leave it off** | With full-row updates, a `PUT` that read the entry before a `mark-seen` and saves after it writes the old, empty mark back: the strip shows that Loot Drop once more. Harmless. With `@DynamicUpdate` the other writer breaks: `seal` sets the mark to empty, Hibernate sees "empty to empty" and leaves it out of its `UPDATE`, so a `mark-seen` that landed between the seal's read and write would stay on a sealed Loot Drop, which would then never reach the strip when it opens. `EntrySeenMarkRaceTest` pins both outcomes, and with `@DynamicUpdate` on `Entry` both tests fail (checked by hand) | A one-in-a-blue-moon replay of a Loot Drop in the strip |
| The strip's shape | `PageResponse<EntrySummary>` like the other lists; **a plain array** | **A plain array** | The contract says `EntrySummary[]` and the strip has no page two: it is at most 20 rows, and marking some seen reveals the next ones | A client can't ask how many are waiting beyond 20 |
| Which twenty | The first twenty to open; the **twenty most recently opened** | **Most recently opened first** | It is what the contract says ("most recently opened first, at most 20"). Older ones wait and show as the user marks the newer ones seen | Someone who ignores the strip for months sees the newest first, not the oldest |
| The order's tie-break | `unlock_date desc` only; add `id desc` | **`unlock_date desc, id desc`** | Two Loot Drops can open in the same instant (sealed together with the same date). Without a total order the database may order them differently between two requests. The same reason as 3.9's sort | An `Incremental Sort` on top of the index scan; `EXPLAIN` shows it costs nothing |
| How to cap at 20 | `Pageable` (adds a count query and a `Page`); a derived `findTop20By…`; **`Limit` parameter** | **`Limit`** | Spring Data 3.2 and later accept a `Limit` as the last parameter of a `@Query` method, and it becomes `fetch first ? rows only`. No count, no `Page`, the number is in the service where the contract's "20" lives | A newer API than many examples show |
| Whether to show the mark in `Entry` or `EntrySummary` | Add `unlockSeenAt` to the DTOs; keep it internal | **Keep it internal** | The strip is how a client learns what is unseen. Adding a field means changing the contract, the mapper's two branches and the generated types for something no screen needs | A client can't tell "seen" from "never opened" for a Loot Drop outside the strip |
| How to test that the index is used | A hand-copied SQL in `EXPLAIN`; the real SQL from `SqlLog`; no test | **The real SQL from `SqlLog`**, parameters put in, `EXPLAIN`ed on generated rows | A copy of the query proves the copy. If someone rewrites the JPQL so that the partial index's condition is no longer implied, only the real statement's plan changes | The test is a little long (50,000 rows, rolled back) and depends on Postgres choosing the index, which it does by a wide margin on this data |
| Where the code lives | All in `EntryService`; strip in `EntryListService` and `mark-seen` in `EntryService` | **Split by reason to change** | The strip is a read that returns rows (queries, statement counts); `mark-seen` is a write with rules about the seal. Same split as 3.9 | The controller takes both services, as it already does |

## 5. How it was built
In the order a reviewer should read it.

1. **[`EntryRepository.java`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L227)** adds two methods.
   - `findOpenedUnseen(userId, now, Limit)` (line 227): `unlock_date is not null and unlock_date <= :now and unlock_seen_at is null`, `order by unlock_date desc, id desc`. The first two conditions are `EntrySeal`'s rule written in SQL (an entry is open at the very instant of its unlock date), so a sealed entry cannot come back from it. Deleted entries are left out by `Entry`'s `@SQLRestriction`.
   - `markSeen(id, userId, now)` (line 259, a [practice block](#11-practice-blocks)): the conditional `UPDATE`, `@Modifying(clearAutomatically = true)`, returning the number of rows. Every rule is in the `WHERE`: the id, the owner, "has an unlock date not after now", "no mark yet".
2. **[`EntryListService.java`](../../../backend/src/main/java/com/memoirist/entry/EntryListService.java#L101)** adds `opened()`: the user from `CurrentUserProvider`, `now` from the injected `Clock`, `findOpenedUnseen(..., Limit.of(OPENED_STRIP_SIZE))`, then the same `summaries(...)` the timeline uses. Every entry the query returns is open, so the media and tags fetches run for all of them and `EntryMapper.toSummary` builds whole rows. The constant `OPENED_STRIP_SIZE = 20` is on line 43.
3. **[`EntryService.java`](../../../backend/src/main/java/com/memoirist/entry/EntryService.java#L266)** adds `markSeen(entryId)`: `find(entryId)` (user-scoped, `404`), then `EntrySeal.isSealed` gives `EntrySealedException` (`409`), then `entries.markSeen(...)`. 4. **[`EntryController.java`](../../../backend/src/main/java/com/memoirist/entry/EntryController.java#L74)** adds `GET /opened` (line 74) and `POST /{entryId}/mark-seen` (line 187, `@ResponseStatus(NO_CONTENT)`), both with `@Operation` and `@ApiResponse`s for every status the contract lists. `/opened` is a literal path next to `/{entryId}`; Spring prefers the literal, so it is not read as an entry id that isn't a UUID.
5. **Docs.** API_CONTRACT: the two table rows, "What exists after 3.10" and a new *The Opened strip* block (which Loot Drops, the shape, `mark-seen`'s checks, "a view mark is not an edit", coming back, cost). ## 8. What went wrong
1. **A test of mine was wrong, not the code.** The first run had 43 tests and one failure: `anEntryThatDoesNotExistIs404AndLooksTheSameAsSomeoneElses` asserted that the *whole* `404` body does not contain the id that was sent, and the body does: the problem's `instance` is the request path (`/api/v1/entries/<id>/mark-seen`). The documented promise (since 3.3) is that `detail` and `fieldErrors` never repeat what the client sent. Fixed by reading `$.detail` with JsonPath. The rule was already recorded in the assumptions of 3.3, 3.6 and 3.7 and I should have reread it before writing the assertion.
2. **A `sed` edit broke the compile.** To read the query plan I tried to add a `System.out.println("PLAN-BEGIN\n" …)` with `sed`; `sed` turned `\n` into a real newline inside the string literal (`unclosed string literal`). Restored the file from the backup I had taken and used the edit tool instead. The plan was then read from the test's XML output (Gradle hides the output of a passing test), and the `println` was removed before the build (`grep -c PLAN-BEGIN` was `0`).
3. **I launched the full build in a way that reported "completed" at once.** I put `( … ) &` inside a command that was itself run in the background, so the tool's notification meant "the shell returned", not "the build finished". The real build kept running; I watched its log for `EXIT 0` instead. (The result: `BUILD SUCCESSFUL in 5m 20s`.)
4. **A dead end I took on paper, not in code:** `@DynamicUpdate` on `Entry` looked like the obvious fix for "a `PUT` can overwrite the mark". I wrote the race test for it, saw that it fixed the first outcome and broke the seal's, and kept `Entry` as it is. Run 3 above is the proof.
5. **My running notes had made-up clock times.** I labelled sections of the notes with times I guessed (they said 03:10, 04:25 and so on) while the machine clock said 02:18 to 02:46. Every time in this entry comes from `date`; the notes carry the correction.
6. **Nothing else failed.** The first run of the other 42 tests, including the index test and the race test, passed. The Spring Data `Limit` parameter, `@Modifying(clearAutomatically = true)` and the `@SQLRestriction` on a bulk `UPDATE` all behaved as hoped the first time; the last one was a guess that `EntryOpenedRepositoryTest.markSeenLeavesAnEntryInRecentlyDeletedAlone` turned into a fact.
7. **Close-out fix pass.** Three of the reviewer's four minor findings were quick and safe and were fixed (two stale javadocs, the "twice"/"three times" slip, one link line). Nothing failed; no code behaviour changed.

## 10. Concepts to learn from this task
- **Conditional (compare-and-set) `UPDATE`** ([`EntryRepository.java:259`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L259)): put the preconditions in the `WHERE` and read the row count, instead of reading the row, deciding and writing. The check and the write are one atomic step, so there is nothing to race with, and a repeat is naturally idempotent (`0` rows). The mistake people make is to check in Java and then `UPDATE` by id alone: another request can change the state between the two.
- **JPQL bulk `UPDATE` skips the entity** (same line): no `@Version`, no `@UpdateTimestamp`, no dirty checking, and the persistence context isn't told. That is the feature here (a look is not an edit) and the trap elsewhere (a stale entity in the context; hence `clearAutomatically = true`). Hibernate 7 still adds the entity's `@SQLRestriction`.
- **`@Modifying`** (same line): required on a Spring Data `@Query` that isn't a `select`. The method returns `int` (the rows changed) or `void`.
- **Spring Data `Limit`** ([`EntryRepository.java:227`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L227)): `Limit.of(20)` as the last parameter caps the rows with `fetch first ? rows only` and adds no count query, unlike `Pageable`.
- **Optimistic locking and which writes bump the version** ([`Entry.java`](../../../backend/src/main/java/com/memoirist/entry/Entry.java) `@Version`, `EntryService.java:266`): `version` should answer "did the *content* change since you read it?". Writes that only record a view, a read receipt or a sync marker usually should not raise it.
- **Partial index and a matching predicate** ([`EntryOpenedIndexTest.java:54`](../../../backend/src/test/java/com/memoirist/entry/EntryOpenedIndexTest.java#L54)): Postgres uses a partial index only when the query's `WHERE` implies the index's `WHERE`. `unlock_seen_at is null` must appear in the query, or the index is useless. `EXPLAIN` on the real statement is how you check.
- **`Incremental Sort`** (same test, in the plan): the index delivers rows in `unlock_date` order; Postgres sorts only each run of equal dates by `id`. A tie-break key costs almost nothing when the leading key is indexed.
- **`REQUIRES_NEW` to play "the other request"** ([`EntrySeenMarkRaceTest.java:73`](../../../backend/src/test/java/com/memoirist/entry/EntrySeenMarkRaceTest.java#L73)): a second `TransactionTemplate` with `PROPAGATION_REQUIRES_NEW` commits on its own connection in the middle of the first one's transaction, which is how you test a race deterministically, with no threads and no sleeps.
- **Time-travel tests** ([`EntryOpenedTest.java:35`](../../../backend/src/test/java/com/memoirist/entry/EntryOpenedTest.java#L35)): `Instant.now(clock)` everywhere lets a test move the clock to one microsecond before, at, and after a boundary. `unlock <= now` is a boundary, and boundaries are where the bugs are.
- **Two orders of UUID** ([`EntryOpenedTest.java:111`](../../../backend/src/test/java/com/memoirist/entry/EntryOpenedTest.java#L111)): Postgres compares `uuid` bytewise; Java's `UUID.compareTo` compares two signed `long`s, so the two orders differ for some ids. The test asks Postgres for the expected order.

## 12. At work
- **"Acknowledge" and "mark as read" endpoints are everywhere in a bank's apps** (notifications, alerts, statements, tasks). The shape here is the one to copy: `POST …/{id}/mark-seen`, `204`, idempotent, a `404` for what isn't yours (never `403`), and one conditional `UPDATE`. The first question in review is "what happens if the client calls it twice, or two devices call it at once?", and the answer is in the `WHERE` clause, not in Java.
- **`updatedAt` and `version` mean something.** On an account or a customer record, an audit trail that says "modified" because someone *looked* at it is wrong, and an optimistic lock that fails because a read receipt was written is a support ticket. A reviewer should ask of every write: is it a change to the record, or a side-record about it? Often the honest answer is a separate column (as here) or a separate table.
- **Which writes may bypass the entity?** Bulk updates are normal for status flags, counters and sweeps, and they are also how stale entities and skipped listeners cause bugs. Look for `@Modifying` without `clearAutomatically`, and for bulk updates on entities with `@Version`, `@PreUpdate` or audit listeners.
- **Deterministic ordering for anything paged or limited.** `ORDER BY created_at DESC LIMIT 20` with ties is a production bug that shows up as "the same row twice". Add the primary key as the last sort key.
- **Test boundaries with an injected clock** (expiry, cut-offs, settlement times, "business day" rules). `<` versus `<=` at the exact instant is the classic defect, and the tests here pin it for the unlock moment.
- **Read the plan, not the query.** `EXPLAIN` on the SQL the ORM really sends, in a test or in review, is how a partial index or a composite index is shown to work. A reviewer who sees a new `@Query` on a big table should ask where its index is.
- **Race tests without threads.** `REQUIRES_NEW` inside a transaction (or a second connection) makes a "two requests at once" scenario repeatable. Worth knowing before someone proposes `Thread.sleep`.
