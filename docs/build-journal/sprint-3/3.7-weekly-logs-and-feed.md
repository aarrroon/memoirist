# Task 3.7: Weekly logs and feed

> **Sprint:** 3 · **Commit:** `Sprint 3.7: Add the feed and weekly logs endpoints` · **Status:** done · **Time taken:** roughly 30 minutes to build (14:27 to about 14:57 on 2026-10-31, unattended, with one failed and one passing full build and four partial test runs) and about 20 more for the review fix pass and the final build (to 15:16)
> **Built:** the journal's main screen has its API: `GET /feed` returns a page of non-empty weeks, newest first, each with its Eras and its entries (sealed Loot Drops as locked rows), `GET /weekly-logs/{id}` returns one week, and a week can be renamed, closed and reopened.

## 1. The goal
Tasks 3.3 to 3.6 made Eras, entries and media, but nothing yet *reads them together*. Task 3.7 builds the two read shapes the whole front end is built around: the **feed** (an Instagram-style list of weeks) and the **week detail** (D-25's week summary uses it), plus the three small writes a week allows: its title (`PUT`), `close` and `reopen`. The block in [SPRINT_PLAN.md](../../SPRINT_PLAN.md) lists five things to prove:
- sealed entries are redacted in the feed and in week detail (D-10);
- the feed holds only non-empty weeks, newest first, with Eras and redacted entries, and Recently deleted entries don't count (D-30);
- the query count of a page doesn't grow with the number of entries or media, asserted with Hibernate statistics;
- `PUT`, `close` and `reopen` work;
- a week's `eras` are every Era whose dates overlap it, pinned first and then latest start, through `WeekEras.of` (built in 3.3), and they change as soon as an Era's dates change (D-22).

Why now: 3.5 gave us `EntryMapper` (the one place that hides a sealed entry), 3.3 gave us `WeekEras`, and 3.6 gave us media to presign. This task is where those meet, and the sealed-entry rule has to hold in a place that returns *many* entries at once. Sprint 4 (the React feed) cannot start without it, and the entry list (3.9) will copy its paging.

The hard part is not the endpoints. It is that a feed is the classic place to write an accidental N+1 (one query for the weeks, then more for each week's entries, each entry's photos, each week's Eras), and the task wants that to be a failing test, not a code-review opinion.

## 3. The plan
1. **Contract and shared pieces first**: `PageResponse` (a record in `common/`), the three week DTOs, the `WeeklyLogUpdateRequest` cleaning rule.
2. **Queries**: the "non-empty weeks" page query (practice block 1) and the "entries of these weeks" finder.
3. **`WeeklyLogMapper`** (a week, its Eras and its entries to one response; every entry through `EntryMapper`), **`WeeklyLogService`** (ownership, clock, the fixed set of queries) and the two thin controllers.
4. **Test infrastructure**: Hibernate statistics on in `application-test.yml`; a `WeekApiTest` base class on top of `EntryApiTest`.
5. **Tests from the outside in**: the feed, then week detail and its writes, then the query counts (practice block 2), then the small unit tests.
6. **Docs** (API_CONTRACT, TECH_STACK, DATABASE_SCHEMA, DEVELOPMENT), a live smoke test of the running app, the full build.

Order: DTOs and queries before the service, because the service is only glue; the test base class before the tests, because the same helpers (an entry on a given day, an Era, a sealed entry) are used by every one of them; the query-count tests after the behaviour tests, because counting statements of a feed that returns the wrong thing proves nothing.

## 5. How it was built

**The page shape: [`PageResponse.java`](../../../backend/src/main/java/com/memoirist/common/PageResponse.java).** A record `(items, page, size, totalItems, totalPages)` with one factory, `of(Page<?> source, List<T> items)` (line 24). The rows are passed in separately because the service maps a whole page as a group.

**The DTOs: [`week/dto/`](../../../backend/src/main/java/com/memoirist/week/dto/).**
- `WeeklyLogResponse`: `closed` is `@JsonProperty("isClosed")` (the rule in `backend.md`), `eras` and `entries` are never `null`.
- `WeekEraResponse`: the five fields the contract lists.
- [`WeeklyLogUpdateRequest`](../../../backend/src/main/java/com/memoirist/week/dto/WeeklyLogUpdateRequest.java): one component, `@Size(max = 200) String title`. The compact constructor (line 16) strips and turns an empty result into `null`, so `@Size` sees the stripped text and "no title" has one spelling. A body field the record doesn't know (`soundtrack`, `isClosed`, `userId`) is ignored by Jackson.

**The queries.**
- [`WeeklyLogRepository.findNonEmptyByUserId`](../../../backend/src/main/java/com/memoirist/week/WeeklyLogRepository.java) (line 94, inside the first practice block): `where user_id = ? and exists (select 1 from entries ...)` with its own `countQuery`, ordered by `startDate desc`.
- [`EntryRepository.findByWeeklyLogIdInAndUserIdOrderByEntryDateAscCreatedAtAsc`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java) (line 77): the entries of all the weeks of a page, sorted so each week reads as a story. The Javadoc warns not to pass an empty list.
- [`EntryRepository.fetchMediaOfOpenEntries` and `fetchTagsOfOpenEntries`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java) (lines 103 and 118, added in the close-out fix pass): `select e from Entry e left join fetch e.media` (or `e.tags`) `where e.weeklyLogId in :weeklyLogIds and e.userId = :userId and (e.unlockDate is null or e.unlockDate <= :now)`. They return the entries the service has just loaded, now with their lazy lists filled in, so the mapper finds them ready. The `where` is the same rule as `EntrySeal` (the instant of the unlock date is open), so a sealed entry's media and tags are never read.

**The mapper: [`WeeklyLogMapper.java`](../../../backend/src/main/java/com/memoirist/week/WeeklyLogMapper.java).** `toResponse(week, userEras, weekEntries, now)` (line 38) runs no query: `WeekEras.of(week, userEras)` picks and orders the Eras, and every entry goes through `entryMapper.toResponse(entry, now)` (line 48). This class never reads a private field of an entry, so the sealed rule stays in one place.

**The service: [`WeeklyLogService.java`](../../../backend/src/main/java/com/memoirist/week/WeeklyLogService.java).**
- `feed(page, size)` (line 77): `findNonEmptyByUserId(userId, PageRequest.of(page, size))`, then `build`, then `PageResponse.of`.
- `get` (line 85) and `update` (line 94): find by id and user (`find`, line 120, `404` otherwise), set the title on the managed entity, and map. There is no `save()`: the entity is managed, so Hibernate writes one `UPDATE` at commit, and none if nothing changed.
- `close`/`reopen` (lines 102 and 107) call `setClosed` (line 111).
- `build` (line 133) is the heart: return at once for an empty page (an empty `IN ()` is not safe), load the user's Eras once, load the entries of every week in one query, and, when at least one of them is open (`EntrySeal.isSealed`), call `fetchMediaOfOpenEntries` and `fetchTagsOfOpenEntries` (lines 146 and 147) once each; then group the entries with `Collectors.groupingBy(Entry::getWeeklyLogId)` (line 151) and map each week. The clock is read once, so every entry in a response is judged against the same "now", in Java and in the two queries.

**The controllers.** [`FeedController`](../../../backend/src/main/java/com/memoirist/week/FeedController.java) takes `@RequestParam(defaultValue = "0") @Min(0) int page` and `@RequestParam(defaultValue = "10") @Min(1) @Max(50) int size` (lines 43 and 44); Spring 7 validates them without `@Validated`, and the existing error handler names the parameter. [`WeeklyLogController`](../../../backend/src/main/java/com/memoirist/week/WeeklyLogController.java) has `GET`, `PUT`, `close` and `reopen`, each with its `@ApiResponse`s. Both are package-private and contain no logic.

**One annotation: [`WeeklyLog.java`](../../../backend/src/main/java/com/memoirist/week/WeeklyLog.java).** `@DynamicUpdate` (line 22), explained in the Javadoc above it.

**Test configuration.** [`application-test.yml`](../../../backend/src/test/resources/application-test.yml) line 16: `hibernate.generate_statistics: true`.

**Docs.** API_CONTRACT: a "How `/feed` and `/weekly-logs` behave (task 3.7)" block and one sentence in *Pagination*; TECH_STACK: the queries, the 5-or-6 statements, `exists` vs a join, what "doesn't grow" means, `@DynamicUpdate`; DATABASE_SCHEMA: the `@DynamicUpdate` note; DEVELOPMENT: the status line and the statistics note.

## 10. Concepts to learn from this task
- **`EXISTS` instead of a join for "has at least one"** ([`WeeklyLogRepository.java:94`](../../../backend/src/main/java/com/memoirist/week/WeeklyLogRepository.java)): a join to the many side repeats the one side (so you need `DISTINCT`, which also breaks paging); `exists` asks a yes/no question per row and stops at the first match. The mistake: joining, then adding `distinct`, then wondering why `count` and the page disagree.
- **N+1** and how to see it (`FeedQueryCountTest.java:75`): N+1 is one query for a list plus one more per row. The first version of this task had the milder form, two extra queries for every further 50 open entries (see `@BatchSize` below). Every flatness test of that version stayed under 50 open entries, so only the review noticed. The answer looks correct and only the number of statements gives it away, so count them. Compare two sizes instead of hard-coding one number: an extra query everyone pays is a design change, an extra query *per row* is the bug.
- **Hibernate `Statistics`** (`FeedQueryCountTest.java:46`): `SessionFactory.getStatistics()` with `clear()` before and `getPrepareStatementCount()` after. It is global, so clear it right before the request. It needs `hibernate.generate_statistics`, here in the test profile only.
- **`@BatchSize`** (`Entry.java`, still there): when a lazy collection of one entry is touched, Hibernate loads the collection for up to 50 loaded entries at once with `where entry_id = any (?)`. The statement count then grows by one per 50, not one per entry. It is a cheap fix and a good default for code that reads a few entries, and it is not a constant. The feed first relied on it and was flagged for it.
- **Filling lazy collections with a second query** ([`EntryRepository.java:103`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java), [`WeeklyLogService.java:146`](../../../backend/src/main/java/com/memoirist/week/WeeklyLogService.java)): after the entries are loaded, `select e from Entry e left join fetch e.media where e.weeklyLogId in :ids ...` returns the *same* managed objects (they are already in the session) and initialises their `media` as it goes. One collection per query is the safe way to fetch several collections without a row explosion or `MultipleBagFetchException`. The mistake to avoid: reading the query's result list instead of the entities you already hold, or fetch-joining two collections in one statement.
- **A mutation check on a test** (section 8, item 11): to learn whether a guard guards anything, break the code on purpose and watch the test fail. One of mine passed anyway, because its data was too small to make the bad path look different.
- **`@SQLRestriction` reaches subqueries** (`Entry.java`, `WeeklyLogRepository.java:94`): the soft-delete filter was applied inside the `exists` subquery without being written there. The captured SQL is the proof; a guard test keeps it true.
- **Spring Data `Page` and its count** (`WeeklyLogService.java:77`): it skips the count query for a short page and computes the total as offset plus rows. Know this before you read statement counts, and before you promise "two queries per page".
- **`@DynamicUpdate`** (`WeeklyLog.java:22`): by default Hibernate's `UPDATE` sets *every* column from the entity's loaded state. Two requests changing different columns of one row can then undo each other. Dynamic update names only changed columns.
- **Dirty checking as idempotency** (`WeeklyLogService.java:111`): setting a field to the value it already has produces no `UPDATE`. That is why `close` twice is safe and cheap, and why there is no `save()` call in these methods.
- **Method validation on controller parameters** (`FeedController.java:43`): `@Min`/`@Max` on a `@RequestParam` work without `@Validated` in Spring 6.1 and later; a failure is a `HandlerMethodValidationException`, which the shared handler turns into `validation-failed` with the parameter's name.
- **Records with a compact constructor** (`WeeklyLogUpdateRequest.java:16`): `public WeeklyLogUpdateRequest { title = cleaned(title); }` reassigns the parameter before the field is set, so validation sees the cleaned value.
- **Java syntax seen here:** `Collectors.groupingBy(Entry::getWeeklyLogId)` returning `Map<UUID, List<Entry>>`; `List.getFirst()` (Java 21); `Map.getOrDefault`; `try`-with-resources on `SqlLog`.

## 12. At work
A paged list that shows each row with its children is on every banking screen: accounts with their recent transactions, cases with their attachments, customers with their products. The questions a reviewer there would ask:
- **How many statements does one page cost, and does it depend on the data?** A list endpoint that is fast with the demo data and slow with a real customer is almost always an N+1. A test that counts statements, run against two sizes of data, is a cheap guard that survives refactoring. Many teams add this as a shared test utility once and use it on every list endpoint.
- **Is the "who may see this" rule written once?** Here every entry goes through one mapper, so a new endpoint can't forget the seal. In a bank the same shape is data masking for a restricted account: one mapper, called from every list, and a test that greps the response body for the secret.
- **Soft deletes and counts.** A hidden `WHERE deleted = false` has to apply to the subquery that decides whether a parent shows up, and to the total shown to the user. Check the generated SQL once, not the annotation.
- **Paging contracts.** A client that asks for `size=10000` should get an answer that teaches it the limit, not a silent clamp that hides a bug in its own paging. Also know whether your total comes from a count query or from "offset plus rows".
- **Idempotent state changes.** `close` twice, `approve` twice, `cancel` twice: say what happens, make it safe, and make sure a repeat doesn't write (and so doesn't touch audit timestamps).
- **Lost updates on one row.** Two screens changing different fields of the same record is routine in a back-office app. Know whether your ORM writes all columns, and choose between dynamic update, optimistic locking and a row lock on purpose.
