> **Sprint:** 3 · **Commit:** `Sprint 3.11: Add restore, erase and the 30-day sweep` (hash in the OVERNIGHT_REPORT) · **Status:** done (every Done-when item is met; `./gradlew build` passes with 1329 tests and no failures; the review is §9) · **Time taken:** roughly 1 hour of work in two sittings, unattended. > **Built:** `GET /api/v1/entries/deleted` (a page of the user's Recently deleted list), `POST /api/v1/entries/{entryId}/restore` and `POST /api/v1/entries/{entryId}/erase`, plus `RecentlyDeletedSweeper.sweep()`, a safe-to-repeat method that erases entries deleted more than 30 days ago with their stored files, and a daily `@Scheduled` job that only calls it. 75 new tests cover it.

## 1. The goal
[Task 3.11](../../SPRINT_PLAN.md#sprint-3-phase-1-api) finishes the life cycle that 3.5 started. Its block:
- **Do:** `GET /entries/deleted`, `POST /entries/{entryId}/restore` and `/erase`, and a sweep that erases entries deleted more than 30 days ago, with their stored files. Erase and the sweep call `EntryErasure.erase(entry)` inside a transaction and read an entry's media with native queries only. The sweep is a service method that is safe to repeat; a daily `@Scheduled` job only calls it, so Sprint 5 can start it another way (Q5).
- **Done when:** tests with a fixed `Clock` prove (1) a deleted entry is left out of the feed, its week, the timeline, tag counts and filters, and the Opened strip, and comes back in all of them when restored; (2) restoring keeps its media, tags and seal, and a sealed entry stays redacted in the list; (3) erasing, and the sweep after 30 days, remove the entry and its stored files, and the sweep leaves younger ones alone; (4) an empty entry is erased at once and never listed; (5) restore and erase return `404` for an entry that isn't in Recently deleted, or is another user's.

Why now:

| Why now | What it gives the next tasks |
|---|---|
| 3.5 built `DELETE` (it sets `deleted_at`, or erases an empty entry at once through `EntryErasure`) and `@SQLRestriction` hides deleted rows everywhere | Until this task a deleted entry could never come back and its files stayed for ever. This is the other half of D-30 |
| 3.6 found that `@SQLRestriction` also hides a deleted entry's media from JPQL, and built `EntryErasure` with native queries for that reason | Erase and the sweep reuse it as it is: this task adds no new way to delete a file |
| 3.9 and 3.10 built the list rows and the Opened strip and left two cautions for this task (the fetch-by-id queries skip deleted rows; a restored, unseen, opened Loot Drop must return to the strip) | Both cautions are now tests |
| The Recently deleted screen (task 4.12) and the delete confirmation that promises "you can restore it for 30 days" | The frontend gets its three endpoints |
| Sprint 5 deploys on a host that may sleep (Q5) | The sweep is a plain method with no `@Scheduled` in it, so an outside scheduler can call it |

## 3. The plan
In the order it was done, and why:
1. **Read the docs and the nearest code** and decide the shape (§4): which class owns what, how a row gets its children, how the lock works.
2. **Repository first.** Five native queries, because everything else is a thin layer on them and the tests of the SQL can run without HTTP.
3. **Services.** `EntryListService.deleted` (the list), `RecentlyDeletedService` (restore, erase), `RecentlyDeletedSweeper` (the work of the sweep), then `RecentlyDeletedSweepJob` and `SchedulingConfiguration`.
4. **Controller** endpoints with their `@Operation`s.
5. **Tests in order of risk.** The HTTP behaviour (list, restore, erase), then the one test that looks at every place an entry shows up, then the sweep on a moved clock, then statement counts and the schedule.
6. **Break it on purpose,** four times (§6), to prove the tests catch a missing lock, a `<` that became `<=`, a missing `SKIP LOCKED` and a missing `detach`.
7. **Docs,** the full build, a live run of the real app against the Compose database, and this entry.

## 4. Decisions and alternatives
| Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|
| Who owns restore and erase | Add them to `EntryService`; a new service | **A new `RecentlyDeletedService`** | `EntryService` already has nine dependencies and every method in it is about a live entry; this class is the only one that looks at deleted entries (non-negotiable 3 and D-30 stay in one file). The list is `EntryListService.deleted`, as the docs already said | One more class and constructor |
| How a restore writes | A native `UPDATE ... SET deleted_at = NULL`; load the entity, `setDeletedAt(null)`, `saveAndFlush` | **Load the locked entity and `saveAndFlush`** | It is an ordinary edit: `version` + 1 and `updated_at` moves (D-23, D-30 "counts as an edit"), so a copy a client read before the delete is stale. The `UPDATE` would leave both as they were. (3.10's `mark-seen` chose the opposite for the opposite reason: a view mark is not an edit) | One extra read, and the entity must be flushed before the response is built |
| Two requests for one entry | No lock (check, then act); `FOR UPDATE`; **`FOR NO KEY UPDATE`**; optimistic `@Version` retry | **`SELECT ... FOR NO KEY UPDATE`** in the finder | Without a lock both requests find the entry: a double tap restores twice and a restore racing an erase both succeed. With it the second request waits, and when the first commits Postgres re-checks `deleted_at IS NOT NULL` on the row's new version, so it finds nothing and answers `404`. `NO KEY UPDATE` is the weaker lock that does not block foreign-key checks from rows that point at the entry (media rows), and nothing here changes the key | Row lock held for the length of one short transaction |
| The sweep's unit of work | One transaction for the whole run; **one transaction per entry**; a `@Transactional` private/own method | **A `TransactionTemplate` per entry** | One transaction for thousands of rows would roll everything back for one bad entry and hold every lock at once. A `@Transactional` method called from inside the same class would skip Spring's proxy and run with no transaction at all (then `EntryErasure`, which is `MANDATORY`, would throw) | A bit more code than an annotation |
| How the sweep avoids erasing what a user just restored | Trust the list it read; re-read each entry; **re-check under a lock that does not wait** | **`findDeletedForSweep`: `deleted_at < :cutoff` again, `FOR NO KEY UPDATE SKIP LOCKED`** | The list of ids is read with no lock, so by the time an entry's turn comes the user may have restored it, erased it, or be doing so right now. The re-check makes the decision and the claim on the row one step; `SKIP LOCKED` leaves a row someone else holds for the next sweep instead of waiting for it. Two sweeps at once never collide | A row that is busy at 16:00 waits until tomorrow |
| What a failing entry does to the sweep | Let the exception stop the run; **log the entry's id and the exception class, go on to the next** | **Catch `RuntimeException` per entry** | A poisoned entry must not block every other deletion (a privacy promise: erased means erased). The entry is rolled back, still due, and tried again at the next sweep. The log has the id and the class, never the message, because a database message can carry row contents | A permanent failure repeats in the log each day (the id makes it findable) |
| The edge of "more than 30 days" | `deleted_at <= now - 30d`; **`deleted_at < now - 30d`** | **Strictly before** | The sprint plan says "more than 30 days ago", D-30 says "wait 30 days". An entry deleted exactly 30 days ago is kept until the next sweep. Both queries use `<`, and two tests pin the edge | An entry may live up to a day over 30 |
| Can a restore happen after day 30 | Refuse after 30 days; **allow while the row exists** | **Allow** | The sweep is a clean-up, and the clock must never be what decides whether a memory can be saved. Refusing would also make the answer depend on whether the sweep had run yet | A memory lives a few hours longer than promised in rare cases |
| How the list's rows get media counts and tags | (a) Reuse `EntryListService`'s fetch-by-id queries; (b) native queries for media and tags and a second mapper path; (c) Hibernate's lazy `@BatchSize` loading as it is; **(d) lazy batches, with the Loot Drops detached first** | **(d)** | (a) starts from `Entry`, which carries `@SQLRestriction`, so it skips every deleted row (3.9's caution, now proven). (b) means a second way to build a row, and the mapper is the one place that must know the sealed rule (D-10). (c) works but a batch loads the lists of *every* entry of the page that has not loaded them, so a page of 7 entries with 3 Loot Drops loaded 7 media lists instead of 4: a sealed entry's children were read from the database, which the other lists never do. (d) detaches the sealed entries (`EntityManager.detach`) before mapping, so the batch skips them | The page's entities are fetched whole, caption included (up to 200 KB each), although a row does not show it. A projection is the first thing to try if this list ever gets slow |
| Order of the list | `deleted_at desc`; **`deleted_at desc, id desc`** | **With the id** | Two entries deleted in the same instant would otherwise swap places between page requests and a client would see one twice or miss one (the same reason as 3.9's timeline). `EntryRepositoryTest` proves a total order | None |
| Page limits | The contract's default 10 with no cap; `rules/api.md` "cap size at 50" | **Default 10, at most 50** | `rules/api.md` caps pages at 50 and the contract states the default. Outside the range is `400 validation-failed` naming `size`/`page`, as in 3.7 and 3.9, never a silent clamp | A client that wants more pages more |
| When the job runs, and how tests avoid it | A fixed `cron` in the annotation; **a property with a daily default and a `-` off switch** | **`${memoirist.recently-deleted.sweep-cron:0 0 16 * * *}`, zone `UTC`; the `test` profile sets `-`** | 16:00 UTC is 02:00 or 03:00 in Melbourne. Spring reads `-` as "disabled", so no test JVM can start a sweep in the middle of a test; one test gives its context a real cron and checks Spring registers it. Sprint 5 can switch the in-app schedule off with the same property and call `sweep()` from outside (Q5) | One more property |
| Where `@EnableScheduling` lives | On the application class; **`common/SchedulingConfiguration`** | **Its own tiny configuration** | Every later job (unlock emails and others) needs it; without it `@Scheduled` is silently ignored. A test would catch a missing one, and the schedule test does | None |
| Test infrastructure | Make a copy of the media helpers for the new tests; **make `MediaApiTest` public and extend `EntryOpenedApiTest`** | **Reuse** | The new tests need both the feed, list and strip helpers and the real SeaweedFS plus the `StorageService` spy, in one Spring context. `MediaApiTest` was package-private and extended `EntryApiTest`; it now sits on top of `EntryOpenedApiTest`, which is `EntryApiTest` plus those helpers, so nothing clashes | A public test base class |

## 5. How it was built
In the order a reviewer should read it.

1. **[`EntryRepository.java`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L315)**: the five native queries (lines 315 to 388). `@SQLRestriction` hides deleted rows from JPQL and derived queries and Hibernate never rewrites native SQL, so each query says `deleted_at IS NOT NULL` itself.
   - `findDeletedByIdAndUserId` (line 327): the unlocked read from 2.4, kept.
   - `findDeletedForUpdateByIdAndUserId` (line 341): the same plus `FOR NO KEY UPDATE`, for restore and erase.
   - `findDeletedPageByUserId` (line 357): `order by deleted_at desc, id desc` with an explicit `countQuery`; replaced 2.4's `List` finder, which had no paging.
   - `findDeletedIdsBefore` (line 368): the ids of every user's entries deleted before the cutoff, oldest first. The only query with no `user_id`, because the sweep has no request.
   - `findDeletedForSweep` (line 388, the query behind a [practice block](#11-practice-blocks)): one entry, still deleted and still before the cutoff, locked with `FOR NO KEY UPDATE SKIP LOCKED`.
2. **[`RecentlyDeletedService.java`](../../../backend/src/main/java/com/memoirist/entry/RecentlyDeletedService.java#L64)** (`@Service @Transactional`). `restore` (line 64) finds the locked entry, sets `deletedAt` to `null`, `saveAndFlush`es, then returns `mapper.toResponse`. It flushes before building the response because the mapper reads the lazy media and tags, which must now be read from a live row, and because Hibernate fills `updatedAt` and the version as it writes. A sealed entry comes back redacted because the response goes through the one mapper. `erase` (line 79) passes the locked entry to `EntryErasure.erase` inside the same transaction. `findDeletedForUpdate` (line 83) is the user-scoped lookup: id and `currentUser.currentUserId()` together, so a live entry, another user's and a missing one are the same `NotFoundException`.
3. **[`RecentlyDeletedSweeper.java`](../../../backend/src/main/java/com/memoirist/entry/RecentlyDeletedSweeper.java#L58)**. `sweep()` (line 58) computes `cutoff = now - RETENTION` from the injected `Clock`, reads the due ids once, then calls `eraseIfStillDue` per id inside a `try/catch` that logs the id and the exception class and moves on. `eraseIfStillDue` (line 89) is a practice block: a `TransactionTemplate` runs `findDeletedForSweep(...)` and, if the row comes back, `EntryErasure.erase(entry)`; it returns whether it erased. It is not `@Transactional` on purpose (§4).
4. **[`RecentlyDeletedSweepJob.java`](../../../backend/src/main/java/com/memoirist/entry/RecentlyDeletedSweepJob.java#L30)** and **[`SchedulingConfiguration.java`](../../../backend/src/main/java/com/memoirist/common/SchedulingConfiguration.java#L12)**. The job's one method (line 31) calls `sweeper.sweep()` and logs how many it erased; the `@Scheduled` cron (line 30) is a property with a default and `zone = "UTC"`. The configuration (line 12) is only `@EnableScheduling`.
5. **[`EntryListService.java`](../../../backend/src/main/java/com/memoirist/entry/EntryListService.java#L129)**: `deleted(page, size)` (line 129) calls `findDeletedPageByUserId`, detaches the sealed entries (line 135), maps every entry with `mapper.toSummary`, and wraps the page in `PageResponse.of`. It does not call `summaries(...)`, the helper the other lists use, for the reason in §4.
6. **[`EntryController.java`](../../../backend/src/main/java/com/memoirist/entry/EntryController.java#L89)**: `GET /deleted` (line 89, `@Min(0) page`, `@Min(1) @Max(50) size`, default 10), `POST /{entryId}/restore` (line 224) and `POST /{entryId}/erase` (line 238, `204`), each with `@Operation` and an `@ApiResponse` for every status in the contract. `/deleted` is a literal path next to `/{entryId}`; Spring prefers the literal.
7. **Small edits.** Comments in `Entry`, `EntryErasure`, `EntryMapper`, `EntryService` and `EntrySummaryResponse` that said "task 3.11 will..." now say what is true.
8. **Docs.** API_CONTRACT: the three rows, "What exists after 3.11" and a new *Recently deleted (task 3.11)* block. DATABASE_SCHEMA: the five native reads and the index that serves them. TECH_STACK: the *Recently deleted* block (who does what, how rows get children, the lock, the sweep, the schedule), the package list and the 3.9 caution turned into a fact. DEVELOPMENT: a curl walkthrough and the `sweep-cron` property.

Nothing else changed: no migration (`deleted_at` and `idx_entries_deleted` have been in V1 since 2.3), no new dependency, no new DTO.

## 8. What went wrong
In order.
1. **A python heredoc with triple-quoted strings failed** ("unexpected EOF while looking for matching") in the first sitting. The script went into a file in the scratchpad instead.
2. **Python edits with `\n` literals matched nothing on files with `\r\n` line endings** (`.gitattributes` has `text=auto` and `core.autocrlf=true`, so `EntryRepository.java` and others are CRLF in the working tree). The fix was a small script that detects the file's line ending. A first run of it used the wrong arguments (`KeyError`); nothing had been written, and `cmp` against a saved good copy proved it.
3. **`theChildrenOfALootDrop...` first failed with 7, not 4.** I expected the media lists loaded to be those of the 4 open entries; Hibernate's `@BatchSize` loader had fetched all 7, three Loot Drops included. The first attempt to measure it also used the wrong accessor: `getFetchCount()` returned 1 because it counts statements, not collections. `getCollectionStatistics(role).getLoadCount()` is the right one. The fix is the `detach` (§4), and removing it makes the test fail again.
4. **A 404 test asserted the id was nowhere in the body.** It is: the problem's `instance` is the request path, which holds the id the client sent. ## 10. Concepts to learn from this task
- **Soft delete with a restriction filter** ([`Entry`](../../../backend/src/main/java/com/memoirist/entry/Entry.java)): `@SQLRestriction("deleted_at IS NULL")` makes every JPQL query, derived query and load by id skip deleted rows. The upside is that nobody can forget the filter; the cost is that the one feature that needs the deleted rows (this one) cannot use the repository the usual way and goes native.
- **`SELECT ... FOR NO KEY UPDATE`** ([`EntryRepository.java:341`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L341)): a row lock that is held until the transaction ends. In Postgres' default `READ COMMITTED`, a waiting statement re-evaluates its `WHERE` against the row's new version when the lock is released, which is why the second of two requests finds nothing instead of acting on stale data. `FOR NO KEY UPDATE` is the weaker form: it does not block the key-share locks that foreign-key checks take, and it is what Postgres itself takes for an ordinary `UPDATE`. The mistake people make is reading, checking in Java, then writing, with nothing to stop another request in between.
- **`SKIP LOCKED`** ([`:388`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L388)): "give me the row only if nobody holds it, and don't wait". It is the standard way to build a work queue in SQL, and the right tool for a job that can leave a busy row to its next run.
- **`TransactionTemplate`** ([`RecentlyDeletedSweeper.java:89`](../../../backend/src/main/java/com/memoirist/entry/RecentlyDeletedSweeper.java#L89)): programmatic transactions. `@Transactional` works through a proxy, so a call from one method of a class to another method of the same class skips it. When the transaction boundary is inside a loop, or inside the class, use the template.
- **A scheduled job as a trigger** ([`RecentlyDeletedSweepJob.java`](../../../backend/src/main/java/com/memoirist/entry/RecentlyDeletedSweepJob.java)): `@Scheduled` needs `@EnableScheduling` (without it the annotation is silently ignored). Put no logic in the job: the work is a service method, so a test, a different trigger or a second instance can call it. `cron = "${property:default}"` reads the schedule from configuration, and `-` is Spring's disabled value.
- **`EntityManager.detach`** ([`EntryListService.java:135`](../../../backend/src/main/java/com/memoirist/entry/EntryListService.java#L135)): takes an entity out of the persistence context. Here it keeps Hibernate's batch loader from fetching a Loot Drop's children. The mistake: detach, then touch a lazy field of the detached entity, and get `LazyInitializationException`. The mapper's sealed branch reads only the entry's own columns.
- **`@BatchSize` and collection statistics** ([`RecentlyDeletedQueryCountTest.java:128`](../../../backend/src/test/java/com/memoirist/entry/RecentlyDeletedQueryCountTest.java#L128)): lazy collections are loaded in groups of up to 50 for every uninitialised owner in the session, not just the one being read. `Statistics#getCollectionStatistics(role).getLoadCount()` counts collections loaded; `getPrepareStatementCount()` counts statements. They answer different questions.
- **Native queries and paging** ([`:357`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L357)): Spring Data adds `LIMIT/OFFSET` to a native query for a `Pageable` but cannot derive a count query from native SQL, so give a `countQuery`. It skips the count for a page that is not full.
- **Testing a race without flakiness** ([`RecentlyDeletedApiTest.atTheSameTime`](../../../backend/src/test/java/com/memoirist/entry/RecentlyDeletedApiTest.java#L123)): release all callers together and assert on the outcome that must hold whichever wins (one `200`, the rest `404`, one version bump), never on who wins. For "the sweep must not wait" use `CompletableFuture...orTimeout(...)` so a bug fails the test instead of hanging it.
- **Idempotent batch work**: `sweep()` returns the number it did, does nothing when nothing is due, re-checks each item under a lock and treats failure per item. Run it twice, or twice at once, and the result is the same.

## 12. At work
Recently deleted is a **soft delete with a retention window and a purge job**, which is what most regulated systems have somewhere: a customer record flagged for deletion, a hold period, then a purge that removes the data and the documents. Where you would meet the same problems in a bank's Spring Boot code:
- **Retention and purge jobs.** Mind the same things a reviewer there would: the purge must be idempotent and safe to run on two instances; it should work in small transactions, not one for the whole table; a failure on one record must not block the rest and must be visible; files and rows must go together (the row delete commits first, the file delete runs after the commit, so a rollback never loses a file and a failed file delete never leaves a row pointing at nothing). On a cluster you would add a lock around the schedule itself (ShedLock or the database's `SKIP LOCKED`) so only one node starts it; here the per-row `SKIP LOCKED` already makes an overlap harmless.
- **Pessimistic versus optimistic locking.** Optimistic (`@Version`) suits users editing the same record over time, where a conflict is rare and a `409` is a fair answer. For "one winner among simultaneous requests for a state change" (confirm, cancel, restore, erase) a short row lock with a re-check is simpler and gives exact answers.
- **The edge of a rule.** "More than 30 days" versus "at least 30 days" is a real question in audit and retention; write it down and test both sides of it.
- **What goes in a log.** The id and the class of the failure, never the exception message or the payload, because a database message can carry personal data. A reviewer will check logs for exactly this.
- **A scheduled job should be a thin trigger** over a service method you can test and call from an operations endpoint or a runbook, and its schedule should come from configuration with an off switch, so tests and non-production environments do not run it.
- **Counting what you ran.** The test that fixes the number of statements (a page costs 3 whatever it holds) is the cheapest guard against an N+1 creeping into a list a year later.
