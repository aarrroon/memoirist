# Task 3.3: Eras CRUD

> **Sprint:** 3 · **Commit:** `Sprint 3.3: Add the Eras endpoints` · **Status:** done, reviewed (every Done-when item is met, and `./gradlew build` passes with 468 tests; the spec review is in §9) · **Time taken:** roughly 37 minutes by the machine clock (03:49 to 04:26 on 2026-10-31), including a break-it run, a manual run of the app, two full builds and this entry
> **Built:** the five `/api/v1/eras` operations. An Era is only its dates (D-22), so creating one, changing its dates or deleting one writes a single row; the weeks an Era "holds" are found by date whenever it is read. `GET /eras/{id}` lists the weeks its dates overlap, each with the number of its entries that fall inside the Era's dates (sealed entries and Recently deleted entries are never counted). `WeekEras` is the Java half of the same date rule, ready for the week endpoints of task 3.7. 109 new tests cover it.

## 1. The goal
[Task 3.3](../../SPRINT_PLAN.md#sprint-3-phase-1-api) is the second endpoint family and the first one with a resource id in the path, so it is where ownership (`404` for someone else's id) and the client-supplied `id` rule (D-12) first run over real HTTP. Its block says:
- **Read:** D-22, API_CONTRACT §Eras.
- **Done when:** every row of §Eras works and is tested (soundtracks in 3.14, covers in 3.15), including: another user's Era is `404`; deleting an Era leaves its weeks, their entries and its other Eras untouched; a new Era holds the existing weeks its dates overlap; changing its dates changes which weeks it holds; `GET /eras/{id}` counts only the entries inside its dates (a Saturday-to-Sunday Era doesn't count the rest of the week), and never sealed or Recently deleted entries; a week's `eras` list puts pinned Eras first, then the latest start.

Why now:

| Why now | What it gives the next tasks |
|---|---|
| Task 3.2 made `UserService.currentUser()`, the "user must exist" rule for creates | This is the first create that uses it. It is also the pattern Templates (3.4) and Entries (3.5) copy: user check, optional client `id`, `201` or `200`, scoped lookups, a hand-written mapper |
| The Era rule (D-22) is date arithmetic with no tables | The week endpoints (3.7) need "a week's Eras" and the Era covers (3.15) need an Era to attach to. `WeekEras` is built and tested here so 3.7 only has to call it |
| The count behind an Era's page needs the seal rule (D-10) and Recently deleted (D-30) in a query | It is the first query that must leave sealed entries out *in the query itself*. The entry list (3.9) and tag counts (3.8) will copy how this one does it |

## 3. The plan
1. **Contract first.** Write the behaviour notes under §Eras in `API_CONTRACT.md` (defaults, limits, order, what the weeks list holds), because the API rule says the contract changes before or with the code.
2. **The date rule, as small pieces that need no database:** `EraDates`, `@ValidEraDates` and its validator, the two request records, `CreateResult`. These are the decisions, so they come before the wiring.
3. **The two queries that carry D-22:** `WeeklyLogRepository.findOverlapping` (the weeks of one Era) and `EntryRepository.countOpenEntriesByWeek` (the counted entries). Then `WeekEras` (the Eras of one week), which says the same rule in Java.
4. **Service, mapper, controller.** The service is where ownership, the client `id` and the user check live; the controller only turns `CreateResult` into `201` or `200`.
5. **Tests in four layers:** unit (the rule table, the validator), repository (the count query's edges), an exhaustive SQL-versus-Java agreement test, and HTTP (every row of the contract plus the D-22 behaviours).
6. **Run them, fix, then break the code on purpose** to see the tests fail.
7. **Run the real app** against Compose and call it with `curl`.
8. **Docs** (`TECH_STACK`, `DEVELOPMENT`), the **full build**, then this entry.

## 6. How it was tested
- **Strategy:** four layers, because there are four kinds of claim.
  1. **The rule and the body, no Spring** (milliseconds): `WeekErasTest` (the overlap table and the order) and `EraRequestValidationTest` (a real Jakarta `Validator`, run on both request records).
  2. **One query's edges against Postgres** (`EntryCountByWeekTest`): the clock is handed in, so a Loot Drop's opening moment is tested to the microsecond.
  3. **Two copies of one rule** (`EraWeekAgreementTest`): SQL against Java on 462 date pairs.
  4. **The wiring, over real HTTP and Postgres** (`EraEndpointTest`, `EraWeeksTest`): status codes, exact JSON keys, `fieldErrors`, database rows, the SQL run, the OpenAPI description.
- Every HTTP test makes its own users and deletes them (decision 20). Weeks and entries are saved through the repositories and removed by the cascade.

## 10. Concepts to learn from this task
- **Class-level Jakarta constraint that reports on a field** ([`ValidEraDates.java`](../../../backend/src/main/java/com/memoirist/era/ValidEraDates.java), [`EraDatesValidator.java:35-57`](../../../backend/src/main/java/com/memoirist/era/EraDatesValidator.java#L35-L57)): a constraint on the *type* can compare fields, but its violation belongs to no field unless you say so. `context.disableDefaultConstraintViolation()` drops the type-level one; `buildConstraintViolationWithTemplate(msg).addPropertyNode("endDate").addConstraintViolation()` adds one on a property. Spring turns that into a `FieldError`, which the advice puts in `fieldErrors`. The mistake: forgetting to disable the default, so the client gets the generic message too.
- **A record that implements an interface** ([`EraCreateRequest.java:27-32`](../../../backend/src/main/java/com/memoirist/era/dto/EraCreateRequest.java#L27-L32), [`EraDates.java`](../../../backend/src/main/java/com/memoirist/era/EraDates.java)): record accessors (`startDate()`) satisfy an interface method of the same name, so two records can share one validator with no glue.
- **Inclusive interval overlap** ([`WeekEras.java:34-39`](../../../backend/src/main/java/com/memoirist/week/WeekEras.java#L34-L39)): two periods overlap when each starts on or before the other ends. Written as `!a.start.isAfter(b.end) && !a.end.isBefore(b.start)`, with `null` end meaning "no end". The mistakes: `<` where `<=` is meant (an Era ending on a Monday), and forgetting the `null`.
- **Comparator composition** ([`Era.java:24-27`](../../../backend/src/main/java/com/memoirist/era/Era.java#L24-L27), [`WeekEras.java:30-31`](../../../backend/src/main/java/com/memoirist/week/WeekEras.java#L30-L31)): `comparing(key).thenComparing(...)`; `.reversed()` flips only what came before it, so it goes right after the first key; `comparing(key, Comparator.reverseOrder())` flips one key; `nullsLast(...)` wraps a key that may be `null`. Booleans sort `false` before `true`, so "true first" needs `reverseOrder()`.
- **HQL constructor expression with `GROUP BY`** ([`EntryRepository.java:46-59`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L46-L59)): `select new com.memoirist.entry.EntryCountByWeek(e.weeklyLogId, count(e))` builds a record from each row, with no entity loaded. The class name must be fully qualified. `count(...)` is a `Long`, so the record component is `long`.
- **Untyped null parameters** ([`WeeklyLogRepository.java:36`](../../../backend/src/main/java/com/memoirist/week/WeeklyLogRepository.java#L36)): Postgres needs a type for every `$n`. In `$3 is null or col <= $3` the first use gives none. `cast(:to as LocalDate)` gives it one. Seen in many drivers as "could not determine data type of parameter".
- **`@SQLRestriction` and aggregate queries** ([`Entry.java`](../../../backend/src/main/java/com/memoirist/entry/Entry.java)): the filter is added to every HQL query with `Entry` as a root, including `count` with `group by`. A native query would not get it. `EraWeeksTest` proves it for this one.
- **`saveAndFlush` and generated columns** ([`EraRepository.java:18`](../../../backend/src/main/java/com/memoirist/era/EraRepository.java#L18)): `@CreationTimestamp` / `@UpdateTimestamp` are filled in when the SQL runs, not when `save` is called. Build a response from the entity before the flush and you send `null`. The mistake: assuming `save` writes.
- **`201` versus `200` from one `POST`** ([`CreateResult.java`](../../../backend/src/main/java/com/memoirist/common/CreateResult.java), [`EraController.java:56-60`](../../../backend/src/main/java/com/memoirist/era/EraController.java#L56-L60)): `ResponseEntity.status(...).body(...)` lets a controller choose the status at run time; the service says which one by returning a small record.
- **Idempotent create** (D-12, [`EraService.java:68-88`](../../../backend/src/main/java/com/memoirist/era/EraService.java#L68-L88)): a client retries a request it isn't sure arrived; the server must answer the same thing, not make a second row or fail. The check is "do I have this id for this user", then "does anyone", then insert. It is not safe against two *simultaneous* first attempts (§9).
- **`instance` in RFC 9457** (§8, item 5): a problem body carries the request path, so anything in the path comes back. That is the standard, and why the contract promises silence only for `detail` and `fieldErrors`.
- **`@ParameterizedTest` + `@CsvSource` as a boundary table** ([`WeekErasTest.java`](../../../backend/src/test/java/com/memoirist/week/WeekErasTest.java)): one row per edge with a comment saying which edge. A new edge is a new row, and the name of each run (`Era "…" to "…": holds the week = "true"`) is the report.
- **An exhaustive agreement test** ([`EraWeekAgreementTest.java`](../../../backend/src/test/java/com/memoirist/week/EraWeekAgreementTest.java)): when one rule is written twice, run both on a grid of inputs and compare. It finds the edge nobody wrote a case for.
- **Counting queries with `SqlLog`** ([`EraWeeksTest.java:381`](../../../backend/src/test/java/com/memoirist/era/EraWeeksTest.java#L381)): "the same number of SELECTs for 1 week as for 8 weeks and 56 entries" is the test for "no N+1", and it needs only the statement list, not a profiler.

## 12. At work
- **Effective dating and overlap are everywhere in banking.** Rates, fees, mandates and account holds have a "valid from" and an optional "valid to". The review questions are the ones in `WeekEras.holds`: are both ends inclusive, what does a missing end mean, and are the SQL and Java versions the same rule? A test that asks both on a grid, like `EraWeekAgreementTest`, is a cheap way to answer the third.
- **Derive, don't store, when the rule is a function of dates.** Because no table says which Era holds which week, there is nothing to migrate or repair when a user edits an Era. The cost is that every read does a small query. Reviewers look for the opposite mistake: a link table that drifts from the dates it was built from.
- **Counts that must not leak.** `entryCount` over sealed entries would tell someone how many sealed items exist. In an enterprise codebase the same shape is a dashboard total that includes items the viewer may not see. The review check is whether the permission rule is *in the query* (as here) or in code that runs afterwards and can be skipped.
- **Idempotent creates** are how payment and booking APIs survive retries: the client sends a key, the server returns the same result for the same key. Know the three answers (created, replayed, conflict) and the race that remains unless the database's unique key is the final arbiter.
- **A `404` for someone else's id** is the same instinct as returning "not found" instead of "forbidden" for an account number you don't own: don't confirm that it exists. The test that sends a second user's id on every verb is the one to ask for in a pull request.
- **Cross-field validation** (settlement date not before trade date, end of a term after its start) belongs next to the fields as a constraint, so the client gets every error in one response. The common bug is a message that only appears in `detail`, so the form can't point at a field.
- **Postgres wants a type for every parameter.** "Could not determine data type of parameter" appears the first time a nullable parameter is used as `:x is null`. Know the `cast` fix, because the tests with a non-null value will all pass.
- **Break it on purpose.** Three small mutations (§6) showed 12 tests fail. If you can remove a rule and nothing fails, the rule isn't tested.

<details><summary>Answers</summary>

1. Yes: an Era that ends on the Monday still has that day in it, so it holds the week. An Era that ended on the 25th (the Sunday before) does not. In Java it is `!era.getStartDate().isAfter(week.getEndDate())` and `era.getEndDate() == null || !era.getEndDate().isBefore(week.getStartDate())` (`WeekEras.holds`); in SQL it is `w.endDate >= :from and (… or w.startDate <= :to)` (`findOverlapping`). `EraWeekAgreementTest` runs both on 462 start and end pairs and fails if they differ.
2. The service runs one query for the Era, one for the overlapping weeks, and one grouped count by week; the counts are merged in memory. Nothing is loaded per week or per entry. It would grow if the mapper asked each week for its entries, or if the count were a query per week (N+1). `theQueryCountForOneEraDoesNotGrowWithTheNumberOfWeeksOrEntries` counts the SELECTs.
3. The count query filters `e.entryDate >= :from and … <= :to` with the Era's dates, so only Saturday and Sunday count. The week list comes from a different query (`findOverlapping`) that looks only at the week's dates, so the week is held and listed, and a week with no counted entries is simply absent from the count map and shows `0` (`getOrDefault`).
4. In the HQL itself: `(e.unlockDate is null or e.unlockDate <= :now)`. At exactly "now" the Loot Drop counts (sealed means the unlock date is *after* now). One microsecond later it doesn't (`aLootDropCountsFromTheMomentItOpensAndNotBefore`). Entries in Recently deleted are excluded by `@SQLRestriction`, not by that line.
5. `200` with the *stored* Era; nothing from the retry's body is applied and there is still one row. A different user gets `409 conflict` with the message "That id is already in use." and no data. The user-scoped lookup runs first, so `existsById` is only asked when the user doesn't have it; it reveals nothing but "taken". The race: two requests with the same new `id` at the same instant can both pass both lookups, and the second insert fails on the primary key and falls to the catch-all (`500`).
6. A service check runs only after bean validation passed, so a client with a blank title and a backwards range would see one problem, fix it and then see the other. A class-level constraint is part of the same validation pass, so every wrong field is reported together. Reporting on the `endDate` node (not just on the class) puts the message in `fieldErrors.endDate`, which a form can show next to the field.
7. Postgres could not tell the type of the third parameter in `$3 is null or … <= $3` when the value was `null` (an ongoing Era), because Hibernate sent an untyped null and the first use gives no type. With a real date every parameter has a type, so tests with only closed Eras pass. `cast(:to as LocalDate) is null` gives the parameter a type in every case.
8. Booleans sort `false` before `true`, so the natural order puts unpinned Eras first; `reverseOrder()` on that key puts pinned first. Two Eras with the same pin state and start date fall through to `Era.LATEST_START_FIRST`: newest created first, then by id, so the order never depends on how the database returned the rows.
