## 1. The goal
[Task 3.13](../../SPRINT_PLAN.md#sprint-3-phase-1-api) is the last task that changes what an `Entry` can say. Its block:
- **Do:** `birthday` on `GET` and `PATCH /users/me`; `replyToEntryId` on `POST` and `PUT /entries`; `replyToEntryId` and `replyIds` on `Entry`.
- **Done when:** (1) a reply can point only at the user's own Loot Drop that has opened; a sealed one or one that was never sealed is `400`, another user's is `404`; (2) `replyIds` lists an opened Loot Drop's replies; (3) deleting either entry leaves the other; (4) a birthday in the future is `400`; (5) a sealed reply is redacted like any entry.

Why now: everything it needs already exists. The columns (`users.birthday`, `entries.reply_to_entry_id` with `ON DELETE SET NULL`, the partial index `idx_entries_reply_to`) came in V1 (task 2.3), `Entry.replyToEntryId` and `User.birthday` were mapped in 2.4, the seal rule is in 3.5, Recently deleted is in 3.11. The mapper has said "replies arrive in 3.13" and returned `List.of()` since 3.5. After this, 3.14 (soundtracks) is the last piece of the `Entry` shape, and the UI tasks can build the "reply to past you" button (D-33) and the *next birthday* unlock suggestion.

What the docs **didn't** settle (each one is an assumption in the report):
- Whether `PATCH` `"birthday": null` clears or leaves alone. The contract says "date or null", so null clears and a missing field leaves alone. That is the only three-state field in the API.
- A lower bound for a birthday. Only "after today" was specified; Postgres `DATE` accepts years the app should not, so I used the same 1900-01-01 floor as entries.
- What a reply to a sealed reply, a self-reply, or a loop does. Self-reply is `400`; longer loops are allowed and documented.
- Whether a still-sealed reply appears in the Loot Drop's `replyIds`. D-10 says sealed entries stay out of every list that is not a locked row, so it does not, until it opens.
- What the link does when the Loot Drop goes to Recently deleted (it stays) or is erased (it becomes `null`, by the foreign key).

|---|---|---|---|---|

A `JsonNode` loses bean validation and the date parsing rules. A mutable class breaks "DTOs are records". | One extra small type, and a `@Schema` annotation so OpenAPI shows a date and not an object. |
| Birthday range | After today only; **not after today and not before 1900-01-01** | Both | A year like 0001 would reach Postgres and fail as a `500`. Entries already use 1900-01-01 (D-09). | A person born before 1900 cannot enter a birthday. Nobody is. |
| Which "today" for the birthday | The server's; the user's current zone; **the zone the user will have after this request** | The new zone | A body that moves the zone and sets a birthday together is judged by the zone the user is about to live in. | The check runs before any field is changed, so a bad birthday saves nothing (not even the name). |
| Which statuses for a bad reply target | All `400`; all `404`; **split by whose entry it is** | Not the user's / missing / deleted: `404`. | How to read the replies of a Loot Drop | A repository query `findRepliesOf(ids)` and a new mapper signature; **a lazy read-only `@OneToMany` with `@BatchSize(50)`** | `Entry.replies` ([`Entry.java:170`](../../../backend/src/main/java/com/memoirist/entry/Entry.java#L170)) | The mapper's signature `toResponse(entry, now)` stays, `@SQLRestriction` hides deleted replies for free, and Hibernate loads 50 lists in one query (the same trick as `media` and `tags`). | A self-referencing `@OneToMany` over a column that is also a plain field needs `insertable = false, updatable = false` or Hibernate would write it twice. |
| Prefetch the replies like media and tags (`left join fetch`) | Add `fetchRepliesOfOpenLootDrops` to the feed; **rely on the batch** | The batch | `EntryReplyQueryCountTest` shows the cost is already "+1 statement for a page that holds an opened Loot Drop", whatever it holds. A prefetch would add code to save nothing. | One more statement on a page with an opened Loot Drop. |
| Sealed replies in the target's `replyIds` | Show every reply; **hide the ones still sealed** | Hide | D-10: a sealed entry is out of every list but a locked row. Its id would also tell the reader that a reply exists. | The list grows when the reply opens, not when it is written. The client can already see the locked row on the timeline. |
| Lock on the reply target | None; `FOR UPDATE` (PESSIMISTIC_WRITE); **`FOR SHARE` (PESSIMISTIC_READ)** | `FOR SHARE` ([`EntryRepository.java:67`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L67)) | Without a lock, an *empty* Loot Drop (which `DELETE` erases at once) can disappear between the check and the insert, and the foreign key then fails as a `500`. `FOR SHARE` lets any number of replies look at the same target together, while the delete's `FOR NO KEY UPDATE` waits. | `PUT` and the link | Always check the target; **check only when it changes** | Only when it changes | The same rule as `templateId`: a reply must stay editable after its Loot Drop was sealed again or deleted. | A stale link can sit on an entry. It is harmless: the reply shows the id and the client gets `404` if it follows it. |
| `PUT` with the field left out | Leave the link alone; **clear it** | Clear it | The contract says `PUT` is a full replace, and it is the rule for `templateId`, `title` and `contentJson`. | A client that forgets the field unlinks the reply. (The same trade-off as 3.5.) |
| Preventing loops (A answers B, B answers A) | Walk the chain on every write; **refuse only self-reply** | Self-reply only | Both entries would have to be opened Loot Drops, so a loop needs a deliberate effort; a walk costs a query per hop on every write. | A client that follows links must stop at an id it has already seen. ## 8. What went wrong
1. **`Optional<LocalDate>` could not tell missing from `null`** (second sitting). I wrote `UserUpdateRequestJsonTest.aMissingBirthdayIsJavaNull` first and it failed: `expected: null but was: Optional.empty`. In Jackson 3 a record component of type `Optional` that is absent from the body is `Optional.empty()`, the same as `"birthday": null`. (`.claude/rules/backend.md` also says `Optional` is for return types only, so I was twice wrong.) I kept the test as `anOptionalCannotTellMissingFromNullSoItIsNotUsed`, then built `BirthdayChange` (last sitting).
2. **Asserting a bare number is a bad date** (last sitting): `{"birthday":12}` was accepted. Jackson reads an integer as a day count since 1970 (1970-01-13), for every date in the API, entry dates included. I did not change that (it is the whole API's behaviour, and the contract now says so); the test sends `true` instead.
3. **The race test could not detect a missing lock.** I wrote `repliesWrittenAtTheSameTimeAsTheDeleteOfAnEmptyLootDrop...` first, removed `@Lock` and ran it three times: it passed every time. The window is milliseconds. It stays as a smoke test with a comment saying so.
4. **The first version of the lock test failed *with* the lock in place.** It opened a transaction, took the lock, and then called `jdbc.sql("... FOR NO KEY UPDATE NOWAIT")` from the same thread: no error. The JPA transaction manager shares its connection with the thread, so `jdbc` joined the same transaction, and a lock never blocks its own holder. The fix is a second `TransactionTemplate` with `PROPAGATION_REQUIRES_NEW`, which gets its own connection (the helper `lockWith` explains it). The test now fails when `@Lock` is removed.
5. **Three older tests broke**, as I expected from the notes: two mass-assignment tests (`EntryEndpointTest`, `EntryUpdateTest`) sent a random `replyToEntryId` to show it was ignored; it is now an editable field and a random id is `404`. I removed it from those bodies (as 3.8 did for `tagIds`). `FeedQueryCountTest` expected 5 statements for a page with an opened Loot Drop and now sees 6 (the replies). Updated with the reason in the assertion.
6. **My query-count test sealed too late.** `EntryReplyQueryCountTest` returned `400 unlockDate must be in the future` because the helper for the second user ran after the first had moved the clock to after the unlock date. Fixed by resetting the clock at the top of the helper.
7. **Test expectations of mine were wrong twice:** `problemType()` returns the suffix (`not-found`), not `urn:memoirist:problem:not-found`; and an unreadable uuid is `malformed-request`, not `validation-failed`. Test code, not product code.
8. **Interrupted sittings.** The first and second sittings were cut off after the user side's design; the notes carried the dead end (item 1) across. The clock times in the builder's running notes were guesses; `date` is the reference.
9. **Close-out fix pass.** Two review findings were fixed in this journal only: the mapper link in section 5 item 9 now points at line 168, and the sitting count and times were corrected. No code changed, so the build was not re-run; the 1431-test green build is the builder's. Nothing failed in this pass.

## 10. Concepts to learn from this task
- **Tri-state PATCH field** ([`BirthdayChange.java:56`](../../../backend/src/main/java/com/memoirist/user/dto/BirthdayChange.java#L56)): "not mentioned", "explicitly null" and "a value" are three different requests. A custom Jackson 3 `ValueDeserializer` separates them with `getAbsentValue()` and `getNullValue()`. The usual mistake is to use `Optional` or a plain field and silently treat "remove" as "ignore".
- **Read-only collection on a foreign-key column** ([`Entry.java:170`](../../../backend/src/main/java/com/memoirist/entry/Entry.java#L170)): `@OneToMany @JoinColumn(insertable = false, updatable = false)` reads the "children" without owning the column. The mistake is leaving the flags off: Hibernate then also tries to write the column from the collection side.
- **`@SQLRestriction` applies to collections too**: a reply in Recently deleted is not in `Entry.replies` without any code, and it comes back on restore. Know what your global filters touch.
- **`@BatchSize` as the cheap fix for N+1**: Hibernate loads the lazy lists of up to 50 entries in one `IN (...)` query. `EntryReplyQueryCountTest` is the guard that notices if it stops.
- **Pessimistic locks by mode** ([`EntryRepository.java:67`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L67)): `PESSIMISTIC_READ` is `FOR SHARE` (many readers, no writers), `PESSIMISTIC_WRITE` is `FOR NO KEY UPDATE` here (one at a time). Use the weakest lock that closes the race.
- **Testing a lock with `NOWAIT`** ([`EntryReplyLockTest.java:60`](../../../backend/src/test/java/com/memoirist/entry/EntryReplyLockTest.java#L60)): `NOWAIT` turns "would block" into an immediate error you can assert. The second attempt must come from a different connection (`REQUIRES_NEW`). Always break the code once to see the test fail.
- **Same answer for different failures** (`requireReplyTarget`): foreign, missing and deleted are one `404`; sealed and never-sealed are one `400`. If two failures need to be indistinguishable, give them one message.
- **Validate on change only** (`replyChanged` in `update`): a rule that depends on the current state of another record (is that Loot Drop still open?) must not block edits that do not touch the link.
- **Redaction as an allow-list**: the sealed branch of the mapper names every field it shows; `replyIds` and `replyToEntryId` are `List.of()` and `null` there. Adding a field to the record would not compile until both branches are decided.

## 12. At work
Three things here show up in any bank codebase:
- **"Optional field in a PATCH" is a real API design problem.** Account-update endpoints that use `null` to mean both "clear" and "don't touch" cause silent data loss. A reviewer will ask: what does the client send to remove a value, and is there a test for it? JSON Merge Patch (RFC 7396) is the standard answer; here the single field gets its own type because adding a library needs approval.
- **Referenced ids in a request body are an authorisation hole if unchecked.** `replyToEntryId` is the same as a payee id or an account id on a transfer: check that it belongs to the caller, and answer with the same `404` whether it is missing or someone else's. Then decide separately what a state problem on the caller's own record (sealed, never sealed) should say. A reviewer looks for the check, the status, and that nothing in the error repeats the id.
- **Check-then-insert needs a lock or a constraint.** The foreign key stops a dangling row, but only as a `500`. Taking a `FOR SHARE` lock on the parent makes concurrent creates cheap and makes the delete wait. In payments code this is the "lock the account, then post the entry" pattern. A reviewer asks how you know the lock works: a `NOWAIT` test that fails without it is a good answer, and "I ran it in a loop and it passed" is not.

<details><summary>Answers</summary>

1. In Jackson 3 a missing record component of type `Optional` is `Optional.empty()`, the same value as an explicit `null`, so "leave alone" and "remove" cannot be told apart. The custom `ValueDeserializer` returns `REMOVE` from `getNullValue()` for an explicit JSON `null`, and its `getAbsentValue()` returns Java `null` so a missing field stays "no change".
2. The foreign one is `404 not-found`, identical to a random id, so you cannot discover other users' entries. The own sealed one is `400 validation-failed` (`fieldErrors.replyToEntryId`), because it is the user's own entry and the problem is its state; it has the same message as a never-sealed one so those two cannot be told apart. `403` would confirm the entry exists.
3. The target's state can change after the reply was written (the Loot Drop may be sealed again, or deleted). If every `PUT` re-checked, the user could no longer fix a typo in the reply. Only a changed link is a new claim that needs checking. It is the same rule as `templateId`.
4. `FOR SHARE` lets many holders in at once and only conflicts with the delete's `FOR NO KEY UPDATE`, so the eight replies do not wait for each other (`twoRepliesCanLookAt...` and `severalRepliesToTheSameLootDrop...`). `FOR UPDATE` would make them queue one after another.
5. The JPA transaction manager binds its connection to the thread, and `JdbcClient` uses that same connection inside the transaction. A lock never blocks the transaction that holds it, so `NOWAIT` succeeded. A `REQUIRES_NEW` template gets a second connection, which is what a different request would have.
6. The Loot Drop's `replyIds` leaves it out (D-10) until the unlock instant. The reply's own `GET` is redacted: `isLocked: true`, `replyToEntryId: null`, `replyIds: []`.
7. After the delete (soft, `deleted_at` set): still the Loot Drop's id, because the link waits and comes back on restore. After the erase: `null`, because the foreign key is `ON DELETE SET NULL`.
8. One more statement. `EntryMapper.replyIdsOf` asks nothing of entries without an unlock date, and for the opened Loot Drops Hibernate loads `Entry.replies` for up to 50 entries in one `IN (...)` query, thanks to `@BatchSize(50)` (`EntryReplyQueryCountTest`).
