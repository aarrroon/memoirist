**What the docs didn't settle** (each is a decision in §4):
- How to find "the same day in any year" in SQL without an index on it, and whether that is acceptable.
- How to say 29 February without breaking either leap years or `LocalDate`.
- Where "today" comes from, since the zone is on the user and a user can be missing.
- Whether an unknown-date entry (D-34) belongs on the strip.
- What order the rows come in when several share a day, and whether "at most 20" can be changed.

## 8. What went wrong
In order:
1. **Two leap-year tests failed with `400` instead of `201`** (first run, 51 tests, 2 failed). Both made an entry dated 2027-02-28 *before* moving the clock from 2026-10-31, so `POST /entries` correctly refused a date in the future. The code was right; the order of the test's steps was wrong. Fix: `clockAt(...)` first, then create the entries. The lesson is the same as 3.10's: with a movable clock, the test setup is a timeline.
2. **The `EXPLAIN` test failed on a wrong guess about the plan.** I asserted `Index Scan using idx_entries_user_date`. Postgres chose `Bitmap Heap Scan` over `Bitmap Index Scan on idx_entries_user_date`, because it cannot see through `extract()` and expects one row, so a bitmap scan looks cheapest. The query is still served by the same index and reads only Alice's rows (3,348 index entries, 3,339 removed by the filter, 9 returned, about 2 ms), so the assertion became "either kind of index scan on that index, no `Seq Scan`, and no more rows thrown away than the user has".
3. **A sentence in my own contract text was wrong.** It said the query stops "after 20 matches". A daily writer has at most one entry per year on a given day, so reaching 20 matches takes 20 years; for a normal user the query reads all their earlier entries. The measurement in item 2 showed it; the contract now says what is true and TECH_STACK carries the numbers.
4. **Dead ends in the break-it script.** The first draft of the "no id tie-break" mutation had a leftover multi-line `sed` that matched nothing (harmless, removed), and the seventh bug I first thought of (the comparison reversed to `>=`) is less useful than `<=` becoming `<`, which pins the unlock instant. Both were fixed before running.
5. **Clock labels in my running notes were guesses** ("07:10", "07:25" written when `date` said 07:03). Every time in this entry comes from `date`. The task brief also says today is 31 October; the machine clock said Sunday 1 November in Melbourne by the time of the live run, so the live entries were dated 1 November. The tests are unaffected: they use the fixed clock.
6. **The background `bootRun` was started with both `&` and `run_in_background`,** so the tool reported it "completed" at once while the app kept running (it was found by port and stopped with `taskkill`). Nothing was left running.
7. **Close-out fix pass.** Fixed review findings 1 and 3 (comments only). My first attempt to reflow the index-test comment with a script failed (the text did not match, because Spotless had split the sentence at a different place than I assumed), so it was done with `sed` by line number. Final check: `spotlessApply`, `spotlessCheck` and `OnThisDayIndexTest` pass. The full 1375-test build ran once during the fix pass (5m 17s, green) before the last comment-only edit.

## 10. Concepts to learn from this task
- **HQL `extract(field from x)`** ([`EntryRepository.java:280`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L280)): the JPA-standard way to take the month or day out of a date in a query; `month(x)` and `day(x)` are shorthand. It returns an `Integer`, and `in :days` takes a collection parameter. The catch is that Postgres cannot use a plain index for the result, which is why the plan is a filter on top of an index range, not an index lookup.
- **Collection parameters and `Limit`** ([`EntryRepository.java:286`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L286)): `@Param("days") Collection<Integer>` binds to `in :days`; `Limit` (Spring Data 3.2 and later) becomes `fetch first ? rows only`. Mistake: an empty collection in an `IN` list is refused by some databases, so pass at least one value (`OnThisDay` always does).
- **`java.time` leap-year handling** ([`OnThisDay.java:36`](../../../backend/src/main/java/com/memoirist/entry/OnThisDay.java#L36)): `LocalDate.isLeapYear()` knows the century rule, `withDayOfYear(1)` is the start of the year, `getMonth()` is an enum (`Month.FEBRUARY`). Avoid `LocalDate.of(year, 2, 29)` (throws in a common year) and `MonthDay.atYear` (silently returns 28 February). Both were run to check.
- **Convert an `Instant` to the user's calendar day** ([`EntryListService.java:146`](../../../backend/src/main/java/com/memoirist/entry/EntryListService.java#L146)): `instant.atZone(zone).toLocalDate()`. Read the clock once and derive everything from that one `Instant`. Mistake: calling `LocalDate.now()` (the JVM's zone) or reading `Clock` twice.
- **A record as a rule's answer** ([`OnThisDay.java:23`](../../../backend/src/main/java/com/memoirist/entry/OnThisDay.java#L23)): `Lookup` bundles three values that belong together and costs one line. The class is `final` with a private constructor, because it is only static functions.
- **Omit versus redact:** the timeline shows a sealed entry as a locked row, because the user needs to know it exists; this strip omits it, because *where it appears* would be the hint. Which one is right depends on whether the position or the existence of the row tells you something.
- **`Optional` as the end of a lookup** ([`EntryListService.java:141`](../../../backend/src/main/java/com/memoirist/entry/EntryListService.java#L141)): `findById` returns `Optional`, `isEmpty()` then `get()` after the guard. The alternative (`orElseThrow`) is a `404`, which the contract reserves for creates.
- **Reading an `EXPLAIN (ANALYZE)` plan** ([`OnThisDayIndexTest.java`](../../../backend/src/test/java/com/memoirist/entry/OnThisDayIndexTest.java#L59)): `Bitmap Index Scan` finds row positions from the index, `Bitmap Heap Scan` reads those rows and applies `Filter`, and `Rows Removed by Filter` is the work the filter threw away. Estimates (`rows=1`) can be far from the actual (`rows=9`) when the planner cannot see through a function.
- **Test the clock as a timeline** ([`OnThisDayEndpointTest.java:136`](../../../backend/src/test/java/com/memoirist/entry/OnThisDayEndpointTest.java#L136)): create entries at the time they are legal, then move the clock, then read. The date validation uses the same clock, so the order of the steps matters (§8, item 1).
- **A test JVM pinned to UTC** (`build.gradle.kts`, `systemProperty("user.timezone", "UTC")`): it makes "the server's zone" wrong on purpose, so a user in Melbourne or Los Angeles can tell it apart from their own.

## 12. At work
Where you would meet this at a bank:
- **Dates and zones.** "Today" for a customer, a branch or a batch is almost never the server's day: cut-off times, statement dates and "same day last year" comparisons all need a stated zone, one clock reading and a test at the boundary (23:59:59 and 00:00:00, a daylight-saving change, New Year). A reviewer should reject `LocalDate.now()`, `new Date()` and `LocalDateTime` in business code and ask where the zone comes from.
- **Calendar rules in one place.** Month-end, leap day and anniversary rules (an account opened on 29 February, a payment due on the 31st) are the classic source of off-by-one bugs. Write the rule as a small pure function with a table of dates beside it, as `OnThisDay` and its test do, and have the query or the batch call it.
- **Omit or mask.** The same decision appears with account numbers, flagged customers and restricted records: a locked row says "this exists", an omitted row says nothing. Reviewers look for the place where a list quietly leaks existence through a count, an order or an empty slot.
- **Filtering in the query, not after.** Filtering secrets out in Java after loading them is a leak waiting for the next change (a log line, a cache). Leave them out in the SQL, then test it with a mutation (remove the condition and watch the test fail).
- **Read the plan, don't guess it.** When a query's cost grows with data, put the real SQL through `EXPLAIN (ANALYZE)` and assert on the plan's shape in a test, with realistic data next to other tenants' data. The most common review comment on a new query is "which index does this use, and what does it read for the biggest customer?"

1. The zone that decides "today" is on the user (`users.timezone`, D-07), so the service looks the user up. A header naming nobody owns no entries, and the contract says every list for such a user is empty (`[]`, `200`); `404` is for creates, which would otherwise fail on a foreign key. That is why it uses `UserRepository.findById`, not `UserService.currentUser()`.
2. Three of the five: 2024-02-29, 2024-02-28 and 2020-02-29, in that order (newest `entry_date` first, so the 29th is above the 28th of the same year). 2024-03-01 is a different day, and 2027-02-28 is today, not an earlier year. On 28 February 2028 (a leap year) only 28 February entries match, so 2024-02-28 appears and 2024-02-29 does not; on 29 February 2028 only earlier 29 February entries match (2024-02-29 and 2020-02-29).
3. `MonthDay.atYear` returns 28 February in a common year, so a rule built on it would match the wrong entries without any error. `LocalDate.of(2027, 2, 29)` throws `DateTimeException`. `LocalDate.isLeapYear()` plus a list of days avoids both.
4. Melbourne is UTC+11 in October, so it is 01:00 on 31 October: the user sees the 31st. Los Angeles is UTC-7 (daylight time), so it is 07:00 on 30 October: the user sees the 30th. With the server's zone (UTC) both would see the 30th, so Melbourne's assertion fails. The test JVM is forced to UTC (`user.timezone`) so the server's zone is never the user's by accident.
5. At 21:59:59Z it is one second early: sealed, so not in the strip. At 22:00:00Z the entry is open (`EntrySeal`: sealed only while the unlock date is *after* now), so it is listed, whole. `aLootDropIsListedWholeFromTheInstantItUnlocks` shows both, and changing `<=` to `<` in the query makes it and `aDeletedLootDropIsNotListedEitherEvenOnceItHasOpened` fail.
6. The rows come from one query; their media from one `left join fetch` for the whole list, and their tags from another (never two collections in one fetch). With the user's lookup that is 4 for any size. When the query finds nothing there is nothing to fetch the children of, so the user lookup and the query are the only two; sealed Loot Drops are not returned, so their children are never read either.
7. The extra keys make the order total. Two entries from one day written in the same instant (a photo dump) would otherwise be free to swap between requests. `entry_date desc` alone already means newest year first because the month and day are equal, but not which of two entries on the same day comes first.
8. Postgres cannot see through `extract()` to estimate how many rows match, so it expects one and picks a bitmap scan of the user's index range. It reads only that user's entries from before this year (3,348 for ten daily years, about 2 ms) and filters on month and day. For a user with 50,000 entries, add a functional index on `(user_id, extract(month …), extract(day …))` in a new migration so the lookup reads the few rows that match.
