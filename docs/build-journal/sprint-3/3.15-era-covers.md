## 5. How it was built
1. **[`MediaRepository.java:48`](../../../backend/src/main/java/com/memoirist/media/MediaRepository.java#L48)** `findAndLockByIdAndEntryUserId`: a JPQL `select m from Media m join fetch m.entry e where m.id = :id and e.userId = :userId` with `@Lock(PESSIMISTIC_READ)`, so Postgres gets `... for share`. The join is what scopes it to the user *and* applies the entry's Recently deleted filter (the existing derived finder works the same way). The entry comes with it, so the seal check costs no second query. [`:59`](../../../backend/src/main/java/com/memoirist/media/MediaRepository.java#L59) `findAllWithEntryByIdInAndUserId` is the same without the lock, for a set of ids.
2. **[`EraCovers.java:55`](../../../backend/src/main/java/com/memoirist/era/EraCovers.java#L55)** `visible(eras, userId, now)`: collects the cover ids, runs one query, drops items whose entry `EntrySeal` calls sealed ([`:62`](../../../backend/src/main/java/com/memoirist/era/EraCovers.java#L62)), and builds the map Era id to `MediaResponse` through `MediaMapper`. Two Eras may use one photo, which is why it builds a map by *media id* first and looks each Era up in it. `of(era, …)` is the one-Era form. (Practice block.)

## 10. Concepts to learn from this task
- **Pessimistic read lock** (`MediaRepository.java:43`): `@Lock(LockModeType.PESSIMISTIC_READ)` on a query makes Hibernate append `FOR SHARE`. Many holders can share the row, but anything that wants to update or delete it waits. Use it when you check a row and then write something that points at it. Mistake: expecting it to work outside a transaction, where the lock is released at once.
- **Referential check plus `ON DELETE SET NULL`**: the database clears a pointer when its target goes, which is how "removing the photo clears the cover" needs no code. Mistake: also writing code that clears it, and then two things must agree.
- **`join fetch`** (`MediaRepository.java:45`): loads the entry in the same query, so the later `getEntry().getUnlockDate()` is free. Rule from `backend.md`: never fetch-join two collections; this is one single-valued association, which is fine.
- **Hibernate's `@SQLRestriction` applies to joins** (D-30): the join to `entries` silently drops media of deleted entries. The same fact was found the hard way in 3.11 (an erase that found no keys).
- **Decide at read time what you stored at write time**: the Era stores an id, and *whether to show it* is recomputed every time, because the world (seal, delete, restore) changes. Mistake: caching the decision in a column.
- **`Collectors.toMap`** (`EraCovers.java:63`): builds `Map<UUID, Media>`. It throws on a duplicate key, which is safe here (ids are unique); with data that can repeat you need a merge function.
- **Full-replace `PUT` semantics**: a missing field means "none". The test `putChangesTheCoverClearsItWhenLeftOut…` pins this down because it is the part clients get wrong.
- **Order of validation as a security decision** (`EraService.java:196`): checking the seal before the type keeps a sealed entry from leaking anything, even the kind of its files.

## 12. At work
- **Referenced ids in a request body** are the classic broken-access-control hole (OWASP "IDOR"): `accountId`, `documentId`, `beneficiaryId`. The habit is the same as `requireCover`: look it up *through the caller's own scope*, answer "not found" for foreign and missing alike, and never echo the id. A reviewer will look for a repository call that takes only an id.
- **Check-then-write races.** A payment that names a payee, a document that names a template: someone deletes the target between your check and your insert. The enterprise answers are a share lock (as here), a foreign key plus a catch, or optimistic versioning. Know which one the team chose and why; a `500` from a foreign-key violation is the symptom reviewers hate.
- **Derived visibility** (hidden while sealed, back when it opens) is the same shape as "masked until the case is released" or "hidden while under review": store the fact, recompute the visibility on every read, in one class, and test the transitions, not just the states.
- **N+1 on list endpoints** is a production incident waiting to happen; a statement-count test like `EraCoverQueryCountTest` is cheap and survives refactors that a code review misses.
- **Mutation-checking your own tests** (break the code on purpose, watch the test fail) is a ten-minute habit that finds tests that only look good.
