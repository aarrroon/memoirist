# Task 3.14: Soundtracks and Spotify search

> **Sprint:** 3 · **Commit:** `Sprint 3.14: Add soundtracks and Spotify search` (hash in the OVERNIGHT_REPORT) · **Status:** done (every Done-when item is met; `./gradlew build` passes with 1536 tests and no failures (1431 before this task, 105 new); the review is §9) · **Time taken:** roughly 30 minutes, in one sitting on 2026-11-05 from 14:01 (times from `date`; the clock labels in my running notes before 14:18 were guesses)
> **Built:** the `soundtrack` field (a checked Spotify URI) on entries, weeks and Eras, hidden while an entry is sealed; `POST /api/v1/music/search`, which logs in to Spotify as the app, reuses the token until a minute before it ends, searches, and returns at most 10 results; and a proof, at the most detailed log level, that the words searched for appear in no log line. No migration: the columns came in V1.

## 1. The goal
[Task 3.14](../../SPRINT_PLAN.md#sprint-3-phase-1-api) finishes the shape of `Entry`, `WeeklyLog` and `Era` (D-35). Its block:
- **Do:** `soundtrack` (a checked Spotify URI) on entries, weeks and Eras; a `SpotifyProperties` record and a `MusicSearchService` that gets an app-only token with the client credentials flow, reuses it until it expires, and calls Spotify's search; `POST /music/search`.
- **Done when**, with a stubbed Spotify (never the real one): (1) a malformed URI is `400`; (2) a sealed entry's soundtrack is hidden; (3) search returns at most 10 results; (4) missing settings, or a `429` from Spotify, return `503 music-search-unavailable`; (5) the token is fetched once and reused; (6) search terms appear in none of our URLs and in no log line, including `RestClient` request logging.

Why now: the columns exist since V1 (task 2.3, `soundtrack VARCHAR(100)` on three tables), the three entities have mapped the field since 2.4, the mapper has nulled it for sealed entries since 3.5 (`EntryMapper` line `null, // soundtrack`), and the error type is waiting (`MusicSearchUnavailableException`, `ProblemKind.MUSIC_SEARCH_UNAVAILABLE`, both from 2.6). Every request record said "arrives with task 3.14". So this task is mostly *new behaviour behind old plumbing*, plus the first outbound HTTP call the app makes. Task 4.15 (the picker and the player) is its client.

2. **The pure parts first, with plain unit tests:** `Soundtrack` (the format) and `SpotifyResults` (Spotify's JSON to our results). Nothing here needs Spring.

4. **`SpotifyProperties`, `MusicSearchService`, `MusicController`** and their DTOs.
5. **Tests against a stubbed Spotify:** the service alone (`MockRestServiceServer`), then over HTTP (a `@WebMvcTest` slice), then the whole app with the settings empty.
6. **The log proof** (`EverythingLogged`), and break it on purpose once.

Why this order: the pure parts are the cheapest to get right and the service is built on them; the privacy proof comes last because it is only meaningful once the whole path (controller, validation, service, advice) exists, and it is the step that found two real leaks (§8).

## 5. How it was built
In the order a reviewer should read it.

## 8. What went wrong
1. **A heredoc with apostrophes in a Java file failed in Git Bash** (`unexpected EOF while looking for matching '`) and wrote only the first few files. I re-created the two large files with the editor tool. No harm, but I checked with `ls` which files had been written before going on.
2. **My first Perl replace on a CRLF file** half-applied (the one-line replacements worked and the multi-line ones did not, because the working copy has Windows line endings while my pattern had `\n`). `git checkout` on that file and the editor tool fixed it. Later multi-line replacements went through a small Java program that normalises the line endings first.
3. **The log proof found a real leak** (the most useful failure of the task). `MusicSearchHttpTest.noLogLine...` failed with:
   `ExceptionHandlerExceptionResolver DEBUG Resolved [MethodArgumentNotValidException: Validation failed for argument [0] ... rejected value [my-private-WORDS-9913my-private-WORDS-...`
   I had put `@NotBlank @Size(max = 200)` on the record. When the words are too long, Spring's own exception message contains the rejected value, and Spring logs the resolved exception at DEBUG. Nothing in our code logged it, and our own `GlobalExceptionHandler` never prints messages, but a developer who turns DEBUG on, or a log shipper at that level, would store the words. Fix: the rules moved into `MusicSearchService.requireQuery`, which throws `ValidationFailedException(field, message)` (the message names the rule, never the value); the record keeps only `@Schema(minLength = 1, maxLength = 200)` for the OpenAPI document. `ValidationFailedException`'s own Javadoc already says "never put the rejected value in them".
4. **The same test then failed on a line that was not the app's.** `DefaultRestClient DEBUG Writing [{query=ok-my-private-WORDS-9913}]`: the *test's* `RestTestClient` is also a `RestClient`, in the same JVM, under the same logger name, and logs a `Map` body at DEBUG. That is the harness, not the app. The test now sends a `byte[]` (logged as `[B@hash`), with a comment saying why. It would have been easy to filter that line out of the assertion instead; I chose not to, because a filter on a logger name would also hide the app's own `RestClient`.
5. **`JdbcClient.single()` with a mapper that returns `null`** threw `TypeMismatchDataAccessException: Result value is null but no null value expected` in three of my own tests (reading a `soundtrack` column that is correctly null). I used `.list().getFirst()`.
6. **A test that matched too widely.** In the log test I first stubbed the three "fine" searches with one `times(3)` expectation on the path only. With `ignoreExpectOrder(true)` it would also have answered the two requests that were meant to fail (`429` and the I/O error), and the test would have passed for the wrong reason. Each request got its own `searchFor(words)` expectation.

## 10. Concepts to learn from this task
- **Custom Jakarta constraint** ([`SpotifyUri.java`](../../../backend/src/main/java/com/memoirist/music/SpotifyUri.java)): an annotation with `@Constraint(validatedBy = ...)` and a `ConstraintValidator<A, T>`. `null` is valid by convention (add `@NotNull` where required). The usual mistake is a message with `{}` in it (read as a template) or one that repeats the value.
- **Client credentials flow** ([`MusicSearchService.java:162`](../../../backend/src/main/java/com/memoirist/music/MusicSearchService.java#L162)): service-to-service OAuth. The app proves who *it* is (id and secret in a Basic header) and gets a token with a lifetime, no user involved. The mistake is asking for a token on every call.
- **Token cache with an early expiry** ([`:145`](../../../backend/src/main/java/com/memoirist/music/MusicSearchService.java#L145)): store `(value, expiresAt)`, compare with the injected `Clock`, subtract a margin. The mistake is `Instant.now()` inside (untestable) or no lock (a thundering herd of logins).
- **`RestClient` fluent API**: `client.get().uri(template, vars...).header(...).retrieve().body(Type.class)`. `retrieve()` throws `RestClientResponseException` for 4xx and 5xx; an I/O failure is `ResourceAccessException`; both extend `RestClientException`. The URI **variables** are encoded as values; the same text concatenated into the template is not.
- **`MockRestServiceServer`** ([`MusicSearchServiceTest.java:67`](../../../backend/src/test/java/com/memoirist/music/MusicSearchServiceTest.java#L67)): `bindTo(RestClient.Builder)` swaps the request factory; `expect(count, matcher).andRespond(...)` stubs; `verify()` fails when an expected call never happened, and a call nobody expected fails at once. `ignoreExpectOrder(true)` when only counts matter.
- **Why bean validation and private input don't mix by default**: the exception message contains the rejected value. For free text the user typed, validate by hand and name the rule only.
- **Redacting in `toString()`**: records print every component; override `toString()` wherever a component is private (`MusicSearchRequest`, `SpotifyProperties`, `Token`).
- **Proving a negative about logs**: capture *everything* (root logger at TRACE, messages, exceptions, causes, frames), and make the test fail once on purpose.
- **URI templates vs string concatenation**: `"?q={q}"` with the value as an argument is encoded whole; `"?q=" + query` is a parameter-injection bug.

## 12. At work
- **Calling another service with an OAuth client-credentials token** is routine in bank back ends (payment rails, KYC, market data). A reviewer asks: is the token cached and refreshed before expiry, what happens under concurrent load, what happens when the identity provider is down, and does a `401` clear the cache? The answers here are a margin, a lock, `503` with a fixed sentence, and `forget`.
- **"Never log customer input" needs a test, not a promise.** Log scrubbing rules in banks exist because a debug line once shipped an account number to a log store. The pattern here (capture every logger at the lowest level and assert absence, and break the code once to see it fail) transfers directly, and so does the lesson that framework exception messages echo input.
- **Fail soft on optional integrations.** Search is a convenience; the product works without it. Mapping every upstream failure to one well-named `503` with a safe sentence, and logging only classes and frames, is what keeps an upstream outage from becoming your outage, and keeps the upstream's URL (with query strings!) out of your logs.
- **Stub the dependency at the HTTP layer.** `MockRestServiceServer` exercises the real client, serialisation and error handling; mocking your own wrapper class would test nothing that can break. Reviewers will ask for a test of each upstream failure mode (429, 5xx, timeout, malformed body).
