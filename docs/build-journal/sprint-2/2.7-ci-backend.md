## 6. How it was tested
- **Strategy.** A workflow file has no unit tests. What can be checked without pushing is, in order: (a) the YAML parses and has the shape I claim; (b) every pinned SHA is the commit of the tag next to it; (c) the commands the job runs pass on a machine like the runner, built from what git would check out; (d) the same commands pass on this PC. (e) The run on GitHub itself comes after a push.
- **Why a Linux container for (c).** The runner is Linux. This PC is Windows with `core.autocrlf=true`, a case-insensitive disk and no executable bits. Building a `git archive` (LF, git's modes, no untracked files) in an `eclipse-temurin:25-jdk` container removes all of those differences except the kernel, and it can be done before anything is pushed.

| Check | Proves | Type |
|---|---|---|
| SnakeYAML parse plus [my checker](#the-checks-in-detail) | The file is valid YAML; triggers are `push`, `pull_request`, `workflow_dispatch`; `permissions.contents` is `read`; the job has `runs-on` and a timeout; every step has exactly one of `uses`/`run`; every `uses` is a 40-hex SHA | Static |
| `gh api repos/<action>/commits/<tag>` for each `uses` | Each pinned SHA is the commit of the tag in its comment (all three match) | Static |
| `docker run eclipse-temurin:25-jdk` on a `git archive`, cold | The job's command works on Linux from a clean checkout: `gradlew` is executable, `spotlessCheck` passes on LF files, nothing needs `.env`, case-sensitive paths resolve, all tests pass | Supporting evidence (the plan's fallback; it doesn't replace the run) |
| The same again with the Gradle folder kept | What the cache saves | Measurement |
| `./gradlew cleanTest build` on this PC | The full build passes with the practice answers in place | Local |
| The run on GitHub | The workflow is accepted by GitHub and passes there | Passed: [run 41060170384](https://github.com/aarrroon/memoirist/actions/runs/41060170384) (§7) |

### The checks in detail
The checker is a small Java program that parses the workflow with SnakeYAML and fails on any rule above. One thing it taught me: the parsed document's top-level keys come out as `[name, true, permissions, concurrency, jobs]`. YAML 1.1 reads a bare `on` as the boolean `true`; GitHub reads it as the word. A checker that looks for the key `"on"` finds nothing and reports a missing trigger, so it looks for `true` as well.

### How to run them yourself
Git Bash, from the repo root. `JAVA_HOME` must point at JDK 25 (task 1.2).

```bash
# (b) every pin is the commit of its tag
grep -E '^\s+uses:' .github/workflows/ci.yml | while read -r _ ref _ tag; do
  repo=${ref%@*}; sha=${ref#*@}; real=$(gh api repos/$repo/commits/$tag --jq .sha)
  [ "$real" = "$sha" ] && echo "MATCH   $repo $tag" || echo "MISMATCH $repo $tag"
done

# (c) the job's command on Linux, from what git would check out (LF, git's modes, no .env, no build/)
git -c core.autocrlf=false -c core.eol=lf archive HEAD backend docs/API_CONTRACT.md -o /path/to/scratch/src.tar
MSYS_NO_PATHCONV=1 docker run --rm -i -v /var/run/docker.sock:/var/run/docker.sock \
  -e TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal eclipse-temurin:25-jdk \
  bash -c 'mkdir /work && tar -x -C /work && cd /work/backend && ./gradlew build --no-daemon' < /path/to/scratch/src.tar

# (d) on this PC, forcing the tests to run (a plain `build` is UP-TO-DATE when nothing changed)
cd backend && ./gradlew cleanTest build --no-daemon
```

The container command needs `TESTCONTAINERS_HOST_OVERRIDE` only because it runs Docker from inside Docker (§8, item 4). On GitHub the tests run on the runner itself and need nothing extra. Passing output ends with `BUILD SUCCESSFUL` and, with the test logging this project has, 219 lines ending in `PASSED`.

## 8. What went wrong
1. **My first container run failed in a second.** `sh: 1: time: not found`. The image's `/bin/sh` is dash, and `time` is a bash keyword. Nothing to do with the project. The output did show the archive had extracted with `-rwxrwxr-x ... gradlew`, so the executable bit survived. Fix: run the script under `bash -c`.
2. **I backgrounded a command twice.** I put `&` inside a command that I also gave to the tool's background option, so the tool reported "completed" immediately while Docker kept running. I found out when the log kept growing. Fix: one level of backgrounding, and poll the log.
3. **The checker didn't compile.** `error: illegal escape character` for `"^[\w.-]+/..."`: the backslash in my regex arrived in the file as a single backslash. Fix: a character class (`[A-Za-z0-9_.-]`) that needs no escape.
4. **The second container build failed: 121 of 219 tests, `BUILD FAILED in 6m 38s`.** Every test class that needs Docker failed with `IllegalStateException: Could not connect to Ryuk at 172.17.0.1:60313`; every class that doesn't need it passed (96 tests). Cause, as far as I can tell (the fix below worked): my container was running Docker from inside Docker through a mounted socket. Testcontainers inside a container looks for its containers' published ports at the container's default gateway, 172.17.0.1, and on Docker Desktop that address doesn't reach them. It was my simulation, not the project, and GitHub's runner runs the tests on the machine that has Docker. Fix: `-e TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal`. The failed run still proved things that don't need a database: the archive built, `compileJava` and `compileTestJava` passed on case-sensitive Linux, `:spotlessCheck` passed on LF files, and the non-Docker tests passed. It also showed that a failed `build` exits non-zero and leaves `build/reports/tests/test/index.html` where the `upload-artifact` step looks.
5. **A dead end on caching.** I was going to use `gradle/actions/setup-gradle`, the usual choice for Gradle. Its v6 release notes say the caching has been extracted into a component that is "no longer open-source" and that upgrading to v6 means accepting its Terms of Use. That is a legal agreement, so I didn't accept it for you, and used `setup-java`'s `cache: gradle` instead (§4, decision 5).
6. **`./gradlew build` on this PC proved nothing the first time.** All ten tasks were `UP-TO-DATE`: no input had changed since 2.6, so no test ran (`0 PASSED` in the log, in 1m 26s, mostly Gradle starting). Fix: `./gradlew cleanTest build`, which ran the tests.

## 10. Concepts to learn from this task
- **A workflow's anatomy** ([ci.yml](../../../.github/workflows/ci.yml)): `on` (events), `permissions`, `concurrency`, then `jobs` made of `steps`. A step either `uses:` an action (someone else's packaged code, at a version) or `run:`s a shell command. Jobs run on a fresh VM each time, which is the point: nothing of yours is on it.
- **Pinning by commit SHA** (line 40): a tag is a label that its owner can move; a SHA names exact content. The usual comment (`# v7.0.1`) is for humans and for tools like Dependabot. The mistake is pinning once and never updating: the pin then freezes known bugs.
- **`pull_request` versus `pull_request_target`** (line 13): the first runs the pull request's own workflow with a read-only token and no secrets when it comes from a fork. The second runs with the base's secrets and write access, and is the classic way to hand a fork's code your keys. Public repositories use the first.
- **The token's permissions** (line 19): `GITHUB_TOKEN` is created for each run. Starting from `contents: read` and adding only what a step names is the least-privilege version of a default-deny security configuration: deny first, then allow what is needed.
- **`concurrency` groups** (line 24): a named queue. With `cancel-in-progress` a new arrival cancels the running member of the same group. The mistake is a group so broad that unrelated runs cancel each other.
- **`if: failure()`** (line 71): step conditions are expressions over the job's status. Without a status function a step has an implicit `success()`, so it would be skipped exactly when you need it.
- **Gradle toolchains versus `JAVA_HOME`** ([build.gradle.kts:14-17](../../../backend/build.gradle.kts#L14-L17)): Gradle can run on one JDK and compile with another. Here the toolchain says 25, and with no download resolver the runner must have 25. `setup-java` sets `JAVA_HOME`, so the wrapper starts on 25 too.
- **Cache keys** ([line 56-58](../../../.github/workflows/ci.yml#L56-L58)): the cache is looked up by a key made from file hashes. Same hash, same cache. No fallback key means a changed build file starts from nothing, which is safe (no stale jars) but slow once.
- **`--no-daemon`** ([line 66](../../../.github/workflows/ci.yml#L66)): the Gradle daemon is a background JVM that stays up for the next build. Good on a laptop, pointless on a VM that is thrown away.
- **YAML 1.1's `on`**: the words `on`, `off`, `yes` and `no` are booleans in YAML 1.1, so a parser can show `true:` where you wrote `on:`. GitHub avoids the trap, a tool that doesn't can mislead you.
- **`git archive`**: writes a tarball of a commit using git's own idea of each file (mode and line endings), with none of your untracked files. It's the closest thing to a CI checkout you can make offline.
- **The executable bit lives in git's index** (`100755` versus `100644`), and Windows doesn't keep it. `git ls-files -s <file>` shows it. This is why 2.1 staged `gradlew` with `--chmod=+x`.
- **Docker in Docker and Testcontainers**: a container that drives the host's Docker through its socket starts *sibling* containers, and published ports land on the host, not inside the container. Testcontainers has to be told where (`TESTCONTAINERS_HOST_OVERRIDE`). On a CI VM the build is on the host itself and none of this applies.

## 12. At work
- **The same file, different runner.** A bank rarely uses GitHub-hosted runners for the main code. The equivalents are a Jenkinsfile, Azure DevOps or GitLab CI on self-hosted agents. The questions don't change: which JDK, where do dependencies come from (an internal Maven mirror such as Nexus or Artifactory, not Maven Central), and where do Testcontainers' images come from (an internal registry, with `TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX`, because Docker Hub is blocked or rate-limited).
- **Docker on the agent.** Testcontainers needs a Docker daemon the build can reach. On shared agents that is often forbidden for security reasons, which leads to a remote Docker host or a service such as Testcontainers Cloud. Expect to explain why the tests need real Postgres (D-14).
- **Supply chain.** Unpinned third-party actions or plugins in a pipeline are a finding in a security review. Pinning by digest, reviewing updates and allow-listing actions at the organisation level are the usual answers. Wrapper validation, SBOMs and dependency scanning belong to the same family.
- **Least privilege.** A CI token that can only read, builds from pull requests that get no secrets, and a separate, protected workflow for deploys. "Who can run what with which secrets" is the whole security model of a pipeline.
- **Branch protection.** A green build only matters if merging requires it. The reviewer's question is "is `Backend (build and test)` a required check, and can an admin bypass it?"
- **Flaky tests.** A test that fails one run in twenty trains people to click re-run. A reviewer would ask how this team handles it: quarantine, fix, or ignore.
- **Cache poisoning.** A shared dependency cache that a pull request can write is a way to plant code. Caches that a pull request from a fork can't write to are a reason to know your CI's cache scopes.
