# Task 2.5: Current user resolution

> **Sprint:** 2 · **Commit:** `Sprint 2.5: Add current user resolution` · **Status:** done (all four Done-when items met; `./gradlew build` passes with 164 tests after the fix pass; spec review: Pass with notes, §9) · **Time taken:** roughly 35 minutes by the machine clock (20:22 to about 20:55 on 2026-10-30), including the mutation checks, two full builds and this entry
> **Built:** the backend can now say who is calling. `CurrentUserProvider.currentUserId()` has one implementation, `DevHeaderCurrentUserProvider`, which exists only in the `local` and `test` profiles, reads `X-Dev-User-Id`, falls back to the seeded dev user and answers a bad header with `400 malformed-request`. 43 new tests prove it, and each kind of test was checked by breaking the code on purpose.

## 1. The goal
[Task 2.5](../../SPRINT_PLAN.md) adds the one seam through which the rest of the backend learns who the current user is (D-11). Nothing needs it yet, but every endpoint from Sprint 3 onwards starts with it, so it has to be right, and hard to misuse, before anything depends on it.

| Piece | What it is |
|---|---|
| `user/CurrentUserProvider` | The interface: `UUID currentUserId()` |
| `user/DevHeaderCurrentUserProvider` | Phase 1's implementation: header `X-Dev-User-Id`, the seeded dev user when it is absent, `@Profile({"local","test"})` |
| `common/MalformedRequestException` | What the provider throws for a header it can't use |
| `common/GlobalExceptionHandler` | A first `@RestControllerAdvice` with one handler, so that exception becomes `400 malformed-request` (task 2.6 adds the rest) |
| 43 tests | Parsing, HTTP behaviour, profile wiring, and the app under a `prod` profile |

It comes now, between the entities (2.4) and error handling (2.6), because:

| Later task | What it needs from 2.5 |
|---|---|
| 2.6 Global error handling | A `GlobalExceptionHandler` to extend, with the problem body shape already working for one type |
| 3.2 `/users/me` and every Sprint 3 service | `CurrentUserProvider` to call, so ownership checks (non-negotiable 3) have a source for the user id |
| Phase 2 (JWT login) | An interface to implement without touching a controller |

**Done when** (copied from the plan): tests prove that the header is honoured; a missing header falls back to the dev user; a malformed header returns `400 malformed-request`; in a non-local profile, the dev provider bean doesn't exist.

No endpoint is added, so there is no new row in `API_CONTRACT.md`; the contract's *Who is the current user?* section gained the exact rules for the header (§5, docs).

## 5. How it was built

**The interface and the exception**
- [`CurrentUserProvider.java`](../../../backend/src/main/java/com/memoirist/user/CurrentUserProvider.java#L18-L25): one method. The Javadoc says what the rest of the code relies on: call it from a request thread, and a background job has no current user.
- [`MalformedRequestException.java`](../../../backend/src/main/java/com/memoirist/common/MalformedRequestException.java#L10-L14): a plain `RuntimeException`. Its message goes to the client as the problem's `detail`, so the Javadoc forbids putting the rejected value in it.

**The provider**
- [`DevHeaderCurrentUserProvider.java`](../../../backend/src/main/java/com/memoirist/user/DevHeaderCurrentUserProvider.java#L24-L52):
  - `@Component` plus `@Profile({"local", "test"})` ([L24-L25](../../../backend/src/main/java/com/memoirist/user/DevHeaderCurrentUserProvider.java#L24-L25)). The array means *local or test*. Component scanning finds the class; the profile decides whether the bean is created.
  - The constructor takes an `HttpServletRequest` ([L36-L38](../../../backend/src/main/java/com/memoirist/user/DevHeaderCurrentUserProvider.java#L36-L38)). Spring has no request when it builds a singleton, so it injects a proxy that looks up the calling thread's request on each use.
  - `currentUserId()` ([L41-L52](../../../backend/src/main/java/com/memoirist/user/DevHeaderCurrentUserProvider.java#L41-L52)) reads every value of the header: none means the dev user, more than one means malformed, one goes to `parse`.
  - `DEV_USER_ID` ([L32](../../../backend/src/main/java/com/memoirist/user/DevHeaderCurrentUserProvider.java#L32)) is the id in `db/seed-local/R__seed_dev_user.sql`.
- [`parse`](../../../backend/src/main/java/com/memoirist/user/DevHeaderCurrentUserProvider.java#L54-L72): the practice block (§11). A regex first, because `UUID.fromString` alone would accept `1-1-1-1-1`.

**The error response**
- [`GlobalExceptionHandler.java`](../../../backend/src/main/java/com/memoirist/common/GlobalExceptionHandler.java#L28-L43): `@RestControllerAdvice` with one `@ExceptionHandler`. A `ProblemDetail` is Spring's class for RFC 9457; returning one from a handler sets the response status from it and writes `application/problem+json`. The method adds the `type` URI (`urn:memoirist:problem:malformed-request`), a `title` and a `timestamp` from the `Clock`; Spring fills in `instance` with the request path. The class comment says task 2.6 extends it.

**The tests** (§6)
- [`DevHeaderCurrentUserProviderTest`](../../../backend/src/test/java/com/memoirist/user/DevHeaderCurrentUserProviderTest.java), [`CurrentUserHttpTest`](../../../backend/src/test/java/com/memoirist/user/CurrentUserHttpTest.java), [`CurrentUserProfileTest`](../../../backend/src/test/java/com/memoirist/user/CurrentUserProfileTest.java), [`CurrentUserWiringTest`](../../../backend/src/test/java/com/memoirist/user/CurrentUserWiringTest.java), [`DevProviderAbsentInProdTest`](../../../backend/src/test/java/com/memoirist/user/DevProviderAbsentInProdTest.java).

**Docs changed with the code**
- [`API_CONTRACT.md`](../../API_CONTRACT.md#who-is-the-current-user): the header must be a canonical UUID and sent once; an empty value is `400`, never the dev user; reading the header doesn't check the user exists; other profiles ignore it. The `malformed-request` row says which cases.
- [`TECH_STACK.md`](../../TECH_STACK.md) §2: *Current user* now explains the request proxy, the strict parse and what a profile without a provider means; *Errors* says `GlobalExceptionHandler` exists and what every problem carries; *Tests* names the web-slice pattern.
- [`DEVELOPMENT.md`](../../DEVELOPMENT.md): the status line, a *Who you are* bullet, and which test classes need no Docker or an extra container.
- Not changed: `DECISIONS.md` (nothing contradicts D-11, and the new details are returned as assumptions for the morning), `DATABASE_SCHEMA.md` (no schema change), `CLAUDE.md`, the README.

## 8. What went wrong
1. **A heredoc that wrote nothing.** The first attempt to write `CurrentUserHttpTest.java` with `cat > file <<'EOF'` failed with `unexpected EOF while looking for matching '`'`. I never found the cause (other heredocs with the same delimiter had worked). The file wasn't created. I wrote it with the Write tool and used `<<'JAVA'` for the others, which worked. (Writing this entry hit a different limit: the whole entry in one shell command gave `ENAMETOOLONG`, because Windows caps the command line, so it went through the Write tool too.)
2. **No Python on this machine.** The first mutation script used `python3`; Windows answered with a Microsoft Store prompt. Redone with `sed`.
3. **A doc edit that "wasn't found".** My `perl` replacement of a line in `API_CONTRACT.md` died with `old text not found`. The file has Windows line endings (CRLF), and `grep -c $'\r'` printed 0 in this shell, which sent me the wrong way for a while. `perl` printing the character codes (`13 10`) showed it. `TECH_STACK.md` and `DEVELOPMENT.md` are LF. A small `subst.pl` helper that matches each file's own line endings fixed it. To check a file: `perl -ne '$c++ if /\r\n$/; END{print $c}' file`.
4. **A mutation that broke compilation instead of behaviour.** The "naive parse" mutation deleted one line too few and left a stray `}`; `compileJava FAILED`. A mutation that doesn't compile proves nothing. Redone with the right line range; then it failed exactly the three lenient cases.
5. **Three mutations at once told me little.** The first mutation run combined "no regex", "empty is absent" and "duplicates ignored": 20 tests failed, and most of them for the wrong reason (`UUID.fromString` throws `IllegalArgumentException`, not my exception). I split them and each pointed at its own tests.
6. **Everything passed on the first run.** All 42 tests then in the package were green on the first try. That is not evidence; it is the reason for the mutation table above.
7. **A test that didn't test what its name said.** `readsTheRequestOfTheMomentNotTheOneItWasBuiltWith` first went *user A, then no header*. With the "keep the first answer in a field" mutation it still passed, because "no header" returns the dev user before the field is read. The concurrency test and three HTTP tests caught that mutation, but the unit test claimed to and didn't. I changed it to go *user A, user B, then no header*; with the mutation it now fails.
8. **The formatter reflowed my practice-block comments.** palantir-java-format wrapped a long `//` line into `… a` / `// client` / `…`. The comments are the exercise's instructions, so I rewrote them to fit in 120 columns; `spotlessApply` leaves them alone now.
9. **Doubled quotes in test names.** `@ParameterizedTest(name = "[{index}] \"{0}\" is malformed")` printed `""1-1-1-1-1""`, because JUnit already quotes string arguments. I dropped my quotes.
10. **My own notes had invented times.** While keeping running notes I wrote clock times like "21:35" that I hadn't read from the clock. ## 10. Concepts to learn from this task
- **`@Profile` with several names** ([`DevHeaderCurrentUserProvider.java:25`](../../../backend/src/main/java/com/memoirist/user/DevHeaderCurrentUserProvider.java#L25)): `@Profile({"local","test"})` means *any of these is active*. The bean is skipped when none is. The mistake: forgetting what happens with no profile set. Spring's `default` profile is then active, which matches neither name, so the provider is absent (tested).
- **Fail closed** (`DevProviderAbsentInProdTest`): the safe default for "who is the user" is *nobody*. In a profile without a provider the app has no `CurrentUserProvider` at all, so when Phase 2 adds controllers that need one, a missing provider stops the app at startup instead of the dev user quietly serving everyone.
- **Injecting a request into a singleton** ([L36-L38](../../../backend/src/main/java/com/memoirist/user/DevHeaderCurrentUserProvider.java#L36-L38)): a controller or service is built once, but a request is per call. Spring injects `HttpServletRequest` as a proxy that finds the *current thread's* request every time you use it. The mistake is copying a value out in a constructor or keeping it in a field, which freezes the first request's data for everyone; the concurrency test and the "keep the answer" mutation exist for that. Outside a request the proxy throws `IllegalStateException`.
- **`UUID.fromString` is forgiving** ([L54-L72](../../../backend/src/main/java/com/memoirist/user/DevHeaderCurrentUserProvider.java#L54-L72)): it accepts `1-1-1-1-1` and pads it. At a trust boundary (anything a client sends) validate the *shape* first and parse second.
- **`Collections.list(enumeration)` and `List.getFirst()`** ([L44-L51](../../../backend/src/main/java/com/memoirist/user/DevHeaderCurrentUserProvider.java#L44-L51)): servlet APIs still return the old `Enumeration`; `Collections.list` turns it into a `List`. `getFirst()` (Java 21, from `SequencedCollection`) replaces `get(0)`.
- **`ProblemDetail` and `@RestControllerAdvice`** ([`GlobalExceptionHandler.java`](../../../backend/src/main/java/com/memoirist/common/GlobalExceptionHandler.java#L28-L43)): RFC 9457 is a standard JSON shape for errors (`type`, `title`, `status`, `detail`, `instance`, plus your own fields). Spring's `ProblemDetail` is its class; returning one from an `@ExceptionHandler` sets the status and the `application/problem+json` content type. `setProperty("timestamp", …)` adds a field of your own.
- **Web slices** ([`CurrentUserHttpTest.java:41-50`](../../../backend/src/test/java/com/memoirist/user/CurrentUserHttpTest.java#L41-L50)): `@WebMvcTest(controllers = X)` starts Spring MVC with only the controller you name, controller advice and what you `@Import`; no database, no scanned services. The mistake is forgetting that `@Component` beans (like the provider) and `@Configuration` classes (like `ClockConfig`) are *not* included until imported.
- **`@TestComponent`** ([`CurrentUserHttpTest.java:188-202`](../../../backend/src/test/java/com/memoirist/user/CurrentUserHttpTest.java#L188-L202)): marks a bean that exists only for tests. Component scanning skips it, so the helper controller never reaches the real app or another test's context. A probe test (deleted afterwards) and `/v3/api-docs` showing no paths confirmed it.
- **`ApplicationContextRunner`** ([`CurrentUserProfileTest.java:26-28`](../../../backend/src/test/java/com/memoirist/user/CurrentUserProfileTest.java#L26-L28)): builds a small Spring context per assertion with chosen beans and properties (`spring.profiles.active=prod`), so conditions like `@Profile` are tested in milliseconds. `assertThat(context).hasSingleBean(…)` and `.doesNotHaveBean(…)` are its assertions.
- **Parameterized tests** ([`DevHeaderCurrentUserProviderTest.java:75-93`](../../../backend/src/test/java/com/memoirist/user/DevHeaderCurrentUserProviderTest.java#L75-L93)): `@ParameterizedTest` + `@ValueSource(strings = …)` runs one method per value, each reported separately. The `name` template (`{index}`, `{0}`) makes the failing row obvious.
- **A closed `ExecutorService`** ([`CurrentUserHttpTest.java:151`](../../../backend/src/test/java/com/memoirist/user/CurrentUserHttpTest.java#L151)): since Java 19 `ExecutorService` is `AutoCloseable`, and `close()` waits for submitted tasks. A `CountDownLatch` holds every task until all are submitted, so they start together.
- **Mutation checking by hand**: change the code to be wrong, run the tests, and require a red result. If a test stays green, it isn't testing what it says (§8, item 7).

## 12. At work
- **One seam for identity.** In an enterprise Spring codebase the equivalent is `SecurityContextHolder`, a `@AuthenticationPrincipal` argument or a small `CurrentUser` service. The review question is the same as here: is there exactly one place that turns a request into a user, and does every query start from it? A user id taken from a body, path or query is a finding in review (an insecure direct object reference).
- **Debug backdoors guarded by configuration.** "Header X lets you be anyone" is a normal feature in dev and a classic incident in production. A reviewer looks for: is the guard on the class (`@Profile`) rather than an `if` inside it; what happens with no profile set; is there a test that proves the bean is absent in the production profile? `DevProviderAbsentInProdTest` is that test, and it runs the whole application, because a unit test of one class can't see a second place that registers the same bean.
- **Fail closed.** If identity resolution can't answer, the answer is an error, never a default user. The empty-header rule is the small version of this.
- **Strict parsing of identifiers.** Anything a client sends is untrusted, including a "dev only" header. Accept the one documented form; refuse near-misses (`1-1-1-1-1`); don't echo the value in the error or the logs.
- **Error shapes are a contract.** Front ends and other services parse the problem `type`, so a test should pin it (the practice block), not only the status code. RFC 9457 `ProblemDetail` is what the standard Spring stack gives you; teams often add a correlation id as one more property.
- **Test the thing that can go wrong in prod.** Fast tests for logic (the table of bad values), a context runner for conditions, one real application start for wiring. Mutation checking is cheap insurance that a security test can fail.

<details><summary>Answers</summary>

1. `getHeader` returns only the first value and ignores the rest. A request with two `X-Dev-User-Id` lines names two users and has no right answer, so `getHeaders` lets the provider see both and refuse (`400`), instead of silently choosing one.
2. It throws `MalformedRequestException` (a `400`) because the shape isn't `8-4-4-4-12` hex digits. A `try/catch` around `fromString` accepts `1-1-1-1-1` (as `00000001-0001-0001-0001-000000000001`), a last group one digit short and a leading `+`. A mutation test showed exactly those three get through. Validate the shape with a regex first.
3. It is a `400 malformed-request`. Treating an empty value as "absent" would be the dangerous choice: a client bug (an undefined variable sent as an empty header) would silently act as the dev user and show another person's data.
4. Spring injects a proxy for `HttpServletRequest` that finds the calling thread's current request each time it is used, and the provider keeps no per-request state. Copying the request, the header or the result into a field would share it between requests; `requestsAtTheSameTimeEachSeeTheirOwnHeader` and the "cache the answer" mutation cover that.
5. An exception thrown inside a controller or service is handled by Spring MVC's exception resolvers, including the `@RestControllerAdvice`, so it becomes a `ProblemDetail`. A filter runs before Spring MVC, so its exceptions bypass the advice and end up as the container's error page. (It also means the provider can be called from a service, which is what D-11 describes.)
6. Start the app (or a small context) under a non-local profile and assert there is no bean of that type. The `ApplicationContextRunner` matrix is fast and covers many profile names without Docker; the real application under `prod` is slow but is the only one that would notice a second place registering the provider (a stray `@Bean`). It also checks the dev user isn't seeded.
7. It protects against the Java constant and the seed SQL drifting apart. The unit tests compare the fallback with `Fixtures.DEV_USER_ID`, not the database, so if the seed's id changed the fallback tests would still pass, and every header-less request would act as a user who doesn't exist.
8. It went user A, then *no header*; with the mutation the second call took the early return for "no header" and gave the dev user before reaching the cached field, so nothing looked wrong. Going user A, then user B, then no header makes the cached answer visibly wrong on the second call.
