## 3. The plan
Order, and why:

1. **`MemoiristApplication`**: `TimeZone.setDefault(UTC)` first in `main`, plus `@ConfigurationPropertiesScan`. Everything else assumes a UTC JVM.
2. **`ClockConfig`**: the one `Clock` bean.
3. **`StorageProperties`**: the record and its constraints, before the YAML that fills it, so that the YAML is written against a type that rejects mistakes.
4. **`application.yml`, `application-local.yml`, `application-test.yml`**: the settings, split by "true everywhere", "where the variables come from locally" and "test values".
5. **`IntegrationTest`**: one composed annotation, so all integration tests share a context. Then `ApplicationSmokeTest` moves onto it.
6. **Tests**: `ConfigurationTest` (the effective settings), `MemoiristApplicationTest` (`main` itself), `StoragePropertiesTest` (binding and failures).
7. **`build.gradle.kts`**: the test JVM starts in UTC.
8. **Prove it by running**: the full test suite, mutation checks (break a setting, watch a test fail), a local boot against Compose, and two ways to make the boot fail on purpose.
9. **Docs**: TECH_STACK §2, DEVELOPMENT.md (status, precedence, two troubleshooting rows), a comment in `.env.example`.

Tests were written with each file rather than at the end, but the proof runs came last, because they need all of it.

## 8. What went wrong
1. **The first attempt was interrupted** after the first local boot (01:14), with the code and tests written, and the docs, the failure-mode runs and this entry not yet done. This session picked up from the notes and the uncommitted files, re-ran the build to check the state, and finished the rest.
2. **A wrong claim, caught by probing.** I had written in `MemoiristApplicationTest` that aborting a run in `starting()` leaves Boot's "suppress all logging" filter in place and "silences the logs of every later test". I'd only read `beforeInitialize` and `initialize`. Probes showed that the next context to start (Boot's `initialize` resets the logger context) logs normally again. What's true: after an abort in `starting()`, log lines vanish *until another Spring Boot app starts in the same JVM*. The test aborts in `environmentPrepared` instead, after logging is set up, and the comment says only that. Lesson: a comment about framework internals needs an experiment behind it.
3. **A test that couldn't fail.** The first draft of the UTC check was only the assertion in `ConfigurationTest`. Once the Gradle flag was added, deleting the line in `main` didn't fail it (mutation check). That's why `MemoiristApplicationTest` exists, and why the mutation checks are in this entry.
4. **Dead ends while proving the Flyway locations.** `--logging.level.org.flywaydb=DEBUG` printed no location lines in this Flyway version (it didn't even warn about a missing location). `/actuator/env/spring.flyway.locations` returned an empty `404`, because a list is bound as `locations[0]`, `locations[1]`. With raw brackets and `curl -g`, piping the empty reply to `python -c "json.load"` failed with a traceback. URL-encoding the brackets (`%5B0%5D`) worked.
5. **Unparseable values show only the first error.** Setting `path-style="yes please"` and `presign-ttl="sixty"` reports a `ConversionFailedException` for path style only: conversion errors stop binding at the first one, while validation errors are collected together. So a user with two wrong values sees them in two rounds, and only validation-type mistakes (missing, blank, out of range) come back together. Not fixed; the message still names the property.
6. **A known gap in the validation.** `public-endpoint=localhost:8333` passes: it parses as a URI with scheme `localhost`. A scheme check would need a custom constraint. Recorded in TECH_STACK rather than built, because the real `.env` and Compose use a full URL, and 3.1's first call would fail loudly anyway.
7. **Formatter:** `spotlessApply` rearranged the annotations in `StorageProperties` (blank lines between multi-line components). Harmless; run it before `build` on this machine (2.1, §8).
8. **A typo that ran a build.** I once mis-typed a redirect (`> ../../../../../../../dev/null`) on a `./gradlew build` command, meaning to skip it. It ran anyway and succeeded (23 tests passed), which is why the next `./gradlew build` said `UP-TO-DATE`. Harmless, but the evidence in §7 is from the explicit `cleanTest build` afterwards.
9. **Close-out fix pass.** The review had no blocker or major finding. ## 10. Concepts to learn from this task
- **`@ConfigurationProperties` on a record** ([`StorageProperties.java:31-33`](../../../backend/src/main/java/com/memoirist/storage/StorageProperties.java#L31)): Boot binds `storage.public-endpoint` (or `STORAGE_PUBLIC_ENDPOINT` mapped by hand) to the component `publicEndpoint`, through the record's constructor, with no setters and no `@ConstructorBinding`. It converts the text for you (`URI`, `Duration` accepts `PT60M`, `60m` or `3600s`). The mistake people make: forgetting to register it, so nothing binds. `@ConfigurationPropertiesScan` or `@EnableConfigurationProperties(X.class)` does that.
- **`@Validated` and fail-fast startup**: without `@Validated`, the constraint annotations on the record are decoration. With it, the binder runs Bean Validation and a failure stops the app with `BindValidationException`, listing every violated property with its value, origin and reason. Compare a failed upload at 2 a.m. three weeks later.
- **`${VAR:}` versus `${VAR}`** ([`application.yml:10`](../../../backend/src/main/resources/application.yml#L10)): `${VAR:default}` uses `default` when `VAR` is unset; with nothing after the colon the default is empty. Without a colon, Boot leaves the literal text in place.
- **Property precedence**: command-line arguments, then Java system properties, then OS environment variables, then imported files (`.env`), then the profile file, then `application.yml`. Proved here with `STORAGE_PRESIGN_TTL=PT60H` in the environment beating the value in `.env`. A **list** from a higher source replaces a lower one entirely (`spring.flyway.locations`).
- **`Clock`** ([`ClockConfig.java:19`](../../../backend/src/main/java/com/memoirist/common/ClockConfig.java#L19)): `java.time.Clock` is a source of "now". `Instant.now(clock)` and `LocalDate.now(clock)` read it, so a test passes `Clock.fixed(...)` and checks a boundary. `Instant.now()` with no argument reads the real clock and can't be tested.
- **`TimeZone.setDefault`** ([`MemoiristApplication.java:21`](../../../backend/src/main/java/com/memoirist/MemoiristApplication.java#L21)): changes the zone for the whole JVM, which is why a test that calls it must restore it in `finally`, and why `@Isolated` is there. It doesn't update the `user.timezone` property.
- **Test context caching and composed annotations** ([`IntegrationTest.java`](../../../backend/src/test/java/com/memoirist/IntegrationTest.java)): Spring keys a context by its configuration (classes, profiles, properties, mock beans). Classes with the same key share it, and so share the Postgres container. An annotation that carries `@SpringBootTest`, `@ActiveProfiles` and `@Import` as meta-annotations is the DRY way to keep the key the same.
- **`ApplicationContextRunner`** ([`StoragePropertiesTest.java`](../../../backend/src/test/java/com/memoirist/storage/StoragePropertiesTest.java)): starts a tiny context for one configuration class, with the properties you give it. `run(context -> ...)` hands you the context whether it started or failed, so you assert on the failure instead of catching an exception. Milliseconds, no database.
- **`SpringApplication.withHook` and `AbandonedRunException`** ([`MemoiristApplicationTest.java:37-55`](../../../backend/src/test/java/com/memoirist/MemoiristApplicationTest.java#L37)): lets a test observe a real `SpringApplication.run` (via a `SpringApplicationRunListener`) and stop it by throwing `AbandonedRunException`. The framework's own way to run `main` without finishing the start.
- **Open session in view**: Boot's default keeps the JPA `EntityManager` (and so a database connection) open for the whole web request. The effect is that lazy fields "just work" in a controller or a view, and every one of them is a query nobody reviewed.
- **Jakarta Bean Validation on records**: `@NotNull`, `@NotBlank`, `@Pattern` and Hibernate Validator's `@DurationMin`/`@DurationMax` (`org.hibernate.validator.constraints.time`). `@NotBlank` is for strings; `@NotNull` for the wrapper types. A primitive `boolean` can't be "missing", which is why the record uses `Boolean`.
- **AssertJ forms used:** `containsOnly` (exactly these, any order), `containsEntry`, `isCloseTo(x, within(5, ChronoUnit.SECONDS))`, `assertThatExceptionOfType(X.class).isThrownBy(...)`.
- **Actuator `env` endpoint**: `GET /actuator/env/{property}` shows one property's value and which source supplied it. Useful to see where a setting came from. **Dangerous** in production: with `show-values=ALWAYS` it prints secrets, so this task only used it on a local run, one property at a time.

## 12. At work
- **Fail-fast configuration is a bank habit.** A service that starts with a missing or malformed setting and fails on the first customer request is an incident. Validated `@ConfigurationProperties` (or the equivalent `@PostConstruct` check) turn that into a failed deploy, which a pipeline catches before traffic. A reviewer looks for `@Validated`, for types over strings, for limits on durations and sizes, and for the message naming the property.
- **Secrets in `toString()`.** Records, Lombok `@Data` and IDE-generated `toString()` methods print everything. Logs at a bank are retained, searched and audited, so a secret printed once is in the log forever. Mask it in the class, not at each logging call.
- **Twelve-factor and the precedence chain.** In production the values come from the platform (environment variables, a secret store mounted as files), not the jar. Knowing the order (arguments, environment, files, profile, defaults) tells you why a pod's setting beats the one in the image, and why a list in a profile file replaces the base one.
- **UTC everywhere, local time only at the edge.** Interest cut-offs, business days and statement dates cause defects when the JVM zone differs by machine. Pinning the server and the test JVM to UTC, injecting a `Clock`, and converting to the customer's zone only for display and "what day is it for them", is the pattern. In review, look for `LocalDateTime.now()`, `new Date()` and `Instant.now()` in business code.
- **Open session in view.** A common finding in Spring code reviews: it hides N+1 queries, and keeps database connections out of the pool for the whole request, including time spent writing a slow response. Many teams switch it off in the base configuration and treat the first `LazyInitializationException` as a design signal.
- **Test profiles and shared contexts.** A suite where every class has its own `@SpringBootTest` configuration takes many minutes. Reviewers on large services push for one base annotation and few distinct contexts.
- **Actuator exposure.** `env`, `configprops`, `heapdump` and `beans` are the endpoints security review asks about. They stay off, or behind authentication, outside local development.
