# Task 2.4: Entities and repositories

> **Sprint:** 2 · **Commit:** `Sprint 2.4: Add the entities and repositories` · **Status:** done (all four Done-when items met; `./gradlew build` passes with 121 tests; spec review: §9) · **Time taken:** roughly 45 minutes of work (18:49 to about 19:35 on 2026-10-30), including two rounds of mutation checks, the docs and this entry
> **Built:** the seven Phase 1 tables now have JPA entities (`User`, `Era`, `Template`, `WeeklyLog`, `Entry`, `Media`, `Tag`) on two base classes, and seven user-scoped repositories. `Entry` hides Recently deleted entries by default, and 43 new tests prove ownership, deletion, optimistic locking, batching and "one INSERT, no SELECT" by reading the SQL itself.

**What the docs didn't settle**
- **How "entry finders leave out entries in Recently deleted" is done.** The sprint plan says only that they do; TECH_STACK says "for example with `@SQLRestriction`". Handled in §4 (decision 2).
- **How the entity gets `source` for a tag.** The API returns each tag with a `source`, but the sprint plan lists no `EntryTag` entity, and a `@ManyToMany` can't read an extra column. Handled in §4 (decision 6): `source` is always `USER` in Phase 1, so a join table is enough until Phase 4.
- **Which JSON library Hibernate uses.** The docs say "Jackson 3" for Spring Boot 4 and note that Jackson 2 is also present ([TECH_STACK.md:77](../../TECH_STACK.md#L77)), but nothing says which one Hibernate's JSON mapper will pick. Found by a failing test (§8, item 2).
- **Whether `created_at` should use the injected `Clock`.** `@CreationTimestamp` uses the JVM clock. Kept (§4, decision 12): audit columns decide nothing.

## 3. The plan
1. **Base classes first** (`BaseEntity`, `TimestampedEntity`), because every entity extends one.
2. **Entities, from the leaves up:** `User`, `Era`, `Template`, `WeeklyLog`, `Tag`, then `Media` and `Entry` (they refer to each other, so they come together).
3. **Repositories** next to each entity, user-scoped.
4. **Compile, then write the tests before trusting any of it:**
   - `PersistableInsertTest` first, because "one INSERT, no SELECT" is the claim most likely to be wrong in a way nobody notices.
   - `EntityMappingTest` second: the context starting is the `validate` check, and the round trips catch what `validate` can't.
   - Then the repository tests: entries (ownership, Recently deleted, tags), versions, media, and the other four repositories.
5. **Mutation checks:** break the code on purpose (six changes at once, then two more) and see which tests notice. This is where two of my own assumptions turned out wrong (§8).
6. **Boot the real app against Compose**, then update the docs, run the full build, and write this entry.

The order matters in one place: the tests came before the mutation checks and the docs, so that what the docs say is what the tests showed.

## 4. Decisions and alternatives
| # | Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|---|
| 1 | How a foreign key (`user_id`, `weekly_log_id`, `template_id`, `reply_to_entry_id`, `cover_media_id`) is mapped | `@ManyToOne(fetch = LAZY)` on every one; a plain `UUID` field | A plain `UUID` field. The only associations are `Entry.media` / `Media.entry` and `Entry.tags` | Nothing walks these relationships: services compare ids and fetch the other side through its own user-scoped repository. A plain id needs no `getReferenceById` to build an entity, can't trigger a lazy-load query, and can't fail when it is touched outside the transaction (open-in-view is off) | No `entry.getTemplate().getName()` and no JPQL path through the relationship (an explicit join on the id works if one is ever needed). The database still enforces every foreign key |
| 2 | How entries in Recently deleted are left out | `@SQLRestriction("deleted_at IS NULL")` on `Entry`; a `…AndDeletedAtIsNull` suffix on every finder; a Hibernate `@Filter` switched on per session | `@SQLRestriction` | It fails safe: it applies to every JPQL and derived query, every load by id and every join to `Entry`, so a finder written next month can't forget it. Forgetting the suffix would leak a deleted entry into a list, a count or (Phase 4) an AI summary. Forgetting that Recently deleted needs its own query fails loudly instead, with an empty list | Two native queries for Recently deleted (`findDeletedByIdAndUserId`, `findDeletedByUserIdOrderByDeletedAtDesc`), because native SQL is not rewritten. Any native query that isn't about deleted entries must add `deleted_at IS NULL` itself. A lazy `Media.entry` of a deleted entry is expected to fail when initialised (not tested) |
| 3 | The repositories' base interface | `JpaRepository<X, UUID>` and a convention not to call `findById`; `Repository<X, UUID>` with only the methods we declare | `Repository<X, UUID>`. Each declares `save`, `delete` and its user-scoped finders | The rule is "never load user data by bare id". With `JpaRepository`, `findById`, `findAll` and `deleteById` are one autocomplete away. With `Repository`, they don't exist, so breaking the rule is a compile error. `UserRepository.findById` is the one exception, because the id there is the user's own | A service that needs a new query adds it to the repository. Test cleanup can't call `deleteAll()` (the tests roll back, or delete through `JdbcClient`) |
| 4 | `Entry.version`: `long` or `Long` | `Long` (null until saved); `long` | `long`. **Revised during the task.** I first chose `Long`, believing a primitive's 0 would make Hibernate treat a saved-once entry as new and INSERT it again. Mutating it to `long` changed no test result (§8, item 3) | Whether an entry is new is `isNew()`'s job (D-12). A primitive means `getVersion()` is never null, so the D-23 comparison in the service (`request.version() != entry.getVersion()`) has no boxing or NPE trap | Spring Data has its own new-check that can read a null wrapper version (as I understand its docs; not tried here), but `Persistable` replaces it for every entity anyway |
| 5 | Java type of `Entry.contentJson` and how Hibernate stores it | `Map<String, Object>`; `String`; Jackson 3 `JsonNode` with Hibernate picking the library; `JsonNode` with the library named in config | Jackson 3 `JsonNode`, and `hibernate.type.json_format_mapper` pinned to `Jackson3JsonFormatMapper` | `JsonNode` is what the TipTap validator and the response DTO want, and Spring MVC already reads request bodies as Jackson 3. Left to detect, Hibernate 7.4 picked Jackson 2 and failed to store a Jackson 3 `JsonNode` (§8, item 2), so the config names the one we use | One line of YAML to keep in step if Jackson 2 ever leaves the classpath (`hibernateStoresJsonWithJackson3` fails loudly if it drifts) |
| 6 | `entry_tags` | `@ManyToMany` with `@JoinTable`; an `EntryTag` entity with a composite key; `@ElementCollection` of tag ids | `@ManyToMany Set<Tag>` on `Entry`, no entity for the link | The sprint plan lists seven entities. Hibernate writes only `entry_id` and `tag_id`, and the table's defaults fill `source = 'USER'` and `created_at`. A `Set` writes only the rows that changed (a test shows one DELETE and one INSERT) | Phase 4 can't record `AI` this way: it needs an `EntryTag` entity then. Until then the API's `source` is always `USER`, which is true |
| 7 | Cascade from `Entry` to `Media` | `cascade = ALL, orphanRemoval = true`; no cascade, with `ON DELETE CASCADE` doing the work | No cascade. `Entry.media` is read-only here; rows are saved through `MediaRepository` | An upload adds one `Media` at a time, so the entry's collection shouldn't have to be loaded to add to it. Erasing an entry is one `DELETE FROM entries`; the foreign key removes the media rows, and a test shows Hibernate never touches the `media` table. The service deletes the stored files first (TECH_STACK §2 Storage) | `entry.getMedia()` can be stale if media is added through the repository in the same transaction |
| 8 | How a test reads the SQL Hibernate sends | Hibernate `Statistics` (counts only); a `StatementInspector` (needs extra Spring config, so a second app context and container); `datasource-proxy` (a new dependency); a Logback list appender on `org.hibernate.SQL` | The Logback appender, as `SqlLog` | Gives the statements themselves. It changes no Spring config, so every test keeps sharing the one cached context and container. No new dependency | It reads a log category, which Hibernate could rename. The control test (`merge` does show a SELECT) fails if the capture ever goes blind |
| 9 | Test style for repositories | `@DataJpaTest` slices; `@IntegrationTest` (the full app) | `@IntegrationTest` | `backend.md` asks for `@SpringBootTest` with Testcontainers for anything touching the database, and the shared context makes each extra class cost milliseconds. Most classes are `@Transactional`, so they roll back | `EntryVersionTest` can't be transactional (it needs real commits) and deletes its own user instead |
| 10 | Build the two "deleted" native finders now? | Wait for task 3.11; build them now | Build the two finders (not restore, erase or the sweep) | A decision with an unproven escape hatch is a gamble. The tests show the filter hides deleted rows, and that these queries, plus `Entry.media` from the deleted entry, are enough for restore and erase | Slightly ahead of 3.11. They are 12 lines and fully tested |
| 11 | `media.purpose` and `media_type` as strings or enums | Java enums with `@Enumerated(STRING)`; `String`s with constants | `String`s, with `PURPOSE_PHOTO` and `PURPOSE_PAGE_SCAN` constants | D-20 says they are checked in the service, so a new purpose needs no migration. | 12 | `createdAt` / `updatedAt` from `@CreationTimestamp` (JVM clock) rather than the `Clock` bean | Inject the `Clock` through a listener; accept Hibernate's clock | Hibernate's | These stamp audit columns that no rule reads. ## 5. How it was built
Read in this order.

**`common/BaseEntity` and `TimestampedEntity`**
- [`BaseEntity.java`](../../../backend/src/main/java/com/memoirist/common/BaseEntity.java#L27-L84): `@MappedSuperclass`, so its fields become columns of every subclass's table. The `id` has no generator; the constructor sets it (D-12). The practice block at [L33-L53](../../../backend/src/main/java/com/memoirist/common/BaseEntity.java#L33-L53) is the `Persistable` part: a `@Transient` flag, `isNew()`, and one method annotated `@PostLoad` and `@PostPersist` that clears it. The protected no-argument constructor is for Hibernate, which builds an entity with it and then fills the fields; because the flag starts `true`, `@PostLoad` is what makes a loaded entity "not new". `equals` compares the real classes (a Hibernate proxy is a subclass) and goes through `getId()`, because a proxy's own `id` field is empty until it is loaded.
- [`TimestampedEntity.java`](../../../backend/src/main/java/com/memoirist/common/TimestampedEntity.java#L24-L31): `@CreationTimestamp` (`updatable = false`) and `@UpdateTimestamp`, both `Instant`, stored as `TIMESTAMPTZ`.

**The entities** (each is a class with `@Column` fields, a protected no-argument constructor and a public one that takes the id)
- [`User`](../../../backend/src/main/java/com/memoirist/user/User.java), [`Era`](../../../backend/src/main/java/com/memoirist/era/Era.java), [`WeeklyLog`](../../../backend/src/main/java/com/memoirist/week/WeeklyLog.java), [`Tag`](../../../backend/src/main/java/com/memoirist/tag/Tag.java): flat. `user_id`, `start_date` and `end_date` are `updatable = false`, so a stray setter can't move a row to another user or week. `WeeklyLog`'s constructor computes `endDate = startDate + 6`; `is_closed` is the field `closed`.
- [`Template`](../../../backend/src/main/java/com/memoirist/template/Template.java#L25): `subheadings` is a `List<String>` with `@JdbcTypeCode(SqlTypes.JSON)`. The getter returns a copy and the setter replaces the whole list, because Hibernate notices a new list but can't see a change made inside the old one.
- [`Media`](../../../backend/src/main/java/com/memoirist/media/Media.java#L24-L58): extends `BaseEntity` only, with `uploaded_at` from `@CreationTimestamp` (the table has no `created_at`/`updated_at`). `entry` is a `LAZY`, non-optional `@ManyToOne`, so Hibernate can map the other side and the finders can reach `entry.userId`.
- [`Entry`](../../../backend/src/main/java/com/memoirist/entry/Entry.java):
  - [L48](../../../backend/src/main/java/com/memoirist/entry/Entry.java#L48) `@SQLRestriction("deleted_at IS NULL")`: the whole Recently deleted design in one line (decision 2).
  - [L69-L71](../../../backend/src/main/java/com/memoirist/entry/Entry.java#L69-L71) `contentJson` as a Jackson 3 `JsonNode`.
  - [L118-L120](../../../backend/src/main/java/com/memoirist/entry/Entry.java#L118-L120) `@Version long version`, with a getter and no setter (D-23).
  - [L128-L144](../../../backend/src/main/java/com/memoirist/entry/Entry.java#L128-L144) `media` (`@OneToMany(mappedBy)`, `@OrderBy`, `@BatchSize(50)`) and `tags` (`@ManyToMany` over `entry_tags`, `@BatchSize(50)`). Both getters return unmodifiable views.
  - [`replaceTags`](../../../backend/src/main/java/com/memoirist/entry/Entry.java#L286) keeps the same `Set` and does `retainAll` then `addAll`, so Hibernate writes only the rows that changed.
  - Its Javadoc says the two things a reader must not forget: never turn an `Entry` into a response by hand (`EntryMapper`, D-10), and the restriction.

**The repositories** (all `extends Repository<X, UUID>`, decision 3)
- [`EntryRepository`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java): `findByIdAndUserId` ([L25](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L25)), `findByIdInAndUserId` for loading a page of weeks' children, the week's entries in feed order (backed by `idx_entries_week_date`), and the two native Recently deleted queries ([L33-L47](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L33-L47)). It does **not** filter sealed entries: the feed shows them as locked rows and `EntryMapper` hides them, and a count or filter that must ignore them says so itself (D-10).
- [`MediaRepository`](../../../backend/src/main/java/com/memoirist/media/MediaRepository.java#L18-L20): `findByIdAndEntryUserId`. Derived-query names walk property paths, so `EntryUserId` is `entry.userId`, which joins `entries`, which carries the Recently deleted restriction.
- [`TagRepository`](../../../backend/src/main/java/com/memoirist/tag/TagRepository.java): includes `findByIdInAndUserId`, so a service can compare the size of the answer with the ids it was given and answer `404` for a tag that isn't theirs.
- [`EraRepository`](../../../backend/src/main/java/com/memoirist/era/EraRepository.java), [`TemplateRepository`](../../../backend/src/main/java/com/memoirist/template/TemplateRepository.java), [`WeeklyLogRepository`](../../../backend/src/main/java/com/memoirist/week/WeeklyLogRepository.java), [`UserRepository`](../../../backend/src/main/java/com/memoirist/user/UserRepository.java): the smallest set Sprint 3 will obviously use.

**Configuration**
- [`application.yml`](../../../backend/src/main/resources/application.yml#L26-L30): `spring.jpa.properties.hibernate.type.json_format_mapper: …Jackson3JsonFormatMapper`, with a comment on why.

**Test support**
- [`SqlLog.java`](../../../backend/src/test/java/com/memoirist/SqlLog.java#L48-L72): attaches a Logback `ListAppender` to `org.hibernate.SQL`, raises that logger to DEBUG and stops it reaching the console, and puts all three back in `close()`. Use it in try-with-resources.
- [`Fixtures.java`](../../../backend/src/test/java/com/memoirist/Fixtures.java): unsaved test objects with random ids.

## 6. How it was tested
**Strategy.** Everything here talks to Postgres, so every class is an `@IntegrationTest` against a Testcontainers Postgres (D-14), sharing the one cached application context from task 2.2. Most classes are `@Transactional`: each test rolls back, `em.flush()` writes to Postgres and `em.clear()` empties the persistence context, so the next query really reads the database. Where a test claims something about SQL, it reads the SQL (`SqlLog`) instead of trusting the code. After the tests passed, I broke the code on purpose to see which tests noticed (§8).

## 10. Concepts to learn from this task
- **`Persistable<UUID>` and `isNew()`** ([`BaseEntity.java:33-53`](../../../backend/src/main/java/com/memoirist/common/BaseEntity.java#L33-L53)): Spring Data's `save()` calls `persist` for a new entity and `merge` for an existing one. For an entity whose id is already set it assumes "existing" and `merge` runs a SELECT first. Implementing `Persistable` lets the entity answer. The mistake people make: forgetting the flag must be cleared after a load, so the entity is "new" forever. Then `delete()` silently does nothing (Spring Data skips deleting a new entity), which `removingAnEntryLeavesItsMediaToTheDatabaseCascade` showed when I broke the flag.
- **`@MappedSuperclass` and JPA lifecycle callbacks** (`BaseEntity`): a mapped superclass isn't an entity itself; its fields and its `@PostLoad`/`@PostPersist` methods are inherited by every entity that extends it.
- **`@Version` and optimistic locking** ([`Entry.java:118`](../../../backend/src/main/java/com/memoirist/entry/Entry.java#L118), `EntryVersionTest`): Hibernate adds `AND version = ?` to each UPDATE and bumps the number; if no row matches, it throws and Spring translates it to `ObjectOptimisticLockingFailureException`. Two places catch a stale write: when you save a detached copy (Hibernate compares versions during `merge`) and when two transactions race (the UPDATE changes zero rows). The mistake: copying the client's version onto the entity, which defeats the check.
- **`@SQLRestriction`** ([`Entry.java:48`](../../../backend/src/main/java/com/memoirist/entry/Entry.java#L48)): a SQL fragment Hibernate adds to every query, load and join for that entity. It is invisible when you read a finder, so it must be documented where it matters (this entry's Javadoc and TECH_STACK). Native queries bypass it, which is how Recently deleted gets in.
- **Native queries returning entities** ([`EntryRepository.java:33-47`](../../../backend/src/main/java/com/memoirist/entry/EntryRepository.java#L33-L47)): `@Query(nativeQuery = true)` can return a mapped entity from `SELECT *`. Hibernate runs the SQL as written; it still fills in the entity and calls `@PostLoad`.
- **Spring Data repository base interfaces** ([`EraRepository.java`](../../../backend/src/main/java/com/memoirist/era/EraRepository.java)): `extends Repository<X, UUID>` exposes nothing; redeclare a method with a standard signature (`save`, `delete`) and Spring Data wires it to its implementation. Derived-query names (`findByIdInAndUserId`, `…EntryUserId`) are parsed into property paths and checked when the application starts, so a typo stops the app rather than failing at the first call.
- **N+1 and `@BatchSize`** ([`Entry.java:128-131`](../../../backend/src/main/java/com/memoirist/entry/Entry.java#L128-L131)): loading N entries and then touching each one's lazy `media` runs N more queries. `@BatchSize(size = 50)` makes Hibernate load the media of up to 50 entries in one query the first time any of them is needed. The test counts the `select … from media` statements.
- **`@OrderBy`** (`Entry.media`): sorts in SQL (`ORDER BY display_order`). Don't rely on the order rows come back in; a test of the *values* can pass by luck, so check the SQL.
- **Plain id versus association:** an `@ManyToOne` gives you navigation and costs you proxies and lazy-loading traps; a `UUID` field gives you neither. Choose by what the code walks.
- **`@ManyToMany` over a join table** (`Entry.tags`): Hibernate writes only the two key columns, so the table's other columns need defaults. Use a `Set`, so removing one link is one DELETE, not "delete all, insert all".
- **`ON DELETE CASCADE` versus JPA `cascade`:** the database can delete children by itself. JPA's `cascade = REMOVE` loads each child and deletes it one at a time. Pick one, and say which in the code.
- **`@JdbcTypeCode(SqlTypes.JSON)` and the JSON format mapper:** Hibernate hands the value to a "format mapper" (Jackson 2, Jackson 3 or JSON-B) to turn it into text. With two Jackson versions present, name the one you mean.
- **`TransactionTemplate` and `PROPAGATION_REQUIRES_NEW`** ([`EntryVersionTest.java`](../../../backend/src/test/java/com/memoirist/entry/EntryVersionTest.java#L56-L73)): run a block in its own transaction from plain test code. `REQUIRES_NEW` suspends the current transaction and uses a second connection, which is how a test plays "another device" in the middle of a transaction.
- **Reading the SQL in a test** ([`SqlLog.java`](../../../backend/src/test/java/com/memoirist/SqlLog.java)): Hibernate logs each statement to `org.hibernate.SQL` at DEBUG; a Logback `ListAppender` collects them. Always write a control that should produce the unwanted statement, so you know the capture works.
- **Mutation checks:** change the code on purpose and see whether a test fails. A test you've never seen fail may not be testing what you think.
- **AssertJ:** `extracting(Media::getId).containsExactly(...)` reads a property from each element; `usingRecursiveComparison().ignoringFields(...)` compares objects field by field.

## 12. At work
- **The ownership test is the one to copy.** Every service that returns a customer's record by id needs a test where someone else asks for it and gets "not found". The common review comment is "where is the negative test?" The second most common is the missing positive control that proves the negative isn't just an empty table.
- **Soft delete and tenant filters** (`@SQLRestriction`, `@Where`, Hibernate `@Filter`, or a database view with row-level security) are the usual way to make "deleted" or "not yours" the default instead of something each query remembers. The review question is the one decision 2 answers: what happens to the next query someone writes, and to native SQL, which skips the filter?
- **Narrow repository interfaces** are a cheap way to make a rule unbreakable. In a codebase with `JpaRepository` everywhere, you'd pair the rule with an architecture test (ArchUnit) instead.
- **Optimistic locking** protects any record two people can edit (a customer's contact details, a payment instruction). The review points: the client sends the version it read; the server compares and returns `409`; the version is never copied from the request; and there is a test for the stale write.
- **Client-chosen ids and `Persistable`** are the same idea as an idempotency key: the caller picks the id, so a retried create is recognised (`200` with the stored record) instead of duplicated. The performance side (no SELECT) is the part that surprises people in review.
- **Dependency conflicts show up as runtime failures.** Two Jackson major versions on one classpath, and a library that "auto-detects" one, is a real production incident waiting for an upgrade. Name the choice in config and test it.
- **"Show me the SQL"** is a normal review request for JPA code. Counting statements in a test (N+1) is far more convincing than saying "it's lazy-loaded".
