**What the docs didn't settle, and how it was handled:**
- **Starter names.** The sprint plan lists "web" and "spring-boot-starter-test" in Boot 3 terms. Boot 4 renamed `spring-boot-starter-web` to `spring-boot-starter-webmvc` (the old name still works but is deprecated) and gives every technology its own test starter, each of which brings `spring-boot-starter-test`; its migration guide says to list those instead. The build follows Boot 4. The sprint plan wasn't edited; this is listed as an assumption.
- **JUnit 5 or 6.** Boot 4.1.2 manages JUnit Jupiter **6.0.3**. D-14 said "JUnit 5", which was merely out of date (the decision is "JUnit and Testcontainers, no H2"), so D-14 now says JUnit 6 and its Updated date is 2026-10-29.

- **How much configuration.** Enough to boot against Compose and no more; §5 lists what 2.2 replaces.
- No open question (Q-x) or flow gap (G-xx) was involved.

## 3. The plan
1. **Pin the versions before writing anything.** "Latest patch" and "the Boot-4-compatible line" are facts that change week to week, and the first dependency download takes minutes, so getting a version wrong is expensive. The sources: Initializr's metadata, Gradle's version service, Maven Central, release notes.
2. **Generate a reference project in the scratchpad, not the repo.** An Initializr project for Boot 4.1.2 and Java 25 shows Boot 4's real starter names (no Boot 3 guesswork) and brings a wrapper. Its wrapper jar's SHA-256 was compared with Gradle's published sum before anything was copied.
3. **Wrapper and build file, then `./gradlew --version`.** That downloads Gradle and proves the checksum line works before any dependency resolves.
4. **Resolve the dependencies and read the tree** (`dependencies`, `dependencyInsight`). Two surprises came out of it: JUnit 6, and Jackson 2 sitting next to Jackson 3.
5. **Minimal configuration**, so the `local` profile can reach Compose.
6. **An exploration test before the real assertions.** A throwaway test printed what each endpoint returns on Boot 4. It changed the test design (§8).
7. **The smoke test, Spotless, then `./gradlew build`.**
8. **Run the app with the `local` profile**, `curl` the endpoints, stop it.
9. **Check one failure mode** (`.env` not found), because 2.1 introduced the import.
10. **Docs, then this entry**, from notes kept since the first command.

## 5. How it was built
Read the change in this order.

**1. The wrapper: [`gradlew`](../../../backend/gradlew), [`gradlew.bat`](../../../backend/gradlew.bat), [`gradle-wrapper.jar`](../../../backend/gradle/wrapper/gradle-wrapper.jar) and [`gradle-wrapper.properties`](../../../backend/gradle/wrapper/gradle-wrapper.properties).** Copied from the Initializr project after checking the jar's hash. The root `.gitattributes` already keeps `gradlew` as LF, `gradlew.bat` as CRLF and the jar as binary, so `backend/` needs no `.gitattributes` of its own.
- Line 3, `distributionSha256Sum`: the SHA-256 of `gradle-9.8.2-bin.zip`, from `https://services.gradle.org/distributions/gradle-9.8.2-bin.zip.sha256`. The first `./gradlew --version` downloaded the zip, checked it and printed `Gradle 9.8.2 … Launcher JVM: 25.0.5 … Daemon JVM: … (no Daemon JVM specified, using current Java home)`.
- Line 4, `distributionUrl`: the `\:` is how a `.properties` file escapes a colon.
- `gradlew` must also be **executable in git**. On Windows, git doesn't record that by default (`core.filemode=false` here), and Linux CI (task 2.7) would fail with `Permission denied`. The close-out staged it with `git add --chmod=+x -- backend/gradlew`, so the commit records it as `100755` (§9, finding 1). Later `git add`s keep that mode.

**2. [`settings.gradle.kts:1`](../../../backend/settings.gradle.kts#L1).** One line: the project name.

**3. [`build.gradle.kts`](../../../backend/build.gradle.kts)**, the heart of the task.
- **Lines 3–8, plugins.** `java`; Spring Boot's plugin (`bootRun`, `bootJar`, and the `-parameters` compiler flag that Spring needs to read parameter names); the dependency-management plugin, which imports Boot's BOM so that dependencies need no versions; Spotless.
- **Lines 13–18, the toolchain.** `languageVersion = JavaLanguageVersion.of(25)`. Gradle compiles and runs the tests with a JDK 25 it finds on the machine, whatever JDK started Gradle. The `=` works because Gradle's Kotlin DSL lets you assign to a `Property<T>`; in older builds you'll see `.set(...)`.
- **Lines 24–29, the AWS BOM.** Boot doesn't manage the AWS SDK, so its own BOM is imported. That's why line 47 has no version.
- **Line 32, `configurations.create("mockitoAgent")`.** A separate bucket of dependencies used only to find Mockito's jar (line 60, `isTransitive = false`: the jar alone).
- **Lines 37–43, the starters.** The Boot 4 names: `spring-boot-starter-webmvc` (Spring MVC and Tomcat), `-data-jpa`, `-validation`, `-actuator` and **`-flyway`**. Line 42, `flyway-database-postgresql`, is Flyway's Postgres support, which Flyway moved out of its core jar. Line 43: the driver is `runtimeOnly`, because code compiles against JDBC's interfaces, never against the driver.
- **Lines 46–47:** springdoc 3.2.0 (the Swagger UI and `/v3/api-docs`) and the S3 module, for task 3.1.
- **Lines 51–59, test dependencies.** Five test starters, Boot's Testcontainers support, the two Testcontainers modules, and `junit-platform-launcher` as `testRuntimeOnly`, which Gradle needs to start the JUnit Platform.
- **Lines 63–73, the `Test` task.** Line 64 runs JUnit. Line 68 adds `-javaagent:<mockito jar>` to the test JVM. The lambda runs when the tests start, so Gradle doesn't resolve the configuration while it reads the build file. Lines 69–72 print every test's result, with full stack traces on failure.
- **Lines 75–80, Spotless.** `palantirJavaFormat("2.102.0")`. Spotless adds `spotlessCheck` to `check`, so `./gradlew build` fails on badly formatted Java.

**4. [`application.yml`](../../../backend/src/main/resources/application.yml)**: only `spring.application.name: memoirist`, which shows up in every log line (`--- [memoirist]`).

**5. [`application-local.yml`](../../../backend/src/main/resources/application-local.yml)**, the minimum that boots against Compose.
- Line 8, `import: optional:file:../.env[.properties]`. `file:` is a path relative to the working directory (`backend/` under `./gradlew bootRun`). `[.properties]` is an *extension hint*: `.env` has no extension Spring recognises, so the hint says "parse it as a `.properties` file", and `KEY=value` lines with `#` comments are valid `.properties`. `optional:` means a missing file is skipped instead of failing startup.
- Lines 10–12: `${DB_URL}`, `${POSTGRES_USER}` and `${POSTGRES_PASSWORD}` are resolved from the imported file. Without `.env`, the error is confusing (§8, item 8).
- **What task 2.2 replaces or adds:** the rest of `application.yml` (`ddl-auto=validate`, `hibernate.jdbc.time_zone=UTC`, multipart limits), the rest of this profile (Flyway locations with `db/seed-local`, `StorageProperties`, the dev user), `application-test.yml`, the UTC default in `main` and the `Clock` bean. It may also move the datasource keys into `application.yml`, so that `prod` sets them from the environment. Not in 2.2's list, but worth deciding there: `spring.jpa.open-in-view`, whose default logs a warning at every start (`spring.jpa.open-in-view is enabled by default…`).

**6. [`MemoiristApplication.java`](../../../backend/src/main/java/com/memoirist/MemoiristApplication.java)**: the plain `@SpringBootApplication` main class. `TimeZone.setDefault(UTC)` belongs to task 2.2, which has a test for it.

**7. [`TestcontainersConfiguration.java`](../../../backend/src/test/java/com/memoirist/TestcontainersConfiguration.java).**
- Line 15, `@TestConfiguration(proxyBeanMethods = false)`: configuration that component scanning ignores, so a test opts in with `@Import`. `proxyBeanMethods = false` skips the CGLIB subclass that would make bean methods calling each other return singletons; nothing here needs it.
- Lines 21–25: a `@Bean` that returns the container, with **`@ServiceConnection`**. Spring Boot starts the container with the context, reads its JDBC URL, user and password, and creates the `DataSource` from them. There's no `spring.datasource.url` for tests at all.
- Line 6: `org.testcontainers.postgresql.PostgreSQLContainer`, the Testcontainers 2 class. The old `org.testcontainers.containers.PostgreSQLContainer` still exists but is deprecated. The class is `public` so test classes in feature packages (`com.memoirist.entry`, …) can import it.

**8. [`ApplicationSmokeTest.java`](../../../backend/src/test/java/com/memoirist/ApplicationSmokeTest.java).**
- Lines 21–25: the whole app on a random port, one test-only property (`show-components`), a `RestTestClient` already pointed at that port, and the Postgres container.
- Lines 31–49: the health test, which is the practice block (§11).
- Lines 51–63: `/v3/api-docs` returns JSON whose `openapi` field starts with `3.` (it's `3.1.0`).
- Lines 65–77: `/swagger-ui.html` ends on an HTML page whose title is `Swagger UI`.

## 6. How it was tested
- **Strategy:** one integration test that starts the whole app on a real port against real Postgres, because every Done-when item is about the assembled app, not a unit of logic. There's no logic yet to unit-test. Then the manual run with the `local` profile, because the tests deliberately don't use it (no `.env` in tests).

| Test | Proves | Type |
|---|---|---|
| `ApplicationSmokeTest.healthIsUpAndIncludesTheDatabase` | The app starts against Postgres 17 in Docker, `/actuator/health` is `200` and `UP`, and `db` is one of the checks, also `UP` | Integration (Testcontainers, real HTTP) |
| `ApplicationSmokeTest.servesTheOpenApiDocument` | springdoc is wired: `/v3/api-docs` is JSON with an `openapi` version 3.x | Integration |
| `ApplicationSmokeTest.swaggerUiLoads` | `/swagger-ui.html` ends on Swagger UI's HTML page | Integration |
| `spotlessCheck` (part of `build`) | Every Java file is formatted | Build check |

- **How to run them yourself** (Git Bash, Docker running):

```bash
cd backend
./gradlew build                                   # compile, spotlessCheck, tests; ends with BUILD SUCCESSFUL
./gradlew test --tests '*ApplicationSmokeTest'    # just the smoke test
```

  Passing output lists `ApplicationSmokeTest > healthIsUpAndIncludesTheDatabase() PASSED` (and the other two), then `BUILD SUCCESSFUL`. The first run takes minutes (downloads); later runs take about 1.5 minutes, of which about a minute is the test's Spring context and Postgres container. The HTML report is `build/reports/tests/test/index.html`.
- **Manual checks**, with Compose up (`docker compose up -d`):

```bash
cd backend && ./gradlew bootRun --args='--spring.profiles.active=local'   # wait for "Started MemoiristApplication"
# in another terminal:
curl -s localhost:8080/actuator/health                                    # {"groups":["liveness","readiness"],"status":"UP"}
curl -s -o /dev/null -w '%{http_code} -> %{redirect_url}\n' localhost:8080/swagger-ui.html   # 302 -> .../swagger-ui/index.html
curl -sL localhost:8080/swagger-ui.html | grep -o '<title>[^<]*</title>'  # <title>Swagger UI</title>
curl -s localhost:8080/v3/api-docs                                        # {"openapi":"3.1.0",...,"paths":{},...}
```

  Then open http://localhost:8080/swagger-ui.html in a browser: the API has no operations yet, which is right until Sprint 3 adds endpoints. Stop the app with Ctrl+C.

## 10. Concepts to learn from this task
- **The Gradle wrapper and its two checksums** ([gradle-wrapper.properties:3](../../../backend/gradle/wrapper/gradle-wrapper.properties#L3)): `gradlew` is a script that runs `gradle-wrapper.jar`, which downloads the Gradle version named in `distributionUrl`. Two things can be tampered with: the jar in the repo (check it against `https://services.gradle.org/distributions/gradle-<v>-wrapper.jar.sha256`; in CI, the `gradle/actions/wrapper-validation` action does it) and the zip it downloads (`distributionSha256Sum`). The common mistake is updating `distributionUrl` without the sum, which fails, or deleting the sum to make it pass.
- **Launcher JVM vs toolchain** ([build.gradle.kts:13](../../../backend/build.gradle.kts#L13)): the JVM that runs Gradle (from `JAVA_HOME`) and the JDK that compiles and tests your code are separate. `./gradlew -q javaToolchains` lists what Gradle found. So Gradle could run on JDK 21 and still build for 25, as long as a JDK 25 is installed.
- **Boot 4's modular starters** ([build.gradle.kts:37](../../../backend/build.gradle.kts#L37)): every technology has `spring-boot-<tech>` (code and auto-configuration, package `org.springframework.boot.<tech>`), `spring-boot-starter-<tech>` and `spring-boot-starter-<tech>-test`. The trap is **silent**: in Boot 3, `flyway-core` alone switched Flyway on, because its auto-configuration lived in the big `spring-boot-autoconfigure` jar. In Boot 4 that class is `org.springframework.boot.flyway.autoconfigure.FlywayAutoConfiguration` in `spring-boot-flyway` (the 4.1.2 `spring-boot-autoconfigure` jar has no Flyway class at all), so with `flyway-core` alone the app starts happily and never migrates. Here, the boot log's Flyway lines prove it runs.
- **BOMs and versionless dependencies** ([build.gradle.kts:24](../../../backend/build.gradle.kts#L24)): a BOM (bill of materials) is a POM that only lists versions. Importing one lets you write `implementation("software.amazon.awssdk:s3")` and get the version the BOM chose, consistent with its siblings. Boot's BOM is why most lines here have no version. `./gradlew dependencyInsight --dependency <name>` explains where any version came from; it found that Jackson 2 comes from springdoc.
- **`implementation`, `runtimeOnly`, `testImplementation`, `testRuntimeOnly`** (lines 37–60): what's on the compile classpath, the runtime classpath, or both, for main code or tests. The Postgres driver is `runtimeOnly` so nobody can import `org.postgresql` classes by accident; the JUnit launcher is `testRuntimeOnly` because only Gradle calls it.
- **`@ServiceConnection` on a container bean** ([TestcontainersConfiguration.java:22](../../../backend/src/test/java/com/memoirist/TestcontainersConfiguration.java#L22)): Spring Boot turns a running container into `ConnectionDetails` (URL, user, password), which beat any `spring.datasource.*` property. Before Boot 3.1 you wrote a `@DynamicPropertySource` method that copied `container.getJdbcUrl()` into properties; you'll still see that in older codebases.
- **Spring's test context cache**: Spring keeps each test application context, keyed by its configuration (classes, properties, profiles, `webEnvironment`, mock beans), and reuses it for every test class with the same key. Containers that are beans are shared along with it. Every new key costs a full context start (about a minute here), so a test suite should use few distinct configurations.
- **`RestTestClient`** ([ApplicationSmokeTest.java:38](../../../backend/src/test/java/com/memoirist/ApplicationSmokeTest.java#L38)): new in Spring Framework 7. It has the same fluent shape as WebFlux's `WebTestClient` (`get().uri(…).exchange().expectStatus().isOk().expectBody().jsonPath(…).isEqualTo(…)`) but works with Spring MVC, against a real server or MockMvc. `@AutoConfigureRestTestClient` points it at the random port.
- **Actuator health in Boot 4**: the response is an *aggregate* of health indicators (`db`, `diskSpace`, `ping`, …); one `DOWN` makes the whole thing `DOWN` (HTTP 503). `show-components` names the indicators; `show-details` adds their details (such as the database product). Both default to `never`, because health URLs are often reachable by load balancers and the public. Boot 4 also turns on the `liveness` and `readiness` groups that Kubernetes probes call.
- **`spring.config.import`** ([application-local.yml:8](../../../backend/src/main/resources/application-local.yml#L8)): pulls in another config source. `optional:` tolerates a missing file, `file:` is relative to the working directory, and `[.properties]` tells Spring how to parse a file with an unknown extension. A placeholder that can't be resolved is left as literal text (§8, item 8).
- **JEP 451, dynamic agents** ([build.gradle.kts:68](../../../backend/build.gradle.kts#L68)): a Java agent can rewrite classes as they load; Mockito uses one for inline mocks (mocking final classes and static methods). Since Java 21 a library that attaches an agent to its own running JVM triggers a warning, and future JDKs will block it, so you name the agent at startup with `-javaagent:`. A `CommandLineArgumentProvider` computes the argument when the task runs, which keeps the configuration lazy.
- **Kotlin DSL syntax worth recalling:** `plugins { id("…") version "…" }`; `tasks.withType<Test> { … }` (a reified generic: configure every task of that type); `configurations.create("name")`; a dependency with a configuration block, `mockitoAgent("g:a") { isTransitive = false }`; property assignment with `=` (`languageVersion = …`, `exceptionFormat = …`).
- **Two Jacksons on one classpath**: Boot 4's JSON is Jackson 3, whose packages moved to `tools.jackson.*`, except the annotations, which stay in `com.fasterxml.jackson.annotation`. springdoc's swagger-core still uses Jackson 2 (`com.fasterxml.jackson.databind`). An IDE will happily auto-import Jackson 2's `ObjectMapper`, and Boot 4 has no bean of that type, so check the package when you import.
- **Line endings, git and formatters**: `core.autocrlf=true` makes git write CRLF into a Windows working copy and store LF in the repository. Tools that compare files byte by byte (Spotless, some test fixtures) have to agree with git, which is why Spotless's default policy reads `.gitattributes` and git's config.

## 12. At work
- **The Boot 3 → 4 upgrade.** Banks run many Spring Boot services, and each will make this jump. The silent Flyway trap (§10) is the one to catch in review: an app that starts fine but never migrates is a production incident waiting for the next release. Look for `flyway-core` or `liquibase-core` without their Boot 4 starters, `spring-boot-starter-test` without the technology test starters, and `TestRestTemplate` or MockMvc tests that lost their `@AutoConfigure…` annotation. The "classic" starters can keep an old app compiling while you migrate.
- **Supply-chain controls.** Banks usually forbid builds that download whatever a URL serves. Expect `distributionUrl` to point at an internal Artifactory or Nexus mirror, `distributionSha256Sum` to be required, `repositories {}` to name only the internal mirror, and Testcontainers to pull images through an internal registry (its *image name substitution*, for example `hub.image.name.prefix`). A reviewer would reject `version "+"`, `latest` tags and unpinned plugins.
- **Health checks behind load balancers and Kubernetes.** Liveness ("restart me if this fails") and readiness ("send me traffic only if this passes") map to Boot 4's two groups. A common bank rule: show details only to authorised callers (`show-details: when-authorized`) and keep slow dependencies out of liveness, so a slow database doesn't make Kubernetes restart every pod at once.
- **Formatting in CI.** A `spotlessCheck` gate ends style comments in reviews. Introduce it in one dedicated "reformat everything" commit, list that commit in `.git-blame-ignore-revs` so `git blame` skips it, and pin the formatter version.
- **Reviewing a build PR.** Ask: are versions pinned and from a BOM where one exists? Is there one mechanism for dependency management, not two? Does `--warning-mode all` come out clean? Do the tests use the real database engine, not H2? Is the wrapper jar unchanged, or validated if it changed?
