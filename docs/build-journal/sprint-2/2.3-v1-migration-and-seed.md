# Task 2.3: V1 migration and local seed

> **Sprint:** 2 · **Commit:** `Sprint 2.3: Add the V1 core schema and the local dev-user seed` · **Status:** done (both Done-when items met; `./gradlew build` passes with 78 tests; spec review: pass with notes, §9) · **Time taken:** roughly 30 minutes of work (18:18 to about 18:48 on 2026-10-30), including the checks, the docs and this entry
> **Built:** the database schema exists. `V1__core_schema.sql` creates the eight Phase 1 tables, and `R__seed_dev_user.sql` adds the dev user in the `local` and `test` profiles only. Four new test classes prove the result: what Flyway applied, what the database refuses, and what it deletes with a parent row.

## 1. The goal
[Task 2.3](../../SPRINT_PLAN.md) turns the V1 SQL that has lived in [DATABASE_SCHEMA.md](../../DATABASE_SCHEMA.md#v1-sql-v1__core_schemasql) since Sprint 1 into two real files that Flyway runs:

| File | Loaded by | What it does |
|---|---|---|
| `db/migration/V1__core_schema.sql` | every profile | Creates `users`, `eras`, `templates`, `weekly_logs`, `entries`, `media`, `tags` and `entry_tags`, with their constraints and 12 explicit indexes (11 plain or partial, and the case-insensitive tag index) |
| `db/seed-local/R__seed_dev_user.sql` | `local` and `test` only | Inserts the dev user `00000000-0000-0000-0000-000000000001` (D-11) |

It comes now because everything after it needs tables to exist:

| Later task | What it needs from 2.3 |
|---|---|
| 2.4 Entities | A schema to validate against: with `ddl-auto=validate` the app refuses to start if an entity maps a column that V1 doesn't have |
| 2.5 Current user | The dev user row, which the dev-header provider falls back to |
| 3.x endpoints | Every repository query, and every test that saves an entity |

Task 2.2 had already put `ddl-auto=validate` and the two Flyway locations in place, so this task is only the SQL and the proof that it behaves as the spec says. There is no Java in `src/main` for it.

**Done when:** a Testcontainers test applies the migrations to an empty database and finds the dev user; a local boot shows V1 in `flyway_schema_history`.

One more constraint shaped the task: **once V1 is committed, a hook blocks edits to it** ([`protect-migrations.mjs`](../../../.claude/hooks/protect-migrations.mjs)), and Flyway would refuse to start a database that applied the old text. So this is the last moment V1 can change cheaply, and the checks below were run before the close-out commits it.

**What the docs didn't settle**
- **Whether to keep the two inline `UNIQUE` names** (1.3's open finding). The sprint plan says "exactly as specified", the conventions say `uq_<table>_<cols>`, and the 1.3 close-out recorded that V1 would be committed with the default names. Handled in §4.

## 3. The plan
1. **Copy the two SQL blocks out of the doc with a script** (`awk` between the code fences), so a typo can't creep in, and diff the result against the doc.
2. **Write the tests before trusting the files** (all in `com.memoirist.db`): `MigrationsTest` (plain Flyway), `SchemaTest` (what the app finds), `SchemaConstraintsTest` (what the database refuses and deletes), `DeferredUniqueConstraintTest` (the commit-time check). Run them.
3. **Break V1 on purpose** (a mutation check) to see that the tests notice.
4. **Check that Flyway's checksum ignores line endings**, because this repo checks files out with CRLF on Windows.
5. **Boot the app locally against Compose**, twice, and look at `flyway_schema_history` with `psql`.
6. **Update the docs** (DATABASE_SCHEMA.md, DEVELOPMENT.md), run the full `./gradlew build`, and write this entry.

The order matters in one place: V1 is edited, if at all, before it is committed, and the local database has applied it since step 5. After that, changing a single character gives a checksum error on this machine.

## 5. How it was built
Read in this order.

1. **[`V1__core_schema.sql`](../../../backend/src/main/resources/db/migration/V1__core_schema.sql)** is a byte-for-byte copy of the doc's block (139 lines). The parts that carry decisions:

   - [Lines 54-76](../../../backend/src/main/resources/db/migration/V1__core_schema.sql#L54-L76), `entries`: `reply_to_entry_id` (D-33), `unlock_seen_at` (D-10), `deleted_at` (D-30), `date_unknown` (D-34), `version BIGINT NOT NULL DEFAULT 0` (D-23), and `chk_entries_entry_date_min` (D-09, no memory before 1900).

An Era's cover is one of the user's photos (D-36), but V1 creates `eras` before `media`, and a foreign key can only point at a table that already exists. So the column is added afterwards. (Creating `media` first would also have worked, since `media` doesn't depend on `eras`; the spec keeps the order it has, and 2.3 copies it as specified.) It is `ON DELETE SET NULL`: deleting the photo leaves the Era without a cover.
   - [Line 106](../../../backend/src/main/resources/db/migration/V1__core_schema.sql#L106), `CREATE UNIQUE INDEX uq_tags_user_name ON tags (user_id, lower(name))`: unique per user ignoring case. A plain `UNIQUE (user_id, name)` can't do that, which is why it is an expression index and not a constraint.
   - [Lines 120-139](../../../backend/src/main/resources/db/migration/V1__core_schema.sql#L120-L139), the indexes. ## 8. What went wrong
1. **Python isn't installed.** I first tried to rewrite a test file with a small Python script; Windows answered `Python was not found` and offered the Store. Nothing was lost. I used the editor tool and a `perl -0pi` one-liner instead.
2. **Two `MigrationsTest` tests failed on the first run (55 tests, 2 failed).** The history of a schema that Flyway created contains an extra first row: `"t_942b3d22..."` (with the quotes), not only `V1__core_schema.sql`. *Cause:* when Flyway creates the schema it is told to manage, it records a row of type `SCHEMA` (`<< Flyway Schema Creation >>`), so the schema's creation is part of its history. `migrationsExecuted` was right (1 and 2); only my list of `script` values was wrong. *Fix:* the helper [`appliedScripts`](../../../backend/src/test/java/com/memoirist/db/MigrationsTest.java#L117) selects `WHERE type = 'SQL'`. Re-run: all 55 tests of the four classes passed.
3. **I didn't know which exception a failed commit throws.** I wrote the practice-block test with a `println` of the exception's class and message instead of an assertion, and ran it. Answer: `org.springframework.dao.DuplicateKeyException: Hibernate transaction: Unable to commit against JDBC Connection; ERROR: duplicate key value violates unique constraint "uq_media_entry_order"`. `JpaTransactionManager` translates the commit failure, and it is the same exception type an immediate violation gives. So the exception type doesn't tell you *when* it happened. The `updateWasAccepted` flag does. I replaced the `println` with the assertions.

## 10. Concepts to learn from this task
- **Versioned and repeatable migrations** (`V1__core_schema.sql`, `R__seed_dev_user.sql`): a `V` file runs once, in version order, and is never edited. An `R` file runs after every `V` file, and again whenever its checksum changes. Use `V` for structure and `R` for things that are safe to apply any number of times. The mistake is a non-idempotent repeatable migration, which fails or duplicates on its second run. Here it is `ON CONFLICT (id) DO NOTHING`.
- **Flyway's history and checksum** ([`MigrationsTest.java:117`](../../../backend/src/test/java/com/memoirist/db/MigrationsTest.java#L117)): `flyway_schema_history` records each file's checksum, and Flyway checks it at every start (`validate`). That is why a committed migration can't change. The checksum is computed line by line, so LF versus CRLF doesn't matter. A schema that Flyway creates gets a `SCHEMA` row too.
- **Locations per profile** ([`application-local.yml`](../../../backend/src/main/resources/application-local.yml)): `spring.flyway.locations` is a list that a profile *replaces*, not extends. `local` and `test` list both folders. Production lists one. That is what keeps the dev user out of production, and why [`MigrationsTest.java:41`](../../../backend/src/test/java/com/memoirist/db/MigrationsTest.java#L41) tests the one-folder case directly.
- **`CHECK`, `UNIQUE` and `FOREIGN KEY` as the last line of defence** ([`V1__core_schema.sql`](../../../backend/src/main/resources/db/migration/V1__core_schema.sql)): the service will validate with friendly messages, but only the database can't be bypassed (a second service, a script, a bug). A constraint that has a name can be reported by name.
- **`ON DELETE` actions** (`CASCADE`, `SET NULL`): `CASCADE` deletes the child rows with the parent; `SET NULL` keeps the child and clears the pointer. Choosing between them is deciding what the child means without its parent: a photo can't exist without its entry, but an Era can exist without its cover. A missing `ON DELETE` means `NO ACTION`, which blocks the delete. The mistake is leaving it out and finding out in production.
- **`DEFERRABLE INITIALLY DEFERRED`** ([`V1__core_schema.sql:87`](../../../backend/src/main/resources/db/migration/V1__core_schema.sql#L87), [`DeferredUniqueConstraintTest.java`](../../../backend/src/test/java/com/memoirist/db/DeferredUniqueConstraintTest.java)): a normal unique constraint is checked after every statement, so swapping two positions fails midway. A deferred one is checked when the transaction commits. `SET CONSTRAINTS name IMMEDIATE` brings the check back to the statement for the rest of that transaction.
- **Partial and expression indexes** ([`V1__core_schema.sql:106`](../../../backend/src/main/resources/db/migration/V1__core_schema.sql#L106), [`:125`](../../../backend/src/main/resources/db/migration/V1__core_schema.sql#L125)): `... WHERE unlock_date IS NOT NULL AND unlock_notified = FALSE` indexes only the rows a query needs; `ON tags (user_id, lower(name))` indexes a computed value, which is how "unique ignoring case" works. The query must use the same expression to benefit.
- **`ON CONFLICT ... DO NOTHING`** ([`R__seed_dev_user.sql`](../../../backend/src/main/resources/db/seed-local/R__seed_dev_user.sql)): an insert that quietly does nothing if the row exists. The cost is that it never updates; if you need that, `DO UPDATE`.
- **`JdbcClient`** ([`SchemaTest.java:47`](../../../backend/src/test/java/com/memoirist/db/SchemaTest.java#L47)): `jdbc.sql("... :id").param("id", x).query(Row.class).single()`. Named parameters, a record as the row type (column `display_name` fills `displayName`), and `.single()` fails if there isn't exactly one row.
- **Spring's exception translation** ([`SchemaConstraintsTest.java:136`](../../../backend/src/test/java/com/memoirist/db/SchemaConstraintsTest.java#L136)): a SQLSTATE in class `23` (integrity constraint violation) becomes `DataIntegrityViolationException`; a duplicate key (`23505`) becomes its subclass `DuplicateKeyException`. Catch the parent for "any constraint", and assert on the message for *which*.
- **Test transactions** ([`SchemaConstraintsTest.java:28`](../../../backend/src/test/java/com/memoirist/db/SchemaConstraintsTest.java#L28) versus [`DeferredUniqueConstraintTest.java`](../../../backend/src/test/java/com/memoirist/db/DeferredUniqueConstraintTest.java)): `@Transactional` on a Spring test rolls back at the end, so tests don't leave data. Rollback never commits, so it can't show anything that happens *at commit*. Use `TransactionTemplate` there, and clean up yourself.
- **Parameterized tests** ([`SchemaTest.java:84`](../../../backend/src/test/java/com/memoirist/db/SchemaTest.java#L84), [`SchemaConstraintsTest.java:134`](../../../backend/src/test/java/com/memoirist/db/SchemaConstraintsTest.java#L134)): `@CsvSource(textBlock = """ ... """)` for a table of values (lines starting with `#` are comments, empty cells are `null`), and `@MethodSource` for rows that are built in code. `name = "..."` makes each row readable in the report.
- **`information_schema`**: the standard catalogue every SQL database answers (`tables`, `columns` with `data_type`, `is_nullable`, `character_maximum_length`). Asking the database what it has, rather than reading the SQL, tests what it did.
- **Testcontainers without Spring** ([`MigrationsTest.java:27-37`](../../../backend/src/test/java/com/memoirist/db/MigrationsTest.java#L27-L37)): `@Testcontainers` and a `static @Container` field start one container per class, and stop it after. A `static` container is shared by the class's tests; a non-static one would restart for every test.

## 12. At work
- **A migration that has run is history.** In a bank, an applied migration is in every environment from dev to production, and some of those databases can't be rebuilt. Teams treat editing one as an incident: it fails the checksum in every environment that has run it. A reviewer looks for a changed old file in the diff, a missing `ON DELETE`, a `NOT NULL` column added without a default to a table with rows, and a destructive statement (`DROP`, `TRUNCATE`) in a normal migration. Fixes go forward, in a new file.
- **Seed data and environments.** The question "can this reach production?" has to be answered by the build, not by a convention. Here a separate Flyway location, loaded only by two profiles, and a test that runs the production configuration and finds zero users. The same idea covers test accounts, default admin passwords and feature flags. Reviewers check that the location list is set per environment, and who can change it.
- **Constraints as the last line of defence.** Service-layer validation is for the user's benefit (clear messages). The database constraint is for the data's benefit: batch jobs, a second service, a script run by operations or a future bug all bypass the service. A strict schema is cheaper to enforce than a clean-up of bad rows afterwards, and in a regulated setting it is what an auditor can read. Put real names on constraints so an error log and an API mapper can point at one rule.
- **Mapping database errors.** When two requests register the same email at the same moment, the unique constraint is the only thing that is right under concurrency. The code catches the violation and turns it into `409`, which needs the constraint's *name*, and the name must not change. That is why §4 pins `users_email_key` in a test.
- **Deferred constraints and reordering.** Any "ordered list" table (rules in priority order, steps in a workflow, columns in a report) hits the swap problem. The options are a deferred unique constraint (Postgres), a gap-numbering scheme, or rewriting the whole list in one transaction. Know the trade-off before someone proposes dropping the constraint to make the code simpler.
- **Foreign key actions are business rules.** `CASCADE` on a customer-owned table means deleting a customer deletes their history. In a bank that is often not allowed (retention rules), and the answer is a soft delete, as this app does for entries (D-30). Reviewers ask of every foreign key: "what happens to this row when the parent goes?"
- **Test the migrations against the real engine, from empty.** A suite that applies every migration to a fresh container on each CI run catches ordering mistakes, a missing extension and a dialect-specific statement that an in-memory database would accept. It also costs seconds. The same image as production (here `pgvector/pgvector:pg17`, as Compose runs) matters more than the speed of H2.
- **Environment parity and line endings.** Developers on Windows and CI on Linux must compute the same checksum. Flyway does (it hashes line by line), but some tools don't, and `.gitattributes` is how a repository states its policy.
