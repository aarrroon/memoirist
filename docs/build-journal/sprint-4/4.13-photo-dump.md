## 1. The goal
[Task 4.13](../../SPRINT_PLAN.md#sprint-4-react-ui):
- **Do:** a photo dump that reads each photo's date (exifr) before shrinking it, groups the photos by day in the user's timezone, and creates one backdated entry per day through capture's upload flow, splitting a day of more than 20 photos; undated photos go into one entry dated today with `dateUnknown: true`, and the card shows a *date unknown, fix it* badge; in capture, a single photo's own date is offered as the memory date; diary pages get a gentler shrink, by shrinking once the purpose is known.
- **Done when:** component tests cover three days becoming three entries, a 25-photo day becoming two entries, undated photos giving one entry with the badge (which goes once the date is changed), a failed upload retried without duplicates, and the date suggestion accepted and dismissed.

Why now: every piece it stands on exists. The API has taken `dateUnknown` on `POST /entries` and cleared it on a `PUT` with a new date since Sprint 3 (D-34); capture's save (`saveEntry`, 4.6) already does create with a client id, upload, reorder; the Write menu has offered *Photo dump* since 4.3, opening New entry as a stand-in (4.6 assumption). It is also the task that has to fix a 4.6 trade-off: capture shrank a photo the moment it was picked, which threw away its EXIF date and made a diary page impossible to shrink differently.

## 10. Concepts to learn from this task
- **Wall-clock time versus an instant** (`photoDate.ts:34`): `"2026:10:23 21:30:00"` alone is a reading of a clock, not a moment. With `+11:00` it becomes a moment (UTC = local − offset), which can then be shown in any zone. Mixing the two, or letting `new Date("…")` read it in the browser's zone, is the classic date bug.
- **Validating a date by round-tripping** (`photoDate.ts`): `Date.UTC(2026, 1, 30)` is 2 March, not an error. Build it, read the parts back, compare.
- **Idempotent retries with a client key** (`PhotoDump.tsx:142`): the id is made once per planned entry and reused, so a lost answer or a failed upload never makes a second entry (D-12).
- **Grouping with a `Map` and chunking with `slice`** (`dumpPlan.ts:41`): a `Map` keeps insertion order, so grouping keeps the pick order inside a day; the outer order comes from sorting the keys.
- **Generic constraints** (`planDump<P extends DumpPhoto>`): the function only needs `key` and `day`, but returns the caller's own type, so `PhotoDump` gets its `file` and `status` back without casts.
- **`WeakMap` as a cache keyed by an object** (`saveEntry.ts:95`): the shrunk copy lives as long as the picked `File` does, with nothing to clean up.
- **Dynamic `import()` for a heavy library** (`photoDate.ts:85`, `DateUnknownBadge.tsx`): the bundler splits it into its own chunk, loaded on first use.
- **Moving focus after an element disappears** (`CaptureForm.tsx:165`): a button that removes itself would drop focus to `<body>`; `requestAnimationFrame` waits for the re-render, then focuses the date chip it was about.

## 12. At work
- **Batch uploads with partial failure** are everywhere in banking: a bulk payment file, a statement import. The pattern here (plan the batches, give each one an idempotency key, retry only what failed, report per item) is what a reviewer looks for: no duplicate payments on retry, and a clear list of what didn't go through.
- **Timestamps from outside systems** (card networks, partner APIs, device logs) arrive with and without offsets. A reviewer asks: is this a local reading or an instant? Which zone decides "the business day"? What happens at midnight and on a clock change?
- **Validating untrusted input defensively**: the EXIF date is data from a file the user picked, possibly from any camera. Refusing impossible dates instead of trusting the parser is the same habit as validating a value date on an incoming instruction.
- **Keeping heavy dependencies off the first page**: the same budget thinking applies to an internal banking SPA's first load on a slow VPN.

1. Shrinking re-encodes the picture on a canvas, and the new file has no EXIF. The date has to be read from the original first (D-34), which is why capture now keeps the picked file and shrinks it when it uploads.
2. The 24th. With an offset the time is an instant: 21:30 at −07:00 is 04:30 UTC on the 24th, which is 15:30 on the 24th in Melbourne (+11:00). The user's zone decides the day (non-negotiable 2).
