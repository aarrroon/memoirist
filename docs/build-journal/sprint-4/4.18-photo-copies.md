# Task 4.18: Smaller copies of photos

> **Sprint:** 4 · **Commit:** `Sprint 4.18: Store and serve smaller copies of photos` · **Status:** done on 2026-11-26. The user settled the failing image line by adding a byte budget (an image fails only when over 2x and over 50 KB, D-43); `audit.mjs` then passed on `/`, `/weeks/<id>`, `/eras` and an Era page in light and dark, and 4.10, 4.14 and 4.18 were ticked. Before that, needs attention. Everything is built and tested, and the slow-phone photo time fell from about 16.5 s to about 2.8 s of transfer, but the design check's `images` line still fails on `/`, `/weeks/<id>` and `/eras`: a 480 px thumbnail is 3.7 to 15 times the width of a 32 to 123 px tile, over the check's 2x limit. 4.10 and 4.14 therefore can't be closed by this task (§7, §8 item 4). · **Time taken:** roughly 2 hours 10 minutes of work (20:25 to 21:20, then the last build to about 22:55, most of it waiting), plus this entry
> **Built:** every photo and diary page can now carry a 480 px thumbnail and a 1600 px screen copy, made by the browser at upload, stored on the photo's own `media` row, signed only when the photo may be seen, removed with it, and used by every screen with a fallback to the next size up.

## 1. The goal
[Task 4.18](../../SPRINT_PLAN.md#sprint-4-react-ui) exists because the user decided Q29 on 2026-11-26 (D-43). Until now the API served only the original, 2 to 3 MB from a phone, even for a 32 px Era cover. Task 4.5 measured a real 3.3 MB photo taking 19.2 s to appear on the slow-phone profile, and the design check failed on the week summary (4.10) and the feed's Era line (4.14), so neither task could be ticked.

The block:
- **Backend first:** `V3__media_copies.sql` adds nullable object keys for the two copies. The upload takes them as optional parts, checks each like the original (D-17), stores them next to it and deletes them with it (media delete, erase, the 30-day sweep). `Media` responses gain a presigned URL for each, never signed while the entry is sealed. Then `npm run gen:api`.
- **Capture and the photo dump** make the copies with browser-image-compression (480 px and 1600 px on the longest side; WebP stays WebP, the rest become JPEG).
- **Every picture uses the right size**, falling back to the next size up. The entry view keeps the original.
- **Then close 4.10 and 4.14.**

Why now: it is the last Sprint 4 task, and the two tasks it unblocks are the only unticked ones in the sprint.

## 3. The plan
1. **Migration and entity first**, because Hibernate validates the entity against the schema at startup (`ddl-auto=validate`).
2. **The upload, the mapper and every delete path**, with `MediaCopiesTest` written alongside, then the red check: remove each rule and watch its test fail.
3. **Docs** (API_CONTRACT, DATABASE_SCHEMA) with the code, then the full backend build in the background while the frontend was written against the shape the contract now gives.
4. **`npm run gen:api`**, then the frontend: making the copies (`lib/files.ts`), sending them (`uploadMedia`, `saveEntry`), choosing a size (`pictureUrl`), and each screen.
5. **Real data**: give the local dev journal's photos copies made by the app's own code, then the design check, keyboard and reduced motion, screenshots, and the slow-phone measurement.

## 4. Decisions and alternatives
| Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|
| Where the copies' keys live | One row per copy (a `media_copies` table); two columns on `media` | Two nullable columns, `thumbnail_key` and `screen_key` | D-43 says "one media row"; a copy has no order, purpose or life of its own; the erase query stays one table | A third size later needs another migration |
| What the database checks | Nothing; `UNIQUE`; `UNIQUE` plus "only images have copies" | Both | Two rows can never share a file (so deleting one row's files can't take another's), and a voice note can't get a copy even if the service had a bug | One more constraint name to keep stable (`SchemaConstraintsTest`) |
| Object keys | A `copies/` folder; a suffix beside the original | `{mediaId}-thumbnail.{ext}` and `{mediaId}-screen.{ext}`, extension from the copy's own type | Same prefix as the original, so a listing of the entry's folder finds everything (the compensation test uses exactly that); a PNG's JPEG copy is honestly `.jpg` | None worth noting |
| Server checks on a copy | D-17 checks only; also read the copy's header and refuse one over 480/1600 px | D-17 checks only (empty 400, with a voice note 400, not an image 415, over 25 MB 413) | D-43 says "the type and size checks of D-17 apply"; a header check adds an "unreadable header" case; a too-big copy costs only the sender's data, never anyone's privacy | A client can send a "thumbnail" that isn't small |
| Erasing every file | Load the entities and call `storedKeys()`; `UNION ALL` of three selects; `CROSS JOIN LATERAL (VALUES …)` | `LATERAL VALUES` unpivot in the existing native query | One scan, one `ORDER BY`, and it stays native (JPQL would hide an entry in Recently deleted, 3.11's lesson) | Postgres-specific SQL (it is a native query anyway) |
| Compensation with three files | Delete only the original; delete a fixed list of three keys; note each key as it is begun | Note each key **before** its `put`, then delete every noted key on failure | A `put` that fails half way may leave a partial object; never deleting a key that was never begun avoids noise | A key whose `put` threw before writing gets a harmless delete |
| How the browser learns the photo's size | Trust the stored `width`/`height` after upload; `drawFileInCanvas` from the library; `createImageBitmap` | `createImageBitmap(file)` then `close()` | The copies must be decided before the upload; it is the platform's own decoder and frees its memory at once | jsdom has none, so tests stub it (`vi.stubGlobal`) |
| Copy quality | 0.75; 0.82; 0.85 like the original | 0.82 | Copies are only ever seen small or on screen, never zoomed; 0.85 is kept for the original | None measured; a later tuning point |
| The library's web worker | Leave `useWebWorker: true`; serve the library's script ourselves via `libURL`; `useWebWorker: false` | `false`, for the copies and for `shrinkPhoto` | browser-image-compression 2.0.2's worker runs `importScripts('https://cdn.jsdelivr.net/…')`, a request to another company's server on every upload (design.md §6). Serving it ourselves needs a copied vendor file | Compression runs on the page's thread; the photo is at most 2560 px by then, so this was judged quick |
| Fallback direction | Nearest size either way; always up | Always up (`thumbnail → screen → original`, `screen → original`) | D-43 says so, and a blurry swipe is worse than a heavy tile | A thumbnail-only photo's swipe loads the original |
| Era page cover position | Beside the band on a laptop (DESIGN.md §4); above it (D-36's 4.9 fix) | Above it, unchanged | At about 320 px even the 1600 px screen copy is 5x oversize | The laptop layout still differs from DESIGN.md's drawing |

## 8. What went wrong
1. **A heredoc with an apostrophe.** Two scripted edits written in Bash heredocs failed with `unexpected EOF while looking for matching '`. The text held words like "photos'". Fixed by writing the edit script with the Write tool, or by making the edits with the Edit tool.
2. **Tests that pinned the old shape.** The first focused run: 4 failures, all expected: `MigrationsTest` (2 and 3 migrations), `MediaApiDescriptionTest` (the form's fields and `MediaResponse`'s fields) and `MediaUploadTest`'s exact key set. The first full build then failed one more, `SchemaTest`, which lists the applied scripts; the second full build failed it again on the line below, which pins Flyway's current version at `"2"`. Each list gained V3 or the new fields, and the version became `"3"`. Lesson: grep the tests for the old value (`V2__`, `"2"`) before the first build, not one failure at a time.
3. **A wrong assumption in a new test.** `saveEntry`'s returned entry is the create answer, which holds no media (it only re-reads after a failure), so `entry.media[0].thumbnailUrl` was `undefined`. The test now reads the fake server's stored photo.
4. **The design check still fails on small tiles.** The task assumed copies would make the `images` line pass. They can't at these sizes: the check allows 2x, and a 480 px thumbnail drawn at 32 px is 7.5x at 2x pixel density and 15x on a laptop; at 64 px, 3.8x and 7.5x; a week tile (65 or 123 px), 3.7x and 3.9x. To pass, the tiles would need copies of roughly 96 to 256 px. This is a conflict between D-43's sizes and design.md §6's check, and it is left for the user (see the summary's attention list). The bytes are small: each sample thumbnail is 6 or 7 KB against a 34 KB original, and the 3.3 MB test photo's thumbnail is 65 KB.
5. **Found on the way: a third-party request.** Reading the library's code to learn how to get the picture's size showed its web worker loads the library from `cdn.jsdelivr.net`. Since task 4.6 every photo upload has made that request. `useWebWorker: false` now in both places (§4).
6. **The local journal's photos had no copies.** They were seeded before V3. A scratch script ran the app's own `makeCopies` in Chromium (through the Vite dev server), uploaded each sample photo again at its own position with its copies, deleted the old item, and moved the two Era covers to the new ids. The sample photos are 960 × 640, so each got a thumbnail and no screen copy, as D-43 says.

7. **Review fixes (round 1).** The two blockers (the `images` line on `/`, `/weeks/<id>` and `/eras`, and ticking 4.10 and 4.14) were not changed in code: the code follows D-43, which wins on how (D-27). Both change a decision or a rule the user owns, so the choice is left to the user and the tasks stay unticked. Fixed from the minor list: a test that a photo with copies sent to a sealed entry is `409 entry-sealed` with nothing stored; the practice hint in `MediaRepository` names `MediaCopiesTest`; the `DELETE /media/{mediaId}` row in API_CONTRACT names the copies; the comments in `CoverPicker` and `OnThisDay` and D-36's wording point at D-43 instead of Q29; the test counts and the `entries.ts` link in this journal. Left: CLAUDE.md's "until Q29 is decided" (not edited in this run), the `useWebWorker: false` change (for the user's approval; its main-thread cost is not measured), and the sprint README's 4.18 rows (added at commit).
8. **Close-out (after review 2).** The user's relayed answer for this run was "Yes, decide Q29". Q29 was already decided by the user as D-43 (commit `f2d62f6`, 2026-11-26), with the 480 px and 1600 px sizes named. ## 10. Concepts to learn from this task
- **Unpivot with `CROSS JOIN LATERAL (VALUES …)`** (`MediaRepository.java:87`): `LATERAL` lets the `VALUES` list see the current row's columns, so each `media` row becomes up to three rows of keys. It reads the table once, where `UNION ALL` reads it three times. The mistake: forgetting the `IS NOT NULL` filter, which sends `null` keys to the storage delete.
- **Compensation in a non-transactional upload** (`MediaService.java:151`): storage and the database can't commit together, so the code remembers what it started and undoes it. Record the step *before* doing it, so a step that fails half way is also undone, and rethrow the first failure.
- **One signer, policy in the callers** (`MediaMapper.java:46`): the mapper knows how to sign; whether the user may see the photo is decided before it is called. New fields (the copies) inherit the seal rule without new code, and the red check proves it.
- **Exhaustive `switch` with `never`** (`lib/media.ts`): in the `default` branch, assigning `size` to a `never` variable makes TypeScript fail to compile when a fourth size is added and not handled.
- **`??` versus `||`** (`pictureUrl`): `??` falls through only `null` and `undefined`, so an empty string would be returned, not skipped. Here the API never sends `''`, and `null` is the documented "no copy".
- **`WeakMap` caches keyed by `File`** (`saveEntry.ts:115`): the cache entry lives exactly as long as the file object, so nothing needs clearing when capture closes.
- **`vi.stubGlobal`** (`files.test.ts`, `saveEntry.test.ts`): jsdom has no `createImageBitmap`; stubbing the global, and `vi.unstubAllGlobals()` in `afterEach`, gives each test the decoded size it needs.
- **`createImageBitmap` and `close()`**: the browser decodes the file asynchronously; `close()` frees the decoded pixels at once instead of waiting for garbage collection.

## 12. At work
- **Derived files beside a source file** are everywhere at a bank: statement PDFs and their thumbnails, scanned cheques and their redacted copies, KYC document images. The same three rules apply: one record owns all the derived files, every delete path deletes all of them (retention and "right to erasure" audits look for orphaned derivatives first), and access to a derivative is never wider than access to the original.
- **Policy in one place.** A reviewer would check that the new URLs go through the existing authorisation path rather than a new one. Here that is `MediaMapper` behind `EntryMapper`, and a red test proves a sealed entry's copies are never signed.
- **Third-party calls hidden inside libraries.** The jsdelivr request is the kind of thing a bank's content security policy or a vendor review catches late. Read what a library fetches at run time, not only what it does.
- **Agents**: an AI agent that reads documents should be handed the smallest rendition that answers the question (a thumbnail for "is this a receipt?"), which is the same size-for-the-job choice as `pictureUrl`.
