## 3. The plan
1. Data layer first, because the screens only draw what it returns: `queryKeys.timelines()`/`timeline(tagId)`, `api/timeline.ts`, and rename/delete hooks in `api/tags.ts`.
2. Seal safety in the caches: every write that can change what a row may show (sealing, deleting, saving, a Loot Drop opening) also refreshes the Timeline.
3. Pure helpers with plain tests: `timelineDay`, `monthKey`, `formatMonth` in `lib/time.ts`; `groupByMonth` in `features/timeline/months.ts`.
4. A stand-in MSW server (`test/msw/timeline.ts`) holding a sealed tagged entry, a deleted entry and another user's entry, applying the server's rules.
5. The two pages, then their component tests; break each rule on purpose and watch the tests go red.
6. Design check, keyboard, reduced motion, screenshots, a live rename against the real backend, the full frontend checks.

## 4. Decisions and alternatives
| Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|
| Where the filter lives | Zustand; component state; the address (`?tag=`) | The address | Reload-safe, and the links from 4.4 and 4.10 already use it. Zustand holds UI state only, and a filter that names a server row belongs in the URL | The tag id shows in the address (an id, never the name) |
| Chips and history | Push a history entry per chip; replace | `setSearchParams(…, { replace: true })` (`TimelinePage.tsx:45`) | Back leaves the Timeline instead of stepping through every chip tapped; a tag link from another screen is still a push, so Back returns there | A chip choice can't be undone with Back |
| Query keys | Under `entries`; a separate `timeline` family | `timelines()` prefix with `timeline(tagId)` beneath (`queryKeys.ts:42`) | One prefix refetches every filtered copy; invalidating one entry (`['entries', id]`) must not refetch 50-row lists | A new family to remember in every entry write |
| Page size | 100 (the limit); 20; 50 | 50 (`timeline.ts:15`) | Several phone screens per request; the server's default, so a request with no `size` looks the same; never over D-42's limit | More requests than 100 for a long journal |
| Who filters sealed entries | The client hides `isLocked` rows from a filtered list; the server | The server; the client draws what comes back | The server already leaves sealed entries out of a tag filter and its totals (D-10); a client filter would make counts and pages disagree. The MSW stand-in applies the server's rule, and tests prove the screen shows no more | The client trusts the server's redaction (proved by Sprint 3's tests) |
| Tags in a row | Links to the filter; text | Text (`TimelinePage.tsx:256`) | The whole row is one link; a link inside a link is invalid HTML and two Tab stops per tag; the chips above filter | Can't tap a tag in a row |
| After a rename or delete | Patch every cache from the answer; invalidate | Invalidate tags, timelines, feed, weeks, entries, opened (`tags.ts:39`) | A rename changes no entry on the server and the answer is just the tag, so there is nothing to patch the lists with; invalidation keeps the screen until the new answer lands | Several refetches after a rare action |
| 409 message | Show the server's `detail`; name the clashing tag | Find the clashing tag in the list already loaded, ignoring case (`TagsPage.tsx:101`) | F-17 asks to suggest the other tag; `detail` never echoes input (CLAUDE.md) | A fallback sentence if the list is stale |
| A 404 tag | Generic error; empty list; an invitation to clear | "This tag isn't in your journal any more." + *Clear the filter* (`TimelinePage.tsx:128`) | A deleted tag's old link should lead somewhere useful | None |
| Lazy-loading routes | Split the routes now; leave it | Leave it | Beyond this task; the main chunk is 199.42 kB gzip, under the 200 kB limit by 0.58 kB | The next screen will likely cross the limit; flagged for the main session |

## 10. Concepts to learn from this task
- **`infiniteQueryOptions`** (`timeline.ts:24`): builds the key, `queryFn`, `initialPageParam` and `getNextPageParam` in one typed object you can pass to `useInfiniteQuery` or `prefetchInfiniteQuery`. The mistake: a key that leaves out a parameter the `queryFn` uses (here `tagId`), so two filters share one cache.
- **Hierarchical query keys** (`queryKeys.ts:42`): `invalidateQueries({ queryKey: ['…','timeline'] })` matches every key that *starts* with it, so one call refreshes every filter. Put a list where single-item invalidations can't reach it.
- **`useSearchParams` with a function and `replace`** (`TimelinePage.tsx:38`): the updater gets the current params, so other parameters survive; `replace: true` changes the address without a new history entry.
- **`key` to reset a subtree** (`TimelinePage.tsx:54`): changing a component's `key` unmounts it and mounts a fresh one, which resets its state and effects. Cheaper and clearer than resetting each piece by hand.
- **`Pick<T, …>` as a guard** (`TimelinePage.tsx:273`): narrowing a prop type means the compiler refuses any read of a sealed row's title or tags.
- **`Array.prototype.at(-1)`** (`months.ts:25`): the last element without `arr[arr.length - 1]`.
- **`aria-pressed` toggle buttons in a `role="group"`** (`TimelinePage.tsx:88`, in the `role="group"` at `:82`): how a screen reader hears "All entries, toggle button, pressed".
- **Returning focus after a dialog opened from state** (`TagsPage.tsx:172-187`): Radix only restores focus to a trigger it knows; here the opener is remembered and, if its row was deleted, focus goes to `<main>` instead of being lost to `<body>`.

## 12. At work
- A transactions screen at a bank is the same shape: an infinite list grouped by month, a filter (account, category) in the URL so a link from a statement opens it filtered, and a page size kept under the API's limit. A reviewer would ask: does the key include every filter? Does a write elsewhere invalidate this list?
- "The server leaves it out, the client draws what comes back" is how entitlements should work: a client-side filter for data the user may not see is a leak waiting for one missed `if`. A reviewer would look for redaction in the API and a test whose data holds the forbidden row.
- Renaming a reference value (a category, a payee label) that many rows show is a cache problem, not a data problem: list every query family that draws it, and invalidate them in one place.
