# Task 4.6: Capture modal

> **Sprint:** 4 · **Commit:** `Sprint 4.6: Build capture: the write sheet, uploads and the draft`, on `phase-1-sprint-4` · **Status:** done (unattended; two spec reviews, the second "pass with notes") · **Time taken:** roughly 45 minutes of build and checks (04:15 to 04:57 AEDT), plus this entry
> **Built:** Write now opens capture: a full-screen Vaul sheet on a phone and a two-column dialog on a laptop, with a title, a TipTap editor, templates, a memory-date picker, tags made inline, photos that upload, reorder and can be marked as diary pages, a draft that survives a reload, and the API's errors shown where they belong.

## 1. The goal
[Task 4.6](../../SPRINT_PLAN.md#sprint-4-react-ui):
- **Do:** an optional title and a TipTap editor (StarterKit + Link with a protocol allow-list); a template picker that inserts headings above existing text, with empty template headings removed on save (D-06, D-23); a memory-date picker (today by default, never in the future, not before 1900); a tag picker that creates tags inline; multi-file upload with reorder, failed items kept with retry or remove, and a diary-page mark (D-20, D-23); a draft in local storage and a keep-or-discard prompt (D-23); the flow create (client UUID) → upload → reorder.
- **Done when:** a title, a tag and two photos show up in the feed in the right week; save is disabled for an empty entry; an empty template prompt isn't saved; a diary page is saved as a page; a backdated save shows a toast linking to its week; a reload keeps the draft; API validation errors show on the right fields; a `409 entry-stale` keeps the typed text and offers the latest version.

Why now: 4.3 built the Write menu and a UI-store flag (`capture`) that nothing read; 4.4 and 4.5 built the feed that a new entry lands in. Capture is the first screen that *writes*, so it is where the client finally exercises D-12 (client ids), D-23 (drafts, partial uploads, stale versions) and D-26 (full `PUT`). Voice notes (4.7), sealing (4.8), the photo dump (4.13) and soundtracks (4.15) all plug into the sheet built here.

## 3. The plan
1. **Data layer first** (`api/entries.ts`, `tags.ts`, `templates.ts`, new query keys), because everything else calls it.
2. **Pure logic with unit tests** (`lib/templateDoc.ts`, `lib/files.ts`, `time.ts` additions, `capture/draft.ts`, `capture/saveEntry.ts`): the rules of D-06, D-17, D-23 live here, where a test is cheap.
3. **UI primitives** (`popover`, `dialog`, `chip`), then the pieces (editor, date chip, template chip, tag picker, media tray), then the form and its frame.
4. **Wire it into the shell** with a small eager `CaptureHost` that lazy-loads the rest.
5. **Component tests** against a stateful fake API (MSW), one per Done-when item.
6. **The browser:** `audit.mjs` light and dark, a Playwright script for the keyboard, reduced motion, screenshots and one real save against the local backend.

## 4. Decisions and alternatives
| Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|
| How the save flow is shaped | A hook per request strung together in the component; one `useMutation` whose function runs the whole flow | One plain async function `saveEntry` called by one `useMutation` | The order matters (create → delete → upload → reorder) and a failed upload must not fail the whole save; one function can be unit-tested with MSW without rendering anything | The cache isn't updated per step; the feed is simply invalidated at the end |
| Form state | react-hook-form + zod (approved, D-13); Zustand; `useState` in the form | `useState` in `CaptureForm` | The fields aren't plain inputs: the editor owns its document, the tray holds Files and per-item status. RHF would wrap most of them in `Controller` for little gain. Zustand is for UI state only (frontend.md) | No declarative validation schema; the few client rules (empty, 150 chars, 20 tags) are written out |
| Where the draft is checked | Trust `JSON.parse`; hand-written checks (like 4.2's `toApiProblem`); a zod schema | zod `safeParse` (practice block) | Local storage is untrusted input; a schema says the whole shape once and `satisfies z.ZodType<Draft>` keeps it in step with the interface | One more place a shape is written down (the compiler links them) |
| Photos in the draft | Store them (IndexedDB); store nothing | Not stored | Files can't go in local storage, IndexedDB needs care with 20 × 2 MB; D-23 speaks of unsaved *text* | A reload loses picked-but-unsaved photos (an assumption) |
| Sheet or dialog | Follow the width live (`useSyncExternalStore` on `matchMedia`); choose once when capture opens | Choose once | Following live remounted the form when the width crossed `lg` and **dropped the picked photos** (seen in the browser, §8). A tablet turning at 1024 px would do that | A window resized while writing keeps the frame it opened with |
| Lazy loading | Import capture with the shell; lazy-load it | `React.lazy` for `CaptureView` and the toaster | design.md §6: the feed must not ship the editor. The feed bundle went from 178.31 to 180.26 KB gzipped; capture's own chunk is 220 KB, fetched on first Write | A short wait the first time Write is pressed |
| Reordering by keyboard | dnd-kit's `KeyboardSensor`; a menu on each thumbnail with Move earlier/later | The menu, plus dnd-kit's mouse and touch sensors | The keyboard sensor takes Space/Enter, which the thumbnail button also needs to open its menu; a menu also tells a screen reader exactly what happens | Two ways to reorder to keep working |
| Touch dragging | `PointerSensor` with a distance; `TouchSensor` with a delay | `MouseSensor` (8 px) + `TouchSensor` (250 ms hold) | A finger starting on a photo should still scroll the sheet; a long press starts the drag | Dragging on a phone needs a hold |
| Retry after a failed upload | A per-item upload call; the same save again | The same save (`PUT` + the missing uploads + order) | One code path; the `PUT` with the read version is harmless and the client id/versions make it safe | A retry also re-sends the text |
| `409 entry-stale` | Merge; overwrite; keep text and offer the latest (D-23) | Keep the text, banner with *Load the latest version* | D-23, and it is the only option that never loses words | Loading the latest replaces what was typed (the user chooses it) |
| Placeholder in the editor | TipTap's Placeholder extension; a drawn hint | A hint drawn over the empty editor, `aria-hidden` | Only StarterKit and Link are allowed (frontend.md) | The hint isn't part of the editor's own accessibility tree (the editor has its label) |
| Disabled Save | Leave the accent; fade it; a neutral fill | `--surface` with `--ink-2` text | A disabled accent button read as the action to take; opacity would fail contrast checks | The primary variant gained two classes (`button.tsx`) |

## 5. How it was built
Read in this order:

1. **The writes:** [`api/entries.ts`](../../../frontend/src/api/entries.ts) (`createEntry` :17, `updateEntry` :22, `getEntry` :28, `deleteEntry` :35, `uploadMedia` :43, `reorderMedia` :66, `deleteMedia` :76). Uploads use openapi-fetch's `bodySerializer` (:55) to build a `FormData`; the generated type calls the file a `string` (OpenAPI's "binary"), so the Blob is cast once there and nowhere else. [`api/tags.ts`](../../../frontend/src/api/tags.ts) has `useTags` and `useCreateTag` (invalidates `tags`), [`api/templates.ts`](../../../frontend/src/api/templates.ts) `useTemplates`; [`queryKeys.ts`](../../../frontend/src/api/queryKeys.ts) gains `tags`, `templates` and `entry(id)`.
2. **Templates in the editor:** [`lib/templateDoc.ts`](../../../frontend/src/lib/templateDoc.ts): `insertTemplateHeadings` (:22) puts each prompt in as an `h2` with an empty paragraph under it, above the existing text; `removeEmptyPrompts` (:37) drops a prompt heading followed only by blank paragraphs until the next heading; `captionForSave` (:76) returns `null` when no words are left, so a photo-only entry has no caption.
3. **Files:** [`lib/files.ts`](../../../frontend/src/lib/files.ts): `ACCEPT` (:9), `fileProblem` (:20, type then 25 MB), `shrinkPhoto` (:35, browser-image-compression to 2560 px and about 2 MB; it keeps the original if shrinking fails or grows the file).
4. **Time:** [`lib/time.ts`](../../../frontend/src/lib/time.ts) gains `formatClock` ("7:41 pm" in the user's zone), `weekOf` (Monday-to-Sunday, D-08), `chipDay` ("Today, Tue 24 Nov"), and `toPickerDate`/`fromPickerDate` (react-day-picker works on the browser's clock, so a calendar day is held at local midnight just for the picker).
5. **The draft:** [`capture/draft.ts`](../../../frontend/src/features/capture/draft.ts): the `Draft` shape, the zod schema (practice block, :32), `readDraft` (:58) and `writeDraft`/`clearDraft`, each wrapped in `try` because storage can be blocked.
6. **The save flow:** [`capture/saveEntry.ts`](../../../frontend/src/features/capture/saveEntry.ts): `TrayItem` (one picture in the tray, with its status), `EntryFields` (everything a `PUT` replaces) and `saveEntry` (practice block, :74; the function at :87).
7. **The editor:** [`capture/editorSetup.ts`](../../../frontend/src/features/capture/editorSetup.ts): `extensions` (:12) switch off StarterKit's `underline`, `codeBlock` and its bundled `link` (:18), then add Link with `isAllowedUri: (url) => safeHref(url) !== null` (:27), reusing 4.5's allow-list; `useEntryEditor` (:37). [`capture/Editor.tsx`](../../../frontend/src/features/capture/Editor.tsx): the toolbar (`role="toolbar"`, one Tab stop, arrow keys move, `aria-pressed` from `useEditorState`) and the text.
8. **The pickers:** [`DateChip.tsx`](../../../frontend/src/features/capture/DateChip.tsx) (a Radix popover around `DayPicker` with `disabled={[{ after: today }, { before: 1900-01-01 }]}`, `weekStartsOn={1}` and token class names instead of its stylesheet); [`TemplateChip.tsx`](../../../frontend/src/features/capture/TemplateChip.tsx) (the dropdown menu, `z-50` so it opens above the sheet); [`TagPicker.tsx`](../../../frontend/src/features/capture/TagPicker.tsx) (chips with a remove button, then *+ Tag*: a field that filters the user's tags or offers *Make "x"*).
9. **The tray:** [`MediaTray.tsx`](../../../frontend/src/features/capture/MediaTray.tsx): dnd-kit's `SortableContext` over the items; each [`Thumbnail`](../../../frontend/src/features/capture/MediaTray.tsx) (:110) is a popover button with *Try again*, *Mark as a diary page*, *Move earlier*, *Move later* and *Remove*. `draggedRef` stops the click that ends a drag from opening the menu.
10. **The form:** [`CaptureForm.tsx`](../../../frontend/src/features/capture/CaptureForm.tsx): state starts from the draft or `freshDraft` (:45); the draft is written 400 ms after changes stop; `save` (:265) runs `saveEntry` and handles the three outcomes (all saved → clear the draft, toast, close; partly saved → keep the entry's id and version, say which failed; all photos failed on an otherwise empty entry → the entry was erased, start again with a new id); `onError` (:317) maps `entry-stale` to the banner and `validation-failed` to field messages via `fieldMessages` (:542); `announceSaved` (:334) shows the backdated toast; `loadLatest` refetches the entry and refuses a sealed one (D-10).
11. **The frame:** [`CaptureView.tsx`](../../../frontend/src/features/capture/CaptureView.tsx): the frame is chosen once (:32); the sheet is a Vaul `Drawer` with `autoFocus` and `handleOnly` (:121); the laptop is `DialogContent` from the new [`components/ui/dialog.tsx`](../../../frontend/src/components/ui/dialog.tsx); closing asks through an `AlertDialog` when the form says it is dirty.
12. **The host:** [`CaptureHost.tsx`](../../../frontend/src/features/capture/CaptureHost.tsx) (mounted in `AppShell`): lazy imports, the `?write=` deep link (:25, removed with `replace` so Back doesn't reopen it), and the toaster kept mounted once capture has been used (:39). [`WriteMenu.tsx`](../../../frontend/src/components/shell/WriteMenu.tsx) `onCloseAutoFocus` (:53) stops the menu pulling focus back to Write behind the sheet.
13. **Primitives:** [`popover.tsx`](../../../frontend/src/components/ui/popover.tsx), [`chip.tsx`](../../../frontend/src/components/ui/chip.tsx) (a 44 px button holding the 32 px chip), and `button.tsx`'s disabled primary.

## 8. What went wrong
1. **Type errors from `noUncheckedIndexedAccess`.** `nodes[i]`, `split(';')[0]` and `buttons[next]` are `T | undefined`. Fixed with `forEach`, `?? ''` and a state index for the toolbar.
2. **Lint, four rules.** `react-hooks/immutability` refused writing `dragged.current` on a ref passed as a prop; renaming it `draggedRef` tells the rule it's a ref. `set-state-in-effect` refused `setUsed(true)` in an effect; it is now set during render (`if (capture !== null && !used) setUsed(true)`), React's pattern for state derived from a change. `react-refresh/only-export-components` wanted the editor setup out of the component file (`editorSetup.ts`). `no-misused-promises` caught `navigate()` (it returns a promise in React Router 8) in the toast action: `void navigate(…)`.
3. **Uploads failed in tests with "AbortError … Premature close".** Probes showed: a `FormData` holding a jsdom `File` reaches the handler, but *reading* its body fails. Attempt 1, `request.formData()`: Node's parser asserts the `File` it makes is Node's (`webidl.is.File`). Attempt 2, replacing the global `File`, `Blob` and `FormData` with Node's: breaks Vitest's own jsdom-to-Node bridge ("Vitest cannot read the bytes of a jsdom Blob"). Attempt 3, `request.text()`: still "Premature close". **Fix:** the fake upload handler doesn't read the body; `watchForms()` in `test/msw/capture.ts` wraps `FormData.prototype.append` and records each form's file name, type and purpose (uploads go one at a time). The app's code didn't change.
4. **Component tests timed out the first time** a test opened capture: the lazy chunk (TipTap, dnd-kit, Vaul) takes seconds to transform. The dialog lookup waits 10 s and the capture tests have 15 s each. Also: two "Write" buttons (tab bar and side nav, both in jsdom), and Sonner calls `setPointerCapture`, which jsdom lacks (stubbed).
5. **A 4.4 test turned flaky in the full run.** "loading: … the shapes only after 300 ms" passed alone but failed twice with the whole suite: under load the 1 s fake answer sometimes beat the 300 ms timer. The fake answer now waits 3 s and the skeleton lookup 2.5 s.
6. **In the browser, three real bugs the tests couldn't see:**
   - Photos vanished when the window crossed `lg`: the frame followed the width live, so the sheet became the dialog and the form remounted. Now the frame is chosen when capture opens.
   - Focus stayed on Write, and Tab went to "Eras" and "You" *behind* the sheet. Vaul's `autoFocus` is off by default, and Radix's menu puts focus back on its trigger when it closes. Now `Drawer.Root autoFocus` and the menu's `onCloseAutoFocus` skips the return when capture opened. The 4.3 test that expected focus back on Write was updated to expect it inside capture.
   - The title field and the editor had no focus ring (`outline-none` beat the global `:focus-visible` rule); removed. A disabled Save looked enabled; it now uses `--surface` and `--ink-2`.
7. **The first design check printed "Failed to fetch dynamically imported module".** Vite's dev server found TipTap and friends on first import and re-optimised its dependencies; the second run was clean. Dev only.
8. **Spec review, major: a restored draft lost track of photos already uploaded.** The draft keeps the entry id and version after a partial save, but the tray came back empty, so those photos couldn't be seen or removed. The next save's `PUT …/media/order` listed only the new photos (a `400` from the API, which wants exactly the entry's media), and an entry with no text whose new uploads all failed would have been erased with its earlier photos. Two fixes, each with its own test:
   - `CaptureForm` reads the entry once when a restored draft has an entry id, and puts its media in the tray as uploaded items (and keeps its soundtrack and reply). The typed text and the version stay the draft's, so a change made elsewhere still meets `409 entry-stale`. A `404` (deleted elsewhere) starts a new entry with a new client id; a sealed entry shows the Loot Drop message (D-10).
   - `saveEntry` builds the order and the "empty entry" check from the server's media list in the create or `PUT` answer, not from the tray alone: tray photos first, then any the tray doesn't show. An entry that still holds photos is never erased.
   - The fake API's order handler now answers `400` when the list isn't exactly the entry's media, as the real one does. New tests: two in `saveEntry.test.ts`, and "after a partial save and a reload…" in `CaptureView.test.tsx` (partial save, remount, the uploaded photo is back, add two, save: the order holds all three, nothing deleted). The first run of that test failed for the wrong reason: `waitFor(() => expect(readDraft()?.entryId).not.toBeNull())` passed at once on `undefined`; it now waits for a string. Break-the-rule: without the server ids in the order, the two `saveEntry` tests went red; without the restore effect, the component test went red.
9. **Spec review, major: TECH_STACK §3 Media still named `lib/images.ts`**, a gentler setting for diary pages and keyboard reordering through dnd-kit. The prose now matches the code: `lib/files.ts` shrinks every photo when it is picked; pages are shrunk like photos for now; dragging uses dnd-kit's mouse and touch sensors and the keyboard uses each thumbnail's menu. The gentler page setting and reading the photo's date before shrinking are noted on task 4.13 in SPRINT_PLAN, which reworks that step (assumption: option 2 of the review, the docs, rather than building the page setting now).

## 10. Concepts to learn from this task
- **Idempotency keys** (`saveEntry.ts:87`, D-12): the client picks the entry's id before the first request, so sending the same `POST` twice can only ever make one entry. The mistake is generating the id inside the retry, which defeats it.
- **Optimistic locking from the client side** (`CaptureForm.tsx:317`, D-23): the client sends the `version` it read; the server refuses an older one with `409`. The client's job is to keep the user's text and offer a choice, never to retry blindly.
- **A full-replace `PUT`** (`saveEntry.ts`, D-26): every field is part of each request, and one left out is cleared. Capture leaves a null field out of the JSON (the generated type doesn't allow null), which clears it, the same effect. That's why `soundtrack` and `replyToEntryId` travel through capture even though it can't edit them.
- **Schema validation at a trust boundary** (`draft.ts:32`): `z.object(...).safeParse(value)` returns `{ success, data }` instead of throwing, and `satisfies z.ZodType<Draft>` makes the compiler compare the schema with the interface.
- **Code splitting with `React.lazy`** (`CaptureHost.tsx`): `lazy(() => import('./CaptureView'))` needs a default export and a `<Suspense>` around it; the import starts the first time it renders.
- **Setting state during render** (`CaptureHost.tsx:39`): React allows `setState` in render when guarded by a condition that becomes false; it re-renders at once without a second commit, unlike an effect.
- **TipTap 3's StarterKit bundles** (`editorSetup.ts:12`): `StarterKit.configure({ underline: false, codeBlock: false, link: false })` removes bundled extensions; forgetting it means the editor can produce documents the server refuses.
- **`useEditorState`** (`Editor.tsx`): TipTap 3 re-renders a component only when the selector's answer changes, not on every keystroke.
- **Focus management in layered UI** (`WriteMenu.tsx:53`, `CaptureView.tsx:121`): a menu returns focus to its trigger on close; a dialog that opens from it must take focus itself, or a keyboard user ends up behind the scrim.
- **Multipart with openapi-fetch** (`api/entries.ts:55`): `bodySerializer` returns a `FormData`; no `Content-Type` is set, so the browser adds the boundary.

## 12. At work
- **Payments and transfers** are this task's save flow with money: an idempotency key chosen by the client (`Idempotency-Key` header), a multi-step process where one step can fail, and a clear answer for each partial state. The questions a reviewer asks are the same: what happens when the response is lost, when step 3 of 4 fails, when the user presses the button twice?
- **Optimistic locking** guards bank records edited from two places (a customer and a back-office user). The UI rule here, keep the user's input and offer the latest, is what stops "my changes vanished" tickets.
- **zod at the edges** is how a TypeScript front end, or an AI agent reading tool output, refuses data it can't trust: parse once at the boundary, then the rest of the code can rely on the type.
- **Accessibility reviews** in regulated industries check exactly the things the browser script checked: focus moves into a dialog, stays there, returns sensibly, and everything works without a mouse.
