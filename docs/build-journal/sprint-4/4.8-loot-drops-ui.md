# Task 4.8: Loot Drops in the UI

> **Sprint:** 4 · **Commit:** `Sprint 4.8: Build Loot Drops: the seal, the star and the Opened row`, on `phase-1-sprint-4` · **Status:** done (unattended; built in two sittings because the run hit its usage limit; two spec reviews, a fix pass and a close-out that made the full test run reliable) · **Time taken:** roughly 45 minutes of building (09:56 to about 10:18 AEDT, then 16:20 to 16:45 after the limit reset), plus this entry
> **Built:** an entry can be sealed from capture or extended from its own page; a sealed entry shows in the feed as a fixed-size card with the travelling star, its opening date and a live countdown; `/entries/:id` is the Loot Drop page (or the opened entry); and a Loot Drop that has opened sits in an *Opened* row at the top of the feed until it is opened or dismissed.

## 1. The goal
[Task 4.8](../../SPRINT_PLAN.md#sprint-4-react-ui):
- **Do:** a seal dialog (pick a day; it opens at 09:00 in the user's timezone, D-23; then a confirmation repeating the date and time), the travelling star as one SVG in `src/assets/`, a sealed card with a live countdown, the Loot Drop page, a `409` that surfaces as a friendly message, and an *Opened* row that takes On this day's place at the top of the feed (D-10, D-41).
- **Done when:** sealing an entry turns it into a sealed card; under a day heading the card shows only the opening date and the countdown, and elsewhere the memory date too; the countdown is correct in the user's zone; the star's lit part matches the days travelled; once the unlock time passes, the entry shows in the Opened row until it is opened or dismissed.

Why now: the backend side of Loot Drops has existed since Sprint 2 (`POST /entries/{id}/seal`, `GET /entries/opened`, `POST /entries/{id}/mark-seen`, and `EntryMapper`'s redaction). Task 4.4 drew a text-only sealed card as a placeholder; 4.6 built capture's save flow and left the fifth add-bar column for Seal. 4.8 needs both. Later tasks lean on it: 4.10 (week bars show the star mark), 4.14 (On this day must fit around the Opened row) and 4.16 (quick unlock dates and Reply to past you plug into the seal form).

## 4. Decisions and alternatives
| Decision | Options considered | Chosen | Why | Trade-off accepted |
|---|---|---|---|---|
| How the one SVG file is drawn in React | Inline the SVG as JSX; `<img src>`; an SVGR-style import (not installed); `<use href="file.svg#part">` | `<use>` on parts by id, imported with `?no-inline` | design.md §5 says the drawing lives in one file in `src/assets/`, not in JSX. `<img>` can't be coloured by tokens or show the lit part; `<use>` copies a part and lets it inherit `color`, so token classes colour it in both modes. `?no-inline` stops Vite turning a 2.7 KB file into a `data:` URL, which Chrome refuses in `<use>`. | One extra (cached) request for the file; the travelled path and the front's position must still be computed in code, so `starPath.ts` repeats the trail's four numbers (a test reads the file and fails if they drift). |
| Measuring "days travelled" along the trail | Use the Bézier parameter *t* = fraction; measure by arc length | Arc length (`starPath.ts:44`) | *t* runs faster on the straight parts, so half of *t* isn't half the way. The lit part is cut from the same curve with de Casteljau, so it lies exactly on the dashed trail. | 256-step lookup table at module load (negligible). |
| What "opens at 09:00" means in code | `new Date(…)` + `setHours(9)`; a fixed `+11:00` offset; `TZDate` with the user's zone | `TZDate(y, m, d, 9, 0, 0, zone)` (`time.ts:200`) | The browser's zone is the wrong one (non-negotiable 2); Melbourne is +11 in summer and +10 in winter, and 4 October 2026 is a change-over day. ## 5. How it was built
Read it in this order.

**Time and geometry (pure code)**
- [`frontend/src/lib/time.ts:179`](../../../frontend/src/lib/time.ts#L179) `addDays`, `:184` `daysBetween`, `:189` `dayIn`: calendar arithmetic on `yyyy-MM-dd` strings in UTC, so a 23- or 25-hour day can't make a count one off.
- [`time.ts:200`](../../../frontend/src/lib/time.ts#L200) `unlockInstant(day, zone)`: 09:00 on `day` in `zone`, as an ISO instant (practice block 1).
- [`time.ts:211`](../../../frontend/src/lib/time.ts#L211) `latestSealDay`: the day before the 100-year anniversary, so the picker can't offer a day the API rejects.
- [`time.ts:228`](../../../frontend/src/lib/time.ts#L228) `sealProgress`: `travelled` (memory date → today) over `total` (memory date → opening day), clamped to 0..1; a same-day seal is 1 once its day comes.
- [`time.ts:121`](../../../frontend/src/lib/time.ts#L121) `countdown` (from 4.4, now used live): counts calendar days in the user's zone: "in 59 days", "tomorrow", "today".
- [`frontend/src/lib/starPath.ts`](../../../frontend/src/lib/starPath.ts): `TRAIL` (the SVG's four points), `pointAt` by de Casteljau, a 256-step length table, `tAtFraction` (`:46`), `frontAt` and `travelledPath` (the lit part as one cubic cut from the trail).

**The drawing**
- [`frontend/src/assets/travelling-star.svg`](../../../frontend/src/assets/travelling-star.svg): parts in `<defs>` with ids `star` (rays and the four-point star), `star-shape`, `trail`, `front`, `you`, `specks`. Every stroke is `currentColor`, 2 px, `vector-effect="non-scaling-stroke"`; no text, nothing rotated.
- [`frontend/src/components/TravellingStar.tsx`](../../../frontend/src/components/TravellingStar.tsx): `<use href={url#id}>` per part, each with a token class (`text-control` for the trail, `text-accent` for the star and front, `fill-page`/`fill-accent` for "You"); the lit path is drawn in code. With a `label` it is `role="img"`; without, it is hidden from screen readers. `StarMark` is the star alone at 16–24 px for the Opened row and the Seal buttons.
- [`frontend/src/index.css:103`](../../../frontend/src/index.css#L103): `--animate-twinkle` and the `twinkle` utility with `transform-box: fill-box` so it scales about the star's own centre. The existing reduced-motion rule stops it.

**Data**

**Screens**

## 8. What went wrong
1. **The run stopped at the usage limit** after the code and tests were written (last write 10:18). The second sitting found the work uncommitted in the tree and the notes ending at the plan, so it ran the checks first rather than starting over.
2. **Prettier**: `npm run lint` failed on `CaptureView.test.tsx` and `LootDrop.test.tsx` ("Code style issues found in 2 files"). Fixed with `prettier --write`.
3. **A test that passed alone and failed in the full run**: `LootDrop.test.tsx:99` "Unable to find role="dialog" and name "Extend the seal"". Alone, the file passed 14/14. Cause: the seal panel is `React.lazy`, and under 29 test files in parallel its first import took longer than `findBy`'s 1 s default. Fix: `const LAZY = { timeout: 10_000 }` on the seal-panel lookups, as capture's sheet test already does (`CaptureView.test.tsx:23`).
4. **Focus fell to the page after Escape**: the Playwright script showed "Escape closed the panel; focus back on: (body)", and the same after the Delete question. Cause: Radix Dialog's `onCloseAutoFocus` prevents the default and focuses its `Trigger`; these dialogs open from state and have none. Fix: a `returnFocus` ref on `SealPanel` and `SealConfirm`, and `onCloseAutoFocus` on the Delete question; capture's Seal button passes its ref too. New tests assert the focus; removing `deleteButton.current.focus()` made "Escape on the delete question…" fail with `expect(element).toHaveFocus()`, and putting it back made it pass.
5. **The reduced-motion check first looked like a failure**: `animationName` still read `twinkle` under reduced motion. The global rule shortens the animation to 0.01 ms and one iteration rather than removing it, so the check was changed to read the duration and `getAnimations()`, which showed it finished.
6. **Two older tests timed out once** (CaptureView "opens from the Write menu…", VoiceRecorder "records with Opus…": "Unable to find role="dialog" and name "New entry"") while the backend, Vite and the audits were still running. After stopping the servers, the full run passed 310/310. The same flakiness under load was seen in 4.6 and 4.7.
7. **Review blocker: a sealed entry's whole copy stayed in the cache (D-10).** When capture restores the draft of a saved entry, or runs *Load the latest version*, it reads the entry whole with `fetchQuery` under `queryKeys.entry(id)`. Sealing from capture called `sealEntry` directly and then invalidated only the feed and tags. With a 30-minute `staleTime`, opening the new sealed card within the 5-minute `gcTime` showed `OpenEntry` with the title, caption and media. Fix: one helper, `afterSeal(queryClient, sealed)` in `api/lootDrops.ts`. It writes the server's redacted answer into `queryKeys.entry(sealed.id)` and invalidates the feed and the Opened strip. `useSeal` and capture's save both call it (`CaptureForm.tsx`, the save's `onSuccess`). New test: `CaptureView.test.tsx` "sealing a restored saved entry leaves no whole copy in the cache…". It restores a saved entry, seals it from capture, goes to `/entries/entry-saved`, and expects the Loot Drop page and neither title. With the fix turned off (`sealed && entry && false`), it failed with "Unable to find an element with the text: /Its light is still on its way to you/". With the fix back, it passes.
8. **Full-run timeouts in `LootDrop.test.tsx`.** Its lazy lookups wait up to 10 s, but its describes kept Vitest's 5 s test timeout: "extends the seal…" failed at 5233 ms in the full run and passed alone. Fix: `SLOW = { timeout: 15_000 }` on its three describes, as capture's describes have.
9. **Minor review findings fixed:** the seal confirmation now also says "and you can still delete it" (USER_FLOWS F-06 step 1). `EntryPage` memoises the list it gives `useUnlockWatch`, so the watch's memo and timer re-run only when the entry changes. The line numbers in §4 and §8 were corrected.

## 10. Concepts to learn from this task
- **SVG `<use>` and `currentColor`** (`TravellingStar.tsx`): `<use href="file.svg#id">` clones a part of another file into this SVG. Properties not set on the part (`color`, `fill`) are inherited from the `<use>`, so one drawing takes token colours per mode. Mistake: an inlined `data:` URL, which Chrome blocks for `<use>`; hence `?no-inline`.
- **Vite asset query suffixes** (`?no-inline`, `?url`, `?raw`): change how an import is turned into a module. Mistake: assuming every small asset stays a file; Vite inlines under 4 KB by default.
- **Arc length vs parameter on a Bézier** (`starPath.ts:44`): the parameter *t* doesn't move at constant speed. Measure length with a table and invert it. Mistake: drawing progress with `t = fraction`.
- **De Casteljau's construction** (`starPath.ts`): repeated linear interpolation gives the point at *t* and, as a by-product, the control points of the curve cut at *t*.
- **Wall-clock time in a named zone** (`time.ts:202`): `new TZDate(y, m, d, 9, 0, 0, zone)` means "09:00 as the clock on the wall there reads", whatever the offset that day. Mistake: `setUTCHours(9 - 11)`.
- **Optimistic updates with rollback** (`lootDrops.ts:89`): `onMutate` → `cancelQueries`, snapshot, `setQueryData`, return the snapshot; `onError` restores it; `onSettled` invalidates. Mistake: forgetting `cancelQueries`, so a refetch that started before the click lands afterwards and brings the row back.
- **`setQueryData` then invalidate** (`useSeal`): put the server's answer in the cache at once, then let related lists refetch.
- **Radix `onCloseAutoFocus`** (`SealPanel.tsx:35`): where focus goes when a dialog closes. Without a `Trigger`, Radix has nowhere to send it; `event.preventDefault()` plus your own `focus()` fixes that.
- **`ref` as a plain prop in React 19** (`LootDropPage.tsx`, `<Button ref={…}>`): no `forwardRef` needed for function components.
- **`React.lazy` and tests**: a lazily loaded component appears after a dynamic import, so `findBy*` may need a longer timeout under load. Better: import the module in a `beforeAll`, so the lazy import resolves from the module cache.
- **Hold a fake answer instead of delaying it** (`FeedPage.test.tsx:234`): an MSW handler that awaits a promise the test resolves makes "the skeleton shows before the data" deterministic; a fixed `delay()` races the timer on a busy machine.

## 12. At work
- **Time zones and cut-offs** are everywhere at a bank: a payment's value date, a statement period, an end-of-day batch that runs "at 6 pm Sydney". The same rule applies: store an instant, compute it from a wall-clock time in a named zone, and test both sides of a daylight-saving change. A reviewer would reject `new Date()` with `setHours`, or a hard-coded `+10:00`.
- **Optimistic UI with rollback** fits dismissing a notification or marking a message read; it does *not* fit moving money. A reviewer would ask "what does the user see if this fails?" and check for `cancelQueries`.
- **Server decides, client asks again**: the client never decides a Loot Drop is open; it asks the server at the right time. The same goes for an AI agent's tool results or an account's status: never trust the device clock for a rule that matters.
- **Redaction by allow-list**: the sealed card reads three fields only, so even a backend mistake couldn't show more. Same idea as masking an account number in the component that renders it, not trusting each caller to strip it.
- **Focus management** is part of accessibility audits (WCAG 2.4.3). Custom dialogs that open from state are the usual place it breaks.

## 13. Check yourself

<details><summary>Answers</summary>

1. `new Date()` works in the browser's zone, which may not be the user's (non-negotiable 2), and a fixed offset is wrong for half the year (Melbourne is +11 in summer, +10 in winter). `TZDate(y, m, d, 9, 0, 0, zone)` means 09:00 on the wall clock there, whatever the offset that day.
2. *t* doesn't move at constant speed along the curve, so *t* = 0.5 isn't halfway along it. `starPath.ts` measures the length with a table and finds the *t* at that length.
3. A refetch that started before the click could finish after it and write the old list, with the dismissed row, back into the cache.
4. The row would appear after the feed had painted and push every entry down: a layout shift (design.md §6 keeps it at 0.1 or less).
5. Vite inlines small assets as `data:` URLs, and Chrome refuses `<use href>` that points at a `data:` URL, so the parts wouldn't draw.
6. A sealed entry can't be changed (D-10), so a photo that failed to upload could never be added. Sealing last, and only when every file is on the server, means nothing is sealed half-finished; a failed seal leaves the entry saved and unsealed (F-06).
7. Radix Dialog sends focus to its `Trigger` on close, and these dialogs open from state and have none. A `returnFocus` ref and `onCloseAutoFocus` (preventDefault, then focus the button) fix it.
8. `useUnlockWatch` sets a timer for one second after the soonest unlock instant and then invalidates the feed, the opened strip and the entry. The server's clock decides what's open (D-10) and only the server can send the content, so the client only asks again at the right time.
